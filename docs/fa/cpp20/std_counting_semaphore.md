# راهنمای جامع `std::counting_semaphore` در ++C20

قابلیت `std::counting_semaphore` که در استاندارد ++C20 به کتابخانهٔ استاندارد اضافه شد، ابزاری برای هماهنگ‌سازی Threadها بر پایهٔ یک شمارنده است. این ابزار زمانی مفید است که یک Thread باید منتظر بماند تا یک یا چند مجوز (permit) در دسترس قرار بگیرد؛ برای مثال، وقتی چند Thread می‌خواهند از مجموعه‌ای با ظرفیت محدود استفاده کنند یا وقتی تولیدکننده باید آماده‌شدن داده را به مصرف‌کننده اعلام کند.

برخلاف `std::mutex` که معمولاً مالکیت انحصاری یک بخش بحرانی را مدیریت می‌کند، Semaphore تعداد مجوزهای موجود را کنترل می‌کند. این تفاوت، کاربردهای آن را از قفل‌کردن داده تا محدودسازی هم‌زمانی و هماهنگ‌سازی Producer/Consumer متمایز می‌سازد.

## معرفی و کاربرد اصلی

Semaphore یک سازوکار هماهنگ‌سازی است که با شمارنده‌ای غیرمنفی کار می‌کند. مقدار شمارنده نشان می‌دهد چند مجوز در حال حاضر قابل دریافت است:

- عملیات `acquire` یک مجوز می‌گیرد. اگر شمارنده مثبت باشد، مقدار آن کاهش می‌یابد و عملیات ادامه پیدا می‌کند؛ در غیر این صورت، Thread منتظر می‌ماند.
- عملیات `release` یک یا چند مجوز را بازمی‌گرداند و می‌تواند Threadهای منتظر را بیدار کند.
- عملیات `try_acquire` تلاش می‌کند بدون انتظار مجوز بگیرد.
- نسخه‌های زمان‌دار مانند `try_acquire_for` و `try_acquire_until` امکان انتظار محدودشده را فراهم می‌کنند.

در یک `std::counting_semaphore` مقدار شمارنده لزوماً تعداد Threadهای منتظر یا تعداد منابع فیزیکی را نشان نمی‌دهد؛ این مقدار تعداد مجوزهای قابل‌دریافت را مدل می‌کند. معنای دقیق مجوزها را طراحی برنامه تعیین می‌کند.

## جایگاه در استاندارد و سربرگ موردنیاز

این نوع از کتابخانهٔ استاندارد ++C20 است و در سربرگ `<semaphore>` تعریف می‌شود. برای استفاده از آن باید پروژه با پشتیبانی ++C20 کامپایل شود.

```cpp
#include <semaphore>
#include <thread>
#include <iostream>

int main() {
    std::counting_semaphore<3> permits{3};

    permits.acquire();
    std::cout << "Permit acquired\n";
    permits.release();
}
```

در مثال بالا، شمارنده با سه مجوز آغاز می‌شود. دریافت یک مجوز آن را به دو می‌رساند و آزادکردن مجوز دوباره مقدار را افزایش می‌دهد.

پشتیبانی واقعی به کتابخانهٔ استاندارد و نسخهٔ toolchain نیز وابسته است؛ تنها انتخاب حالت زبان ++C20 تضمین نمی‌کند که همهٔ قابلیت‌های کتابخانه در یک پیاده‌سازی قدیمی موجود باشند.

## آشنایی با نوع و پارامتر قالب

تعریف کلی نوع به این صورت است:

```cpp
template<std::ptrdiff_t LeastMaxValue = /* implementation-defined */>
class counting_semaphore;
```

پارامتر قالب `LeastMaxValue` حداقل بیشینهٔ مقداری را مشخص می‌کند که پیاده‌سازی باید برای Semaphore پشتیبانی کند. این پارامتر تعداد اولیهٔ مجوزها نیست؛ مقدار اولیه هنگام ساخت شیء تعیین می‌شود.

```cpp
std::counting_semaphore<5> sem{3};
```

در این نمونه، مقدار اولیه سه است، اما پارامتر قالب پنج است. پیاده‌سازی باید ظرفیت شمارنده‌ای دست‌کم به اندازهٔ پنج را پشتیبانی کند.

نوع `std::counting_semaphore` یک alias برای specialization متناسب با `LeastMaxValue` است. پیاده‌سازی استاندارد همچنین `std::binary_semaphore` را به‌عنوان alias برای Semaphore با ظرفیت حداقل یک ارائه می‌کند؛ این نوع معمولاً برای الگوهای دارای دو حالت مجوز/بدون مجوز استفاده می‌شود.

```cpp
std::binary_semaphore ready{0};
```

`std::binary_semaphore` از نظر معنایی نامی مناسب برای Semaphore با مجوز صفر یا یک است، اما نباید آن را با `std::mutex` یکی دانست: Semaphore الزام مالکیت Thread را ندارد و برای قفل انحصاری داده‌ها جایگزین مستقیم Mutex نیست.

## بررسی عملیات اصلی

### دریافت مجوز با `acquire`

تابع `acquire` تا زمانی که مجوزی موجود شود منتظر می‌ماند، سپس یک مجوز را مصرف می‌کند.

```cpp
#include <semaphore>
#include <thread>
#include <iostream>

int main() {
    std::counting_semaphore<2> sem{1};

    std::jthread worker([&] {
        sem.acquire();
        std::cout << "Worker acquired a permit\n";
        sem.release();
    });

    sem.acquire();
    std::cout << "Main acquired a permit\n";
    sem.release();
}
```

این برنامه نشان‌دهندهٔ دریافت مجوز از سوی دو Thread است. ترتیب دقیق پیام‌ها تضمین‌شده نیست. در برنامه‌های واقعی، بهتر است دسترسی هم‌زمان به خروجی یا داده‌های مشترک نیز با سازوکار مناسب مدیریت شود.

### انتشار مجوز با `release`

تابع `release(update = 1)` شمارنده را به اندازهٔ `update` افزایش می‌دهد و ممکن است Threadهای منتظر را بیدار کند.

```cpp
std::counting_semaphore<4> sem{0};

// Make two permits available.
sem.release(2);
```

پارامتر `update` باید مثبت باشد. همچنین باید مطمئن شوید افزایش شمارنده از بیشینهٔ مجاز عبور نمی‌کند. اگر محدودیت شمارنده نقض شود، رفتار برنامه تعریف‌نشده است؛ بنابراین `release` را نباید بدون مدل‌کردن دقیق مجوزها فراخوانی کرد.

انتشار مجوز به معنی انتقال مالکیت از یک Thread مشخص نیست. در مقابل، `std::mutex::unlock` باید با قواعد مالکیت Mutex سازگار باشد.

### تلاش بدون انتظار با `try_acquire`

تابع `try_acquire` فوراً تلاش می‌کند مجوزی دریافت کند و نتیجه را به‌صورت `bool` برمی‌گرداند.

```cpp
if (sem.try_acquire()) {
    // Use the resource protected by this permit.
    use_resource();
    sem.release();
} else {
    // No permit was acquired.
    do_other_work();
}
```

اگر تابع `false` برگرداند، مجوزی دریافت نشده است. موفقیت این تابع به‌تنهایی تضمین‌کنندهٔ ترتیب عادلانه یا اولویت‌بندی Threadها نیست. همچنین ممکن است فراخوانی در شرایطی که از دید برنامه مجوزی موجود به نظر می‌رسد، به دلیل جزئیات هم‌زمانی موفق نشود؛ کد نباید بر رفتار عادلانه یا ترتیب مشخص تکیه کند.

### انتظار محدودشده با زمان

نوع `std::counting_semaphore` از عملیات زمان‌دار `try_acquire_for` و `try_acquire_until` پشتیبانی نمی‌کند؛ این عملیات متعلق به `std::counting_semaphore` نیستند. API استاندارد Semaphore شامل `acquire`، `release` و `try_acquire` است. اگر انتظار زمان‌دار لازم است، باید از سازوکار دیگری مانند `std::condition_variable` یا طراحی مبتنی بر timeout استفاده کرد. انتخاب جایگزین به این بستگی دارد که آیا شرطی پیچیده‌تر از موجودبودن مجوز باید بررسی شود یا خیر.

## مقدار اولیه و مدل‌سازی مجوزها

مقدار اولیه هنگام ساخت شیء تعیین می‌شود و باید نامنفی و در محدودهٔ پشتیبانی‌شده باشد. مقدار صفر به این معناست که هیچ مجوزی از ابتدا در دسترس نیست و دریافت‌کنندگان باید تا انتشار مجوز منتظر بمانند.

```cpp
std::counting_semaphore<10> slots{10};
std::counting_semaphore<10> items{0};
```

در یک صف Producer/Consumer با ظرفیت ده، `slots` می‌تواند تعداد خانه‌های خالی و `items` تعداد آیتم‌های آماده را مدل کند. با این حال، Semaphore به‌تنهایی حافظه یا ساختار صف را مدیریت نمی‌کند؛ ایمنی دسترسی به خود صف باید جداگانه تضمین شود.

## مثال کاربردی: محدودکردن تعداد عملیات هم‌زمان

فرض کنید برنامه اجازه دارد حداکثر سه درخواست را به‌طور هم‌زمان اجرا کند. Semaphore با سه مجوز می‌تواند تعداد عملیات فعال را محدود کند.

```cpp
#include <semaphore>
#include <thread>
#include <vector>
#include <iostream>

std::counting_semaphore<3> request_slots{3};

void process_request(int id) {
    request_slots.acquire();

    // The permit must be returned even if processing throws.
    try {
        std::cout << "Processing request " << id << '\n';
        // Perform the request work here.
    } catch (...) {
        request_slots.release();
        throw;
    }

    request_slots.release();
}

int main() {
    std::vector<std::jthread> workers;
    for (int i = 0; i < 8; ++i) {
        workers.emplace_back([i] {
            process_request(i);
        });
    }
}
```

این نمونه نشان می‌دهد که Semaphore چگونه می‌تواند تعداد عملیات هم‌زمان را محدود کند. برای کد production، آزادسازی مجوز در تمام مسیرهای خروج اهمیت زیادی دارد. در کد بالا از `try/catch` برای نشان‌دادن این الزام استفاده شده است؛ راهکار مطمئن‌تر معمولاً یک guard مبتنی بر RAII است تا آزادسازی در مسیرهای عادی و استثنایی به‌طور خودکار انجام شود.

### مدیریت مجوز با RAII

از آنجا که Semaphore به‌صورت خودکار مجوز را هنگام خروج از scope برنمی‌گرداند، می‌توان یک guard کوچک ساخت. این guard باید فقط زمانی ساخته شود که مجوز واقعاً دریافت شده باشد.

```cpp
#include <semaphore>

class semaphore_guard {
public:
    explicit semaphore_guard(std::counting_semaphore<3>& sem)
        : sem_(sem) {
        sem_.acquire();
    }

    semaphore_guard(const semaphore_guard&) = delete;
    semaphore_guard& operator=(const semaphore_guard&) = delete;

    ~semaphore_guard() {
        sem_.release();
    }

private:
    std::counting_semaphore<3>& sem_;
};

std::counting_semaphore<3> slots{3};

void do_work() {
    semaphore_guard guard{slots};
    // The permit is returned when guard leaves scope.
    perform_work();
}
```

این guard برای عملیات مسدودشونده طراحی شده است؛ اگر دریافت مجوز باید قابل‌لغو یا دارای timeout باشد، باید API guard متناسب با همان رفتار طراحی شود. همچنین طول عمر Semaphore باید از guard بیشتر باشد؛ نگه‌داشتن reference به Semaphoreای که زودتر نابود می‌شود، خطای عمر شیء است.

## مثال کاربردی: هماهنگ‌سازی Producer و Consumer

در الگوی Producer/Consumer، Semaphore می‌تواند تعداد آیتم‌های آماده را نمایش دهد. در نمونهٔ سادهٔ زیر یک صف محافظت‌شده با Mutex و یک Semaphore برای اعلان تعداد آیتم‌ها استفاده شده است.

```cpp
#include <condition_variable>
#include <deque>
#include <mutex>
#include <semaphore>
#include <thread>
#include <iostream>

class work_queue {
public:
    void push(int value) {
        {
            std::lock_guard<std::mutex> lock(mutex_);
            queue_.push_back(value);
        }
        items_.release();
    }

    int pop() {
        items_.acquire();

        std::lock_guard<std::mutex> lock(mutex_);
        int value = queue_.front();
        queue_.pop_front();
        return value;
    }

private:
    std::mutex mutex_;
    std::deque<int> queue_;
    std::counting_semaphore<> items_{0};
};

int main() {
    work_queue queue;

    std::jthread consumer([&] {
        for (int i = 0; i < 3; ++i) {
            std::cout << queue.pop() << '\n';
        }
    });

    queue.push(10);
    queue.push(20);
    queue.push(30);
}
```

در این طراحی، ابتدا داده زیر حفاظت Mutex به صف افزوده می‌شود و سپس یک مجوز منتشر می‌شود. مصرف‌کننده ابتدا یک مجوز می‌گیرد و بعد آیتم را از صف حذف می‌کند. این ترتیب مهم است: انتشار مجوز پیش از درج داده می‌تواند مصرف‌کننده را به وضعیتی برساند که مجوز دارد اما صف هنوز آیتم متناظر را ندارد.

این نمونه برای آموزش است و سیاست shutdown یا بستن صف را پیاده‌سازی نمی‌کند. در یک سیستم واقعی باید راهی برای خاتمهٔ مصرف‌کننده‌ها، مدیریت خطا و جلوگیری از انتظار بی‌پایان هنگام توقف برنامه در نظر گرفته شود. `condition_variable` نیز می‌تواند انتخاب مناسبی باشد، به‌ویژه اگر مصرف‌کننده باید چند شرط را بررسی کند یا صف نیازمند سیاست پیچیده‌تری برای shutdown باشد.

## ارتباط با مدل حافظه و هم‌زمانی

عملیات Semaphore فقط شمارنده را تغییر نمی‌دهند؛ عملیات موفق `release` و دریافت متناظر می‌توانند برای هماهنگ‌سازی حافظه نیز به کار روند. عملیات `release` اثرات حافظه‌ای پیش از انتشار را با دریافت موفقی که مجوز منتشرشده را مصرف می‌کند، هماهنگ می‌سازد. این ویژگی اجازه می‌دهد داده‌ای که پیش از انتشار آماده شده، پس از دریافت مجوز توسط Thread دیگر قابل مشاهده باشد، مشروط بر آنکه طراحی به رابطهٔ هم‌زمانی استاندارد تکیه کند.

با این وجود، Semaphore جایگزین Mutex برای حفاظت از یک ساختار دادهٔ مشترک نیست. اگر چند Thread هم‌زمان یک `std::deque` را تغییر دهند، صرف داشتن Semaphore با شمارندهٔ مثبت لزوماً دسترسی به صف را ایمن نمی‌کند. برای دادهٔ مشترک باید یک پروتکل هماهنگ‌سازی کامل داشته باشید؛ معمولاً ترکیب Semaphore با Mutex یا ساختار داده‌ای که خودش thread-safe است.

## تفاوت با Mutex و Condition Variable

| ویژگی | `std::counting_semaphore` | `std::mutex` | `std::condition_variable` |
|---|---|---|---|
| مفهوم اصلی | شمارندهٔ مجوزها | مالکیت انحصاری قفل | انتظار برای تغییر شرط |
| مقدار اولیه | شمار مجوزهای آغازین | قفل‌شده یا آزاد | فاقد شمارندهٔ مجوز |
| انتظار | تا دریافت مجوز | تا قفل‌شدن | تا اعلان و بررسی مجدد predicate |
| مالکیت Thread | ندارد | دارد | با Mutex استفاده می‌شود |
| کاربرد معمول | محدودکردن ظرفیت، اعلان تعداد رخدادها | حفاظت از دادهٔ مشترک | انتظار برای شرط پیچیده |
| نگه‌داشتن اعلان | مجوز منتشرشده می‌تواند باقی بماند | موضوعیت ندارد | اعلان به‌تنهایی ذخیره نمی‌شود |

انتخاب باید بر اساس مدل مسئله انجام شود. برای محافظت از یک map مشترک، Mutex معمولاً انتخاب طبیعی‌تری است. برای محدودکردن تعداد اتصال‌های هم‌زمان به یک سرویس، Semaphore مناسب است. برای انتظار تا زمانی که چند شرط روی وضعیت یک شیء برقرار شوند، `condition_variable` اغلب بیان روشن‌تری دارد.

## محدودیت‌ها و نکات مهم طراحی

### جلوگیری از انتشار بیش از حد

هر `release` باید با یک مجوز واقعی و مدل‌شده در طراحی سازگار باشد. انتشار تکراری یا انتشار بیشتر از ظرفیت تعریف‌شده می‌تواند شمارنده را از محدودهٔ معتبر خارج کند. بهتر است هر مسیر دریافت و آزادسازی در طراحی قابل‌ردیابی باشد و invariantهای مربوط به شمارنده مستند شوند.

### نبود تضمین عدالت

استاندارد تضمین نمی‌کند که Threadهای منتظر دقیقاً به ترتیب ورودشان مجوز دریافت کنند. بنابراین نباید برای FIFO بودن، اولویت‌بندی یا جلوگیری قطعی از starvation به Semaphore تکیه کرد، مگر آنکه لایهٔ دیگری این سیاست را پیاده‌سازی کند.

### خطر deadlock

اگر همهٔ مجوزها دریافت شوند و هیچ مسیر اجرایی آن‌ها را آزاد نکند، سایر Threadها ممکن است برای همیشه منتظر بمانند. خطاهای زودهنگام، exceptionها، returnهای متعدد و shutdown باید در طراحی آزادسازی پوشش داده شوند. RAII می‌تواند خطر فراموش‌کردن `release` را کاهش دهد.

### عمر شیء و پایان برنامه

Semaphore باید تا پایان تمام عملیات‌هایی که به آن دسترسی دارند زنده بماند. نابودکردن Semaphore در حالی که Thread دیگری در حال انتظار روی آن است یا هنوز از آن استفاده می‌کند، طراحی معتبری نیست. پیش از نابودکردن شیء، Threadهای مرتبط را متوقف و join کنید و مسیر shutdown را صریح طراحی کنید.

### توقف و لغو عملیات

`acquire` رابطی برای cancellation یا timeout ارائه نمی‌کند. اگر برنامه باید هنگام shutdown انتظار را قطع کند، لازم است پروتکل جداگانه‌ای طراحی شود؛ برای نمونه، مجوزهای shutdown، یک شرط توقف مستقل، یا سازوکار دیگری که همهٔ انتظارها را به‌درستی بیدار کند. این راهکارها باید طوری طراحی شوند که مجوزهای مصنوعی با آیتم‌های واقعی اشتباه نشوند.

### کارایی و جزئیات پیاده‌سازی

پیاده‌سازی ممکن است از قابلیت‌های سیستم‌عامل، primitiveهای سخت‌افزاری یا ترکیبی از آن‌ها استفاده کند. استاندارد، پیاده‌سازی داخلی خاصی را الزام نمی‌کند. بنابراین دربارهٔ lock-free بودن، هزینهٔ دقیق هر عملیات یا برتری همیشگی Semaphore نسبت به `condition_variable` فرض عمومی نکنید؛ برای workload واقعی اندازه‌گیری کنید.

## خطاهای رایج

- **اشتباه گرفتن Semaphore با قفل:** داشتن یک مجوز به‌تنهایی حفاظت خودکار از تمام دسترسی‌های دادهٔ مشترک ایجاد نمی‌کند.
- **فراخوانی `release` بدون مجوز متناظر:** این کار ممکن است invariant شمارنده را خراب کند و حتی رفتار تعریف‌نشده ایجاد کند.
- **فراموش‌کردن آزادسازی هنگام exception:** برای مدیریت عمر مجوز از RAII استفاده کنید.
- **فرض FIFO بودن:** ترتیب بیدارشدن و دریافت مجوز را قطعی فرض نکنید.
- **انتشار مجوز قبل از آماده‌شدن داده:** ابتدا وضعیت مشترک را به‌روزرسانی کنید و سپس مجوز را منتشر کنید.
- **نابودکردن Semaphore زودتر از Threadها:** طول عمر هماهنگ‌ساز باید تمام استفاده‌کنندگان را پوشش دهد.
- **فرض وجود timeout:** `std::counting_semaphore` در API استاندارد خود `try_acquire_for` یا `try_acquire_until` ندارد.

## انتخاب مقدار قالب و بیشینهٔ شمارنده

پارامتر `LeastMaxValue` یک حداقل تضمین‌شده برای بیشینهٔ شمارنده است، نه الزاماً بیشینهٔ دقیق پیاده‌سازی. عضو ثابت `max()` بیشینهٔ پشتیبانی‌شده را گزارش می‌کند. در طراحی‌های قابل‌حمل، مقدارهای موردنیاز را در محدودهٔ تضمین‌شده نگه دارید و به ظرفیت اضافی یک کتابخانهٔ خاص وابسته نشوید.

```cpp
#include <semaphore>
#include <iostream>

int main() {
    std::counting_semaphore<8> sem{4};
    std::cout << sem.max() << '\n';
}
```

خروجی دقیق این برنامه لزوماً هشت نیست؛ مقدار بازگشتی نشان‌دهندهٔ بیشینهٔ پشتیبانی‌شده در همان پیاده‌سازی است و تضمین قالب حداقل ظرفیت را بیان می‌کند.

## مقایسه با روش‌های قدیمی‌تر

پیش از ++C20، برنامه‌ها اغلب از `std::mutex` به همراه `std::condition_variable` برای ساخت الگوی Semaphore استفاده می‌کردند. این راهکار همچنان برای شرایط پیچیده مناسب است، اما پیاده‌سازی دستی شمارنده، predicate و حلقهٔ انتظار را بر عهدهٔ برنامه‌نویس می‌گذارد. `std::counting_semaphore` یک abstraction استاندارد و مستقیم برای شمار مجوزها فراهم می‌کند.

نمونهٔ سادهٔ زیر فقط ایدهٔ کلی پیاده‌سازی قدیمی را نشان می‌دهد؛ در کد واقعی، predicate باید در حلقهٔ انتظار بررسی شود و متغیر شمارنده همیشه زیر همان Mutex محافظت شود.

```cpp
std::mutex mutex;
std::condition_variable cv;
int permits = 0;

void acquire_legacy() {
    std::unique_lock<std::mutex> lock(mutex);
    cv.wait(lock, [] { return permits > 0; });
    --permits;
}

void release_legacy() {
    {
        std::lock_guard<std::mutex> lock(mutex);
        ++permits;
    }
    cv.notify_one();
}
```

این قطعه برای استفادهٔ مستقل کامل نیست، زیرا سربرگ‌ها و مدیریت حد شمارنده را نشان نمی‌دهد؛ هدف آن نمایش مسئولیت‌هایی است که abstraction استاندارد Semaphore کاهش می‌دهد. در پیاده‌سازی دستی باید از سرریز شمارنده، invariantها و پروتکل shutdown نیز محافظت شود.

## راهنمای انتخاب در پروژه‌های واقعی

- برای محدودکردن تعداد عملیات هم‌زمان یا منابعی با ظرفیت مشخص، `std::counting_semaphore` گزینهٔ مناسبی است.
- برای اعلان تعداد آیتم‌های آماده در یک صف، Semaphore می‌تواند همراه با Mutex و ساختار دادهٔ صف استفاده شود.
- برای حفاظت انحصاری از داده، `std::mutex` یا در صورت مناسب‌بودن `std::shared_mutex` را بررسی کنید.
- برای انتظار بر اساس predicate پیچیده، چند شرط، یا نیاز به timeout، `std::condition_variable` ممکن است مناسب‌تر باشد.
- برای طراحی‌های قابل‌توقف، از ابتدا پروتکل shutdown و پایان عمر Threadها را مشخص کنید.
- برای کارایی، معیارسنجی را روی سیستم‌عامل، کتابخانه و workload هدف انجام دهید؛ از ادعاهای کلی دربارهٔ سرعت پرهیز کنید.

## جمع‌بندی

نوع `std::counting_semaphore` در ++C20 شمار مجوزهای قابل‌دریافت را مدیریت می‌کند و برای محدودسازی هم‌زمانی و هماهنگ‌سازی Threadها مناسب است. سه عملیات اصلی آن `acquire`، `release` و `try_acquire` هستند. برخلاف Mutex، Semaphore مالکیت Threadمحور ندارد و به‌تنهایی تضمین نمی‌کند که دسترسی به یک ساختار دادهٔ مشترک ایمن باشد.

استفادهٔ مطمئن از این ابزار به مدل‌سازی دقیق مجوزها، رعایت حد شمارنده، آزادسازی قابل‌اعتماد، توجه به نبود تضمین عدالت و طراحی صریح shutdown وابسته است. وقتی مسئله واقعاً دربارهٔ تعداد مجوزها یا ظرفیت محدود است، Semaphore abstraction مناسبی است؛ اما برای قفل‌کردن داده یا انتظار بر اساس شرط‌های پیچیده، ابزارهای دیگری از کتابخانهٔ استاندارد ممکن است انتخاب روشن‌تری باشند.
