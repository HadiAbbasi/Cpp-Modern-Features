# بررسی ویژگی `[[no_unique_address]]` در ++C20

## مقدمه

ویژگی `[[no_unique_address]]` یکی از قابلیت‌های زبان ++C20 است که برای بهینه‌سازی چیدمان حافظهٔ اشیا (Object Layout) معرفی شد. این ویژگی به کامپایلر اجازه می‌دهد یک عضو داده‌ای غیرایستا (Non-static Data Member) را به‌گونه‌ای در حافظه قرار دهد که الزاماً فضای آدرس منحصربه‌فردی نسبت به سایر اعضای شیء نداشته باشد.

اهمیت این قابلیت زمانی آشکار می‌شود که یک کلاس شامل اعضایی با اندازهٔ بسیار کم، به‌ویژه اشیای خالی (Empty Objects)، باشد. چنین اشیایی ممکن است به‌دلیل محدودیت‌های مربوط به چیدمان اعضا، هم‌ترازی (Alignment) و قواعد هویت اشیا، باعث افزایش اندازهٔ کلاس شوند؛ حتی اگر از نظر منطقی هیچ داده‌ای ذخیره نکنند.

برای مثال، کلاس‌های مبتنی بر `std::allocator`، سیاست‌های قالبی (Template Policies)، تابع‌های مقایسه، اشیای سفارشی‌سازی رفتار و انواع مشابه می‌توانند از این ویژگی سود ببرند.

نکتهٔ کلیدی این است که `[[no_unique_address]]` **اندازهٔ عضو را به صفر تبدیل نمی‌کند**؛ بلکه محدودیت مربوط به الزام داشتن آدرس متمایز را برای آن عضو کاهش می‌دهد تا پیاده‌سازی بتواند از فضای حافظه بهینه‌تر استفاده کند.

## مفهوم آدرس منحصربه‌فرد در زبان ++C

### رفتار اشیای خالی

در ++C، یک نوع کلاس خالی معمولاً هیچ عضو داده‌ای ندارد؛ بااین‌حال، اندازهٔ یک شیء کامل (Complete Object) از آن نوع صفر نیست.

```
#include <iostream>

struct Empty {};

int main() {
    std::cout << sizeof(Empty) << '\n';
}
```

در پیاده‌سازی‌های متداول، خروجی برابر با `1` است.

این محدودیت به قواعد زبان دربارهٔ اندازه و هویت اشیا مربوط است. هر شیء کامل باید اندازهٔ غیرصفر داشته باشد تا اشیای هم‌نوع در آرایه بتوانند در آدرس‌های متمایز قرار بگیرند.

برای نمونه، دو شیء مستقل از نوع `Empty` نمی‌توانند در یک آدرس قرار بگیرند، زیرا زبان باید امکان تشخیص هویت دو شیء مستقل از یک نوع را حفظ کند.

### مشکل اعضای خالی در کلاس‌ها

فرض کنید یک کلاس شامل یک عدد صحیح و یک عضو از نوع خالی باشد:

```
struct Empty {};

struct Regular {
    int value;
    Empty tag;
};
```

اندازهٔ دقیق `Regular` به پیاده‌سازی، هم‌ترازی و چیدمان اعضا وابسته است. در یک پیاده‌سازی متداول، اندازهٔ آن برابر با `8` بایت خواهد بود:

- عضو `value` چهار بایت فضا اشغال می‌کند.
- عضو `tag` معمولاً حداقل یک بایت نیاز دارد.
- فضای باقی‌مانده می‌تواند به padding اختصاص یابد.

البته این اعداد تضمین استاندارد نیستند؛ اندازهٔ `int` و جزئیات چیدمان به پیاده‌سازی وابسته‌اند.

اگر عضو `tag` صرفاً برای نمایش یک سیاست یا رفتار در طراحی کلاس حضور داشته باشد، اختصاص فضای جداگانه به آن می‌تواند غیرضروری باشد.

ویژگی `[[no_unique_address]]` برای کاهش این نوع سربار طراحی شده است.

## معرفی ویژگی `[[no_unique_address]]`

### تعریف و نحو استفاده

ویژگی `[[no_unique_address]]` یک Attribute استاندارد زبان است که از ++C20 در دسترس قرار گرفته است.

این ویژگی روی اعلان یک عضو داده‌ای غیرایستا اعمال می‌شود:

```
struct Empty {};

struct Optimized {
    int value;
    [[no_unique_address]] Empty tag;
};
```

در این مثال، کامپایلر مجاز است عضو `tag` را در بخشی از فضای حافظهٔ اشغال‌شده توسط عضو `value` یا سایر قسمت‌های مجاز چیدمان قرار دهد.

در نتیجه، اندازهٔ `Optimized` ممکن است به اندازهٔ `sizeof(int)` برسد؛ البته این نتیجه تضمین‌شده نیست.

### معنای دقیق ویژگی

این Attribute به پیاده‌سازی اجازه می‌دهد که برای عضو مشخص‌شده، الزام آدرس منحصربه‌فرد نسبت به سایر اشیای مرتبط را نادیده بگیرد؛ اما این اجازه محدود به قواعد زبان است.

به بیان دقیق‌تر، پیاده‌سازی می‌تواند:

- فضای اشغال‌شده توسط یک عضو خالی را با فضای عضو دیگری هم‌پوشانی دهد.
- از فضای padding موجود در چیدمان کلاس استفاده کند.
- برخی اعضای دارای نوع غیرخالی را نیز در صورت امکان با فضای سایر اعضا هم‌پوشانی دهد.
- بدون تغییر معنای منطقی اعضا، اندازهٔ نهایی کلاس را کاهش دهد.

در مقابل، این ویژگی به کامپایلر اجازه نمی‌دهد که هویت یک شیء را به‌طور دلخواه حذف کند، طول عمر آن را تغییر دهد یا دسترسی قانونی به آن را از بین ببرد.

### تفاوت میان هم‌پوشانی حافظه و حذف عضو

استفاده از این Attribute به معنای حذف عضو از کلاس نیست.

```
struct Empty {};

struct Example {
    int value;
    [[no_unique_address]] Empty tag;
};
```

عضو `tag` همچنان یک عضو داده‌ای واقعی است. می‌توان آن را مقداردهی کرد، به آن دسترسی داشت و از آن در عملیات مربوط به شیء استفاده کرد.

```
Example object{42, Empty{}};

object.tag = Empty{};
```

این کد معتبر است و مستقل از اینکه کامپایلر برای `tag` فضای جداگانه‌ای اختصاص داده باشد یا نه، معنای مشخصی دارد.

بنابراین، باید میان **وجود منطقی عضو** و **فضای فیزیکی اختصاص‌یافته به آن** تفاوت قائل شد.

## بررسی رفتار حافظه با مثال‌های عملی

### مقایسهٔ چیدمان عادی و بهینه‌شده

مثال زیر دو کلاس با ساختار یکسان را مقایسه می‌کند:

```
#include <iostream>

struct Empty {};

struct WithoutOptimization {
    int value;
    Empty tag;
};

struct WithOptimization {
    int value;
    [[no_unique_address]] Empty tag;
};

int main() {
    std::cout << sizeof(WithoutOptimization) << '\n';
    std::cout << sizeof(WithOptimization) << '\n';
}
```

در بسیاری از پیاده‌سازی‌های متداول، نتیجه ممکن است مشابه زیر باشد:

```
8
4
```

این خروجی صرفاً نمونه‌ای از رفتار احتمالی است و نباید به‌عنوان نتیجه‌ای تضمین‌شده در همهٔ کامپایلرها یا ABIها در نظر گرفته شود.

استاندارد ++C حداقل الزامات معنایی را مشخص می‌کند، اما چیدمان دقیق اعضا و میزان padding را در بسیاری از موارد به پیاده‌سازی واگذار می‌کند.

### مشاهدهٔ اندازه و هم‌ترازی

برای بررسی نتیجه در محیط واقعی، می‌توان از `sizeof` و `alignof` استفاده کرد:

```
#include <iostream>

struct Empty {};

struct Example {
    char prefix;
    [[no_unique_address]] Empty tag;
    int value;
};

int main() {
    std::cout << "sizeof(Example): " << sizeof(Example) << '\n';
    std::cout << "alignof(Example): " << alignof(Example) << '\n';
}
```

در این مثال، هم‌ترازی اعضا و padding احتمالی می‌توانند بر نتیجه تأثیر بگذارند.

نکتهٔ مهم آن است که `[[no_unique_address]]` مستقیماً مقدار `alignof` را کاهش نمی‌دهد. هم‌ترازی نوع عضو همچنان بخشی از قواعد چیدمان است؛ تنها محدودیت آدرس منحصربه‌فرد برای عضو مشخص‌شده کاهش می‌یابد.

## بررسی اشیای خالی و قواعد هویت

### تفاوت شیء کامل و زیرشیء

یکی از مهم‌ترین مفاهیم برای درک این Attribute، تفاوت میان یک شیء کامل (Complete Object) و یک زیرشیء (Subobject) است.

یک شیء کامل از نوع کلاس خالی نمی‌تواند اندازهٔ صفر داشته باشد. در مقابل، یک زیرشیء از نوع خالی می‌تواند تحت قواعد مشخصی با سایر بخش‌های چیدمان هم‌پوشانی داشته باشد.

برای مثال:

```
struct Empty {};

struct Container {
    [[no_unique_address]] Empty first;
    [[no_unique_address]] Empty second;
};
```

در این ساختار، کامپایلر می‌تواند از فضای یکسانی برای هر دو عضو استفاده کند؛ زیرا این دو عضو دارای نوع یکسان هستند و Attribute محدودیت آدرس منحصربه‌فرد را برای آن‌ها کاهش داده است.

بااین‌حال، چنین هم‌پوشانی‌ای اجباری نیست و نباید اندازهٔ دقیق `Container` را از روی تعداد اعضا محاسبه کرد.

### حفظ هویت اعضای هم‌نوع

استفاده از `[[no_unique_address]]` به معنای یکسان‌شدن دو شیء مستقل نیست.

```
struct Empty {};

struct Pair {
    [[no_unique_address]] Empty first;
    [[no_unique_address]] Empty second;
};
```

در این کلاس، `first` و `second` همچنان دو عضو مستقل هستند. بااین‌حال، کامپایلر می‌تواند در چارچوب قواعد زبان، آدرس‌های آن‌ها را یکسان یا متفاوت انتخاب کند.

به همین دلیل، نباید از این Attribute برای فرض‌کردن یک رابطهٔ ثابت میان آدرس اعضا استفاده کرد.

در طراحی نرم‌افزار، هر زمان هویت یا آدرس اعضا بخشی از قرارداد برنامه باشد، باید این موضوع را با دقت بیشتری بررسی کرد.

## کاربردهای مهم در طراحی کلاس‌ها

### بهینه‌سازی کلاس‌های سیاست‌محور

یکی از رایج‌ترین کاربردهای این ویژگی، کلاس‌های مبتنی بر Policy-Based Design است.

در این الگو، رفتار کلاس با استفاده از انواعی مانند تابع مقایسه، تخصیص‌دهنده، سیاست مدیریت منابع یا سیاست اعتبارسنجی قابل تنظیم می‌شود.

بسیاری از این انواع می‌توانند خالی باشند، زیرا فقط رفتار را مشخص می‌کنند و داده‌ای ذخیره نمی‌کنند.

```
#include <functional>
#include <memory>

template <typename T,
          typename Allocator = std::allocator<T>,
          typename Compare = std::less<T>>
struct Storage {
    [[no_unique_address]] Allocator allocator;
    [[no_unique_address]] Compare compare;

    T value;
};
```

در این طراحی، اگر `Allocator` و `Compare` واجد شرایط مناسب باشند و پیاده‌سازی بتواند از هم‌پوشانی استفاده کند، سربار حافظهٔ ناشی از این اعضا کاهش می‌یابد.

البته خالی‌بودن یک نوع به‌تنهایی تضمین نمی‌کند که اندازهٔ نهایی کلاس کاهش پیدا کند. برای نمونه، ممکن است یک نوع دارای اعضای داده‌ای باشد یا محدودیت‌های دیگری مانع استفادهٔ مؤثر از این قابلیت شوند.

### کاهش سربار در Wrapperها

کلاس‌های Wrapper معمولاً یک مقدار اصلی را در کنار اطلاعات جانبی نگه می‌دارند.

برای مثال، یک Wrapper ممکن است یک مقدار و یک سیاست تبدیل یا اعتبارسنجی داشته باشد:

```
template <typename T, typename Validator>
struct ValidatedValue {
    T value;
    [[no_unique_address]] Validator validator;
};
```

اگر `Validator` یک نوع خالی باشد، پیاده‌سازی می‌تواند از فضای موجود در چیدمان استفاده کند.

این تکنیک در کتابخانه‌های عمومی، انواع کوچک و کلاس‌هایی که در تعداد زیاد ساخته می‌شوند، می‌تواند مفید باشد.

### بهینه‌سازی انواع تابعی

اشیای تابعی (Function Objects) اغلب در الگوریتم‌ها و ساختارهای داده استفاده می‌شوند. یک Function Object ممکن است بدون ذخیرهٔ هیچ داده‌ای، رفتار خاصی را ارائه کند.

```
struct Increment {
    int operator()(int value) const {
        return value + 1;
    }
};

template <typename Function>
struct FunctionHolder {
    [[no_unique_address]] Function function;
};
```

در این مثال، `Increment` یک نوع خالی است. با استفاده از Attribute، پیاده‌سازی می‌تواند فضای اختصاص‌یافته به `function` را کاهش دهد.

در طراحی‌های پیچیده‌تر، این روش به‌ویژه هنگامی اهمیت دارد که چندین سیاست یا Function Object به‌صورت هم‌زمان در یک شیء نگهداری شوند.

## ارتباط با Empty Base Optimization

### معرفی Empty Base Optimization

پیش از ++C20، یکی از روش‌های رایج برای کاهش سربار اشیای خالی، استفاده از ارث‌بری خصوصی یا الگوی Empty Base Optimization بود که معمولاً با نام EBO شناخته می‌شود.

```
struct Empty {};

struct BaseOptimized : private Empty {
    int value;
};
```

در پیاده‌سازی‌های متداول، زیرشیء پایهٔ خالی می‌تواند فضای جداگانه‌ای اشغال نکند و اندازهٔ کلاس تقریباً برابر با اندازهٔ عضو `value` باشد.

بااین‌حال، نتیجهٔ دقیق همچنان به قواعد استاندارد و پیاده‌سازی وابسته است.

### تفاوت EBO و `[[no_unique_address]]`

روش EBO از ارث‌بری برای بهره‌برداری از ویژگی خالی‌بودن نوع استفاده می‌کند، درحالی‌که `[[no_unique_address]]` مستقیماً روی عضو داده‌ای اعمال می‌شود.

| ویژگی                           | روش EBO                | ویژگی `[[no_unique_address]]` |
| ------------------------------- | ---------------------- | ----------------------------- |
| روش استفاده                     | ارث‌بری                | عضو داده‌ای                   |
| تغییر ساختار ارث‌بری            | لازم است               | لازم نیست                     |
| خوانایی در ترکیب با Composition | گاهی ضعیف‌تر           | معمولاً بهتر                  |
| کاربرد برای اعضای غیرخالی       | محدود به قواعد ارث‌بری | امکان هم‌پوشانی در موارد مجاز |
| پشتیبانی زبانی                  | از نسخه‌های قدیمی ++C  | از ++C20                      |

مزیت اصلی `[[no_unique_address]]` این است که امکان استفاده از Composition را بدون نیاز به تبدیل یک عضو به کلاس پایه فراهم می‌کند.

### محدودیت‌های EBO و تفاوت‌های ظریف

در الگوی EBO، نوع پایه و ساختار ارث‌بری بر نتیجه تأثیر می‌گذارند. همچنین، محدودیت‌هایی دربارهٔ هم‌پوشانی زیرشیءهای پایهٔ هم‌نوع وجود دارد.

برای مثال، قواعد هویت اشیا اجازه نمی‌دهند دو زیرشیء مستقل از یک نوع در همهٔ شرایط به‌طور دلخواه در یک آدرس قرار گیرند.

ویژگی `[[no_unique_address]]` نیز این محدودیت‌ها را به‌طور کامل حذف نمی‌کند؛ بلکه مسیر دیگری برای بهینه‌سازی چیدمان ارائه می‌دهد.

در پروژه‌های جدید، بهتر است انتخاب میان این دو روش بر اساس مدل طراحی، نیازهای سازگاری و چیدمان واقعی انجام شود، نه بر اساس فرض‌های کلی دربارهٔ اندازهٔ اشیا.

## ارتباط با `std::tuple` و `std::pair`

### بهینه‌سازی انواع ترکیبی

انواعی مانند `std::tuple` و `std::pair` برای نگهداری چند مقدار با نوع‌های مختلف استفاده می‌شوند. اگر برخی از این نوع‌ها خالی باشند، کاهش سربار حافظه می‌تواند مفید باشد.

برای نمونه:

```
#include <tuple>

struct Empty {};

using Data = std::tuple<int, Empty, Empty>;
```

پیاده‌سازی کتابخانهٔ استاندارد می‌تواند برای کاهش اندازهٔ این ساختار از تکنیک‌هایی مانند EBO یا `[[no_unique_address]]` استفاده کند.

بااین‌حال، استاندارد الزام نمی‌کند که تمام پیاده‌سازی‌ها از یک روش مشخص استفاده کنند یا اندازهٔ دقیق یکسانی ارائه دهند.

### تفاوت رفتار کتابخانه با تضمین زبان

باید میان قابلیت زبان و جزئیات پیاده‌سازی کتابخانه تمایز قائل شد.

ویژگی `[[no_unique_address]]` یک Attribute زبان است؛ اما نحوهٔ استفاده از آن در پیاده‌سازی `std::tuple` یا `std::pair` به طراحی کتابخانه و محدودیت‌های ABI وابسته است.

بنابراین، نباید از روی وجود این Attribute در یک پیاده‌سازی نتیجه گرفت که همهٔ کتابخانه‌ها رفتار حافظه‌ای یکسانی خواهند داشت.

## بررسی اعضای غیرخالی

### امکان هم‌پوشانی اعضای غیرخالی

نام این ویژگی ممکن است این تصور را ایجاد کند که فقط انواع خالی می‌توانند از آن استفاده کنند. چنین برداشتی دقیق نیست.

```
struct Data {
    int value;
};

struct Container {
    int id;
    [[no_unique_address]] Data data;
};
```

عضو `data` خالی نیست؛ اما این Attribute همچنان می‌تواند به پیاده‌سازی اجازه دهد چیدمان آن را با بخش‌های دیگری از شیء هم‌پوشانی دهد، مشروط بر اینکه تمام قواعد زبان رعایت شوند.

برای نمونه، وجود فضای padding یا تفاوت‌های میان محدوده‌های ذخیره‌سازی اعضا می‌تواند در نتیجه نقش داشته باشد.

بااین‌حال، این موضوع به معنی امکان قرار دادن دلخواه دو عضو داده‌ای دارای مقادیر مستقل روی یک محدودهٔ حافظه نیست. قواعد مربوط به هم‌پوشانی زیرشیءها، اندازه، هم‌ترازی و دسترسی به مقادیر همچنان معتبر هستند.

### پرهیز از فرض‌های مبتنی بر اندازه

در طراحی کلاس‌ها بهتر است به جای فرض‌کردن یک اندازهٔ ثابت، از اندازهٔ واقعی در محیط هدف استفاده شود.

```
#include <iostream>

struct Data {
    int value;
};

struct Container {
    int id;
    [[no_unique_address]] Data data;
};

int main() {
    std::cout << sizeof(Data) << '\n';
    std::cout << sizeof(Container) << '\n';
}
```

خروجی این برنامه اطلاعاتی دربارهٔ پیاده‌سازی جاری فراهم می‌کند، اما برای همهٔ معماری‌ها و کامپایلرها قابل تعمیم نیست.

## محدودیت‌های زبانی و قواعد استاندارد

### Attribute به‌جای دستور اجرایی

ویژگی `[[no_unique_address]]` یک Attribute است، نه یک تابع، کلاس یا دستور اجرایی.

این ویژگی در زمان اجرای برنامه عملیات مستقلی انجام نمی‌دهد و هیچ سربار اجرایی مستقیمی به شکل یک تابع یا الگوریتم ایجاد نمی‌کند.

اثر اصلی آن در چیدمان اشیا و نحوهٔ تخصیص حافظه توسط پیاده‌سازی ظاهر می‌شود.

### وابستگی به نسخهٔ استاندارد

این ویژگی از ++C20 بخشی از استاندارد زبان است.

برای استفاده از آن، باید کامپایلر و تنظیمات ساخت پروژه از استاندارد ++C20 پشتیبانی کنند.

در کامپایلرهایی که این ویژگی را به‌صورت افزونه در نسخه‌های قدیمی‌تر ارائه می‌کنند، رفتار ممکن است مختص همان کامپایلر باشد. بنابراین، نباید پشتیبانی یک نسخهٔ قدیمی را معادل پشتیبانی استاندارد در نظر گرفت.

### تفاوت پشتیبانی کامپایلرها

پشتیبانی واقعی از این ویژگی به نسخهٔ کامپایلر، هدف ساخت و تنظیمات استاندارد بستگی دارد.

برای پروژه‌های چندسکویی، بهتر است کد با کامپایلرهای اصلی و تمام پیکربندی‌های هدف آزمایش شود. بررسی مستندات نسخهٔ مشخص کامپایلر و استفاده از تست‌های کوچک برای `sizeof` و `alignof` می‌تواند به تشخیص تفاوت‌های پیاده‌سازی کمک کند.

### تضمین‌نشدن کاهش اندازه

مهم‌ترین محدودیت عملی این ویژگی آن است که **استفاده از آن کاهش اندازهٔ کلاس را تضمین نمی‌کند**.

کامپایلر تنها اجازهٔ استفاده از چیدمان بهینه‌تر را دریافت می‌کند. تصمیم نهایی به قواعد زبان و پیاده‌سازی وابسته است.

بنابراین، اگر کاهش حافظه یک الزام حیاتی است، باید نتیجه در محیط‌های هدف اندازه‌گیری و بررسی شود.

## ملاحظات مهم دربارهٔ آدرس اعضا

### پرهیز از وابستگی به آدرس اعضا

هنگامی که از `[[no_unique_address]]` استفاده می‌شود، نباید فرض کرد که آدرس عضو همیشه از آدرس سایر اعضا متفاوت است.

```
struct Empty {};

struct Example {
    int value;
    [[no_unique_address]] Empty tag;
};
```

در این ساختار، مقایسهٔ آدرس `tag` با آدرس بخش‌های دیگر ممکن است نتیجه‌ای متفاوت از انتظار سادهٔ مبتنی بر چیدمان معمول اعضا داشته باشد.

بنابراین، از آدرس عضو برای استنتاج اندازهٔ واقعی، تشخیص هویت منطقی یا تعیین رابطهٔ مالکیت استفاده نکنید، مگر اینکه قواعد مربوط به نوع و چیدمان به‌دقت بررسی شده باشند.

### تفاوت هم‌پوشانی و Aliasing

هم‌پوشانی حافظه به معنای مجازشدن هر نوع دسترسی به حافظه نیست.

قواعد Aliasing، طول عمر اشیا، نوع واقعی شیء و الزامات دسترسی به مقادیر همچنان برقرار هستند.

این Attribute مجوزی عمومی برای تفسیر حافظه از طریق نوع‌های نامرتبط یا دور زدن قواعد زبان ایجاد نمی‌کند.

در نتیجه، نباید آن را جایگزین ابزارهایی مانند `std::bit_cast` در ++C20 یا روش‌های استاندارد مدیریت نمایش داده‌ها دانست.

### تأثیر بر کدهای مبتنی بر ABI

چیدمان کلاس‌ها در بسیاری از محیط‌ها بخشی از ABI است. تغییر چیدمان یک کلاس عمومی می‌تواند بر سازگاری باینری، تبادل داده میان ماژول‌ها یا نحوهٔ استفاده از کتابخانه‌ها تأثیر بگذارد.

به همین دلیل، افزودن `[[no_unique_address]]` به اعضای کلاس‌هایی که از مرز ABI عبور می‌کنند، باید با دقت انجام شود.

حتی اگر تغییر اندازه در یک کامپایلر مطلوب باشد، ممکن است برای مصرف‌کنندگان باینری موجود ناسازگاری ایجاد کند.

## نکات مهم در طراحی کتابخانه‌ها

### استفاده در انواع کوچک و پرتکرار

این ویژگی بیشترین ارزش را معمولاً در کلاس‌هایی نشان می‌دهد که تعداد بسیار زیادی از آن‌ها ساخته می‌شوند و هر بایت کاهش اندازه اهمیت دارد.

برای مثال، گره‌های ساختارهای داده، Wrapperهای کوچک، اشیای سیاست‌محور و انواع مورد استفاده در کانتینرهای سفارشی می‌توانند از این قابلیت سود ببرند.

بااین‌حال، کاهش اندازهٔ یک شیء لزوماً به معنی افزایش سرعت برنامه نیست. اثر نهایی باید با اندازه‌گیری واقعی و در نظر گرفتن الگوی دسترسی به حافظه ارزیابی شود.

### توجه به استانداردهای پروژه

در کتابخانه‌هایی که باید با نسخه‌های مختلف ++C سازگار باشند، ممکن است لازم باشد مسیرهای پیاده‌سازی متفاوتی برای استانداردهای قدیمی و جدید در نظر گرفته شوند.

برای مثال، یک کتابخانه می‌تواند در نسخهٔ ++C20 از `[[no_unique_address]]` استفاده کند و برای نسخه‌های قدیمی‌تر به روش‌های دیگری مانند EBO متکی باشد.

چنین راهکاری باید بر اساس الزامات واقعی پروژه طراحی شود و نباید به فرض‌های غیرقابل‌حمل دربارهٔ رفتار کامپایلر متکی باشد.

### پرهیز از پیچیدگی غیرضروری

استفاده از این Attribute برای هر عضو داده‌ای لزوماً طراحی بهتری ایجاد نمی‌کند.

اگر نوع خالی نیست، کلاس به‌اندازهٔ کافی کوچک است یا اندازهٔ آن در عملکرد برنامه تأثیر قابل‌توجهی ندارد، ممکن است پیچیدگی ناشی از تفاوت‌های چیدمان و سازگاری ارزشمند نباشد.

بهتر است ابتدا ساختار داده بر اساس نیازهای منطقی طراحی شود و سپس، در صورت وجود دلیل عملی، از این ویژگی برای بهینه‌سازی استفاده شود.

## اشتباهات رایج

### فرض صفرشدن اندازهٔ عضو

استفاده از `[[no_unique_address]]` به معنای صفرشدن `sizeof` عضو نیست. اندازهٔ نوع مستقل از این Attribute همچنان تابع قواعد استاندارد است.

### انتظار نتیجهٔ یکسان در همهٔ کامپایلرها

چیدمان اعضا، هم‌ترازی و padding می‌توانند بین پیاده‌سازی‌ها متفاوت باشند. نتیجهٔ یک کامپایلر نباید بدون آزمایش به سایر محیط‌ها تعمیم داده شود.

### استفاده برای تغییر معنای برنامه

این ویژگی صرفاً بر آزادی پیاده‌سازی در چیدمان حافظه اثر می‌گذارد. استفاده از آن نباید برای حذف وضعیت منطقی عضو یا ایجاد فرض‌های جدید دربارهٔ هویت اشیا انجام شود.

### نادیده‌گرفتن سازگاری باینری

تغییر چیدمان کلاس‌های عمومی می‌تواند ABI را تحت تأثیر قرار دهد. این مسئله در کتابخانه‌های مشترک و پروژه‌هایی که از چند نسخهٔ کامپایل‌شده استفاده می‌کنند، اهمیت ویژه‌ای دارد.

### استفاده بدون اندازه‌گیری

اگر هدف بهینه‌سازی حافظه است، اندازه‌گیری `sizeof`، `alignof` و در صورت نیاز تحلیل مصرف حافظه در محیط واقعی ضروری است. صرف وجود Attribute تضمینی برای بهبود عملکرد ارائه نمی‌دهد.

برای تصمیم‌گیری دربارهٔ استفاده از `[[no_unique_address]]` می‌توان معیارهای زیر را در نظر گرفت:

## جمع‌بندی

ویژگی `[[no_unique_address]]` در ++C20 ابزاری برای بهینه‌سازی چیدمان اعضای داده‌ای و کاهش سربار حافظه است. این ویژگی به‌خصوص در کلاس‌های دارای اعضای خالی، طراحی‌های مبتنی بر Policy-Based Design و Wrapperهای کوچک کاربرد دارد.

مهم‌ترین مزیت آن این است که بدون نیاز به تغییر ساختار ارث‌بری، امکان بهره‌برداری از فضای حافظهٔ قابل‌استفاده را فراهم می‌کند. در نتیجه، می‌توان از Composition استفاده کرد و در عین حال از برخی مزایای مرتبط با Empty Base Optimization بهره برد.

بااین‌حال، این ویژگی کاهش اندازه را تضمین نمی‌کند، قواعد هویت اشیا و Aliasing را کنار نمی‌گذارد و می‌تواند در چیدمان کلاس‌های دارای اهمیت ABI اثرگذار باشد.

رویکرد حرفه‌ای آن است که ابتدا طراحی منطقی کلاس انجام شود، سپس از این Attribute در نقاطی استفاده شود که کاهش سربار حافظه ارزشمند است و در نهایت، نتیجه با اندازه‌گیری و آزمایش روی کامپایلرها و پیکربندی‌های هدف تأیید شود.
