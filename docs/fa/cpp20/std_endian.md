# راهنمای جامع `std::endian` در ++C20

## مقدمه

ترتیب بایت‌ها یا Endianness مشخص می‌کند وقتی یک مقدار چندبایتی در حافظه قرار می‌گیرد، بایت‌های تشکیل‌دهنده آن با چه ترتیبی آدرس‌دهی می‌شوند. این موضوع در برنامه‌هایی که فقط با مقادیر انتزاعی زبان کار می‌کنند معمولاً پنهان می‌ماند؛ اما هنگام کار با فایل‌های باینری، پروتکل‌های شبکه، حافظهٔ مشترک، سخت‌افزار، serialization و داده‌های تولیدشده روی معماری‌های متفاوت اهمیت پیدا می‌کند.

استاندارد ++C20 نوع شمارشی `std::endian` را در header با نام `<bit>` معرفی کرد. این نوع راهی استاندارد و قابل استفاده در زمان کامپایل برای پرس‌وجو دربارهٔ ترتیب بایت انواع scalar در محیط اجرا فراهم می‌کند. این قابلیت به‌تنهایی داده‌ها را تبدیل نمی‌کند، ترتیب یک فایل یا پروتکل را تعیین نمی‌کند و جایگزین طراحی صحیح قالب داده نیست؛ فقط اطلاعاتی دربارهٔ محیط اجرای فعلی در اختیار برنامه می‌گذارد.

## مفهوم ترتیب بایت‌ها

### ترتیب بایت در مقادیر چندبایتی

برای درک Endianness فرض کنید یک مقدار صحیح ۳۲ بیتی با نمایش شانزده‌شانزدهی `0x12345678` داریم. اگر این مقدار در چهار بایت متوالی ذخیره شود، دو ترتیب رایج چنین‌اند:

| آدرس افزایشی حافظه | Big-endian | Little-endian |
|---|---|---|
| آدرس اول | `0x12` | `0x78` |
| آدرس دوم | `0x34` | `0x56` |
| آدرس سوم | `0x56` | `0x34` |
| آدرس چهارم | `0x78` | `0x12` |

در روش Big-endian، بایت دارای بیشترین اهمیت عددی (Most Significant Byte یا MSB) در آدرس پایین‌تر قرار می‌گیرد. در روش Little-endian، بایت دارای کمترین اهمیت (Least Significant Byte یا LSB) در آدرس پایین‌تر قرار می‌گیرد.

این تفاوت فقط ترتیب بایت‌ها در نمایش حافظه را توصیف می‌کند. مقدار عددی انتزاعی در هر دو محیط همان `0x12345678` است؛ تفاوت زمانی دیده می‌شود که نمایش شیء را به‌صورت بایت بررسی کنیم یا داده را بدون تبدیل مناسب میان محیط‌ها جابه‌جا کنیم.

### تفاوت Endianness با ترتیب بیت‌ها

ترتیب بایت‌ها را نباید با ترتیب انتقال یا شماره‌گذاری بیت‌ها اشتباه گرفت. Endianness دربارهٔ ترتیب بایت‌های یک مقدار چندبایتی در حافظه است. ترتیب بیت‌ها درون یک بایت و ترتیب ارسال بیت‌ها روی یک رابط سخت‌افزاری، موضوعات جداگانه‌ای هستند و باید مطابق مشخصات همان قالب یا پروتکل بررسی شوند.

### انواع رایج و حالت‌های دیگر

- **Little-endian:** بایت کم‌ارزش‌تر در آدرس پایین‌تر قرار می‌گیرد. این روش در بسیاری از پردازنده‌های امروزی رایج است.
- **Big-endian:** بایت پرارزش‌تر در آدرس پایین‌تر قرار می‌گیرد. بسیاری از قالب‌های باینری و قراردادهای شبکه ترتیب مشخصی دارند که مستقل از Endianness میزبان است.
- **Mixed-endian:** ترتیب بایت‌ها برای همهٔ انواع scalar یکسان نیست یا نمایش آن‌ها از الگوی سادهٔ Big-endian و Little-endian پیروی نمی‌کند. چنین محیط‌هایی امروزه کمتر رایج‌اند، اما استاندارد آن‌ها را از نظر مفهومی نادیده نمی‌گیرد.

## معرفی `std::endian`

### محل تعریف و نسخهٔ استاندارد

نوع `std::endian` از ++C20 در header استاندارد `<bit>` تعریف شده است. این قابلیت بخشی از Standard Library است، نه یک keyword زبان و نه یک قابلیت مختص کامپایلر خاص.

```cpp
#include <bit>

constexpr std::endian native_order = std::endian::native;
```

تعریف مفهومی این نوع به شکل زیر است:

```cpp
namespace std {
    enum class endian {
        little = /* implementation-defined */,
        big    = /* implementation-defined */,
        native = /* implementation-defined */
    };
}
```

مقادیر عددی enumeratorها توسط پیاده‌سازی تعیین می‌شوند. بنابراین نباید فرض کرد که `little` الزاماً صفر، `big` الزاماً یک یا `native` الزاماً برابر مقدار خاصی است. کاربرد قابل‌حمل این نوع مقایسهٔ enumeratorها با یکدیگر است، نه اتکا به مقدار عددی زیرین آن‌ها.

### معنای `little` و `big`

مقدار `std::endian::little` نشان‌دهندهٔ ترتیب Little-endian و مقدار `std::endian::big` نشان‌دهندهٔ ترتیب Big-endian است. در محیطی که انواع scalar چندبایتی از یک ترتیب یکنواخت پیروی می‌کنند، این دو مقدار از یکدیگر متمایزند.

### معنای `native`

مقدار `std::endian::native` ترتیب بایت‌های native محیط اجرا را توصیف می‌کند. این مقدار برای بررسی وضعیت پلتفرم فعلی استفاده می‌شود:

- اگر همهٔ انواع scalar به‌صورت Little-endian باشند، `native` با `little` برابر است.
- اگر همهٔ انواع scalar به‌صورت Big-endian باشند، `native` با `big` برابر است.
- در محیط Mixed-endian، `native` با هیچ‌یک از `little` و `big` برابر نیست.
- اگر اندازهٔ تمام انواع scalar دقیقاً یک بایت باشد، هر سه مقدار `little`، `big` و `native` برابرند؛ زیرا در این حالت ترتیب چند بایت مطرح نیست.

نکتهٔ مهم این است که `native` لزوماً مترادف Little-endian نیست. برنامه‌ای که فقط دو حالت Little و Big را بررسی می‌کند باید حالت سوم را نیز به‌صورت صریح مدیریت کند.

## نحوهٔ بررسی Endianness در زمان کامپایل

### تشخیص ساده با `if constexpr`

از آنجا که مقادیر `std::endian` ثابت‌های قابل ارزیابی در زمان کامپایل هستند، می‌توان از `if constexpr` برای انتخاب شاخهٔ مناسب استفاده کرد:

```cpp
#include <bit>
#include <iostream>

int main() {
    if constexpr (std::endian::native == std::endian::little) {
        std::cout << "Native byte order: little-endian\n";
    } else if constexpr (std::endian::native == std::endian::big) {
        std::cout << "Native byte order: big-endian\n";
    } else {
        std::cout << "Native byte order: mixed or otherwise non-standard\n";
    }
}
```

این روش برای انتخاب پیاده‌سازی وابسته به معماری، فعال‌کردن مسیر بهینه‌سازی یا گزارش اطلاعات محیط مناسب است. عبارت `if constexpr` شاخهٔ نامعتبر یا غیرقابل‌استفاده را در زمان کامپایل حذف می‌کند، اما هر سه شاخه از نظر نحوی باید معتبر باشند.

### استفاده در `static_assert`

اگر یک مؤلفه فقط روی یک نوع مشخص از Endianness پشتیبانی می‌شود، می‌توان محدودیت را هنگام کامپایل اعلام کرد:

```cpp
#include <bit>

static_assert(
    std::endian::native == std::endian::little,
    "This component requires a little-endian target"
);
```

این الگو برای کدی مناسب است که واقعاً به یک قرارداد سخت‌افزاری وابسته است؛ برای مثال یک لایهٔ پایین‌دستی بسیار تخصصی. با این حال، استفاده از آن در کتابخانهٔ عمومی یا برنامه‌ای که باید روی چند معماری اجرا شود، قابلیت حمل را بی‌دلیل محدود می‌کند. در چنین مواردی بهتر است به‌جای ردکردن پلتفرم، تبدیل بایت‌ها به‌صورت صریح انجام شود.

### تشخیص در کد generic

در کد template می‌توان مقدار `std::endian::native` را در تصمیم‌های compile-time دخالت داد. باید توجه داشت که این اطلاعات دربارهٔ محیط اجرا و پیاده‌سازی است، نه دربارهٔ نوع template به‌تنهایی. نوع مقصد، اندازهٔ آن و قرارداد داده همچنان باید جداگانه بررسی شوند.

## محدوده و تضمین‌های استاندارد

### ارتباط با انواع scalar

استاندارد، `std::endian` را برای توصیف Endianness انواع scalar محیط اجرا تعریف می‌کند. منظور از انواع scalar در مدل نوعی ++C، دسته‌هایی مانند انواع حسابی و انواع اشاره‌گر است؛ این مفهوم را نباید به‌سادگی با هر نوع class یا هر ساختار مرکب یکی دانست.

برای یک `struct` شامل چند عضو، `std::endian` ترتیب کلی اعضا، padding یا layout ساختار را مشخص نمی‌کند. حتی اگر اعضای ساختار scalar باشند، ترتیب قرارگیری اعضا و padding موضوعات جداگانه‌ای هستند.

### انواع یک‌بایتی

اگر تمام انواع scalar در پیاده‌سازی اندازهٔ یک بایت داشته باشند، استاندارد اجازه می‌دهد هر سه enumerator مقدار یکسانی داشته باشند. در نتیجه، شرط زیر در چنین محیطی می‌تواند درست باشد:

```cpp
std::endian::native == std::endian::little
```

اما این برابری لزوماً به معنای وجود یک ترتیب بایت قابل‌تمایز نیست؛ فقط بیانگر حالت خاصی است که در آن تمام scalarها یک‌بایتی‌اند.

### محیط‌های Mixed-endian

در محیط Mixed-endian، `native` نه برابر `little` است و نه برابر `big`. پس کد زیر کامل نیست:

```cpp
if constexpr (std::endian::native == std::endian::little) {
    // Little-endian path
} else {
    // Incorrectly assumes every other platform is big-endian
}
```

شاخهٔ `else` الزاماً Big-endian نیست. اگر پشتیبانی از چنین محیط‌هایی اهمیت دارد، باید حالت سوم را صریحاً مدیریت کرد یا محدودیت پلتفرم را مستند و enforce کرد.

## ارتباط با نمایش شیء و حافظه

### نمایش شیء چیست؟

هر شیء در ++C دارای Object Representation است؛ یعنی دنباله‌ای از بایت‌ها که شیء در حافظه با آن نمایش داده می‌شود. Endianness یکی از ویژگی‌هایی است که می‌تواند بر ترتیب بایت‌های نمایش scalarهای چندبایتی اثر بگذارد.

با این حال، Object Representation فقط به Endianness محدود نیست. اندازهٔ نوع، padding bits، representationهای مجاز، alignment و قواعد مربوط به نوع نیز اهمیت دارند. بنابراین مشاهدهٔ بایت‌های یک شیء و ذخیرهٔ مستقیم آن‌ها در فایل، به‌تنهایی یک serialization قابل‌حمل ایجاد نمی‌کند.

### مشاهدهٔ بایت‌های یک مقدار

برای مشاهدهٔ نمایش بایتی یک شیء می‌توان از `unsigned char` یا `std::byte` استفاده کرد. نمونهٔ زیر ترتیب بایت‌های یک مقدار ۳۲ بیتی را چاپ می‌کند:

```cpp
#include <cstdint>
#include <iostream>

int main() {
    const std::uint32_t value = 0x12345678;
    const auto* bytes = reinterpret_cast<const unsigned char*>(&value);

    for (std::size_t i = 0; i < sizeof(value); ++i) {
        std::cout << std::hex
                  << static_cast<unsigned int>(bytes[i]) << ' ';
    }

    std::cout << '\n';
}
```

این کد برای مشاهدهٔ نمایش شیء در همان اجرای برنامه مفید است. خروجی آن روی Little-endian معمولاً `78 56 34 12` و روی Big-endian معمولاً `12 34 56 78` خواهد بود. این نمونه ابزار تشخیص مستقل از `std::endian` نیست و برای تبدیل دادهٔ ورودی یا خروجی نیز کافی محسوب نمی‌شود.

### نقش `std::byte`

نوع `std::byte` از ++C17 برای نمایش دادهٔ خام بایتی معرفی شده است. می‌توان از آن برای کار با bufferها و نمایش شیء استفاده کرد، اما این نوع به‌خودی‌خود هیچ تبدیل Endianness انجام نمی‌دهد.

```cpp
#include <array>
#include <bit>
#include <cstddef>
#include <cstdint>

int main() {
    const std::uint32_t value = 0x12345678;
    const auto bytes = std::bit_cast<std::array<std::byte, sizeof(value)>>(value);

    (void)bytes;
}
```

در این مثال، `std::bit_cast` از ++C20 نمایش شیء را به آرایه‌ای هم‌اندازه منتقل می‌کند. ترتیب بایت‌های آرایه همان نمایش native مقدار روی پلتفرم جاری است؛ این کار آن را به قالب Little-endian یا Big-endian مشخصی تبدیل نمی‌کند.

## تبدیل ترتیب بایت‌ها

### تشخیص با تبدیل یکسان نیست

`std::endian` فقط وضعیت محیط را گزارش می‌کند. این نوع تابعی مانند `to_big_endian` یا `swap_bytes` ارائه نمی‌دهد. برای تبدیل داده باید قرارداد مقصد مشخص باشد و سپس بایت‌ها مطابق آن قرارداد جابه‌جا شوند.

برای مثال، اگر پروتکل یک عدد را به‌صورت Big-endian تعریف کرده باشد، برنامه باید مستقل از Endianness میزبان، مقدار را به نمایش Big-endian تبدیل کند. صرفاً بررسی `native` و ارسال مستقیم حافظه کافی نیست.

### استفاده از `std::byteswap` در ++C23

تابع `std::byteswap` در ++C23 و در header استاندارد `<bit>` معرفی شده است. این تابع بایت‌های یک مقدار integer را معکوس می‌کند؛ اما تصمیم اینکه چه زمانی باید آن را فراخوانی کرد، بر عهدهٔ برنامه است.

```cpp
#include <bit>
#include <cstdint>

constexpr std::uint32_t to_big_endian(std::uint32_t value) {
    if constexpr (std::endian::native == std::endian::little) {
        return std::byteswap(value);
    } else if constexpr (std::endian::native == std::endian::big) {
        return value;
    } else {
        static_assert(
            std::endian::native == std::endian::little ||
            std::endian::native == std::endian::big,
            "Mixed-endian platforms require a dedicated conversion"
        );
    }
}
```

این نمونه برای پلتفرم‌های یکنواخت Little-endian و Big-endian طراحی شده است. در محیط Mixed-endian تبدیل اختصاصی لازم است. همچنین `std::byteswap` برای انواع integer تعریف شده و محدودیت‌های آن باید در انتخاب نوع ورودی رعایت شود؛ این تابع راه عمومی برای معکوس‌کردن بایت‌های هر نوع دلخواه، از جمله `float` یا یک `struct`، نیست.

### پیاده‌سازی تبدیل دستی در ++C20

اگر پروژه به ++C20 محدود است و به `std::byteswap` دسترسی ندارد، می‌توان تبدیل را برای یک نوع unsigned مشخص با عملیات bitwise پیاده‌سازی کرد:

```cpp
#include <cstdint>

constexpr std::uint32_t byte_swap(std::uint32_t value) noexcept {
    return ((value & 0x000000FFu) << 24) |
           ((value & 0x0000FF00u) << 8)  |
           ((value & 0x00FF0000u) >> 8)  |
           ((value & 0xFF000000u) >> 24);
}
```

این تابع فقط برای `std::uint32_t` نوشته شده است و نباید بدون بازبینی به انواع دیگر تعمیم داده شود. مزیت این روش، شفاف‌بودن عملیات و مستقل‌بودن آن از aliasing است. در کد production معمولاً بهتر است از قابلیت استاندارد نسخهٔ زبان مورد استفاده یا abstraction آزموده‌شدهٔ پروژه بهره بگیرید.

## کاربرد در فایل‌های باینری و شبکه

### فایل‌های باینری

قالب فایل باید ترتیب بایت فیلدهای چندبایتی را به‌صراحت تعریف کند. اگر فایل با ترتیب Little-endian تعریف شده باشد، برنامه‌ای که روی میزبان Big-endian اجرا می‌شود باید هنگام خواندن و نوشتن تبدیل لازم را انجام دهد.

ذخیرهٔ مستقیم یک متغیر با `write(reinterpret_cast<const char*>(&value), sizeof(value))` معمولاً برای قالب فایل قابل‌حمل کافی نیست؛ زیرا ممکن است اندازهٔ نوع، Endianness، padding، representation و حتی قرارداد نسخه‌بندی در پلتفرم دیگر متفاوت باشد.

### پروتکل‌های شبکه

پروتکل باید ترتیب بایت‌ها را مستقل از میزبان مشخص کند. بسیاری از قراردادهای شبکه از Network Byte Order استفاده می‌کنند که در پروتکل‌های رایج مبتنی بر IP به معنای Big-endian است. برای سازگاری، داده را بر اساس قرارداد پروتکل encode و decode کنید؛ فرض نکنید تمام میزبان‌ها native order یکسان دارند.

### حافظهٔ مشترک و IPC

در Shared Memory، داده ممکن است میان پردازه‌هایی به اشتراک گذاشته شود که روی یک سیستم و معمولاً یک ABI اجرا می‌شوند. حتی در این وضعیت نیز قرارداد layout باید روشن باشد. اگر داده قرار است میان نسخه‌های متفاوت برنامه، معماری‌های مختلف یا سیستم‌های مستقل مبادله شود، استفاده از قالب باینری صریح و تبدیل کنترل‌شده مطمئن‌تر است.

## ارتباط با قابلیت‌های دیگر استاندارد

### تفاوت با `std::bit_cast`

تابع `std::bit_cast` از ++C20، بیت‌های نمایش یک شیء را به شیء دیگری با اندازهٔ برابر منتقل می‌کند، مشروط به رعایت محدودیت‌های استاندارد. این تابع تبدیل Endianness نیست. نتیجهٔ آن به Object Representation نوع مبدأ و مقصد و پلتفرم جاری وابسته است.

### تفاوت با `reinterpret_cast`

عملگر `reinterpret_cast` یک تبدیل نوع در سطح زبان انجام می‌دهد و نباید به‌عنوان راه‌حل عمومی برای serialization یا دسترسی امن به هر نوع حافظه تلقی شود. برای مشاهدهٔ بایت‌های یک شیء، دسترسی از مسیر `char`، `unsigned char` یا `std::byte` الگوی مناسب‌تری است. برای تبدیل representation میان انواع هم‌اندازه، در صورت انطباق با محدودیت‌ها `std::bit_cast` گزینهٔ استاندارد ++C20 است.

### تفاوت با `std::memcpy`

تابع `std::memcpy` بایت‌ها را از یک ناحیهٔ حافظه به ناحیهٔ دیگر کپی می‌کند؛ اما ترتیب بایت‌ها را تغییر نمی‌دهد و قالب داده را قابل‌حمل نمی‌کند. استفاده از آن می‌تواند برای انتقال representation بین اشیای مناسب مفید باشد، ولی مسئولیت Endianness و اعتبار representation همچنان باقی است.

### ارتباط با `std::uintN_t`

انواعی مانند `std::uint32_t` در صورت پشتیبانی پیاده‌سازی، نوع unsigned با عرض دقیقاً مشخص هستند. این ویژگی برای قالب‌های باینری بسیار مفید است، زیرا اندازهٔ عددی را روشن می‌کند؛ با این حال، عرض دقیق به‌تنهایی ترتیب بایت‌ها را تعیین نمی‌کند. برای قالب قابل‌حمل باید هم اندازه و هم ترتیب بایت‌ها را مشخص کنید.

## بررسی قابلیت پشتیبانی کتابخانه

### ماکروی تشخیص قابلیت

ماکروی feature-test مربوط به `std::endian` برابر `__cpp_lib_endian` و مقدار استانداردشدهٔ آن `201907L` است. برای بررسی دسترسی به این قابلیت در کتابخانهٔ استاندارد می‌توان از آن استفاده کرد:

```cpp
#include <bit>

#ifndef __cpp_lib_endian
#error "std::endian is not available"
#elif __cpp_lib_endian < 201907L
#error "A sufficiently recent std::endian implementation is required"
#endif
```

این ماکرو قابلیت کتابخانه را مشخص می‌کند و با ماکروهای تشخیص نسخهٔ زبان یا شناسهٔ کامپایلر یکسان نیست. برای استفاده از `std::endian` باید هم حالت زبان مناسب و هم پیاده‌سازی کتابخانهٔ استاندارد دارای پشتیبانی باشند.

## خطاهای رایج و نکات طراحی

### فرض اینکه همهٔ سیستم‌ها Little-endian هستند

رایج‌بودن Little-endian تضمین استانداردی برای تمام پلتفرم‌ها نیست. کد قابل‌حمل باید یا Endianness را تشخیص دهد و تبدیل کند، یا محدودیت پلتفرم را صریحاً اعلام کند.

### فرض اینکه هر حالت غیر Little، برابر Big است

این فرض در محیط Mixed-endian نادرست است. برای پوشش کامل قرارداد `std::endian`، هر سه حالت را در نظر بگیرید.

### استفاده از `std::endian` برای تشخیص ترتیب یک فایل

ترتیب بایت فایل ویژگی قالب فایل است، نه ویژگی سیستم میزبان. `std::endian::native` فقط برای مقایسهٔ محیط میزبان با قرارداد فایل مفید است؛ خود آن قرارداد را کشف نمی‌کند.

### معکوس‌کردن کل buffer بدون توجه به فیلدها

در یک ساختار باینری ممکن است فیلدهای یک‌بایتی، چندبایتی، رشته‌ها و بخش‌های دارای ترتیب مستقل وجود داشته باشند. معکوس‌کردن کل buffer می‌تواند داده را خراب کند. تبدیل باید بر اساس تعریف هر فیلد انجام شود.

### ذخیرهٔ مستقیم ساختارها

نوشتن مستقیم حافظهٔ یک `struct` در فایل می‌تواند به دلیل padding، alignment، layout و representation انواع عضو غیرقابل‌حمل باشد. برای قالب پایدار، هر فیلد را جداگانه encode کنید و اندازه و ترتیب بایت آن را تعریف کنید.

### استفادهٔ نادرست از `byteswap`

معکوس‌کردن بایت‌ها همیشه معادل تبدیل معنایی مقدار نیست. تنها زمانی آن را به‌کار ببرید که قرارداد داده دقیقاً چنین تبدیلی را لازم بداند و نوع ورودی در محدودهٔ پشتیبانی تابع باشد.

### اشتباه‌گرفتن Endianness با bit order

برای پروتکل‌هایی که بیت‌ها را در سطح بایت با ترتیب خاصی تعریف می‌کنند، صرف بررسی `std::endian` کافی نیست. مشخصات پروتکل دربارهٔ ترتیب بیت‌ها، framing و encoding باید جداگانه رعایت شود.

## جمع‌بندی

نوع `std::endian` در ++C20 ابزاری کوچک اما مهم از کتابخانهٔ استاندارد است که وضعیت Endianness انواع scalar محیط اجرا را به‌شکل استاندارد و قابل استفاده در زمان کامپایل گزارش می‌کند. سه مقدار `little`، `big` و `native` حالت‌های رایج و حالت‌های خاص مانند Mixed-endian را مدل می‌کنند؛ بنابراین نباید `native` را بدون بررسی معادل Little-endian یا Big-endian فرض کرد.

مهم‌ترین اصل طراحی این است که Endianness میزبان را از قرارداد داده جدا نگه دارید. برای فایل‌ها، شبکه و تبادل داده، ترتیب بایت‌ها باید در قالب یا پروتکل تعریف شود و برنامه باید encode/decode را مطابق همان قرارداد انجام دهد. `std::endian` ابزار تشخیص است؛ `std::byteswap` در ++C23 ابزار معکوس‌کردن بایت‌های integer است؛ و ابزارهایی مانند `std::bit_cast` یا `std::memcpy` نیز جایگزین serialization صریح نیستند.
