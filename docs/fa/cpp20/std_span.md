# آموزش جامع `std::span` در ++C20

## مقدمه و هدف طراحی

قابلیت `std::span` یکی از ابزارهای مهم Standard Library در استاندارد ++C20 است که برای نمایش یک نمای غیرمالکانه (Non-owning View) روی دنباله‌ای از عناصر متوالی در حافظه طراحی شده است. این نوع به برنامه‌نویس اجازه می‌دهد بدون کپی‌کردن داده‌ها و بدون انتقال مالکیت آن‌ها، به مجموعه‌ای از عناصر دسترسی داشته باشد.

در بسیاری از APIهای ++C، توابع به‌جای دریافت مستقیم یک مجموعه از عناصر، به یک اشاره‌گر و تعداد عناصر نیاز دارند. این الگو اگرچه ساده است، اما ممکن است باعث ایجاد خطاهایی مانند ناهماهنگی طول آرایه با تعداد اعلام‌شده، انتقال نادرست اندازه و دشواری استفاده مجدد از توابع شود.

برای مثال، رابط برنامه‌نویسی زیر را در نظر بگیرید:

```
#include <cstddef>
#include <iostream>

void printValues(const int* data, std::size_t size) {
    for (std::size_t i = 0; i < size; ++i) {
        std::cout << data[i] << ' ';
    }

    std::cout << '\n';
}
```

این تابع به دو آرگومان مستقل نیاز دارد. کامپایلر نمی‌تواند تضمین کند که `size` با تعداد عناصر قابل‌دسترسی از طریق `data` مطابقت داشته باشد.

در ++C20 می‌توان همین رابط را با `std::span` ساده‌تر کرد:

```
#include <iostream>
#include <span>

void printValues(std::span<const int> values) {
    for (int value : values) {
        std::cout << value << ' ';
    }

    std::cout << '\n';
}
```

در این طراحی، اشاره‌گر به داده‌ها و تعداد عناصر به‌صورت یک View واحد نمایش داده می‌شوند.

مزیت‌های اصلی این رویکرد عبارت‌اند از:

- جلوگیری از کپی غیرضروری عناصر.
- انتقال هم‌زمان اطلاعات مربوط به آدرس و تعداد عناصر.
- سازگاری با آرایه‌های C، `std::array`، `std::vector` و بسیاری از Containerهای دیگر.
- فراهم‌کردن یک رابط عمومی برای الگوریتم‌هایی که با دنباله‌های متوالی کار می‌کنند.
- پشتیبانی از بررسی محدوده در برخی عملیات، بدون تحمیل هزینه مالکیت یا تخصیص حافظه.

بااین‌حال، `std::span` مالک داده‌ها نیست و به‌تنهایی طول عمر آن‌ها را تضمین نمی‌کند. این نکته مهم‌ترین اصل در استفاده صحیح از این نوع است.

## مفهوم و ساختار `std::span`

### نمای غیرمالکانه چیست؟

یک Non-owning View شیئی است که امکان دسترسی به داده‌های موجود را فراهم می‌کند، اما مسئول ایجاد، نگهداری یا آزادسازی آن داده‌ها نیست.

برای نمونه، اگر یک `std::vector<int>` شامل پنج عنصر باشد، می‌توان یک `std::span<int>` ساخت که به تمام یا بخشی از عناصر آن اشاره کند. تغییر عناصر از طریق Span در همان حافظه اصلی اعمال می‌شود.

```
#include <iostream>
#include <span>
#include <vector>

int main() {
    std::vector<int> numbers{10, 20, 30, 40, 50};

    std::span<int> values{numbers};

    values[1] = 200;

    std::cout << numbers[1] << '\n';
}
```

خروجی:

```
200
```

در این مثال، هیچ نسخه مستقلی از عناصر ساخته نشده است. متغیر `values` صرفاً نمایی از حافظه متعلق به `numbers` است.

### اجزای مفهومی Span

یک Span معمولاً با دو مؤلفه مفهومی قابل توصیف است:

- Pointer: آدرس نخستین عنصر.
- Extent: تعداد عناصر قابل‌دسترسی از طریق View.

این توصیف مفهومی است؛ استاندارد ++C الزام نمی‌کند که پیاده‌سازی دقیقاً از دو فیلد با همین ساختار استفاده کند.

دو شکل اصلی برای Extent وجود دارد:

- Dynamic Extent: اندازه در زمان اجرا مشخص می‌شود.
- Static Extent: اندازه بخشی از نوع در زمان کامپایل است.

برای نمونه:

```
#include <span>

std::span<int> dynamicValues;
std::span<int, 4> fixedValues;
```

در این مثال، `dynamicValues` اندازه ثابتی در نوع خود ندارد، اما `fixedValues` نمایی با Extent ثابت چهار عنصر را نشان می‌دهد.

### هدر و استاندارد موردنیاز

قابلیت `std::span` در استاندارد ++C20 و در هدر زیر معرفی شده است:

```
#include <span>
```

برای استفاده از آن باید کامپایلر و Standard Library مورد استفاده، پشتیبانی لازم از ++C20 را داشته باشند.

برای مثال، در محیط‌هایی که از GCC یا Clang استفاده می‌کنند، ممکن است لازم باشد استاندارد زبان را صریحاً تعیین کنید:

```
g++ -std=c++20 main.cpp -o main
```

یا:

```
clang++ -std=c++20 main.cpp -o main
```

تعیین گزینه استاندارد به‌تنهایی تضمین نمی‌کند که تمام امکانات موردنیاز در نسخه نصب‌شده از کتابخانه استاندارد پیاده‌سازی شده باشند.

## تفاوت Dynamic Extent و Static Extent

### بررسی Dynamic Extent

در Dynamic Extent، تعداد عناصر بخشی از نوع نیست و هنگام اجرا مشخص می‌شود.

```
#include <iostream>
#include <span>
#include <vector>

int main() {
    std::vector<int> values{1, 2, 3, 4, 5};

    std::span<int> view{values};

    std::cout << view.size() << '\n';
}
```

خروجی:

```
5
```

نوع `std::span<int>` می‌تواند نماهایی با طول‌های متفاوت را نمایش دهد. به همین دلیل برای رابط‌های عمومی و توابعی که اندازه ورودی آن‌ها متغیر است، معمولاً انتخاب مناسبی محسوب می‌شود.

### بررسی Static Extent

در Static Extent، اندازه بخشی از پارامتر قالب نوع است.

```
#include <iostream>
#include <span>

void processFour(std::span<int, 4> values) {
    values[0] = 100;

    std::cout << values.size() << '\n';
}

int main() {
    int data[4]{1, 2, 3, 4};

    processFour(data);
}
```

خروجی:

```
4
```

استفاده از Static Extent زمانی مناسب است که تعداد عناصر از نظر طراحی API ثابت باشد؛ برای مثال، در توابعی که همیشه یک بردار چهاربعدی یا یک بلوک با اندازه مشخص را دریافت می‌کنند.

Static Extent می‌تواند اطلاعات بیشتری در اختیار سیستم نوع قرار دهد، اما به‌تنهایی تضمین نمی‌کند که داده‌های زیربنایی معتبر باشند یا عناصر خارج از محدوده دسترسی پیدا نکنند.

### مقایسه دو نوع Extent

| ویژگی                             | Dynamic Extent           | Static Extent                     |
| --------------------------------- | ------------------------ | --------------------------------- |
| نمونه نوع                         | `std::span<int>`         | `std::span<int, 4>`               |
| اندازه در نوع                     | مشخص نیست                | ثابت است                          |
| انعطاف‌پذیری                      | بیشتر                    | محدود به اندازه ثابت              |
| مناسب برای                        | APIهای عمومی و طول متغیر | ساختارهای با اندازه مشخص          |
| نیاز به ذخیره اندازه در زمان اجرا | معمولاً بله              | برای خود Extent ثابت، الزامی نیست |
| امکان تبدیل به Dynamic Extent     | بله                      | بله                               |

نکته مهم این است که Static Extent الزاماً به معنای بهینه‌تر بودن در تمام پیاده‌سازی‌ها نیست. مزیت اصلی آن بیان محدودیت اندازه در سطح نوع و فراهم‌کردن اطلاعات بیشتر برای کامپایلر و خواننده کد است.

## روش‌های ساخت Span

### ساخت از آرایه C

یکی از ساده‌ترین روش‌ها، ساخت مستقیم Span از آرایه‌ای با اندازه معلوم است.

```
#include <span>

int main() {
    int values[3]{10, 20, 30};

    std::span<int> allValues{values};
    std::span<int, 3> fixedValues{values};
}
```

در این مثال، اندازه آرایه در زمان کامپایل مشخص است و سازنده مناسب می‌تواند آن را به Span منتقل کند.

### ساخت از `std::array`

نوع `std::array` برای آرایه‌هایی با اندازه ثابت استفاده می‌شود و با `std::span` سازگاری مستقیم دارد.

```
#include <array>
#include <span>

int main() {
    std::array<int, 4> values{1, 2, 3, 4};

    std::span<int> view{values};
    std::span<int, 4> fixedView{values};
}
```

از آنجا که `std::array` مالک عناصر خود است، طول عمر Span به طول عمر آرایه وابسته خواهد بود.

### ساخت از `std::vector`

برای Containerهای دارای حافظه پیوسته مانند `std::vector` نیز می‌توان از Span استفاده کرد.

```
#include <span>
#include <vector>

int main() {
    std::vector<int> values{5, 10, 15, 20};

    std::span<int> view{values};
}
```

Span در این حالت مالک حافظه Vector نیست. اگر عملیاتی مانند `push_back` باعث تخصیص مجدد حافظه Vector شود، اشاره‌گرهای قبلی ممکن است نامعتبر شوند و Span نیز دیگر نمای معتبری از عناصر نباشد.

### ساخت با اشاره‌گر و اندازه

در مواردی که داده از یک API قدیمی، یک کتابخانه خارجی یا یک بخش مشخص از حافظه دریافت می‌شود، ممکن است فقط اشاره‌گر و اندازه در دسترس باشند.

```
#include <cstddef>
#include <span>

void process(std::span<const int> values);

int main() {
    int data[5]{1, 2, 3, 4, 5};

    std::span<const int> firstFour{data, std::size_t{4}};

    process(firstFour);
}
```

در این روش، برنامه‌نویس مسئول اطمینان از معتبر بودن اشاره‌گر و کافی بودن تعداد عناصر است.

اگر اندازه از منبع نامعتبر یا ورودی خارجی به دست آمده باشد، ساخت Span به‌خودی‌خود صحت آن را بررسی نمی‌کند.

### ساخت از دو Iterator یا Sentinel

در ++C20، سازنده‌های مبتنی بر Iterator و Sentinel نیز برای ایجاد Span در شرایط مناسب وجود دارند.

```
#include <array>
#include <span>

int main() {
    std::array<int, 5> values{10, 20, 30, 40, 50};

    std::span<int> view{values.begin(), values.end()};
}
```

این روش برای محدوده‌هایی مناسب است که Iteratorهای آن‌ها با الزامات لازم سازگار باشند و عناصر به‌صورت پیوسته در حافظه قرار گرفته باشند.

هر محدوده‌ای قابل تبدیل به Span نیست. برای مثال، `std::list` عناصر را در حافظه به‌صورت پیوسته ذخیره نمی‌کند و نمی‌توان مستقیماً آن را به Span تبدیل کرد.

### ساخت Span خالی

یک Span با Dynamic Extent را می‌توان به‌صورت خالی ایجاد کرد.

```
#include <span>

int main() {
    std::span<int> empty;

    return empty.empty() ? 0 : 1;
}
```

در مقابل، یک Span با Static Extent مثبت، مانند `std::span<int, 4>`، نمی‌تواند نمای خالی باشد؛ زیرا Extent آن بخشی از نوع است.

## دسترسی به عناصر و اطلاعات اندازه

### استفاده از `size` و `empty`

متدهای `size` و `empty` برای بررسی اندازه View به کار می‌روند.

```
#include <iostream>
#include <span>
#include <vector>

int main() {
    std::vector<int> values{2, 4, 6};

    std::span<int> view{values};

    std::cout << view.size() << '\n';
    std::cout << view.empty() << '\n';
}
```

خروجی:

```
3
0
```

متد `size` تعداد عناصر را برمی‌گرداند و `empty` مشخص می‌کند که آیا تعداد عناصر صفر است یا خیر.

نوع بازگشتی `size` از نوع `std::size_t` است.

### دسترسی با `operator[]`

برای دسترسی مستقیم به عناصر می‌توان از عملگر `[]` استفاده کرد.

```
#include <iostream>
#include <span>

int main() {
    int data[]{10, 20, 30};

    std::span<int> values{data};

    std::cout << values[1] << '\n';
}
```

خروجی:

```
20
```

دسترسی با `operator[]` در ++C20 بررسی محدوده را تضمین نمی‌کند. استفاده از اندیس نامعتبر، رفتار تعریف‌نشده (Undefined Behavior) ایجاد می‌کند.

بنابراین، اگر اندیس از ورودی کاربر یا داده‌های غیرقابل‌اعتماد به دست می‌آید، باید اعتبار آن را پیش از دسترسی بررسی کنید.

### استفاده از `front` و `back`

متدهای `front` و `back` برای دسترسی به اولین و آخرین عنصر استفاده می‌شوند.

```
#include <iostream>
#include <span>

int main() {
    int data[]{3, 6, 9};

    std::span<int> values{data};

    std::cout << values.front() << '\n';
    std::cout << values.back() << '\n';
}
```

خروجی:

```
3
9
```

فراخوانی این متدها روی Span خالی معتبر نیست و می‌تواند به رفتار تعریف‌نشده منجر شود.

### استفاده از `data`

متد `data` اشاره‌گر به نخستین عنصر را برمی‌گرداند.

```
#include <span>
#include <iostream>

void legacyFunction(const int* data, std::size_t size);

int main() {
    int values[]{1, 2, 3};

    std::span<const int> view{values};

    legacyFunction(view.data(), view.size());
}
```

این ویژگی برای اتصال APIهای جدید به توابع قدیمی مفید است. بااین‌حال، پس از استخراج اشاره‌گر، اطلاعات مربوط به Extent دیگر همراه آن نیست و مسئولیت رعایت محدوده دوباره بر عهده فراخواننده و تابع مقصد قرار می‌گیرد.

### پیمایش با Range-based for

در بسیاری از کاربردها، پیمایش مستقیم Span خواناتر است.

```
#include <iostream>
#include <span>

int main() {
    int values[]{1, 2, 3, 4};

    std::span<int> view{values};

    for (int& value : view) {
        value *= 2;
    }

    for (int value : view) {
        std::cout << value << ' ';
    }
}
```

خروجی:

```
2 4 6 8
```

در این مثال، استفاده از `int&` باعث می‌شود عناصر اصلی تغییر کنند. اگر فقط خواندن عناصر موردنظر باشد، استفاده از `const` در نوع Span انتخاب مناسب‌تری است.

## تفاوت `std::span<T>` و `std::span<const T>`

### مدیریت دسترسی نوشتنی

نوع `std::span<T>` اجازه تغییر عناصر را می‌دهد، مشروط بر اینکه داده اصلی قابل‌تغییر باشد.

```
#include <span>

void modify(std::span<int> values) {
    if (!values.empty()) {
        values[0] = 42;
    }
}
```

در مقابل، `std::span<const T>` دسترسی خواندنی به عناصر فراهم می‌کند.

```
#include <iostream>
#include <span>

void print(std::span<const int> values) {
    for (int value : values) {
        std::cout << value << ' ';
    }
}
```

نوع دوم برای بسیاری از توابعی که صرفاً داده‌ها را می‌خوانند، انتخاب مناسب‌تری است؛ زیرا قصد تابع را روشن می‌کند و از تغییر تصادفی عناصر از طریق همان View جلوگیری می‌کند.

### تفاوت const بودن Span با const بودن عناصر

دو اعلان زیر معنای متفاوتی دارند:

```
std::span<int> values;
const std::span<int> fixedView;
```

در اعلان نخست، خود Span قابل‌تغییر است و عناصر نیز از طریق آن قابل‌تغییر هستند.

در اعلان دوم، خود شیء Span ثابت است، اما عناصر همچنان از طریق نوع `int` قابل‌تغییر باقی می‌مانند.

برای جلوگیری از تغییر عناصر، باید از `std::span<const int>` استفاده شود.

```
std::span<const int> readOnlyValues;
```

در این حالت، حتی اگر خود Span متغیر باشد، عناصر از طریق آن قابل‌نوشتن نیستند.

### تبدیل از Span قابل‌تغییر به Span فقط‌خواندنی

تبدیل از نمای قابل‌تغییر به نمای فقط‌خواندنی امکان‌پذیر است.

```
#include <span>
#include <vector>

int main() {
    std::vector<int> values{1, 2, 3};

    std::span<int> writable{values};
    std::span<const int> readable{writable};
}
```

این تبدیل دسترسی نوشتنی را از طریق View جدید حذف می‌کند، اما خود داده اصلی را به حافظه فقط‌خواندنی تبدیل نمی‌کند. کد دیگری که دسترسی قابل‌تغییر دارد، همچنان می‌تواند عناصر را تغییر دهد.

## استفاده از Span در طراحی API

### جایگزینی اشاره‌گر و اندازه

یکی از مهم‌ترین کاربردهای `std::span`، طراحی توابعی است که با دنباله‌ای از عناصر پیوسته کار می‌کنند.

```
#include <span>
#include <numeric>

int sum(std::span<const int> values) {
    return std::accumulate(values.begin(), values.end(), 0);
}
```

اکنون این تابع می‌تواند با منابع مختلفی فراخوانی شود:

```
#include <array>
#include <vector>
#include <iostream>

int main() {
    int raw[]{1, 2, 3};

    std::array<int, 3> fixed{4, 5, 6};

    std::vector<int> dynamic{7, 8, 9};

    std::cout << sum(raw) << '\n';
    std::cout << sum(fixed) << '\n';
    std::cout << sum(dynamic) << '\n';
}
```

این مثال فرض می‌کند تعریف تابع `sum` در همان واحد ترجمه یا از طریق هدر مناسب در دسترس باشد.

چنین طراحی‌ای نیاز به Overloadهای جداگانه برای آرایه، Vector و Array را کاهش می‌دهد.

### استفاده در APIهای خواندنی

برای تابعی که صرفاً داده‌ها را تحلیل می‌کند، معمولاً `std::span<const T>` مناسب است.

```
#include <span>
#include <algorithm>

bool containsZero(std::span<const int> values) {
    return std::find(values.begin(), values.end(), 0) != values.end();
}
```

این تابع بدون نیاز به کپی داده‌ها می‌تواند با هر منبع سازگار فراخوانی شود.

### استفاده در APIهای تغییر‌دهنده

اگر تابع باید عناصر موجود را تغییر دهد، می‌توان Span قابل‌تغییر دریافت کرد.

```
#include <span>

void clearValues(std::span<int> values) {
    for (int& value : values) {
        value = 0;
    }
}
```

این تابع عناصر را تغییر می‌دهد، اما اندازه یا مالکیت Container اصلی را تغییر نمی‌دهد.

### انتخاب Span یا Container مالک

برای طراحی API باید میان دریافت یک View و دریافت یک Container مالک تمایز قائل شد.

| نیاز                                  | انتخاب مناسب                          |
| ------------------------------------- | ------------------------------------- |
| مشاهده یا پردازش عناصر موجود          | `std::span<const T>`                  |
| تغییر عناصر موجود بدون تغییر اندازه   | `std::span<T>`                        |
| مالکیت مستقل داده‌ها                  | `std::vector<T>` یا Container مناسب   |
| افزودن و حذف عناصر                    | Container مالک مانند `std::vector<T>` |
| نمایش دنباله‌ای با اندازه ثابت در نوع | `std::span<T, N>`                     |
| دسترسی به عناصر غیرپیوسته             | Container یا View مناسب دیگر          |

انتخاب Span نباید صرفاً به دلیل کاهش تعداد خطوط کد انجام شود. اگر تابع باید داده را برای استفاده بعدی نگه دارد، Span به‌تنهایی انتخاب امنی نیست؛ زیرا طول عمر داده خارجی را مدیریت نمی‌کند.

## عملیات روی زیرمحدوده‌ها

یکی از قابلیت‌های مهم `std::span`، ساخت View روی بخشی از دنباله بدون کپی‌کردن عناصر است.

### استفاده از `first`

متد `first` نمایی شامل تعدادی از عناصر ابتدایی ایجاد می‌کند.

```
#include <iostream>
#include <span>

int main() {
    int values[]{10, 20, 30, 40, 50};

    std::span<int> view{values};

    auto firstThree = view.first<3>();

    for (int value : firstThree) {
        std::cout << value << ' ';
    }
}
```

خروجی:

```
10 20 30
```

دو شکل اصلی وجود دارد:

```
auto a = view.first<3>();
auto b = view.first(3);
```

در شکل نخست، تعداد عناصر در زمان کامپایل مشخص است و نتیجه دارای Static Extent مناسب خواهد بود. در شکل دوم، تعداد عناصر هنگام اجرا تعیین می‌شود و نتیجه دارای Dynamic Extent است.

تعداد درخواست‌شده باید از اندازه Span بیشتر نباشد. نقض این شرط در ++C20 رفتار تعریف‌نشده ایجاد می‌کند.

### استفاده از `last`

متد `last` نمایی از آخرین عناصر دنباله ایجاد می‌کند.

```
#include <iostream>
#include <span>

int main() {
    int values[]{10, 20, 30, 40, 50};

    std::span<int> view{values};

    auto lastTwo = view.last<2>();

    for (int value : lastTwo) {
        std::cout << value << ' ';
    }
}
```

خروجی:

```
40 50
```

این متد برای دسترسی به پسوند دنباله مفید است و بدون تخصیص حافظه یا کپی‌کردن عناصر عمل می‌کند.

### استفاده از `subspan`

متد `subspan` برای ساخت نمایی از بخش دلخواه دنباله استفاده می‌شود.

```
#include <iostream>
#include <span>

int main() {
    int values[]{10, 20, 30, 40, 50};

    std::span<int> view{values};

    auto middle = view.subspan(1, 3);

    for (int value : middle) {
        std::cout << value << ' ';
    }
}
```

خروجی:

```
20 30 40
```

پارامتر نخست موقعیت شروع و پارامتر دوم تعداد عناصر را مشخص می‌کند.

همچنین می‌توان از تعداد عناصر باقی‌مانده استفاده کرد:

```
auto suffix = view.subspan(2);
```

در این مثال، نمای حاصل شامل عناصر از اندیس دوم تا انتهای دنباله خواهد بود.

اگر Offset یا تعداد عناصر از محدوده معتبر خارج شود، رفتار تعریف‌نشده ممکن است رخ دهد. برای ورودی‌های غیرقابل‌اعتماد، باید ابتدا محدوده را بررسی کرد.

### استفاده از `std::dynamic_extent`

در ++C20، مقدار `std::dynamic_extent` برای نمایش Dynamic Extent در سیستم نوع استفاده می‌شود.

```
#include <span>

static_assert(std::span<int>::extent == std::dynamic_extent);
static_assert(std::span<int, 4>::extent == 4);
```

این مقدار برای نوشتن قالب‌ها و بررسی ویژگی‌های نوع در زمان کامپایل مفید است.

## بررسی محدوده و ایمنی حافظه

### تفاوت `std::span` با ابزارهای Checked Access

نوع `std::span` اطلاعات محدوده را نگه می‌دارد، اما تمام دسترسی‌های آن را به‌صورت خودکار بررسی نمی‌کند.

برای مثال، کد زیر ایمن نیست:

```
#include <span>

int main() {
    int values[]{1, 2, 3};

    std::span<int> view{values};

    return view[10];
}
```

اندیس ده خارج از محدوده سه عنصر است. در ++C20، عملگر `operator[]` برای Span بررسی محدوده را تضمین نمی‌کند و این کد رفتار تعریف‌نشده دارد.

در مقابل، بررسی دستی امکان کنترل رفتار برنامه را فراهم می‌کند:

```
#include <span>
#include <stdexcept>

int readValue(std::span<const int> values, std::size_t index) {
    if (index >= values.size()) {
        throw std::out_of_range("Index out of range");
    }

    return values[index];
}
```

این روش برای APIهایی که با اندیس‌های ورودی کار می‌کنند، مناسب است.

### تفاوت با `std::vector::at`

متد `at` در `std::vector` در صورت خارج‌بودن اندیس از محدوده، استثنای `std::out_of_range` پرتاب می‌کند.

اما در ++C20، `std::span` متدی به نام `at` ندارد.

بنابراین، اگر بررسی محدوده در هر دسترسی الزامی باشد، باید آن را صریحاً انجام داد یا از یک Abstraction مناسب استفاده کرد که این تضمین را فراهم می‌کند.

### نقش Sanitizerها

ابزارهایی مانند AddressSanitizer می‌توانند بسیاری از خطاهای دسترسی به حافظه را در زمان اجرا شناسایی کنند.

برای نمونه، در محیط‌های سازگار می‌توان از گزینه‌های زیر استفاده کرد:

```
g++ -std=c++20 -fsanitize=address,undefined -fno-omit-frame-pointer main.cpp -o main
```

این ابزارها در یافتن خطاهای رایج مفید هستند، اما جایگزین طراحی صحیح و بررسی منطقی محدوده‌ها نیستند.

## طول عمر داده‌ها و خطر Dangling Span

### اصل اساسی طول عمر

از آنجا که Span مالک داده‌ها نیست، اعتبار آن به طول عمر داده زیربنایی وابسته است.

برای نمونه، تابع زیر یک Span نامعتبر برمی‌گرداند:

```
#include <span>
#include <vector>

std::span<const int> createValues() {
    std::vector<int> values{1, 2, 3};

    return std::span<const int>{values};
}
```

پس از پایان تابع، متغیر محلی `values` نابود می‌شود و حافظه آن دیگر برای استفاده از Span معتبر نیست.

در نتیجه، استفاده از Span بازگشتی می‌تواند رفتار تعریف‌نشده ایجاد کند.

### روش صحیح بازگرداندن داده

اگر تابع باید داده‌هایی تولید کند که پس از بازگشت نیز معتبر باقی بمانند، معمولاً باید مالکیت داده را به فراخواننده منتقل کند.

```
#include <vector>

std::vector<int> createValues() {
    return {1, 2, 3};
}
```

فراخواننده می‌تواند سپس Span را از Vector معتبر ایجاد کند:

```
#include <span>
#include <vector>

int main() {
    std::vector<int> values = createValues();

    std::span<const int> view{values};
}
```

در این طراحی، مالکیت داده روشن است و طول عمر Span به متغیر `values` وابسته خواهد بود.

### خطر Span روی Temporary

یکی از اشتباهات رایج، ساخت Span از یک Container موقت و نگه‌داشتن آن پس از پایان عبارت است.

```
#include <span>
#include <vector>

int main() {
    std::span<const int> view{std::vector<int>{1, 2, 3}};

    return view[0];
}
```

در ++C20، سازنده‌های معمول Span به‌گونه‌ای محدود شده‌اند که بسیاری از تبدیل‌های ناامن از Rangeهای موقت را رد کنند. بنابراین، این شکل از ساخت در پیاده‌سازی‌های منطبق معمولاً کامپایل نمی‌شود.

بااین‌حال، این محدودیت تمام سناریوهای مربوط به طول عمر را حل نمی‌کند. اگر برنامه ابتدا یک اشاره‌گر، Reference یا Span نامعتبر از مسیر دیگری دریافت کند، ساخت Span جدید از آن منبع لزوماً مشکل را آشکار نمی‌کند.

اصل مهم این است که داده زیربنایی باید در تمام مدت استفاده از Span معتبر باقی بماند.

### تأثیر تخصیص مجدد حافظه در Vector

حتی اگر Vector هنوز زنده باشد، تغییر ساختار آن می‌تواند Span را نامعتبر کند.

```
#include <span>
#include <vector>

int main() {
    std::vector<int> values{1, 2, 3};

    std::span<int> view{values};

    values.push_back(4);

    // The span may be invalid if vector reallocation occurred.
}
```

اگر `push_back` باعث Reallocation شود، اشاره‌گرهای قبلی به عناصر Vector نامعتبر می‌شوند.

از آنجا که Span از همان اشاره‌گرهای زیربنایی استفاده می‌کند، ممکن است دیگر به حافظه معتبر اشاره نکند.

اگر ظرفیت Vector برای درج عنصر جدید کافی باشد، درج عنصر در انتهای Vector معمولاً اشاره‌گرهای مربوط به عناصر قبلی را نامعتبر نمی‌کند؛ اما طراحی API نباید بدون بررسی شرایط دقیق، اعتبار Span را تضمین‌شده فرض کند.

### تأثیر تغییر اندازه و حذف عناصر

عملیات‌هایی مانند `erase`، `clear` و تغییر اندازه Vector ممکن است اعتبار Span را تحت تأثیر قرار دهند.

حتی در شرایطی که آدرس حافظه تغییر نکند، حذف یا نابودی عناصر می‌تواند دسترسی از طریق Span را نامعتبر کند.

بنابراین، اعتبار Span تنها به زنده‌بودن Container وابسته نیست؛ وضعیت عناصر و قواعد Invalidation آن Container نیز اهمیت دارند.

## استفاده از Span در توابع ناهمگام و کلاس‌ها

### نگهداری Span در اعضای کلاس

ذخیره Span در یک متغیر محلی معمولاً ساده است، اما نگهداری آن به‌عنوان عضو یک کلاس نیازمند طراحی دقیق‌تری است.

```
#include <span>

class Processor {
public:
    explicit Processor(std::span<const int> values)
        : values_(values) {}

    int firstValue() const {
        return values_.empty() ? 0 : values_.front();
    }

private:
    std::span<const int> values_;
};
```

این کلاس مالک داده نیست. بنابراین، فراخواننده باید تضمین کند که داده اصلی در تمام مدت استفاده از `Processor` زنده و معتبر باقی بماند.

برای کلاس‌هایی که عمر طولانی دارند یا داده‌ها را برای استفاده‌های آینده نگه می‌دارند، ذخیره Span ممکن است انتخاب مناسبی نباشد؛ مگر آنکه قرارداد طول عمر کاملاً روشن باشد.

### استفاده در Callbackها و Taskهای ناهمگام

در برنامه‌های ناهمگام، خطر Dangling Span بیشتر می‌شود؛ زیرا زمان اجرای Callback ممکن است با زمان عمر داده اصلی متفاوت باشد.

برای مثال، اگر یک Task پس از بازگشت تابع اجرا شود، Span محلی یا Span متصل به یک Buffer موقت ممکن است دیگر معتبر نباشد.

در چنین شرایطی، گزینه‌های مناسب می‌توانند شامل موارد زیر باشند:

- انتقال مالکیت داده به Task.
- نگهداری یک `std::vector` یا Container مالک در شیء مشترک.
- استفاده از یک مالکیت اشتراکی مناسب، مانند `std::shared_ptr`، همراه با طراحی روشن برای طول عمر.
- محدودکردن Span به محدوده اجرای همگام و تضمین‌شده.

استفاده از `std::span` به‌تنهایی هیچ تضمینی درباره Thread Safety، Synchronization یا طول عمر ناهمگام ایجاد نمی‌کند.

## مقایسه Span با Pointer، Container و Viewهای دیگر

### تفاوت با Pointer و Size

الگوی سنتی Pointer و Size به‌صورت زیر است:

```
void process(const int* data, std::size_t size);
```

در مقابل، رابط مبتنی بر Span به شکل زیر نوشته می‌شود:

```
void process(std::span<const int> values);
```

رابط دوم اندازه و اشاره‌گر را در یک شیء واحد قرار می‌دهد و احتمال اشتباه در ترتیب آرگومان‌ها یا جداشدن آن‌ها از یکدیگر را کاهش می‌دهد.

بااین‌حال، Span تضمین نمی‌کند که اشاره‌گر و اندازه اولیه معتبر بوده‌اند. اگر سازنده Span با اشاره‌گر نامعتبر یا اندازه نادرست فراخوانی شود، View حاصل همچنان می‌تواند نامعتبر باشد.

### تفاوت با `std::vector`

نوع `std::vector` یک Container مالک است که حافظه عناصر را مدیریت می‌کند.

در مقابل، `std::span` صرفاً یک View است.

| ویژگی                   | `std::span` | `std::vector`               |
| ----------------------- | ----------- | --------------------------- |
| مالکیت حافظه            | ندارد       | دارد                        |
| تخصیص حافظه برای عناصر  | ندارد       | ممکن است انجام شود          |
| تغییر اندازه            | ندارد       | دارد                        |
| افزودن و حذف عناصر      | ندارد       | دارد                        |
| دسترسی به عناصر پیوسته  | دارد        | دارد                        |
| مناسب برای APIهای ورودی | بسیار مناسب | بسته به نیاز                |
| مستقل از طول عمر منبع   | خیر         | بله، برای مالکیت مستقل خودش |

اگر هدف فقط پردازش عناصر موجود باشد، Span اغلب انتخاب بهتری برای پارامتر تابع است. اگر هدف نگهداری یا ساخت مجموعه‌ای مستقل باشد، Container مالک مناسب‌تر است.

### تفاوت با `std::string_view`

نوع `std::string_view` نیز یک Non-owning View است، اما برای دنباله‌های کاراکتری طراحی شده است.

در مقابل، `std::span` برای عناصر متوالی از نوع دلخواه استفاده می‌شود.

```
#include <span>
#include <string_view>

void processBytes(std::span<const unsigned char> bytes);

void processText(std::string_view text);
```

برای متن، `std::string_view` معمولاً رابط طبیعی‌تری است؛ زیرا عملیات مرتبط با رشته را فراهم می‌کند و با رشته‌های متداول سازگاری دارد.

برای داده‌های باینری، Bufferها و آرایه‌های عددی، `std::span` معمولاً مناسب‌تر است.

هر دو نوع غیرمالکانه هستند و باید از نظر طول عمر داده اصلی با دقت استفاده شوند.

### تفاوت با `std::ranges::subrange`

در ++C20، نوع `std::ranges::subrange` برای نمایش یک محدوده با استفاده از Iterator و Sentinel معرفی شده است.

برخلاف Span، یک `subrange` الزاماً به عناصر متوالی در حافظه محدود نیست.

برای مثال، می‌توان محدوده‌ای از یک Container مبتنی بر List را با `subrange` نمایش داد، در حالی که `std::span` برای چنین Container غیرپیوسته‌ای مناسب نیست.

در نتیجه، انتخاب میان این دو به ساختار داده و نیاز الگوریتم بستگی دارد:

- برای دنباله متوالی و دسترسی مستقیم به حافظه، `std::span` مناسب است.
- برای محدوده‌ای مبتنی بر Iterator و Sentinel که لزوماً پیوسته نیست، `std::ranges::subrange` می‌تواند مناسب باشد.

### تفاوت با `std::mdspan`

در ++C23، نوع `std::mdspan` برای نمایش چندبعدی داده‌ها معرفی شد.

Span معمولی یک دنباله یک‌بعدی از عناصر متوالی را نمایش می‌دهد، در حالی که `std::mdspan` می‌تواند دسترسی چندبعدی را با استفاده از Layoutهای مختلف مدل کند.

برای مثال، اگر داده‌ها در حافظه به‌صورت یک آرایه دوبعدی ذخیره شده باشند، `std::mdspan` می‌تواند دسترسی مبتنی بر اندیس‌های سطر و ستون را فراهم کند.

بنابراین، برای یک Buffer ساده از عناصر، Span معمولاً کافی است؛ اما برای مدل‌سازی ماتریس‌ها و داده‌های چندبعدی، `std::mdspan` ممکن است انتخاب دقیق‌تری باشد.

## کاربردهای عملی در پروژه‌های واقعی

### پردازش Bufferهای باینری

در سیستم‌هایی که داده از فایل، شبکه یا دستگاه سخت‌افزاری دریافت می‌شود، معمولاً یک Buffer به همراه اندازه آن در اختیار برنامه قرار می‌گیرد.

نوع `std::span<const std::byte>` می‌تواند این داده را بدون کپی‌کردن نمایش دهد.

```
#include <cstddef>
#include <span>

bool hasEnoughData(std::span<const std::byte> bytes,
                   std::size_t requiredSize) {
    return bytes.size() >= requiredSize;
}
```

این الگو برای بررسی اندازه Buffer پیش از پردازش مفید است.

بااین‌حال، Span به‌تنهایی اعتبار قالب فایل، صحت Protocol یا ایمن‌بودن داده دریافتی را تضمین نمی‌کند. این موارد باید به‌صورت جداگانه بررسی شوند.

### پردازش زیرمحدوده‌های فایل یا شبکه

اگر یک Buffer شامل Header و Payload باشد، می‌توان با استفاده از `first` و `subspan` بخش‌های مختلف را بدون کپی جدا کرد.

```
#include <cstddef>
#include <span>

struct PacketParts {
    std::span<const std::byte> header;
    std::span<const std::byte> payload;
};

PacketParts splitPacket(std::span<const std::byte> packet,
                        std::size_t headerSize) {
    if (headerSize > packet.size()) {
        return {};
    }

    return {
        packet.first(headerSize),
        packet.subspan(headerSize)
    };
}
```

این مثال نشان می‌دهد که چگونه می‌توان یک Buffer را به چند نمای مستقل تقسیم کرد، بدون آنکه حافظه داده‌ها جابه‌جا یا کپی شود.

اعتبار نماهای بازگشتی همچنان به طول عمر و اعتبار Buffer ورودی وابسته است.

### کار با داده‌های عددی

در الگوریتم‌های عددی، Span می‌تواند رابط مشترکی برای داده‌های متعلق به Containerهای مختلف فراهم کند.

```
#include <numeric>
#include <span>

double average(std::span<const double> values) {
    if (values.empty()) {
        return 0.0;
    }

    const double total =
        std::accumulate(values.begin(), values.end(), 0.0);

    return total / static_cast<double>(values.size());
}
```

در این طراحی، رفتار تابع برای ورودی خالی صریح است. در کاربردهای مالی یا علمی، ممکن است به‌جای صفر لازم باشد خطا یا نتیجه‌ای مانند `std::optional` برگردانده شود؛ انتخاب مناسب به قرارداد API بستگی دارد.

### استفاده در مرز میان کتابخانه‌ها

گاهی یک کتابخانه قدیمی از اشاره‌گر و اندازه استفاده می‌کند، در حالی که بخش جدید برنامه بر مبنای Span طراحی شده است.

در چنین شرایطی، می‌توان Span را به رابط قدیمی تبدیل کرد:

```
#include <cstddef>
#include <span>

void oldApi(const unsigned char* data, std::size_t size);

void newApi(std::span<const unsigned char> bytes) {
    oldApi(bytes.data(), bytes.size());
}
```

این روش امکان مهاجرت تدریجی APIها را فراهم می‌کند، بدون اینکه لازم باشد تمام بخش‌های قدیمی برنامه به‌صورت هم‌زمان بازنویسی شوند.

## عملکرد و هزینه اجرایی

### هزینه ساخت Span

ساخت Span معمولاً بسیار ارزان است؛ زیرا داده‌ها را کپی نمی‌کند و حافظه‌ای برای عناصر تخصیص نمی‌دهد.

در بسیاری از پیاده‌سازی‌ها، یک Span با Dynamic Extent از اطلاعاتی معادل اشاره‌گر و اندازه استفاده می‌کند. بااین‌حال، استاندارد تنها رفتار و قرارداد نوع را مشخص می‌کند و ساختار دقیق حافظه آن را تضمین نمی‌کند.

### تأثیر بر Inline و Optimization

از آنجا که Span یک نوع ساده برای نمایش View است، استفاده از آن معمولاً مانع Optimizationهای رایج کامپایلر نمی‌شود.

کامپایلر ممکن است توابعی را که Span دریافت می‌کنند Inline کند یا اطلاعات Static Extent را برای ساده‌سازی حلقه‌ها و دسترسی‌ها به کار ببرد.

بااین‌حال، هیچ تضمینی وجود ندارد که استفاده از Span در همه شرایط سریع‌تر از Pointer و Size باشد. تفاوت واقعی به کد تولیدشده، کامپایلر، معماری هدف و نحوه استفاده بستگی دارد.

برای تصمیم‌های حساس به کارایی، Benchmark و بررسی Assembly تولیدشده از حدس‌زدن مطمئن‌تر است.

### آیا Static Extent همیشه سریع‌تر است؟

Static Extent اطلاعات بیشتری درباره تعداد عناصر در زمان کامپایل فراهم می‌کند و ممکن است به Optimization بهتر کمک کند.

اما اگر اندازه واقعی در زمان اجرا متغیر باشد یا API به انعطاف‌پذیری بیشتری نیاز داشته باشد، Dynamic Extent معمولاً طراحی مناسب‌تری خواهد بود.

انتخاب Static Extent باید عمدتاً از قرارداد واقعی داده‌ها ناشی شود، نه صرفاً این فرض که هر نوع با اندازه ثابت الزاماً عملکرد بهتری دارد.

## نکات مهم در استفاده حرفه‌ای

### پرهیز از نگهداری طولانی‌مدت View بدون قرارداد مالکیت

در طراحی API، مشخص کنید که Span فقط برای مدت فراخوانی تابع معتبر است یا قرار است پس از آن نیز نگهداری شود.

اگر View در یک عضو کلاس، Callback یا Task ذخیره می‌شود، باید مسئولیت طول عمر داده‌ها روشن باشد.

### پرهیز از استفاده برای Containerهای غیرپیوسته

نوع `std::span` برای عناصر متوالی در حافظه طراحی شده است. استفاده از آن برای مدل‌سازی یک مجموعه غیرپیوسته، مانند `std::list`، مناسب نیست.

اگر الگوریتم فقط به پیمایش نیاز دارد و پیوستگی حافظه اهمیت ندارد، استفاده از Rangeها و Iteratorها انعطاف‌پذیری بیشتری فراهم می‌کند.

### توجه به Invalidation

پس از تغییر ساختاری Container مالک، اعتبار Span را دوباره بررسی کنید. عملیات درج، حذف، تغییر اندازه یا تخصیص مجدد حافظه می‌تواند Viewهای موجود را نامعتبر کند.

### استفاده از نوع فقط‌خواندنی در صورت امکان

اگر تابع قرار نیست عناصر را تغییر دهد، دریافت `std::span<const T>` معمولاً قرارداد روشن‌تر و ایمن‌تری ایجاد می‌کند.

### بررسی اندازه پیش از ساخت زیرمحدوده

در عملیات‌هایی مانند `first`، `last` و `subspan`، اندازه و Offset را پیش از ساخت View بررسی کنید، به‌خصوص زمانی که این مقادیر از داده خارجی به دست می‌آیند.

### تفکیک مالکیت از دسترسی

Span راهکاری برای دسترسی به حافظه موجود است، نه راهکاری برای مالکیت، مدیریت منابع یا همگام‌سازی Threadها. اگر این نیازها در مسئله وجود دارند، باید از ابزارهای دیگری در کنار آن استفاده شود.

## محدودیت‌های مهم `std::span`

با وجود کاربرد گسترده، Span محدودیت‌هایی دارد که باید هنگام طراحی سیستم در نظر گرفته شوند:

- نبود مالکیت: Span مسئول آزادسازی یا نگهداری داده‌ها نیست.
- نبود بررسی خودکار همه دسترسی‌ها: استفاده از `operator[]` خارج از محدوده می‌تواند رفتار تعریف‌نشده ایجاد کند.
- نیاز به پیوستگی حافظه: داده‌ها باید به‌صورت عناصر متوالی قابل‌دسترسی باشند.
- نبود قابلیت تغییر اندازه: Span نمی‌تواند عناصر را به Container اضافه یا از آن حذف کند.
- وابستگی به طول عمر منبع: نابودی داده اصلی یا نامعتبرشدن آدرس آن، Span را نیز نامعتبر می‌کند.
- نبود تضمین Thread Safety: استفاده هم‌زمان از Span برای خواندن و نوشتن نیازمند رعایت قواعد همگام‌سازی است.
- محدودیت در مالکیت مستقل: برای نگهداری داده در بلندمدت، Container مالک معمولاً مناسب‌تر است.

این محدودیت‌ها نقص طراحی Span نیستند؛ بلکه نتیجه هدف آن، یعنی نمایش سبک و غیرمالکانه یک دنباله موجود، محسوب می‌شوند.

## جمع‌بندی نهایی

نوع `std::span` در استاندارد ++C20 ابزاری ساده و مؤثر برای نمایش دنباله‌ای از عناصر متوالی در حافظه است. این نوع به توسعه‌دهندگان اجازه می‌دهد APIهایی طراحی کنند که به‌جای دریافت جداگانه اشاره‌گر و اندازه، یک View واحد دریافت کنند.

مهم‌ترین کاربردهای آن عبارت‌اند از:

- پردازش آرایه‌ها، `std::array` و `std::vector` از طریق یک رابط مشترک.
- طراحی توابعی که به مالکیت داده‌ها نیاز ندارند.
- تقسیم Bufferها به زیرمحدوده‌ها بدون کپی‌کردن داده.
- اتصال APIهای مدرن به رابط‌های قدیمی مبتنی بر Pointer و Size.
- بیان اندازه ثابت یا متغیر از طریق Static Extent و Dynamic Extent.

در انتخاب این نوع باید به چند اصل توجه کرد: Span مالک داده‌ها نیست، اعتبار آن به طول عمر و وضعیت حافظه منبع وابسته است، و دسترسی خارج از محدوده را به‌طور خودکار ایمن نمی‌کند.

اگر تابع صرفاً باید داده‌های موجود را بخواند یا تغییر دهد، `std::span` اغلب یک انتخاب مناسب برای طراحی API است. اما اگر برنامه به مالکیت مستقل، تغییر اندازه، نگهداری طولانی‌مدت یا مدیریت پیچیده طول عمر نیاز دارد، باید از Containerها و ابزارهای مالکیت مناسب استفاده کرد.

در نهایت، استفاده صحیح از Span زمانی بیشترین ارزش را دارد که همراه با طراحی روشن درباره مالکیت، طول عمر، محدوده دسترسی و قرارداد API باشد.
