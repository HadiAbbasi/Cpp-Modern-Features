# **آشنایی جامع با&#x20;**`std::latch`**&#x20;در ++C20**

## **مقدمه**

در برنامه‌های چندنخی، گاهی لازم است یک یا چند Thread پیش از ادامهٔ اجرای خود منتظر بمانند تا تعداد مشخصی از عملیات مستقل به پایان برسند. برای مثال، ممکن است چند Thread داده‌های جداگانه‌ای را بارگذاری کنند و Thread اصلی فقط پس از آماده‌شدن تمام داده‌ها، مرحلهٔ بعدی پردازش را آغاز کند.

برای پیاده‌سازی این نوع هماهنگی می‌توان از `std::mutex`، `std::condition_variable` یا شمارنده‌های اتمیک استفاده کرد؛ اما این راهکارها معمولاً به کدنویسی تکراری و مدیریت دستی وضعیت هم‌زمانی نیاز دارند.

کتابخانهٔ استاندارد ++C20 با معرفی `std::latch` یک ابزار تخصصی برای پیاده‌سازی این الگوی هماهنگی فراهم کرده است.

کلاس `std::latch` یک synchronization primitive یک‌بارمصرف است که با یک شمارندهٔ اولیه ساخته می‌شود. هر Thread یا عملیات می‌تواند پس از تکمیل سهم خود، شمارنده را کاهش دهد. Threadهای منتظر نیز زمانی آزاد می‌شوند که شمارنده به صفر برسد.

## **مفهوم و هدف طراحی**

### **مسئله‌ای که latch حل می‌کند**

فرض کنید برنامه‌ای چند وظیفهٔ مستقل را به‌صورت موازی اجرا می‌کند و ادامهٔ کار به تکمیل همهٔ آن‌ها وابسته است.

این الگو شامل مراحل زیر است:

- چند عملیات به‌صورت مستقل آغاز می‌شوند.
- هر عملیات پس از تکمیل، پایان سهم خود را اعلام می‌کند.
- یک یا چند Thread منتظر صفرشدن شمارنده می‌مانند.
- پس از تکمیل آخرین سهم، تمام Threadهای منتظر امکان ادامهٔ اجرا پیدا می‌کنند.

این الگو در موارد زیر کاربرد دارد:

- آماده‌سازی موازی منابع برنامه
- بارگذاری هم‌زمان چند فایل
- راه‌اندازی چند سرویس داخلی
- اجرای مرحله‌ای از یک pipeline
- جمع‌آوری نتایج چند وظیفهٔ مستقل
- هماهنگی Thread اصلی با چند Thread کارگر

### **ماهیت یک‌بارمصرف**

مهم‌ترین ویژگی طراحی `std::latch` این است که پس از رسیدن شمارنده به صفر، دوباره قابل افزایش یا مسلح‌سازی نیست.

بنابراین، این کلاس برای یک نقطهٔ هماهنگی مشخص در طول عمر خود طراحی شده است، نه برای تکرار چندین دور هماهنگی.

برای مثال، اگر چند Thread فقط یک بار باید اعلام کنند که منابع موردنیاز آماده شده‌اند، `std::latch` انتخاب مناسبی است.

اما اگر همان Threadها باید در چندین iteration با یکدیگر هماهنگ شوند، معمولاً `std::barrier` گزینهٔ مناسب‌تری خواهد بود.

## **سرآیند و فضای نام**

برای استفاده از این قابلیت باید سرآیند استاندارد زیر را وارد کرد:

```
#include <latch>
```

نوع `latch` در فضای نام `std` قرار دارد:

```
std::latch ready{3};
```

این قابلیت بخشی از Standard Library در ++C20 است و به افزونهٔ اختصاصی Compiler تعلق ندارد.

البته پشتیبانی واقعی آن به نسخهٔ Compiler و کتابخانهٔ استاندارد همراه آن وابسته است.

## **رابط برنامه‌نویسی**

### **سازنده**

امضای اصلی سازنده به شکل زیر است:

```
explicit latch(std::ptrdiff_t expected);
```

پارامتر `expected` مقدار اولیهٔ شمارنده را تعیین می‌کند.

این مقدار مشخص می‌کند چه تعداد سهم باید اعلام شوند تا latch به وضعیت تکمیل برسد.

مقدار `expected` باید نامنفی باشد و از مقدار `std::latch::max()` بیشتر نباشد.

مقدار صفر نیز معتبر است. در این حالت latch از همان ابتدا آماده است و عملیات انتظار بدون مسدودشدن بازمی‌گردند.

### **تابع max**

تابع ایستای `max` بیشترین مقدار مجاز برای شمارنده را برمی‌گرداند:

```
static constexpr std::ptrdiff_t max() noexcept;
```

این مقدار به پیاده‌سازی وابسته است؛ بنابراین نباید یک مقدار ثابت و قابل‌حمل را برای تمام پلتفرم‌ها فرض کرد.

### **تابع count_down**

تابع `count_down` شمارنده را کاهش می‌دهد:

```
void count_down(std::ptrdiff_t update = 1) noexcept;
```

مقدار پیش‌فرض `update` برابر یک است.

این تابع برای اعلام تکمیل سهم یک عملیات استفاده می‌شود و منتظر صفرشدن شمارنده نمی‌ماند.

مقدار `update` باید نامنفی باشد و نباید از شمارندهٔ فعلی بیشتر شود.

نقض پیش‌شرط‌های این عملیات رفتار تعریف‌نشده (Undefined Behavior) ایجاد می‌کند.

مقدار صفر باعث کاهش شمارنده نمی‌شود و برای اعلام تکمیل یک سهم کاربردی ندارد.

نکتهٔ مهم این است که `count_down` یک عملیات انتظار نیست. اگر کاهش شمارنده آن را به صفر برساند، Thread فراخواننده می‌تواند بلافاصله ادامه دهد؛ در حالی که Threadهای دیگری که منتظر هستند نیز آزاد خواهند شد.

### **تابع wait**

تابع `wait` تا صفرشدن شمارنده منتظر می‌ماند:

```
void wait() const;
```

این تابع مقدار شمارنده را تغییر نمی‌دهد.

اگر شمارنده از قبل صفر باشد، تابع بدون انتظار بازمی‌گردد.

چند Thread می‌توانند هم‌زمان روی یک latch منتظر بمانند. هنگامی که شمارنده به صفر برسد، همهٔ آن‌ها از نقطهٔ انتظار عبور می‌کنند.

### **تابع try_wait**

تابع `try_wait` وضعیت latch را بدون انتظار مسدودکننده بررسی می‌کند:

```
bool try_wait() const noexcept;
```

اگر شمارنده صفر باشد، مقدار `true` و در غیر این صورت مقدار `false` برمی‌گرداند.

این تابع برای بررسی آماده‌بودن latch مناسب است، نه برای جایگزین‌کردن یک پروتکل انتظار صحیح.

استفادهٔ مکرر از `try_wait` در یک حلقهٔ busy-wait می‌تواند CPU را بی‌دلیل درگیر کند.

اگر Thread باید تا تکمیل عملیات منتظر بماند، معمولاً `wait` انتخاب ساده‌تر و کارآمدتری است.

### **تابع arrive_and_wait**

تابع `arrive_and_wait` سهم مشخصی را اعلام می‌کند و سپس تا صفرشدن شمارنده منتظر می‌ماند:

```
void arrive_and_wait(std::ptrdiff_t update = 1);
```

این تابع از نظر مفهومی معادل اجرای `count_down(update)` و سپس `wait()` است.

مقدار `update` باید مثبت باشد و از شمارندهٔ فعلی بیشتر نباشد.

این عملیات زمانی مفید است که خود Thread نیز یکی از مشارکت‌کنندگان در رسیدن به نقطهٔ هماهنگی باشد و پس از اعلام سهم خود، نباید پیش از تکمیل دیگر سهم‌ها ادامه دهد.

## **مدل حافظه و تضمین‌های هم‌زمانی**

### **ترتیب‌دهی حافظه**

`std::latch` فقط یک شمارندهٔ ساده نیست؛ بلکه برای هماهنگ‌سازی حافظه میان Threadها نیز تضمین استاندارد ارائه می‌کند.

عملیات‌هایی که پیش از کاهش شمارنده توسط Threadهای مشارکت‌کننده انجام شده‌اند، از طریق سازوکار synchronization مربوط به latch می‌توانند برای Threadهایی که پس از صفرشدن شمارنده از `wait` عبور می‌کنند قابل مشاهده باشند.

به بیان عملی، اگر هر Thread داده‌ای را آماده کند و سپس سهم خود را با `count_down` اعلام کند، Thread منتظر می‌تواند پس از بازگشت `wait` به نتایج آماده‌شده دسترسی پیدا کند؛ مشروط بر اینکه خود داده‌ها نیز بدون data race استفاده شده باشند.

این ویژگی به معنی بی‌نیازی از طراحی درست مالکیت داده نیست.

اگر چند Thread به‌طور هم‌زمان یک شیء غیراتمیک را بنویسند یا Thread دیگری مستقل از پروتکل latch به آن دسترسی داشته باشد، همچنان احتمال data race وجود دارد.

### **نقطهٔ تکمیل**

هنگامی که یک عملیات کاهش، شمارنده را به صفر می‌رساند، latch به وضعیت تکمیل می‌رسد.

بازگشت فراخوانی‌های `wait` که این وضعیت را مشاهده می‌کنند با عملیات تکمیل ارتباط synchronization دارد.

در طراحی برنامه بهتر است `count_down` را پس از پایان واقعی کار و پس از آماده‌سازی تمام داده‌های موردنیاز فراخوانی کنید؛ نه در ابتدای عملیات یا پیش از ثبت نتیجه.

### **تفاوت با خاتمهٔ Thread**

رسیدن latch به صفر به این معنی نیست که تمام Threadهای مشارکت‌کننده خاتمه یافته‌اند.

این وضعیت فقط نشان می‌دهد تعداد اعلام‌شده‌ای از سهم‌ها ثبت شده است.

ممکن است یک Thread پس از اجرای `count_down` همچنان کدهای دیگری اجرا کند.

اگر لازم است خاتمهٔ کامل Threadها نیز تضمین شود، باید از مکانیزم مناسب مدیریت عمر Thread، مانند `join`، استفاده کرد.

## **مثال‌های کاربردی**

### **انتظار Thread اصلی برای آماده‌شدن چند کارگر**

در مثال زیر سه Thread هرکدام بخشی از داده را آماده می‌کنند. Thread اصلی تا تکمیل هر سه کار منتظر می‌ماند:

```
#include <array>
#include <iostream>
#include <latch>
#include <thread>

int main() {
    constexpr int workerCount = 3;

    std::latch ready{workerCount};
    std::array<int, workerCount> results{};

    std::array<std::jthread, workerCount> workers;

    for (int i = 0; i < workerCount; ++i) {
        workers[i] = std::jthread([&, i] {
            results[i] = (i + 1) * 10;
            ready.count_down();
        });
    }

    ready.wait();

    int total = 0;
    for (int value : results) {
        total += value;
    }

    std::cout << "Total: " << total << '\n';
}
```

در این نمونه هر Thread فقط عنصر اختصاصی خود را در آرایه می‌نویسد؛ بنابراین نوشتن عناصر مستقل با یکدیگر تداخل ندارد.

Thread اصلی پس از بازگشت `wait` نتایج را جمع می‌کند.

استفاده از `std::jthread` که در ++C20 معرفی شده است، مدیریت پایان Threadها را ساده‌تر می‌کند.

Destructor هر `jthread` در صورت joinable بودن، ابتدا درخواست توقف می‌دهد و سپس Thread را join می‌کند.

در این مثال Threadها پیش از خروج از `main` کار خود را تمام کرده‌اند.

### **مشارکت Thread اصلی در نقطهٔ هماهنگی**

گاهی Thread اصلی نیز یک کار مستقل انجام می‌دهد و باید همراه کارگران به نقطهٔ هماهنگی برسد.

در این حالت می‌توان از `arrive_and_wait` استفاده کرد:

```
#include <iostream>
#include <latch>
#include <thread>

int main() {
    std::latch phaseReady{3};

    std::jthread first([&] {
        // Perform the first preparation task
        phaseReady.arrive_and_wait();

        // Continue after all participants arrive
        std::cout << "First worker continues\n";
    });

    std::jthread second([&] {
        // Perform the second preparation task
        phaseReady.arrive_and_wait();

        // Continue after all participants arrive
        std::cout << "Second worker continues\n";
    });

    // Perform the main thread preparation task
    phaseReady.arrive_and_wait();

    std::cout << "Main thread continues\n";
}
```

در این مثال شمارنده از سه شروع می‌شود:

- یک سهم متعلق به Thread اول است.
- یک سهم متعلق به Thread دوم است.
- یک سهم متعلق به Thread اصلی است.

هر مشارکت‌کننده پس از انجام کار خود سهمش را اعلام می‌کند و تا رسیدن مشارکت‌کنندگان دیگر منتظر می‌ماند.

### **بررسی آماده‌بودن بدون مسدودشدن**

گاهی برنامه می‌خواهد در صورت آماده‌بودن مرحلهٔ بعد را اجرا کند و در غیر این صورت کار دیگری انجام دهد:

```
#include <iostream>
#include <latch>
#include <thread>

int main() {
    std::latch completed{1};

    std::jthread worker([&] {
        // Perform some work
        completed.count_down();
    });

    if (completed.try_wait()) {
        std::cout << "Work is already complete\n";
    } else {
        std::cout << "Work is still running\n";
        completed.wait();
    }

    std::cout << "Continue execution\n";
}
```

نتیجهٔ `try_wait` فقط وضعیت latch در زمان بررسی را نشان می‌دهد.

اگر مقدار `false` باشد، ممکن است عملیات بلافاصله پس از آن کامل شود؛ بنابراین این نتیجه نباید به‌عنوان تضمین ادامه‌دارِ آماده‌نبودن تفسیر شود.

### **آماده‌سازی موازی منابع**

یکی از کاربردهای مناسب latch، انتظار برای آماده‌شدن چند منبع مستقل است.

برای مثال، یک برنامه می‌تواند تنظیمات، جدول‌های داده و فایل‌های موردنیاز را به‌صورت موازی بارگذاری کند و سپس پردازش اصلی را آغاز کند:

```
#include <latch>
#include <thread>

struct ApplicationState {
    int configurationVersion = 0;
    int dataVersion = 0;
    int cacheVersion = 0;
};

int main() {
    ApplicationState state;
    std::latch initialized{3};

    std::jthread configLoader([&] {
        state.configurationVersion = 1;
        initialized.count_down();
    });

    std::jthread dataLoader([&] {
        state.dataVersion = 2;
        initialized.count_down();
    });

    std::jthread cacheBuilder([&] {
        state.cacheVersion = 3;
        initialized.count_down();
    });

    initialized.wait();

    // All initialization tasks have reported completion.
    // The application can now use the prepared state.
}
```

هر Thread در این مثال عضو جداگانه‌ای از `state` را می‌نویسد.

پس از بازگشت `wait`، Thread اصلی می‌تواند وضعیت آماده‌شده را بخواند.

در یک برنامهٔ واقعی، خطاهای بارگذاری نیز باید مدیریت شوند؛ زیرا latch به‌تنهایی سازوکار گزارش خطا نیست.

## **طراحی و الگوهای استفاده**

### **تعیین تعداد مشارکت‌کنندگان**

مقدار اولیه باید با تعداد واقعی اعلام‌های مورد انتظار هماهنگ باشد.

اگر مقدار بیش از تعداد اعلام‌های واقعی باشد، Threadهای منتظر ممکن است برای همیشه مسدود بمانند.

اگر مقدار کمتر باشد، latch زودتر از تکمیل همهٔ کارها به صفر می‌رسد.

بهتر است تعداد کارها از یک منبع واحد محاسبه شود و همان مقدار هم برای ساخت latch و هم برای ایجاد کارها به کار رود.

از پراکندن عددهای ثابت در چند بخش برنامه خودداری کنید.

### **ثبت سهم دقیقاً یک‌بار**

هر سهم باید دقیقاً مطابق پروتکل طراحی‌شده اعلام شود.

اگر یک عملیات دوبار `count_down` را برای یک سهم اجرا کند، ممکن است شمارنده بیش از حد کاهش یابد و رفتار تعریف‌نشده رخ دهد.

اگر یک مسیر اجرایی هرگز سهم خود را اعلام نکند، انتظار ممکن است هیچ‌گاه پایان نیابد.

برای مدیریت مسیرهای دارای چند خروجی، از جمله exception یا early return، باید مطمئن شوید پروتکل تکمیل سهم نقض نمی‌شود.

در صورت نیاز می‌توان یک guard اختصاصی با RAII طراحی کرد تا اعلام سهم در مسیرهای خروج تضمین شود؛ البته باید مراقب بود که اعلام سهم در زمان نامناسب یا بیش از یک بار انجام نشود.

### **مدیریت خطا و لغو عملیات**

`std::latch` مکانیزم داخلی برای exception، cancellation یا timeout ندارد.

اگر یکی از کارها شکست بخورد و سهم خود را اعلام نکند، Threadهای منتظر ممکن است برای همیشه منتظر بمانند.

یک طراحی مقاوم باید نتیجهٔ هر کار را در ساختاری مناسب ثبت کند و حتی در مسیر شکست نیز پروتکل شمارش را کامل کند.

سپس Thread منتظر می‌تواند پس از بازگشت `wait` وضعیت خطاها را بررسی کند.

اگر نیاز به timeout دارید، `std::latch` به‌تنهایی API مربوط به زمان انتظار ارائه نمی‌کند.

در چنین شرایطی باید از طراحی دیگری مانند `std::condition_variable` یا سازوکار هماهنگی مناسب‌تر استفاده کنید.

### **عمر شیء و مالکیت**

شیء latch باید تا پایان تمام عملیات‌هایی که به آن دسترسی دارند زنده بماند.

نابودکردن latch در حالی که Thread دیگری هنوز در `count_down`، `wait` یا عملیات مرتبط با آن است، طراحی معتبری نیست و می‌تواند به رفتار تعریف‌نشده منجر شود.

برای جلوگیری از dangling reference، معمولاً latch را در محدوده‌ای قرار دهید که طول عمر آن از تمام Threadهای مشارکت‌کننده بیشتر باشد.

پیش از نابودی شیء، پایان دسترسی Threadها را با `join` یا سازوکار مالکیت مناسب تضمین کنید.

## **محدودیت‌ها و خطاهای رایج**

### **تلاش برای استفادهٔ مجدد**

پس از صفرشدن شمارنده، امکان افزایش مجدد آن وجود ندارد.

بنابراین استفاده از یک latch برای چند مرحلهٔ متوالی، مانند چند دور پردازش، اشتباه است.

برای هماهنگی تکرارشونده از `std::barrier` یا primitive متناسب با مسئله استفاده کنید.

### **مقداردهی با تعداد نادرست**

اگر شمارنده بزرگ‌تر از تعداد اعلام‌های واقعی باشد، انتظار خاتمه پیدا نمی‌کند.

اگر کوچک‌تر باشد، Thread منتظر ممکن است پیش از تکمیل واقعی کارها آزاد شود.

تعداد مشارکت‌کنندگان را با دقت طراحی کنید.

### **کاهش بیش از مقدار باقی‌مانده**

مجموع کاهش‌ها نباید از شمارندهٔ فعلی بیشتر شود.

این شرط را با منطق برنامه تضمین کنید؛ `std::latch` برای کاهش نامعتبر، exception یا خطای قابل‌بازیابی تولید نمی‌کند.

### **فرض اشتباه دربارهٔ join**

بازگشت `wait` به معنای پایان عمر یا خاتمهٔ Threadهای کارگر نیست.

این تابع فقط اعلام می‌کند همهٔ سهم‌های مورد انتظار ثبت شده‌اند.

برای اطمینان از خاتمهٔ Threadها از `join` استفاده کنید.

### **استفاده از polling غیرضروری**

حلقه‌ای که مرتب `try_wait` را فراخوانی می‌کند، می‌تواند مصرف CPU را افزایش دهد.

اگر نیازی به انجام کارهای دیگر در همان Thread ندارید، `wait` را ترجیح دهید.

### **انتظار برای مشارکت‌کننده‌ای که هرگز اجرا نمی‌شود**

اگر شمارنده برای کاری در نظر گرفته شده باشد که به علت خطای زمان‌بندی، شکست ایجاد Thread یا مسیر اجرایی خاص هرگز سهم خود را اعلام نمی‌کند، انتظار ممکن است دائمی شود.

طراحی پروتکل باید مسیرهای شکست و عدم اجرای وظیفه را نیز پوشش دهد.

### **تصور تضمین ترتیب اجرای Threadها**

`std::latch` تضمین نمی‌کند Threadها به ترتیب مشخصی از `wait` خارج شوند یا پس از آزادشدن به ترتیب خاصی اجرا شوند.

زمان‌بندی Threadها در اختیار سیستم‌عامل و پیاده‌سازی runtime است.

## **مقایسه با ابزارهای هم‌خانواده**

### **تفاوت با std::barrier**

هر دو ابزار برای هماهنگی میان چند Thread استفاده می‌شوند، اما هدف طراحی متفاوتی دارند:

| ویژگی               | `std::latch`                       | `std::barrier`                                 |
| ------------------- | ---------------------------------- | ---------------------------------------------- |
| استاندارد معرفی     | ++C20                              | ++C20                                          |
| ماهیت               | یک‌بارمصرف                         | چندمرحله‌ای و قابل استفادهٔ مجدد               |
| شمارنده             | فقط کاهش می‌یابد                   | تعداد مشارکت‌کنندگان در هر phase مدیریت می‌شود |
| انتظار مشارکت‌کننده | `wait` یا `arrive_and_wait`        | `arrive_and_wait` و عملیات مرتبط               |
| کاربرد اصلی         | انتظار تا تکمیل مجموعه‌ای از کارها | همگام‌سازی تکرارشوندهٔ چند مرحله               |
| افزایش مجدد شمارنده | ندارد                              | هر phase با سازوکار barrier مدیریت می‌شود      |

برای مثال، اگر چند Thread باید فقط یک بار منابع را آماده کنند و سپس برنامه ادامه یابد، latch ساده‌تر است.

اگر همان Threadها باید در هر iteration نتایج را جمع کنند و سپس وارد iteration بعدی شوند، barrier معمولاً مناسب‌تر است.

### **تفاوت با std::condition_variable**

`std::condition_variable` یک ابزار عمومی‌تر برای انتظار بر اساس predicate است.

برنامه‌نویس باید mutex، وضعیت مشترک و حلقهٔ بررسی predicate را مدیریت کند.

در مقابل، latch یک شمارندهٔ مشخص و یک هدف ساده دارد و برای الگوی «منتظر بمان تا N سهم ثبت شود» کدنویسی کمتری می‌طلبد.

اگر شرط انتظار پیچیده است، وضعیت باید تغییرپذیر باشد، timeout لازم است یا امکان بیدارشدن بر اساس چند شرط وجود دارد، `condition_variable` انعطاف بیشتری فراهم می‌کند.

### **تفاوت با std::atomic**

شمارندهٔ اتمیک امکان پیاده‌سازی شمارش هم‌زمان را فراهم می‌کند، اما به‌تنهایی یک سازوکار انتظار چند Thread نیست.

پیاده‌سازی دستی latch با atomic معمولاً به مدیریت حلقهٔ انتظار، notification و مدل حافظه نیاز دارد.

از ++C20 می‌توان در برخی سناریوها از `std::atomic::wait` و عملیات notification استفاده کرد؛ با این حال، latch یک abstraction سطح‌بالاتر برای شمارش سهم‌ها و انتظار تا صفرشدن شمارنده است.

انتخاب میان آن‌ها به نیاز دقیق پروتکل وابسته است.

### **تفاوت با std::future و std::promise**

`std::future` و `std::promise` برای انتقال نتیجه یا exception یک عملیات ناهم‌زمان به مصرف‌کننده مناسب‌اند.

latch صرفاً تکمیل تعداد معینی سهم را هماهنگ می‌کند و نتیجهٔ هر کار را منتقل نمی‌کند.

اگر باید نتیجهٔ مستقل هر عملیات را دریافت کنید، futureها ممکن است انتخاب مناسب‌تری باشند.

اگر هدف تنها اعلام آماده‌شدن چند کار مستقل است، latch می‌تواند راه‌حل سبک‌تری باشد.

## **نکات پیاده‌سازی و قابلیت حمل**

### **پشتیبانی Compiler و کتابخانه**

وجود زبان ++C20 در Compiler به‌تنهایی تضمین نمی‌کند تمام قابلیت‌های Standard Library نیز در نسخهٔ نصب‌شده کامل باشند.

پشتیبانی `std::latch` به پیاده‌سازی کتابخانهٔ استاندارد، مانند libstdc++، libc++ یا Microsoft STL، و نسخهٔ آن وابسته است.

برای فعال‌سازی حالت ++C20 معمولاً باید گزینهٔ استاندارد مناسب Compiler را تنظیم کنید؛ برای نمونه:

```
g++ -std=c++20 -pthread main.cpp -o app
```

```
clang++ -std=c++20 -pthread main.cpp -o app
```

```
cl /std:c++20 /EHsc main.cpp
```

گزینه‌های دقیق و نیاز به تنظیمات اضافی به Compiler، سیستم‌عامل و toolchain وابسته است.

گزینهٔ `-pthread` در محیط‌های GCC و Clang روی بسیاری از سیستم‌های POSIX برای فعال‌سازی پشتیبانی Thread استفاده می‌شود.

### **بررسی feature-test macro**

برای بررسی پشتیبانی کتابخانه از latch می‌توان از feature-test macro استاندارد استفاده کرد:

```
#include <version>

#if defined(__cpp_lib_latch) && __cpp_lib_latch >= 201907L
    // std::latch is available
#else
    #error "This standard library does not provide std::latch"
#endif
```

مقدار شناخته‌شدهٔ `__cpp_lib_latch` برابر `201907L` است.

این macro قابلیت کتابخانه را گزارش می‌کند، نه صرفاً نسخهٔ زبان انتخاب‌شده را.

### **هزینهٔ اجرایی و انتخاب ابزار**

استاندارد تضمین نمی‌کند پیاده‌سازی latch حتماً lock-free باشد یا از یک primitive سخت‌افزاری مشخص استفاده کند.

جزئیات داخلی مانند استفاده از atomic، futex یا سازوکارهای بومی سیستم‌عامل به پیاده‌سازی وابسته است.

در عمل، `std::latch` معمولاً نسبت به ساخت دستی یک پروتکل شمارش و انتظار، ساده‌تر و کم‌خطاتر است.

با این حال، برای مسیرهای بسیار حساس به latency باید رفتار واقعی پیاده‌سازی هدف را اندازه‌گیری کنید و تنها بر اساس نام abstraction دربارهٔ هزینهٔ آن نتیجه‌گیری نکنید.

## **توصیه‌های طراحی حرفه‌ای**

- برای یک نقطهٔ هماهنگی یک‌باره، `std::latch` را به راهکارهای دستی مبتنی بر شمارنده و انتظار ترجیح دهید.
- تعداد اولیه را از تعداد واقعی وظایف استخراج کنید تا شمارنده با پروتکل اجرا سازگار بماند.
- هر سهم را دقیقاً یک بار و پس از تکمیل واقعی کار اعلام کنید.
- مسیرهای exception، لغو، شکست ایجاد Thread و عدم اجرای وظیفه را در طراحی لحاظ کنید.
- داده‌های مشترک را طوری تقسیم کنید که پیش از نقطهٔ هماهنگی data race رخ ندهد.
- طول عمر latch را از طول عمر تمام Threadهای استفاده‌کننده بیشتر نگه دارید.
- برای انتظار زمان‌دار یا شرط‌های پیچیده، ابزار مناسب‌تری مانند `std::condition_variable` انتخاب کنید.
- برای چندین phase تکرارشونده، `std::barrier` را بررسی کنید.
- برای دریافت نتیجه و exception یک کار ناهم‌زمان، `std::future` و `std::promise` را در نظر بگیرید.
- برای اطمینان از خاتمهٔ Threadها، علاوه بر latch از `join` یا مدیریت عمر معادل استفاده کنید.

## **جمع‌بندی**

کلاس `std::latch` در Standard Library استاندارد ++C20 یک primitive ساده و مؤثر برای هماهنگی یک‌بارهٔ چند عملیات هم‌زمان است.

این کلاس با یک شمارندهٔ اولیه کار می‌کند؛ مشارکت‌کنندگان با `count_down` سهم خود را ثبت می‌کنند و Threadهای منتظر با `wait` تا صفرشدن شمارنده متوقف می‌مانند.

مزیت اصلی latch آن است که یک الگوی رایج هم‌زمانی را بدون نیاز به مدیریت دستی mutex، predicate و شمارنده در اختیار برنامه‌نویس می‌گذارد.

در مقابل، یک‌بارمصرف‌بودن، نبود timeout و نبود سازوکار داخلی برای مدیریت خطا یا cancellation از محدودیت‌های مهم آن هستند.

در نتیجه، `std::latch` زمانی انتخاب مناسبی است که چند کار مستقل باید یک بار تکمیل خود را اعلام کنند و ادامهٔ برنامه به تکمیل همهٔ آن‌ها وابسته باشد.

برای هماهنگی چندمرحله‌ای، انتظار شرطی پیچیده یا دریافت نتیجهٔ مستقل عملیات، باید ابزارهای دیگری از Standard Library را انتخاب کرد.
