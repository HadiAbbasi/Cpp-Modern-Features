# راهنمای جامع `std::atomic<std::weak_ptr<T>>` در ++C20

## مقدمه

در برنامه‌های چندریسمانی، گاهی لازم است چند thread به یک شیء مشترک اشاره
کنند، بدون آن‌که هر اشاره‌گرِ ناظر طول عمر آن شیء را افزایش دهد. در چنین
طراحی‌هایی، `std::weak_ptr<T>` ابزار مهمی است: ارجاعی ضعیف به شیئی که
مالکیت آن با `std::shared_ptr<T>` مدیریت می‌شود و به‌تنهایی مانع نابودی
شیء نمی‌شود.

اما استفاده از یک `std::weak_ptr<T>` معمولی میان چند thread، در حالی که
دست‌کم یکی از آن‌ها همان متغیر `weak_ptr` را هم‌زمان می‌خواند یا تغییر
می‌دهد، به‌خودی‌خود ایمن نیست. استاندارد ++C20 تخصصی‌سازی اتمی
`std::atomic<std::weak_ptr<T>>` را معرفی کرد تا دسترسی و تغییر خودِ مقدار
اشاره‌گر ضعیف را به‌صورت اتمی انجام دهد.

این نوع، هم‌زمانی روی متغیر اشاره‌گر را مدیریت می‌کند؛ اما اجرای امن عملیات
روی شیء مورد اشاره، هماهنگی برای تغییرات درون آن شیء، و منطق مالکیت سطح
برنامه همچنان بر عهدهٔ طراحی شماست.

## مفهوم `std::weak_ptr` و مالکیت مشترک

### تفاوت اشاره‌گر ضعیف با اشاره‌گر مالک

نوع `std::shared_ptr<T>` مالکیت مشترک یک شیء را با شمارش reference count
مدیریت می‌کند. تا وقتی دست‌کم یک مالک مشترک باقی بماند، شیء زنده می‌ماند.
در مقابل، `std::weak_ptr<T>` مالکیت مشترک را افزایش نمی‌دهد و صرفاً امکان
بررسی یا تلاش برای دستیابی به شیء را فراهم می‌کند.

برای استفاده از شیء، معمولاً `weak_ptr` را با تابع `lock()` به یک
`shared_ptr` تبدیل می‌کنیم. اگر شیء هنوز زنده باشد، نتیجه یک `shared_ptr`
معتبر است و مالکیت آن تا پایان عمر آن `shared_ptr` حفظ می‌شود؛ اگر شیء از
بین رفته باشد، نتیجه خالی است.

``` cpp
#include <memory>
#include <iostream>

int main() {
    auto owner = std::make_shared<int>(42);
    std::weak_ptr<int> observer = owner;

    if (auto locked = observer.lock()) {
        std::cout << *locked << '\n';
    }
}
```

در این مثال، `observer` زنده ماندن شیء را تضمین نمی‌کند. فقط `locked` در
صورت موفقیت، مالکیت موقتی ایجاد می‌کند.

### مسئلهٔ رقابت روی خود متغیر `weak_ptr`

استاندارد اجازه می‌دهد threadهای مختلف به اشیای اشاره‌شده و کنترل‌بلوک
مشترک `shared_ptr`/`weak_ptr` طبق قواعد کتابخانه دسترسی داشته باشند؛ با
این حال، این موضوع با ایمنی هم‌زمانی روی یک نمونهٔ واحد از متغیر هوشمند
یکسان نیست. اگر یک thread روی متغیر `weak_ptr` مشخصی بنویسد و thread
دیگری هم‌زمان همان متغیر را بخواند، بدون همگام‌سازی مناسب data race رخ
می‌دهد.

نمونهٔ زیر الگوی نامعتبر را نشان می‌دهد:

``` cpp
#include <memory>

std::weak_ptr<int> shared_observer;

// Thread A:
shared_observer = std::make_shared<int>(7);

// Thread B:
auto local = shared_observer.lock();
```

این‌که عملیات روی شمارنده‌های داخلی کنترل‌بلوک thread-safe باشند، دسترسی
هم‌زمان به خود متغیر `shared_observer` را ایمن نمی‌کند. برای چنین سناریویی
می‌توان از mutex یا `std::atomic<std::weak_ptr<T>>` استفاده کرد.

## معرفی `std::atomic<std::weak_ptr<T>>`

### هدف و زمان معرفی

تخصصی‌سازی `std::atomic<std::weak_ptr<T>>` در استاندارد ++C20 ارائه شد.
این نوع اجازه می‌دهد یک مقدار `weak_ptr` به‌صورت اتمی بارگذاری، جایگزین،
مبادله یا مقایسه‌وجایگزین شود. به‌این‌ترتیب، threadها می‌توانند یک اشاره‌گر
ضعیف مشترک را بدون data race روی همان متغیر بخوانند و تغییر دهند.

هدر موردنیاز `<memory>` است. اعلان آن در فضای نام `std` قرار دارد و نوع
آن یک تخصصی‌سازی از قالب `std::atomic` محسوب می‌شود.

``` cpp
#include <atomic>
#include <memory>

std::atomic<std::weak_ptr<int>> observer;
```

در اینجا `observer` یک متغیر اتمی است که مقدار آن یک `weak_ptr<int>`
است. این موضوع با اتمی‌کردن خود شیء `int` تفاوت دارد: فقط عملیات روی
مقدار اشاره‌گر اتمی هستند.

### این نوع چه چیزی را تضمین نمی‌کند؟

اتمی بودن متغیر اشاره‌گر، به‌معنای اتمی بودن تمام عملیات مرتبط با شیء مقصد
نیست. به‌طور مشخص:

-   این نوع، خواندن و تغییر مقدار `weak_ptr` ذخیره‌شده را همگام می‌کند.
-   این نوع، شیء مقصد را زنده نگه نمی‌دارد؛ برای این کار باید `lock()`
    موفق شود و یک `shared_ptr` محلی نگه داشته شود.
-   این نوع، دسترسی هم‌زمان به اعضای mutable شیء مقصد را ایمن نمی‌کند.
-   این نوع، الزاماً lock-free نیست.
-   این نوع، تضمین نمی‌کند که چند عملیات جداگانه روی متغیر اتمی، یک
    تراکنش واحد بسازند.

## ساخت و مقداردهی اولیه

### ساخت پیش‌فرض

ساخت پیش‌فرض، یک `weak_ptr` خالی را درون اتمیک قرار می‌دهد:

``` cpp
#include <atomic>
#include <memory>

std::atomic<std::weak_ptr<int>> current;
```

در این وضعیت، فراخوانی `load()` یک `weak_ptr` خالی برمی‌گرداند.

### مقداردهی با یک `weak_ptr` موجود

می‌توان اتمیک را با مقدار اولیهٔ `weak_ptr` ساخت:

``` cpp
#include <atomic>
#include <memory>

auto owner = std::make_shared<int>(10);
std::weak_ptr<int> weak = owner;

std::atomic<std::weak_ptr<int>> current{weak};
```

مقداردهی اولیه باید پیش از انتشار شیء به threadهای دیگر انجام شود. اتمیک
بودن عملیات پس از ساخت، به‌خودی‌خود شیء در حال ساخت را پیش از تکمیل
مقداردهی به threadهای دیگر منتشر نمی‌کند.

### محدودیت کپی و انتساب

اشیای `std::atomic` قابل کپی نیستند. بنابراین نمی‌توان خود متغیر اتمی را
مانند یک `weak_ptr` معمولی کپی کرد یا با یک اتمیک دیگر جایگزین کرد. باید
مقدار را با عملیات اتمی مناسب بخوانید یا بنویسید.

``` cpp
std::weak_ptr<int> snapshot = current.load();
```

## عملیات اصلی

### بارگذاری با `load()`

عملیات `load()` یک نسخه از مقدار `weak_ptr` ذخیره‌شده را به‌صورت اتمی
برمی‌گرداند:

``` cpp
auto snapshot = current.load();
```

پارامتر اختیاری آن `std::memory_order` است. ترتیب پیش‌فرض
`std::memory_order_seq_cst` است. اگر مقدار خوانده‌شده قرار است داده‌های
دیگری را که thread منتشرکننده آماده کرده مشاهده کند، باید رابطهٔ
همگام‌سازی و ترتیب حافظه را با دقت طراحی کرد؛ صرفاً استفاده از اتمیک، هر
نوع رابطهٔ انتشار و مصرف دلخواه را ایجاد نمی‌کند.

### ذخیره با `store()`

عملیات `store()` مقدار اتمی را با مقدار جدید جایگزین می‌کند:

``` cpp
std::weak_ptr<int> next = std::make_shared<int>(20);
current.store(next);
```

عملیات `store()` از ترتیب‌های `std::memory_order_relaxed`،
`std::memory_order_release` و `std::memory_order_seq_cst` پشتیبانی
می‌کند. استفاده از `std::memory_order_acquire` یا
`std::memory_order_acq_rel` برای `store()` معتبر نیست.

### مبادله با `exchange()`

عملیات `exchange()` مقدار جدید را ذخیره می‌کند و مقدار قبلی را
برمی‌گرداند:

``` cpp
std::weak_ptr<int> replacement = std::make_shared<int>(30);
auto previous = current.exchange(replacement);
```

این الگو زمانی مفید است که لازم باشد مقدار قبلی را نیز بررسی کنید.
پارامتر ترتیب حافظه برای این عملیات باید یک ترتیب مجاز برای عملیات
read-modify-write باشد.

### مقایسه و جایگزینی با `compare_exchange_weak()` و `compare_exchange_strong()`

عملیات compare-exchange مقدار فعلی را با مقدار مورد انتظار مقایسه می‌کند.
اگر برابر باشد، مقدار جدید را ذخیره می‌کند؛ در غیر این صورت، مقدار فعلی
را در آرگومان `expected` می‌نویسد.

``` cpp
std::weak_ptr<int> expected = current.load();
std::weak_ptr<int> desired = std::make_shared<int>(40);

if (current.compare_exchange_strong(expected, desired)) {
    // The replacement succeeded.
} else {
    // expected now contains the value observed by the failed operation.
}
```

تابع `compare_exchange_weak()` ممکن است حتی در شرایطی که مقایسه از نظر
مقدار موفق می‌بود، به‌صورت کاذب شکست بخورد (spurious failure). ازاین‌رو
معمولاً در حلقه استفاده می‌شود. تابع `compare_exchange_strong()` چنین شکست
کاذبی ندارد، ولی همچنان ممکن است به دلیل تفاوت مقدار واقعی با `expected`
شکست بخورد.

در مقایسهٔ `weak_ptr`ها باید قواعد مقایسهٔ مالکیت و اشاره‌گر در استاندارد
مربوط را در نظر گرفت. دو `weak_ptr` را صرفاً بر اساس این فرض که «به نظر
می‌رسد به یک شیء اشاره می‌کنند» مقایسه نکنید. در الگوهای حساس به هویت،
تفاوت میان مقدار اشاره‌گر و مالکیت مشترک اهمیت دارد؛ همچنین، شیئی که عمرش
پایان یافته ممکن است دیگر قابل دسترسی نباشد، هرچند کنترل‌بلوک تا زمانی که
ارجاع‌های ضعیف وجود دارند باقی بماند.

### ترتیب‌های حافظه

پارامترهای `std::memory_order` مشخص می‌کنند عملیات اتمی چگونه با عملیات
حافظهٔ دیگر در threadها مرتب شوند. ترتیب پیش‌فرض برای بسیاری از عملیات،
`std::memory_order_seq_cst` است. گزینه‌های ضعیف‌تر می‌توانند هزینه را کاهش
دهند، اما فقط وقتی درست هستند که الگوریتم به تضمین‌های ضعیف‌تر نیاز داشته
باشد.

-   `std::memory_order_relaxed` اتمی بودن عملیات را حفظ می‌کند، اما
    به‌تنهایی رابطهٔ synchronizes-with برای انتشار داده‌های دیگر ایجاد
    نمی‌کند.
-   `std::memory_order_release` برای انتشار تغییرات پیشین در thread
    نویسنده استفاده می‌شود.
-   `std::memory_order_acquire` برای مشاهدهٔ تغییرات منتشرشده توسط عملیات
    release متناظر کاربرد دارد.
-   `std::memory_order_acq_rel` معمولاً برای عملیات read-modify-write
    است.
-   `std::memory_order_seq_cst` علاوه بر قواعد acquire/release، در ترتیب
    کلِ عملیات sequentially consistent شرکت می‌کند.

برای `load()` از `release` و `acq_rel` استفاده نکنید. برای `store()` از
`consume`، `acquire` و `acq_rel` استفاده نکنید. در overloadهای
compare-exchange نیز ترتیب موفقیت و شکست محدودیت‌های متفاوتی دارند؛ ترتیب
شکست نمی‌تواند `release` یا `acq_rel` باشد و نباید قوی‌تر از ترتیب موفقیت
باشد.

اگر دلیل روشنی برای انتخاب ترتیب ضعیف‌تر ندارید، ابتدا از ترتیب پیش‌فرض
استفاده کنید و بعد از اندازه‌گیری و تحلیل الگوریتم، آن را بهینه کنید.

## تبدیل مقدار اتمی به شیء قابل استفاده

### استفاده از `load()` و سپس `lock()`

الگوی رایج، خواندن اتمی یک `weak_ptr` و سپس تلاش برای قفل‌کردن آن است:

``` cpp
#include <atomic>
#include <memory>
#include <iostream>

std::atomic<std::weak_ptr<int>> current;

void consume() {
    auto weak = current.load();

    if (auto strong = weak.lock()) {
        std::cout << *strong << '\n';
    }
}
```

در این الگو، `load()` یک snapshot از مقدار اشاره‌گر می‌گیرد. سپس `lock()`
تلاش می‌کند مالکیت موقت ایجاد کند. اگر مالکیت اصلی پیش از آن از بین رفته
باشد، `lock()` مقدار خالی می‌دهد و باید این حالت مدیریت شود.

### چرا نباید فقط `expired()` را بررسی کرد؟

بررسی `expired()` و سپس فراخوانی `lock()` به‌عنوان دو عملیات جداگانه، یک
بررسی و استفادهٔ اتمی ایجاد نمی‌کند. ممکن است وضعیت شیء میان این دو
فراخوانی تغییر کند. بهتر است مستقیماً از نتیجهٔ `lock()` استفاده کنید:

``` cpp
if (auto strong = weak.lock()) {
    // Use the object while strong remains alive.
}
```

### نگه‌داشتن `shared_ptr` محلی

پس از موفقیت `lock()`، متغیر `shared_ptr` محلی را در تمام مدتی که به شیء
نیاز دارید نگه دارید. اگر فقط به raw pointer تبدیل کنید و مالکیت محلی را
زودتر آزاد کنید، ممکن است شیء در حین استفاده نابود شود.

## انتظار و اعلان تغییرات با `wait()` و `notify_*()`

تخصصی‌سازی اتمی smart pointerها در ++C20 از عملیات انتظار و اعلان اتمی
نیز پشتیبانی می‌کند. این عملیات می‌تواند برای الگویی مفید باشد که threadها
تا تغییر مقدار اتمی منتظر می‌مانند، به‌جای آن‌که مرتب مقدار را polling
کنند.

نمونهٔ سادهٔ زیر نشان می‌دهد که یک thread می‌تواند مقدار مشاهده‌شده را
بارگذاری کند و تا تغییر آن منتظر بماند:

``` cpp
#include <atomic>
#include <memory>

std::atomic<std::weak_ptr<int>> current;

void wait_for_change() {
    auto old_value = current.load();

    current.wait(old_value);

    auto new_value = current.load();
    (void)new_value;
}

void publish(std::weak_ptr<int> next) {
    current.store(next);
    current.notify_all();
}
```

عملیات `wait(old_value)` تا زمانی منتظر می‌ماند که مقدار اتمی از مقدار
مقایسه‌ای متفاوت شود؛ ممکن است برای جلوگیری از بیداری‌های کاذب، پیاده‌سازی
دوباره مقدار را بررسی کند. پس از بیدارشدن، برنامه باید مقدار را دوباره
بخواند و وضعیت را بررسی کند. `notify_one()` یک منتظر را بیدار می‌کند و
`notify_all()` همهٔ منتظران را بیدار می‌کند، اما خود اعلان مقدار را تغییر
نمی‌دهد.

در طراحی واقعی باید مطمئن شوید که تغییر مقدار و اعلان، از نظر منطق
برنامه هماهنگ هستند. اگر thread منتظر بتواند بعد از بارگذاری مقدار جدید
و پیش از شروع `wait()` از تغییر جا بماند، عملیات wait با مقدار قدیمی
باید طبق قرارداد اتمیک دوباره بررسی شود؛ بااین‌حال، شرط حلقه و پروتکل
اعلان را ساده و صریح طراحی کنید.

## مثال کاربردی: انتشار امن یک شیء قابل تعویض

فرض کنید یک سرویس، نسخهٔ فعلی یک شیء را نگه می‌دارد و threadهای مصرف‌کننده
فقط ناظر هستند. شیء اصلی با `shared_ptr` در بخش دیگری از برنامه مالکیت
دارد، در حالی که سرویس یک `weak_ptr` اتمی منتشر می‌کند.

``` cpp
#include <atomic>
#include <memory>
#include <string>
#include <iostream>

struct Config {
    std::string endpoint;
};

class ConfigRegistry {
public:
    void publish(const std::shared_ptr<Config>& config) {
        current_.store(config, std::memory_order_release);
    }

    std::shared_ptr<Config> acquire() const {
        auto weak = current_.load(std::memory_order_acquire);
        return weak.lock();
    }

private:
    std::atomic<std::weak_ptr<Config>> current_;
};

int main() {
    ConfigRegistry registry;

    auto config = std::make_shared<Config>();
    config->endpoint = "https://example.invalid";
    registry.publish(config);

    if (auto active = registry.acquire()) {
        std::cout << active->endpoint << '\n';
    }
}
```

در این مثال، `ConfigRegistry` مالک `Config` نیست. مالکیت باید در بخش
دیگری از برنامه باقی بماند؛ اگر تمام `shared_ptr`های مالک از بین بروند،
`acquire()` می‌تواند یک `shared_ptr` خالی برگرداند.

نکتهٔ مهم این است که ترتیب‌های acquire/release روی متغیر اتمی، به‌تنهایی
اجازه نمی‌دهند `Config` پس از انتشار به‌صورت هم‌زمان و بدون همگام‌سازی تغییر
کند. این مثال باید به‌عنوان الگوی انتشار اشاره‌گر به شیئی که پس از انتشار
تغییرات ناسازگار ندارد، یا شیئی که تغییراتش جداگانه همگام‌سازی شده‌اند،
استفاده شود.

## کاربردهای مناسب

### رجیستری ناظرها و callbackها

در سیستم‌هایی که یک مؤلفه باید به شیء دیگری اشاره کند، اما نباید طول عمر
آن را کنترل کند، یک `weak_ptr` اتمی می‌تواند به threadهای متعدد اجازه دهد
ناظر فعلی را بخوانند یا جایگزین کنند.

### انتشار نسخهٔ فعلی یک منبع

برای پیکربندی، وضعیت یا منبعی که مالکیت آن جای دیگری مدیریت می‌شود،
می‌توان یک ارجاع ضعیف اتمی منتشر کرد. این طراحی وقتی مفید است که ناظر
نباید با نگه‌داشتن ارجاع، عمر منبع را طولانی کند.

### جلوگیری از چرخهٔ مالکیت

`weak_ptr` برای شکستن چرخه‌های `shared_ptr` مناسب است. اتمی‌کردن آن
می‌تواند هم‌زمانی روی متغیر ناظر را ایمن کند، اما خودِ این نوع چرخهٔ مالکیت
را به‌صورت خودکار تشخیص نمی‌دهد یا رفع نمی‌کند.

## مواردی که انتخاب مناسبی نیست

### زمانی که مصرف‌کننده باید شیء را زنده نگه دارد

اگر مصرف‌کننده برای انجام کار باید تضمین کند شیء تا پایان عملیات زنده
می‌ماند، اغلب بهتر است یک `shared_ptr` را به‌صورت اتمی منتشر کنید یا
مالکیت را صریحاً به مصرف‌کننده بدهید. استفاده از `weak_ptr` عمداً اجازه
می‌دهد شیء پیش از دسترسی مصرف‌کننده از بین برود.

### زمانی که همهٔ دسترسی‌ها از قبل با mutex محافظت می‌شوند

اگر متغیر `weak_ptr` از قبل زیر یک mutex مشترک خوانده و نوشته می‌شود،
جایگزینی آن با اتمیک ممکن است پیچیدگی را افزایش دهد، بی‌آن‌که مزیت
قابل‌اندازه‌گیری داشته باشد. راهکار را بر اساس نیاز واقعی و اندازه‌گیری
انتخاب کنید.

### زمانی که باید چند مقدار با هم سازگار بمانند

یک اتمیک منفرد نمی‌تواند به‌صورت خودکار چند متغیر مستقل را به‌صورت تراکنشی
به‌روزرسانی کند. اگر اشاره‌گر و چند فیلد دیگر باید یک snapshot سازگار
تشکیل دهند، از یک شیء immutable که با یک اشاره‌گر منتشر می‌شود، mutex یا
پروتکل همگام‌سازی مناسب استفاده کنید.

## نکات مهم دربارهٔ طول عمر و هویت

### اتمیک بودن، مالکیت قوی ایجاد نمی‌کند

مقدار ذخیره‌شده از نوع `weak_ptr` است و مالکیت قوی ندارد. خود متغیر اتمی،
به‌تنهایی تضمین نمی‌کند که شیء مقصد پس از بارگذاری زنده بماند. فقط موفقیت
`lock()` و نگه‌داشتن `shared_ptr` حاصل، چنین تضمینی را برای مدت نگه‌داری
آن مالکیت ایجاد می‌کند.

### نابودی شیء و نابودی کنترل‌بلوک یکسان نیستند

وقتی آخرین `shared_ptr` از بین می‌رود، شیء مدیریت‌شده نابود می‌شود. اما
کنترل‌بلوک ممکن است تا زمانی که ارجاع‌های ضعیف باقی مانده‌اند زنده بماند.
بنابراین ممکن است `weak_ptr` همچنان ساختار مالکیت قابل‌مقایسه‌ای داشته
باشد، در حالی که دیگر نتوان با `lock()` به شیء دسترسی پیدا کرد.

### از اشاره‌گر خام برای دورزدن مالکیت استفاده نکنید

پس از `lock()` موفق، استفاده از `strong.get()` در محدوده‌ای که `strong`
زنده است ممکن است لازم باشد؛ اما ذخیرهٔ آن raw pointer برای استفاده پس از
پایان عمر `strong` ایمن نیست. این کار تضمین مالکیت `shared_ptr` را از
بین می‌برد.

`atomic<weak_ptr<T>>` در ++C20 نیستند. برای تصمیم دربارهٔ نسخهٔ استاندارد،
کتابخانهٔ استاندارد و پیاده‌سازی هدف را بررسی کنید.

## محدودیت‌ها و هزینه‌های پیاده‌سازی

### تضمین lock-free وجود ندارد

وجود API اتمی به معنای اجرای lock-free نیست. برای این تخصصی‌سازی،
پیاده‌سازی می‌تواند از قفل داخلی استفاده کند. اگر تأخیر یا رفتار real-time
مهم است، مشخصات پیاده‌سازی هدف را بررسی و رفتار واقعی را اندازه‌گیری کنید.

### هزینهٔ reference counting و کنترل‌بلوک

عملیات `weak_ptr` و `shared_ptr` ممکن است به به‌روزرسانی شمارنده‌های
کنترل‌بلوک نیاز داشته باشند. هزینهٔ دقیق به کتابخانهٔ استاندارد، معماری و
الگوی استفاده وابسته است. از فرض‌هایی مانند «اتمی همیشه سریع‌تر از mutex
است» یا «این عملیات همیشه lock-free است» پرهیز کنید.

### وابستگی به پشتیبانی کتابخانه

کامپایلر باید در حالت ++C20 کار کند و کتابخانهٔ استاندارد مورد استفاده
باید تخصصی‌سازی `std::atomic<std::weak_ptr<T>>` و اعضای مورد نیاز را
پیاده‌سازی کرده باشد. نسخهٔ کامپایلر به‌تنهایی تضمین نمی‌کند که تمام امکانات
کتابخانه در هر پلتفرم موجود یا یکسان باشند.

## خطاهای رایج

-   **اشتباه گرفتن thread-safety کنترل‌بلوک با thread-safety متغیر:** چند
    thread می‌توانند با اشیای smart pointer متفاوتی که مالکیت مشترک دارند
    کار کنند، اما دسترسی هم‌زمان به یک متغیر غیراتمی واحد همچنان به
    همگام‌سازی نیاز دارد.
-   **نادیده‌گرفتن نتیجهٔ `lock()`:** ممکن است شیء قبلاً نابود شده باشد؛
    همیشه خالی‌بودن نتیجه را مدیریت کنید.
-   **استفاده از `expired()` به‌عنوان تضمین:** وضعیت می‌تواند بعد از بررسی
    تغییر کند؛ نتیجهٔ `lock()` را معیار قرار دهید.
-   **فرض زنده‌ماندن شیء به‌دلیل ذخیره در اتمیک:** مقدار ذخیره‌شده ضعیف است
    و مالکیت قوی نگه نمی‌دارد.
-   **استفادهٔ بی‌دلیل از `memory_order_relaxed`:** اتمی بودن را حفظ
    می‌کند، اما ترتیب انتشار داده‌های دیگر را تضمین نمی‌کند.
-   **نادیده‌گرفتن همگام‌سازی خود شیء مقصد:** اتمی بودن اشاره‌گر، فیلدهای
    داخلی شیء را اتمی نمی‌کند.
-   **فرض lock-free بودن:** باید مستندات و رفتار پیاده‌سازی بررسی شود.
-   **انتظار داشتن از یک اتمیک برای هماهنگ‌کردن چند متغیر:** برای
    invariantهای چندمقداری، طراحی همگام‌سازی جداگانه لازم است.

## توصیه‌های طراحی

-   ابتدا مشخص کنید مصرف‌کننده باید مالکیت قوی داشته باشد یا فقط یک ناظر
    غیرمالک.
-   اگر مصرف‌کننده به شیء نیاز دارد، مقدار را بارگذاری کنید و بلافاصله
    `lock()` را فراخوانی کنید؛ سپس `shared_ptr` حاصل را تا پایان استفاده
    نگه دارید.
-   تا وقتی نیاز الگوریتم روشن نشده است، از ترتیب حافظهٔ پیش‌فرض استفاده
    کنید.
-   اگر چند مقدار باید با هم سازگار باشند، آن‌ها را در یک وضعیت immutable
    بسته‌بندی کنید و همان وضعیت را منتشر کنید، یا از mutex استفاده کنید.
-   اگر عملکرد مهم است، الگوی واقعی را benchmark کنید؛ از روی نام
    `atomic` دربارهٔ lock-free بودن یا سرعت نتیجه‌گیری نکنید.
-   برای اشیای تغییرپذیر، قرارداد جداگانه‌ای برای همگام‌سازی اعضای داخلی
    تعریف کنید.

## جمع‌بندی

نوع `std::atomic<std::weak_ptr<T>>` در ++C20 راهی استاندارد برای خواندن
و تغییر اتمی یک مقدار `weak_ptr` در محیط چندریسمانی فراهم می‌کند. کاربرد
اصلی آن انتشار یا تعویض امن یک ارجاع ضعیف است، بدون آن‌که متغیر اتمی خودش
مالکیت قوی شیء مقصد را حفظ کند.

مهم‌ترین نکته این است که سه مسئله را از هم جدا نگه دارید: همگام‌سازی مقدار
اشاره‌گر، تضمین طول عمر شیء و همگام‌سازی داده‌های درون شیء. اتمیک این نوع
فقط مسئلهٔ نخست را حل می‌کند؛ `lock()` و نگه‌داشتن `shared_ptr` برای مسئلهٔ
دوم لازم‌اند و مسئلهٔ سوم به طراحی هم‌زمانی مستقل نیاز دارد.
