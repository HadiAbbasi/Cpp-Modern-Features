# بررسی جامع عملگر مقایسه سه‌طرفه `<=>` در ++C20

## مقدمه

عملگر مقایسه سه‌طرفه (Three-way Comparison Operator) که با نماد `<=>` نمایش داده می‌شود، یکی از قابلیت‌های مهم استاندارد ++C20 است. این عملگر امکان مقایسه دو مقدار را در قالب یک نتیجه واحد فراهم می‌کند که علاوه بر مشخص کردن برابری یا نابرابری، ترتیب نسبی دو مقدار را نیز نشان می‌دهد.

پیش از معرفی این قابلیت، توسعه‌دهندگان برای پیاده‌سازی مقایسه انواع سفارشی معمولاً مجبور بودند چندین عملگر مانند `operator<`، `operator<=`، `operator>`، `operator>=`، `operator==` و `operator!=` را جداگانه تعریف کنند. این روش علاوه بر افزایش حجم کد، احتمال ناسازگاری میان رفتار عملگرهای مختلف را نیز افزایش می‌داد.

عملگر `<=>` با معرفی یک سازوکار استاندارد برای مقایسه سه‌طرفه و پشتیبانی از تولید ضمنی برخی عملگرهای مقایسه، این مشکل را تا حد زیادی برطرف می‌کند.

این قابلیت در کنار `operator==`، مقایسه پیش‌فرض‌شده (Defaulted Comparison)، نوع‌های نتیجه جدید در کتابخانه استاندارد و قابلیت‌های دیگر ++C20، طراحی کلاس‌هایی با رفتار مقایسه‌ای صحیح و قابل نگهداری را ساده‌تر می‌کند.

## مفهوم مقایسه سه‌طرفه

### تعریف مقایسه سه‌طرفه

در مقایسه معمولی، عبارت‌هایی مانند `a < b` یا `a == b` یک مقدار `bool` تولید می‌کنند. این نتیجه تنها به یک پرسش مشخص پاسخ می‌دهد.

در مقابل، عملگر `<=>` نتیجه‌ای از یک نوع مقایسه‌ای تولید می‌کند که وضعیت ترتیب دو مقدار را مشخص می‌کند.

برای مثال:

```
#include <compare>
#include <iostream>

int main() {
    int a = 10;
    int b = 20;

    auto result = a <=> b;

    if (result < 0) {
        std::cout << "a is less than b\n";
    } else if (result > 0) {
        std::cout << "a is greater than b\n";
    } else {
        std::cout << "a and b are equivalent\n";
    }
}
```

در این مثال، نتیجه مقایسه از نوعی مانند `std::strong_ordering` است. این نتیجه امکان تشخیص ترتیب دو عدد را از طریق مقایسه با صفر فراهم می‌کند.

نکته مهم این است که نتیجه عملگر `<=>` الزاماً یک عدد صحیح نیست. استاندارد ++C20 سه نوع اصلی برای نمایش نتایج مقایسه در کتابخانه استاندارد معرفی می‌کند که هرکدام معنا و محدودیت‌های متفاوتی دارند.

### دلیل استفاده از مقایسه سه‌طرفه

مهم‌ترین مزایای این قابلیت عبارت‌اند از:

- **کاهش کد تکراری:** نیازی نیست تمام عملگرهای ترتیبی برای هر کلاس به‌صورت مستقل پیاده‌سازی شوند.
- **سازگاری بیشتر:** چند عملگر مقایسه می‌توانند از یک منطق مشترک استفاده کنند.
- **پشتیبانی از مقایسه پیش‌فرض‌شده:** کامپایلر می‌تواند مقایسه اعضای یک کلاس را به‌صورت خودکار تولید کند.
- **بیان دقیق‌تر معنای ترتیب:** می‌توان مشخص کرد که مقایسه از نوع ترتیب قوی، ضعیف یا جزئی است.
- **بهبود قابلیت استفاده در کتابخانه‌ها:** ساختارهای داده، الگوریتم‌های مرتب‌سازی و نوع‌های سفارشی می‌توانند از رابط مقایسه‌ای استاندارد استفاده کنند.

بااین‌حال، این عملگر جایگزین تمام عملیات مقایسه نیست. برای مثال، برابری معنایی یک شیء لزوماً از ترتیب آن نتیجه نمی‌شود و در بسیاری از طراحی‌ها همچنان باید `operator==` به‌طور مستقل تعریف شود.

## معرفی انواع نتیجه مقایسه

### آشنایی با هدر `<compare>`

هدر استاندارد `<compare>` در ++C20 تعریف نوع‌های اصلی مقایسه و ابزارهای مرتبط را در اختیار برنامه‌نویس قرار می‌دهد.

سه نوع مهم این هدر عبارت‌اند از:

- `std::strong_ordering`
- `std::weak_ordering`
- `std::partial_ordering`

این نوع‌ها نشان می‌دهند که نتیجه یک مقایسه تا چه اندازه می‌تواند ترتیب دو مقدار را مشخص کند.

### بررسی `std::strong_ordering`

نوع `std::strong_ordering` برای رابطه ترتیبی‌ای استفاده می‌شود که در آن هر دو مقدار یا برابرند یا یکی از آن‌ها به‌طور قطعی کوچک‌تر از دیگری است.

این نوع سه مقدار ثابت مهم دارد:

- `std::strong_ordering::less`
- `std::strong_ordering::equal`
- `std::strong_ordering::greater`

برای مثال، اعداد صحیح معمولی دارای ترتیب قوی هستند.

```
#include <compare>
#include <iostream>

int main() {
    int a = 42;
    int b = 42;

    std::strong_ordering result = a <=> b;

    if (result == std::strong_ordering::equal) {
        std::cout << "Values are equal\n";
    }
}
```

در ترتیب قوی، دو مقدار معادل از دید عملگر مقایسه، از دید رابطه برابری متناظر نیز برابر محسوب می‌شوند.

این ویژگی برای انواعی مناسب است که برابری و ترتیب آن‌ها باید کاملاً با یکدیگر سازگار باشند؛ مانند اعداد صحیح، شناسه‌های عددی و برخی انواع مبتنی بر کلید.

### بررسی `std::weak_ordering`

نوع `std::weak_ordering` برای رابطه‌ای استفاده می‌شود که ترتیب آن قطعی است، اما معادل بودن دو مقدار الزاماً به معنای برابری دقیق آن‌ها نیست.

این نوع سه مقدار ثابت دارد:

- `std::weak_ordering::less`
- `std::weak_ordering::equivalent`
- `std::weak_ordering::greater`

برای نمونه، فرض کنید دو رشته بدون حساسیت به بزرگی و کوچکی حروف مقایسه می‌شوند. رشته‌های `"Alice"` و `"ALICE"` ممکن است از دید این مقایسه معادل باشند، درحالی‌که از نظر مقایسه دقیق رشته‌ها یکسان نیستند.

```
#include <compare>
#include <cctype>
#include <string_view>

constexpr unsigned char toLower(unsigned char ch) {
    if (ch >= 'A' && ch <= 'Z') {
        return static_cast<unsigned char>(ch - 'A' + 'a');
    }

    return ch;
}

std::weak_ordering compareCaseInsensitive(
    std::string_view lhs,
    std::string_view rhs
) {
    const std::size_t commonSize =
        lhs.size() < rhs.size() ? lhs.size() : rhs.size();

    for (std::size_t i = 0; i < commonSize; ++i) {
        const auto a = toLower(static_cast<unsigned char>(lhs[i]));
        const auto b = toLower(static_cast<unsigned char>(rhs[i]));

        if (a < b) {
            return std::weak_ordering::less;
        }

        if (a > b) {
            return std::weak_ordering::greater;
        }
    }

    if (lhs.size() < rhs.size()) {
        return std::weak_ordering::less;
    }

    if (lhs.size() > rhs.size()) {
        return std::weak_ordering::greater;
    }

    return std::weak_ordering::equivalent;
}
```

در این مثال، دو رشته‌ای که تنها در بزرگی و کوچکی حروف تفاوت دارند، می‌توانند معادل باشند.

این پیاده‌سازی صرفاً نمونه‌ای برای مقایسه ASCII است و جایگزین کامل Unicode case folding یا مقایسه زبانی (Collation) نیست.

همچنین، اگر برابری دقیق رشته‌ها همچنان اهمیت داشته باشد، نباید فرض کرد که معادل بودن در این ترتیب به معنای برابر بودن با `operator==` است.

### بررسی `std::partial_ordering`

نوع `std::partial_ordering` برای مقایسه‌هایی استفاده می‌شود که ممکن است هیچ‌یک از دو مقدار نسبت به دیگری کوچک‌تر، بزرگ‌تر یا معادل نباشد.

این نوع چهار مقدار ثابت مهم دارد:

- `std::partial_ordering::less`
- `std::partial_ordering::equivalent`
- `std::partial_ordering::greater`
- `std::partial_ordering::unordered`

حالت `unordered` برای مقایسه‌هایی کاربرد دارد که اصولاً نمی‌توان برای آن‌ها ترتیب مشخصی تعیین کرد.

یکی از نمونه‌های مهم، مقایسه اعداد ممیز شناور با مقدار NaN است.

```
#include <compare>
#include <cmath>
#include <iostream>
#include <limits>

int main() {
    const double value = 10.0;
    const double nan = std::numeric_limits<double>::quiet_NaN();

    auto result = value <=> nan;

    if (result == std::partial_ordering::unordered) {
        std::cout << "The values are unordered\n";
    }
}
```

مقدار NaN نه از عدد معمولی کوچک‌تر است، نه از آن بزرگ‌تر و نه با آن برابر است. بنابراین، مقایسه سه‌طرفه اعداد `double` می‌تواند نتیجه `unordered` تولید کند.

این ویژگی برای طراحی انواعی که شامل مقادیر ممیز شناور هستند اهمیت زیادی دارد.

### مقایسه انواع نتیجه

جدول زیر تفاوت اصلی این سه نوع را نشان می‌دهد.

| ویژگی                                  | `strong_ordering`         | `weak_ordering`                 | `partial_ordering`            |
| -------------------------------------- | ------------------------- | ------------------------------- | ----------------------------- |
| نتیجه کوچک‌تر                          | دارد                      | دارد                            | دارد                          |
| نتیجه بزرگ‌تر                          | دارد                      | دارد                            | دارد                          |
| نتیجه معادل                            | دارد                      | دارد                            | دارد                          |
| حالت نامرتب                            | ندارد                     | ندارد                           | دارد                          |
| معادل بودن الزاماً به معنای برابری است | بله                       | خیر                             | خیر                           |
| کاربرد متداول                          | اعداد صحیح و کلیدهای دقیق | مقایسه بدون تمایز برخی ویژگی‌ها | اعداد ممیز شناور و روابط جزئی |

در این جدول، منظور از برابری، برابری متناظر با رابطه مقایسه‌ای است؛ این مفهوم لزوماً با برابری بیتی یا برابری تمام اجزای داخلی یک شیء یکسان نیست.

## نحوه استفاده از عملگر `<=>`

### مقایسه مستقیم مقادیر

عملگر `<=>` را می‌توان مستقیماً برای مقایسه مقادیر دارای این عملگر به کار برد.

```
#include <compare>
#include <iostream>

int main() {
    int x = 7;
    int y = 12;

    auto result = x <=> y;

    std::cout << std::boolalpha;
    std::cout << (result < 0) << '\n';
    std::cout << (result == 0) << '\n';
    std::cout << (result > 0) << '\n';
}
```

خروجی این برنامه به‌ترتیب `true`، `false` و `false` خواهد بود.

نکته مهم این است که در ++C20 نباید به عدد صحیح مشخصی مانند `-1` یا `1` بودن نتیجه تکیه کرد. قرارداد مقایسه‌ای، معنا و رابطه نتیجه با صفر است، نه مقدار عددی مشخص آن.

### تفاوت نتیجه مقایسه با مقدار بولی

عملگر `<=>` نتیجه‌ای از نوع مقایسه‌ای تولید می‌کند، درحالی‌که عملگرهای `<`، `>`، `<=` و `>=` مقادیر بولی تولید می‌کنند.

```
int a = 5;
int b = 8;

auto comparison = a <=> b;
bool isLess = a < b;
```

در این مثال، متغیر `comparison` اطلاعاتی درباره رابطه ترتیب دو مقدار دارد، اما `isLess` تنها مشخص می‌کند که آیا مقدار نخست کوچک‌تر از مقدار دوم است یا خیر.

این تفاوت هنگام طراحی API اهمیت دارد؛ زیرا خروجی `<=>` برای استفاده مستقیم در شرط `if` طراحی نشده است.

کد زیر معتبر نیست:

```
int a = 5;
int b = 8;

if (a <=> b) {
}
```

نوع‌های استاندارد مقایسه‌ای تبدیل ضمنی به `bool` ندارند. برای بررسی نتیجه باید از مقایسه با صفر یا یکی از مقادیر ثابت نوع مربوط استفاده کرد.

### مقایسه با صفر و عملگرهای ترتیبی

نتیجه مقایسه‌ای را می‌توان با صفر مقایسه کرد.

```
#include <compare>

int main() {
    int a = 3;
    int b = 9;

    auto result = a <=> b;

    bool less = result < 0;
    bool greater = result > 0;
    bool equivalent = result == 0;
}
```

این روش برای بیشتر کاربردهای عمومی مناسب است.

برای تشخیص نتیجه دقیق نیز می‌توان از ثابت‌های نوع مربوط استفاده کرد. این روش به‌ویژه زمانی مفید است که کد باید تفاوت میان `equivalent` و `equal` یا حالت `unordered` را آشکار کند.

## تولید خودکار عملگرهای مقایسه

### معرفی عملگرهای مقایسه بازنویسی‌شده

یکی از مهم‌ترین ویژگی‌های مرتبط با `<=>` در ++C20، قواعد بازنویسی عملگرها (Operator Rewriting) است.

با تعریف یک عملگر `<=>` مناسب، کامپایلر می‌تواند در بسیاری از عبارت‌ها از آن برای پیاده‌سازی رفتار عملگرهای ترتیبی استفاده کند.

برای مثال:

```
#include <compare>

struct Version {
    int major;
    int minor;
    int patch;

    auto operator<=>(const Version&) const = default;
};

int main() {
    Version v1{1, 2, 0};
    Version v2{1, 3, 0};

    bool result = v1 < v2;
}
```

در این مثال، نیازی به تعریف جداگانه `operator<` نیست. عملگر `<` می‌تواند با استفاده از قواعد بازنویسی مبتنی بر `<=>` رفتار مناسبی داشته باشد.

این قابلیت برای عملگرهای ترتیبی مانند `<`، `>`، `<=` و `>=` کاربرد دارد، اما نباید آن را با تولید خودکار تمام عملگرهای مقایسه یکسان دانست.

### تفاوت بازنویسی عملگرها با تولید همه عملگرها

تعریف `operator<=>` به‌تنهایی به این معنا نیست که `operator==` نیز در تمام شرایط به‌صورت خودکار تولید می‌شود.

برای کلاس‌های معمولی، باید در صورت نیاز به برابری، `operator==` را جداگانه تعریف کرد یا آن را به‌صورت `= default` اعلام کرد.

در مقابل، وقتی `operator<=>` به‌صورت پیش‌فرض‌شده اعلام می‌شود، قواعد زبان برای تولید ضمنی یک `operator==` متناظر نیز اعمال می‌شوند؛ البته این رفتار به شرایط و محدودیت‌های مربوط به Defaulted Comparison وابسته است.

این تفاوت یکی از نکات مهم طراحی کلاس‌های مقایسه‌پذیر در ++C20 است.

### نحوه استفاده از مقایسه پیش‌فرض‌شده

مقایسه پیش‌فرض‌شده (Defaulted Comparison) به کامپایلر اجازه می‌دهد تا مقایسه اعضای یک کلاس را طبق قواعد استاندارد تولید کند.

```
#include <compare>
#include <string>

struct Person {
    std::string firstName;
    std::string lastName;
    int age;

    auto operator<=>(const Person&) const = default;
    bool operator==(const Person&) const = default;
};
```

در این مثال، اعضا به ترتیب اعلان‌شان مقایسه می‌شوند. اگر مقایسه عضو نخست نتیجه‌ای غیر از برابری داشته باشد، مقایسه اعضای بعدی برای تعیین نتیجه ترتیب ادامه پیدا نمی‌کند.

برای برابری نیز اعضا طبق قواعد مقایسه پیش‌فرض‌شده بررسی می‌شوند.

تعریف صریح `operator==` در این مثال برای روشن شدن رابط کلاس است؛ در صورتی که `<=>` به‌صورت پیش‌فرض‌شده تعریف شده باشد و شرایط لازم برقرار باشند، کامپایلر می‌تواند `operator==` متناظر را نیز به‌طور ضمنی تولید کند.

### تفاوت مقایسه اعضا با مقایسه حافظه

مقایسه پیش‌فرض‌شده، مقایسه معنایی اعضای کلاس را انجام می‌دهد و معادل مقایسه بایت‌به‌بایت حافظه نیست.

برای مثال، مقایسه دو شیء شامل `std::string` از طریق مقایسه رشته‌ها انجام می‌شود، نه از طریق بررسی مستقیم آدرس یا نمایش داخلی حافظه.

این ویژگی باعث می‌شود مقایسه پیش‌فرض‌شده برای بسیاری از کلاس‌های ارزش‌محور (Value Types) مناسب باشد.

بااین‌حال، اگر کلاس شامل اشاره‌گر خام، شناسه مالکیت، منابع خارجی یا داده‌های cache‌شده باشد، مقایسه پیش‌فرض‌شده ممکن است معنای مورد انتظار طراحی را منعکس نکند.

## طراحی کلاس‌های سفارشی با `<=>`

### مقایسه پیش‌فرض‌شده برای انواع ساده

برای کلاس‌هایی که ترتیب آن‌ها مستقیماً از ترتیب اعضایشان به دست می‌آید، معمولاً بهترین انتخاب استفاده از `= default` است.

```
#include <compare>
#include <string>

struct Product {
    int id;
    std::string name;
    double price;

    auto operator<=>(const Product&) const = default;
};
```

در این مثال، ترتیب ابتدا بر اساس `id`، سپس `name` و در نهایت `price` تعیین می‌شود.

از آنجا که `double` می‌تواند NaN داشته باشد، نوع نتیجه استنباط‌شده برای این مقایسه ممکن است `std::partial_ordering` باشد.

همچنین، چون مقایسه پیش‌فرض‌شده ترتیب اعضا را بر اساس ترتیب اعلان آن‌ها تعیین می‌کند، باید دقت کرد که ترتیب اعضای کلاس واقعاً با ترتیب معنایی مورد نظر سازگار باشد.

اگر هدف مقایسه محصولات تنها بر اساس شناسه باشد، مقایسه پیش‌فرض‌شده این کلاس انتخاب مناسبی نیست؛ زیرا تغییر نام یا قیمت نیز می‌تواند نتیجه ترتیب را تغییر دهد.

### پیاده‌سازی دستی مقایسه لغت‌نامه‌ای

در برخی کلاس‌ها لازم است ترتیب مقایسه متفاوت از ترتیب اعضای داخلی باشد.

برای مثال، یک آدرس شبکه ممکن است ابتدا بر اساس خانواده پروتکل و سپس بر اساس مقدار عددی آدرس مرتب شود.

در چنین شرایطی می‌توان عملگر `<=>` را به‌صورت دستی تعریف کرد.

```
#include <compare>
#include <cstdint>

struct NetworkAddress {
    std::uint8_t family;
    std::uint32_t address;

    std::strong_ordering operator<=>(
        const NetworkAddress& other
    ) const {
        if (auto result = family <=> other.family;
            result != 0) {
            return result;
        }

        return address <=> other.address;
    }

    bool operator==(const NetworkAddress& other) const {
        return family == other.family &&
               address == other.address;
    }
};
```

در این پیاده‌سازی، ابتدا خانواده آدرس بررسی می‌شود. اگر خانواده‌ها متفاوت باشند، نتیجه همان مقایسه نخست خواهد بود؛ در غیر این صورت، مقدار آدرس مقایسه می‌شود.

این الگو برای کلاس‌هایی مفید است که ترتیب آن‌ها باید از چند معیار اولویت‌دار تشکیل شود.

### استفاده از `std::tie` در روش‌های قدیمی‌تر

پیش از معرفی `<=>`، یکی از روش‌های متداول برای مقایسه لغت‌نامه‌ای استفاده از `std::tie` بود.

```
#include <tuple>
#include <string>

struct User {
    std::string name;
    int id;

    bool operator<(const User& other) const {
        return std::tie(name, id) <
               std::tie(other.name, other.id);
    }
};
```

این روش همچنان معتبر است و برای طراحی‌هایی که فقط به یک عملگر ترتیبی خاص نیاز دارند، می‌تواند انتخاب مناسبی باشد.

بااین‌حال، در ++C20 اگر کلاس به یک رابط مقایسه‌ای کامل و سازگار نیاز داشته باشد، استفاده از `<=>` می‌تواند کد را ساده‌تر کند.

نکته مهم این است که `std::tie` فقط ترتیب اعضای انتخاب‌شده را تعیین می‌کند و به‌خودی‌خود عملگرهای دیگر را تولید نمی‌کند.

## قواعد مقایسه پیش‌فرض‌شده

### ترتیب مقایسه اعضای غیرایستا

در مقایسه پیش‌فرض‌شده، اعضای غیرایستای کلاس به ترتیب اعلان‌شان بررسی می‌شوند.

برای نمونه:

```
#include <compare>

struct Coordinate {
    int x;
    int y;

    auto operator<=>(const Coordinate&) const = default;
};
```

در این کلاس، ابتدا `x` و سپس `y` مقایسه می‌شوند.

بنابراین، نقطه `(2, 100)` از نقطه `(3, 0)` کوچک‌تر محسوب می‌شود، زیرا مقدار `x` در نقطه نخست کوچک‌تر است.

این رفتار با مقایسه هندسی فاصله از مبدأ یکسان نیست. اگر ترتیب هندسی مورد نظر باشد، باید منطق مقایسه به‌صورت دستی طراحی شود.

### مقایسه کلاس‌های پایه

اگر کلاس از کلاس پایه ارث‌بری کرده باشد، مقایسه پیش‌فرض‌شده ابتدا زیرشیء مربوط به کلاس پایه را بررسی می‌کند و سپس اعضای غیرایستای کلاس مشتق‌شده را به ترتیب اعلان مقایسه می‌کند.

```
#include <compare>

struct Base {
    int id;

    auto operator<=>(const Base&) const = default;
};

struct Derived : Base {
    int priority;

    auto operator<=>(const Derived&) const = default;
};
```

در این مثال، ترتیب ابتدا از `Base::id` تأثیر می‌گیرد و سپس `priority` بررسی می‌شود.

این رفتار برای طراحی سلسله‌مراتب کلاس‌ها اهمیت دارد؛ زیرا ترتیب کلاس مشتق‌شده ممکن است به مقایسه کلاس پایه وابسته باشد.

### محدودیت‌های مقایسه پیش‌فرض‌شده

مقایسه پیش‌فرض‌شده در تمام کلاس‌ها قابل استفاده نیست. برای نمونه، اگر اعضا یا کلاس‌های پایه نتوانند عملگرهای لازم را فراهم کنند، تعریف پیش‌فرض‌شده ممکن است حذف‌شده (Deleted) شود.

همچنین، وجود اعضایی که مقایسه معنایی آن‌ها تعریف نشده یا با نیازهای کلاس سازگار نیست، می‌تواند استفاده از این قابلیت را نامناسب کند.

در چنین مواردی باید بررسی شود که آیا پیاده‌سازی دستی `<=>` مناسب‌تر است یا اینکه اساساً کلاس نباید ترتیب کلی داشته باشد.

## تفاوت `operator==` با `operator<=>`

### نقش برابری در طراحی نوع‌ها

عملگر `operator==` برای بررسی برابری دو مقدار استفاده می‌شود، درحالی‌که `operator<=>` رابطه ترتیب آن‌ها را مشخص می‌کند.

این دو مفهوم مرتبط‌اند، اما الزاماً یکسان نیستند.

برای مثال، در یک کلاس رشته‌ای که مقایسه بدون حساسیت به حروف را پیاده‌سازی می‌کند، ممکن است دو رشته از دید ترتیب معادل باشند، ولی از دید برابری دقیق متفاوت باشند.

در طراحی API باید مشخص شود که برابری معنایی کلاس چیست و آیا باید با معادل بودن در ترتیب آن هماهنگ باشد یا خیر.

### نمونه‌ای از برابری مستقل

فرض کنید کلاس `User` بر اساس شناسه مرتب می‌شود، اما تمام اطلاعات آن باید در برابری بررسی شوند.

```
#include <compare>
#include <string>

struct User {
    int id;
    std::string name;

    std::strong_ordering operator<=>(
        const User& other
    ) const {
        return id <=> other.id;
    }

    bool operator==(const User& other) const {
        return id == other.id &&
               name == other.name;
    }
};
```

در این طراحی، دو کاربر با شناسه یکسان اما نام متفاوت، از نظر ترتیب معادل‌اند، ولی از نظر `operator==` برابر نیستند.

چنین طراحی‌ای ممکن است برای برخی کاربردهای خاص معتبر باشد، اما می‌تواند برای الگوریتم‌ها و ساختارهای داده‌ای که به سازگاری رابطه ترتیب و برابری وابسته‌اند، مشکل‌ساز شود.

برای مثال، در مرتب‌سازی معمولی ممکن است این دو شیء به یک موقعیت ترتیبی برسند، درحالی‌که از نظر برابری متفاوت باشند.

اگر این تفاوت هدفمند نیست، بهتر است تعریف برابری و ترتیب بر اساس یک مدل معنایی سازگار طراحی شود.

## مقایسه اعداد ممیز شناور و مسئله NaN

### رفتار `double` در مقایسه سه‌طرفه

یکی از نکات مهم در طراحی مقایسه، رفتار اعداد ممیز شناور است.

در ++C20، مقایسه سه‌طرفه نوع‌های ممیز شناور مانند `float` و `double` از نوع `std::partial_ordering` است؛ زیرا وجود NaN باعث می‌شود ترتیب کلی برقرار نباشد.

```
#include <compare>
#include <limits>

int main() {
    double a = 1.0;
    double b = std::numeric_limits<double>::quiet_NaN();

    auto result = a <=> b;

    bool unordered =
        result == std::partial_ordering::unordered;
}
```

در این مثال، نتیجه مقایسه `unordered` خواهد بود.

بنابراین، اگر کلاس شما شامل مقادیر ممیز شناور است، نباید بدون بررسی معنای مقایسه فرض کنید که ترتیب آن از نوع `std::strong_ordering` است.

### پیامدهای NaN در مرتب‌سازی

مقایسه NaN می‌تواند در طراحی الگوریتم‌های مرتب‌سازی و ساختارهای داده‌ای که به یک ترتیب ضعیف سخت‌گیرانه (Strict Weak Ordering) نیاز دارند، مسئله ایجاد کند.

برای مثال، مقایسه‌های معمولی ممیز شناور در حضور NaN ممکن است نتوانند رابطه ترتیبی مورد انتظار الگوریتم را فراهم کنند.

اگر برنامه به مرتب‌سازی قابل پیش‌بینی مقادیر شامل NaN نیاز دارد، باید سیاست مشخصی تعریف شود؛ برای مثال، تمام NaNها در انتهای ترتیب قرار بگیرند.

```
#include <compare>
#include <cmath>

std::strong_ordering compareDouble(double lhs, double rhs) {
    const bool lhsNan = std::isnan(lhs);
    const bool rhsNan = std::isnan(rhs);

    if (lhsNan && rhsNan) {
        return std::strong_ordering::equal;
    }

    if (lhsNan) {
        return std::strong_ordering::greater;
    }

    if (rhsNan) {
        return std::strong_ordering::less;
    }

    if (lhs < rhs) {
        return std::strong_ordering::less;
    }

    if (lhs > rhs) {
        return std::strong_ordering::greater;
    }

    return std::strong_ordering::equal;
}
```

این نمونه، NaN را بزرگ‌تر از هر مقدار غیر-NaN در نظر می‌گیرد و تمام NaNها را از نظر ترتیب معادل می‌داند.

این سیاست صرفاً یک انتخاب طراحی است؛ رفتار آن با تمام نیازهای کاربردی، از جمله تمایز میان نمایش‌های مختلف NaN یا ترتیب بیتی ممیز شناور، یکسان نیست.

همچنین، در حضور مقدارهای ویژه باید سیاست مربوط به صفر مثبت و صفر منفی و نحوه برخورد با ورودی‌های غیرعادی نیز متناسب با نیاز برنامه مشخص شود.

## مقایسه با انواع استاندارد کتابخانه

### استفاده از `std::compare_three_way`

کتابخانه استاندارد در ++C20 تابع شیء `std::compare_three_way` را ارائه می‌کند.

این ابزار یک شیء فراخوانی‌پذیر است که برای مقایسه سه‌طرفه مقادیر مناسب طراحی شده است.

```
#include <compare>
#include <iostream>

int main() {
    std::compare_three_way compare;

    auto result = compare(10, 20);

    std::cout << (result < 0) << '\n';
}
```

این ابزار برای کدهای عمومی و قالب‌هایی که می‌خواهند عملیات مقایسه سه‌طرفه را به‌عنوان یک شیء تابع دریافت کنند، مفید است.

در طراحی قالب‌ها باید توجه کرد که قابل استفاده بودن `std::compare_three_way` به سازگاری نوع‌های ورودی با نیازهای آن بستگی دارد؛ بنابراین، نباید فرض کرد که هر نوع دلخواهی بدون تعریف عملگر مناسب قابل مقایسه است.

### تفاوت `std::compare_three_way` با `std::less`

شیء تابع `std::less` یک مقایسه دودویی انجام می‌دهد و نتیجه آن `bool` است. در مقابل، `std::compare_three_way` برای تولید نتیجه مقایسه سه‌طرفه طراحی شده است.

```
#include <compare>
#include <functional>

int main() {
    std::less<> less;
    std::compare_three_way compare;

    bool isLess = less(10, 20);
    auto ordering = compare(10, 20);
}
```

انتخاب میان این دو ابزار به نیاز برنامه بستگی دارد.

اگر تنها لازم است بدانیم یک مقدار از مقدار دیگر کوچک‌تر است یا خیر، `std::less` کافی است. اگر به نتیجه‌ای نیاز داریم که نوع رابطه ترتیب را مشخص کند، `std::compare_three_way` انتخاب مناسب‌تری است.

### بررسی `std::strong_order`

کتابخانه استاندارد ++C20 تابع `std::strong_order` را برای درخواست ترتیب قوی در انواعی که از این عملیات پشتیبانی می‌کنند، معرفی کرده است.

این تابع با `std::compare_three_way` یکسان نیست. درحالی‌که تابع دوم از مقایسه سه‌طرفه متناسب با نوع استفاده می‌کند، `std::strong_order` برای به دست آوردن یک ترتیب قوی طراحی شده است.

```
#include <compare>

int main() {
    double a = 1.0;
    double b = 2.0;

    auto result = std::strong_order(a, b);
}
```

در انواع ممیز شناور، ترتیب قوی می‌تواند تفاوت‌هایی مانند NaN را طبق قرارداد مربوط مدیریت کند. این عملیات با مقایسه معمولی `<=>` که ممکن است `unordered` تولید کند، یکسان نیست.

برای استفاده از این ابزار باید قرارداد دقیق تابع و الزامات نوع مورد نظر بررسی شود؛ زیرا در همه انواع سفارشی نمی‌توان انتظار داشت که ترتیب قوی به‌طور خودکار و بدون طراحی مناسب در دسترس باشد.

## نقش `<=>` در Concepts و Generic Programming

### استفاده در `std::three_way_comparable`

در ++C20، مفهوم `std::three_way_comparable` در هدر `<compare>` تعریف شده است.

این مفهوم مشخص می‌کند که یک نوع برای عملیات مقایسه سه‌طرفه مورد انتظار، شرایط لازم را برآورده می‌کند یا خیر.

```
#include <compare>
#include <concepts>

template <typename T>
requires std::three_way_comparable<T>
bool isOrderedBefore(const T& lhs, const T& rhs) {
    return lhs < rhs;
}
```

در این مثال، تابع تنها برای نوع‌هایی قابل استفاده است که مفهوم `std::three_way_comparable` را برآورده کنند.

این مفهوم فقط وجود یک عبارت `<=>` را بررسی نمی‌کند؛ بلکه مجموعه‌ای از الزامات معنایی و نحوی مربوط به عملیات مقایسه را نیز در نظر می‌گیرد.

### تفاوت `std::three_way_comparable` با `std::totally_ordered`

مفهوم `std::totally_ordered` برای نوع‌هایی استفاده می‌شود که عملیات معمول مقایسه و روابط معنایی متناظر را فراهم می‌کنند.

در مقابل، `std::three_way_comparable` مشخصاً به عملیات مقایسه سه‌طرفه و رابطه میان آن و عملگرهای مقایسه مرتبط است.

همچنین، `std::three_way_comparable_with` برای بررسی سازگاری مقایسه میان دو نوع متفاوت کاربرد دارد.

این مفاهیم در طراحی کتابخانه‌های قالبی مفید هستند؛ زیرا امکان بیان دقیق‌تر نیازهای یک الگوریتم یا API را فراهم می‌کنند.

بااین‌حال، باید به این نکته توجه کرد که برآورده کردن یک Concept صرفاً به معنای قابل کامپایل بودن عبارت‌ها نیست؛ الزامات معنایی آن نیز باید رعایت شوند.

## کاربرد در مرتب‌سازی و ساختارهای داده

### مرتب‌سازی انواع سفارشی

یکی از کاربردهای رایج `<=>` طراحی نوع‌هایی است که باید در مجموعه‌ها یا الگوریتم‌های مرتب‌سازی استفاده شوند.

```
#include <algorithm>
#include <compare>
#include <vector>

struct Task {
    int priority;
    int id;

    auto operator<=>(const Task&) const = default;
};

int main() {
    std::vector<Task> tasks{
        {3, 10},
        {1, 20},
        {2, 30}
    };

    std::sort(tasks.begin(), tasks.end());
}
```

در این مثال، ترتیب ابتدا بر اساس `priority` و سپس بر اساس `id` تعیین می‌شود.

از آنجا که هر دو عضو از نوع صحیح هستند، مقایسه پیش‌فرض‌شده ترتیب قوی مناسبی تولید می‌کند.

اگر نیاز باشد وظایف بر اساس اولویت نزولی مرتب شوند، می‌توان comparator جداگانه‌ای به `std::sort` داد یا طراحی ترتیب را متناسب با نیاز تغییر داد.

### استفاده در `std::set` و `std::map`

ساختارهایی مانند `std::set` و `std::map` به یک رابطه ترتیب مناسب نیاز دارند. در این ساختارها، comparator به تعیین جایگاه عناصر کمک می‌کند.

وجود `<=>` در یک نوع سفارشی به‌خودی‌خود به این معنا نیست که تمام ساختارهای داده مستقیماً از نتیجه آن استفاده می‌کنند؛ این ساختارها معمولاً از comparatorهایی مانند `std::less` استفاده می‌کنند.

اگر عملگر `<` برای نوع مورد نظر از طریق قواعد بازنویسی `<=>` در دسترس باشد، این نوع می‌تواند در بسیاری از موارد با comparator پیش‌فرض سازگار باشد.

```
#include <compare>
#include <map>

struct Version {
    int major;
    int minor;

    auto operator<=>(const Version&) const = default;
};

int main() {
    std::map<Version, int> versions;

    versions[{1, 0}] = 100;
    versions[{2, 0}] = 200;
}
```

این مثال نشان می‌دهد که چگونه یک نوع دارای مقایسه پیش‌فرض‌شده می‌تواند به‌عنوان کلید در یک ساختار مرتب‌شده استفاده شود.

نکته مهم این است که comparator مورد استفاده در ساختارهای مرتب‌شده باید الزامات رابطه ترتیب ضعیف سخت‌گیرانه را رعایت کند. وجود `<=>` به‌تنهایی تضمین نمی‌کند که تمام روابط مقایسه‌ای نوع برای هر کاربردی مناسب باشند.

## تفاوت عملگر `<=>` با روش‌های قدیمی

### روش سنتی در برابر روش مدرن

در روش سنتی، توسعه‌دهنده معمولاً باید عملگرهای مورد نیاز را جداگانه پیاده‌سازی می‌کرد.

```
struct Number {
    int value;

    bool operator==(const Number& other) const {
        return value == other.value;
    }

    bool operator<(const Number& other) const {
        return value < other.value;
    }
};
```

در ++C20، همین طراحی برای بسیاری از انواع می‌تواند ساده‌تر شود.

```
#include <compare>

struct Number {
    int value;

    auto operator<=>(const Number&) const = default;
};
```

در نسخه دوم، مقایسه بر اساس عضو `value` انجام می‌شود و کامپایلر می‌تواند عملگرهای ترتیبی لازم را از طریق قواعد بازنویسی پشتیبانی کند.

همچنین، تعریف پیش‌فرض‌شده `<=>` امکان تولید ضمنی `operator==` متناظر را فراهم می‌کند، مشروط بر اینکه شرایط لازم برقرار باشند.

بااین‌حال، اگر کلاس دارای معنای مقایسه‌ای خاص باشد، روش دستی ممکن است دقیق‌تر و مناسب‌تر باشد.

### تفاوت با مقایسه دستی چندمرحله‌ای

در روش‌های قدیمی‌تر، توسعه‌دهنده برای مقایسه لغت‌نامه‌ای معمولاً باید هر عضو را جداگانه بررسی می‌کرد و در صورت برابر بودن به عضو بعدی می‌رفت.

عملگر `<=>` می‌تواند همین منطق را در قالب یک رابط استاندارد پیاده‌سازی کند.

این تغییر به معنای حذف کامل نیاز به طراحی مقایسه نیست؛ بلکه امکان پیاده‌سازی سازگارتر و کم‌تکرارتری را فراهم می‌کند.

## محدودیت‌ها و خطاهای رایج

### فرض نادرست درباره مقدار عددی نتیجه

یکی از خطاهای رایج، فرض کردن این است که نتیجه `<=>` همیشه دقیقاً `-1`، `0` یا `1` است.

درحالی‌که استاندارد چنین تضمینی ارائه نمی‌کند. باید نتیجه را از طریق مقایسه با صفر یا مقادیر ثابت نوع مقایسه‌ای بررسی کرد.

### فرض بر تولید تمام عملگرها

اشتباه رایج دیگر این است که تصور شود تعریف `<=>` در هر شرایطی تمام عملگرهای مقایسه را تولید می‌کند.

در عمل، قواعد بازنویسی عملگرها و تولید ضمنی `operator==` شرایط مشخصی دارند. اگر کلاس به معنای برابری خاصی نیاز داشته باشد، باید آن را آگاهانه طراحی کرد.

### استفاده نادرست از `auto`

استفاده از `auto` برای نوع بازگشتی `<=>` در بسیاری از موارد مناسب است، به‌ویژه هنگامی که نوع اعضا تعیین‌کننده نوع نتیجه است.

بااین‌حال، اگر API عمومی باید نوع نتیجه مشخصی داشته باشد، ممکن است اعلان صریح `std::strong_ordering` یا یکی از نوع‌های دیگر مناسب‌تر باشد.

برای مثال، اگر یکی از اعضای کلاس ممیز شناور باشد، استنباط خودکار می‌تواند به `std::partial_ordering` منجر شود. در چنین شرایطی، اعلان صریح یک نوع قوی‌تر ممکن است با رفتار واقعی مقایسه سازگار نباشد.

### مقایسه اعضایی که معنای مناسبی ندارند

مقایسه پیش‌فرض‌شده تمام اعضای غیرایستا و زیرشیء پایه را طبق قواعد استاندارد بررسی می‌کند. این رفتار لزوماً همان چیزی نیست که از دید دامنه کاربرد باید مقایسه شود.

برای مثال، یک کلاس دارای شناسه پایدار و داده cache‌شده ممکن است تنها بر اساس شناسه پایدار مقایسه شود، نه بر اساس مقدار cache.

در چنین شرایطی، پیاده‌سازی دستی معمولاً انتخاب بهتری است.

### نادیده گرفتن رفتار NaN

در کلاس‌های شامل اعداد ممیز شناور، نادیده گرفتن حالت `unordered` می‌تواند باعث ایجاد مشکلات منطقی در مقایسه و مرتب‌سازی شود.

اگر نوع باید ترتیب کلی داشته باشد، باید سیاست برخورد با NaN به‌صراحت مشخص شود.

### اشتباه گرفتن ترتیب با برابری

ترتیب و برابری دو مفهوم مرتبط اما متمایزند. اگر دو شیء در ترتیب معادل باشند، لزوماً از نظر تمام ویژگی‌های معنایی برابر نیستند.

این مسئله به‌ویژه در کلاس‌هایی که مقایسه بدون حساسیت به حروف، مقایسه بر اساس کلید یا مقایسه بر اساس یک زیرمجموعه از اعضا را پیاده‌سازی می‌کنند، اهمیت دارد.

## نکات طراحی برای توسعه‌دهندگان حرفه‌ای

### انتخاب نوع نتیجه مناسب

نوع نتیجه باید با قرارداد معنایی کلاس سازگار باشد.

اگر تمام مقادیر باید یک ترتیب کلی داشته باشند و معادل بودن با برابری متناظر سازگار باشد، `std::strong_ordering` مناسب است.

اگر ترتیب قطعی است اما چند مقدار می‌توانند از دید ترتیب معادل باشند، `std::weak_ordering` انتخاب مناسبی است.

اگر برخی مقادیر قابل مقایسه ترتیبی نیستند، `std::partial_ordering` مناسب‌تر خواهد بود.

### طراحی بر اساس معنا، نه صرفاً نحو

قابل کامپایل بودن یک عملگر `<=>` به معنای درست بودن رابطه ترتیب نیست.

در طراحی نوع‌های عمومی باید بررسی شود که رابطه ترتیب:

- با نیازهای الگوریتم‌های مصرف‌کننده سازگار باشد.
- رفتار قابل پیش‌بینی داشته باشد.
- در صورت نیاز، با `operator==` سازگار باشد.
- نسبت به تغییر اعضای داخلی کلاس، ناخواسته تغییر معنا ندهد.

### توجه به سازگاری با نسخه‌های قدیمی‌تر

عملگر `<=>` و نوع‌های اصلی مقایسه متعلق به ++C20 هستند. بنابراین، کدی که از این قابلیت‌ها استفاده می‌کند، به کامپایلری نیاز دارد که پشتیبانی مناسب از ++C20 و کتابخانه استاندارد متناظر را ارائه کند.

اگر کتابخانه‌ای باید با ++C17 یا نسخه‌های قدیمی‌تر سازگار باشد، نمی‌توان بدون تغییر طراحی از این قابلیت‌ها استفاده کرد.

در پروژه‌های چندسکویی نیز باید میان پشتیبانی زبان در کامپایلر و پشتیبانی کتابخانه استاندارد از هدر `<compare>` و اجزای آن تفاوت قائل شد.

## جمع‌بندی

عملگر مقایسه سه‌طرفه `<=>` یکی از قابلیت‌های مهم ++C20 برای طراحی انواع مقایسه‌پذیر است. این عملگر امکان نمایش نتیجه مقایسه در قالب یک نوع استاندارد را فراهم می‌کند و در کنار قواعد بازنویسی عملگرها و مقایسه پیش‌فرض‌شده، حجم کد تکراری را کاهش می‌دهد.

سه نوع اصلی `std::strong_ordering`، `std::weak_ordering` و `std::partial_ordering` هرکدام برای معنای مشخصی از ترتیب طراحی شده‌اند. انتخاب میان آن‌ها باید بر اساس قرارداد معنایی نوع انجام شود، نه صرفاً بر اساس سادگی پیاده‌سازی.

برای بسیاری از کلاس‌های ارزش‌محور، تعریف پیش‌فرض‌شده `<=>` انتخاب مناسبی است. بااین‌حال، در کلاس‌هایی که ترتیب معنایی با ترتیب اعضای داخلی تفاوت دارد، پیاده‌سازی دستی ضروری است.

در نهایت، استفاده صحیح از `<=>` تنها به نوشتن یک عملگر محدود نمی‌شود؛ بلکه مستلزم درک رابطه میان ترتیب، برابری، رفتار مقادیر ویژه، الزامات الگوریتم‌های استاندارد و قراردادهای API است. رعایت این اصول به ساخت نوع‌هایی قابل اعتمادتر، خواناتر و سازگارتر با امکانات مدرن ++C کمک می‌کند.
