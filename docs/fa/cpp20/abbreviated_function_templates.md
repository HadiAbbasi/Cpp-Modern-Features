# معرفی Abbreviated Function Templates در ++C20

## مقدمه

قابلیت **Abbreviated Function Templates** یکی از امکانات مهم ++C20 است که نوشتن توابع Generic را ساده‌تر و خواناتر می‌کند. این قابلیت به برنامه‌نویس اجازه می‌دهد به‌جای تعریف صریح پارامترهای `template`، از `auto` در فهرست پارامترهای تابع استفاده کند. کامپایلر برای هر پارامتر دارای `auto`، یک پارامتر متناظر از نوع Template ایجاد می‌کند.

این قابلیت به‌ویژه در توابع کمکی، الگوریتم‌های Generic، پردازش Rangeها، توابع مبتنی بر `Concepts` و کدهایی که با انواع مختلف داده کار می‌کنند، کاربرد دارد.

برای مثال، تابع زیر را در نظر بگیرید:

```
template <typename T>
T add(T lhs, T rhs) {
    return lhs + rhs;
}
```

با استفاده از Abbreviated Function Templates می‌توان آن را به شکل زیر نوشت:

```
auto add(auto lhs, auto rhs) {
    return lhs + rhs;
}
```

هر دو تعریف از Template برای ایجاد نسخه‌های مناسب تابع بر اساس نوع آرگومان‌ها استفاده می‌کنند؛ اما این دو تعریف از نظر معنایی کاملاً یکسان نیستند. در نسخه دوم، هر پارامتر `auto` یک پارامتر Template مستقل ایجاد می‌کند. بنابراین، امکان استنتاج انواع متفاوت برای `lhs` و `rhs` وجود دارد و نوع بازگشتی نیز با استفاده از قواعد `auto` استنتاج می‌شود.

برای درک صحیح این قابلیت، باید تفاوت آن با Function Templateهای معمولی، نقش `Concepts`، نحوه استنتاج نوع، محدودیت‌های زبان و کاربردهای عملی آن را بررسی کرد.

## مفهوم Abbreviated Function Templates

### تعریف اصلی

در استاندارد ++C20، اگر در فهرست پارامترهای یک تابع از `auto` به‌عنوان نوع پارامتر استفاده شود، تابع به‌صورت یک Function Template تعریف می‌شود.

به این ترتیب، کد زیر:

```
void printValue(auto value) {
    // Process value
}
```

از نظر مفهومی تقریباً معادل تعریف زیر است:

```
template <typename T>
void printValue(T value) {
    // Process value
}
```

در هر دو حالت، نوع پارامتر هنگام استفاده از تابع و بر اساس آرگومان ارسالی استنتاج می‌شود.

نکته مهم این است که `auto` در اینجا به معنای تعریف یک متغیر محلی نیست. این کلمه در فهرست پارامترهای تابع، یک Placeholder Type است که باعث ایجاد پارامتر Template می‌شود.

### دلیل ایجاد این قابلیت

پیش از ++C20، برای تعریف یک تابع Generic معمولاً لازم بود پارامترهای Template به‌صورت صریح نوشته شوند:

```
template <typename T>
void process(const T& value) {
    // Process value
}
```

اگر تابعی ساده بود و فقط یک یا دو پارامتر Template داشت، این ساختار ممکن بود کمی پرجزئیات به نظر برسد.

قابلیت Abbreviated Function Templates این بخش تکراری را حذف می‌کند:

```
void process(const auto& value) {
    // Process value
}
```

مزایای اصلی این روش عبارت‌اند از:

- کاهش Boilerplate و کوتاه‌تر شدن تعریف توابع Generic.
- خوانایی بهتر برای توابعی که پارامترهای Template پیچیده‌ای ندارند.
- امکان استفاده مستقیم از `Concepts` در فهرست پارامترها.
- هماهنگی بیشتر با سبک نوشتاری Generic Programming مدرن.
- آسان‌تر شدن تعریف توابع کمکی برای الگوریتم‌ها، Rangeها و Typeهای مختلف.

بااین‌حال، این قابلیت جایگزین تمام Function Templateهای سنتی نیست. زمانی که به نام‌گذاری صریح پارامترهای Template، تعیین نوع بازگشتی بر اساس یک پارامتر خاص یا تعریف Templateهای دارای چند پارامتر وابسته نیاز باشد، روش سنتی همچنان ضروری است.

## تفاوت با Function Templateهای معمولی

### مقایسه ساختارها

دو تعریف زیر را مقایسه کنید:

```
template <typename T>
void display(const T& value) {
    // Display value
}
```

```
void display(const auto& value) {
    // Display value
}
```

تعریف دوم یک Abbreviated Function Template است. در هر دو حالت، پارامتر تابع یک Reference به `const` است و نوع پایه بر اساس آرگومان استنتاج می‌شود.

اما در تعریف دوم، نام پارامتر Template در دسترس نیست. این موضوع برای پارامترهای ساده مشکلی ایجاد نمی‌کند، ولی اگر نوع بازگشتی، پارامتر دیگری یا یک Template دیگر به همان نوع وابسته باشد، محدودیت ایجاد می‌شود.

برای مثال، در تعریف زیر، نوع `T` در بخش‌های مختلف اعلان قابل استفاده است:

```
template <typename T>
T identity(T value) {
    return value;
}
```

ولی نمی‌توان صرفاً با نوشتن `auto` در پارامتر تابع، نام `T` را در بخش بازگشتی یا بدنه تابع به دست آورد:

```
auto identity(auto value) {
    return value;
}
```

در تعریف دوم، نوع بازگشتی با استفاده از قواعد `auto` استنتاج می‌شود. اگر لازم باشد نوع بازگشتی صریحاً به نوع پارامتر Template وابسته باشد، روش سنتی انتخاب مناسب‌تری است.

### تفاوت میان پارامترهای Template

در تعریف سنتی زیر، هر دو پارامتر تابع از یک نوع Template استفاده می‌کنند:

```
template <typename T>
auto add(T lhs, T rhs) {
    return lhs + rhs;
}
```

در نتیجه، استنتاج معمول این تابع برای آرگومان‌هایی با انواع متفاوت، مانند `int` و `double`، موفق نخواهد بود؛ زیرا یک `T` واحد باید با هر دو آرگومان سازگار باشد.

اما در تعریف زیر:

```
auto add(auto lhs, auto rhs) {
    return lhs + rhs;
}
```

هر پارامتر `auto` یک پارامتر Template مستقل ایجاد می‌کند. بنابراین، تابع می‌تواند آرگومان‌هایی با انواع متفاوت دریافت کند، مشروط بر اینکه عبارت `lhs + rhs` معتبر باشد.

برای مثال:

```
#include <iostream>

int main() {
    std::cout << add(10, 2.5) << '\n';
}
```

این کد با تعریف دوم، نتیجه `12.5` را تولید می‌کند.

اگر بخواهیم دو پارامتر از یک نوع داشته باشیم، می‌توانیم از یک Template Parameter صریح استفاده کنیم یا در صورت مناسب بودن، از `Concepts` برای اعمال محدودیت‌های لازم بهره ببریم.

## نحوه استنتاج نوع پارامترها

### قواعد استنتاج `auto`

پارامترهای `auto` در فهرست پارامتر تابع، از قواعد استنتاج Template پیروی می‌کنند. درک این قواعد برای جلوگیری از کپی‌های ناخواسته، حفظ Referenceها و مدیریت `const` ضروری است.

برای مثال:

```
void byValue(auto value) {
    // value is a separate object
}
```

این تابع پارامتر را به‌صورت Value دریافت می‌کند. در نتیجه، قواعد استنتاج مشابه Template Parameterهای مقداری اعمال می‌شوند و در حالت معمول، آرگومان به پارامتر تابع کپی یا منتقل می‌شود.

در مقابل، تعریف زیر Reference است:

```
void byReference(auto& value) {
    // value refers to the original object
}
```

این تعریف برای آرگومان‌های موقت غیرقابل استفاده است، زیرا یک Lvalue Reference غیر `const` نمی‌تواند به یک Rvalue متصل شود.

همچنین می‌توان از `const auto&` استفاده کرد:

```
void inspect(const auto& value) {
    // Read value without copying it
}
```

این فرم برای مشاهده داده‌های بزرگ، Containerها و انواعی که کپی آن‌ها پرهزینه است، بسیار مناسب است.

### استفاده از `const auto&`

در بسیاری از توابع Generic، دریافت پارامتر به‌صورت `const auto&` انتخاب مناسبی است:

```
#include <iostream>
#include <string>

void print(const auto& value) {
    std::cout << value << '\n';
}

int main() {
    print(42);
    print(std::string{"Modern C++"});
}
```

در این مثال، تابع بدون نیاز به کپی کردن آرگومان، انواع مختلف داده را دریافت می‌کند؛ البته فقط در صورتی که عملیات درج در جریان خروجی برای نوع مربوطه معتبر باشد.

استفاده از `const auto&` به این معنا نیست که تمام توابع Generic باید چنین امضایی داشته باشند. اگر تابع قرار است یک نسخه مستقل از داده بسازد یا مالکیت یک مقدار را دریافت کند، استفاده از Value یا `auto&&` ممکن است مناسب‌تر باشد.

### استفاده از `auto&&`

پارامتر `auto&&` یک Forwarding Reference ایجاد می‌کند:

```
void forwardValue(auto&& value) {
    // value can bind to lvalues and rvalues
}
```

در این حالت، نوع پارامتر بر اساس نوع آرگومان و قواعد Reference Collapsing تعیین می‌شود.

برای مثال، اگر آرگومان یک Lvalue باشد، پارامتر به Lvalue Reference تبدیل می‌شود؛ اگر آرگومان یک Rvalue باشد، پارامتر به Rvalue Reference تبدیل خواهد شد.

این روش برای نوشتن Wrapperها و توابعی که باید دسته Value Category آرگومان را حفظ کنند مفید است. بااین‌حال، دریافت پارامتر با `auto&&` به‌تنهایی به معنای Perfect Forwarding نیست. برای انتقال صحیح دسته Value Category باید از `std::forward` استفاده شود:

```
#include <utility>

void wrapper(auto&& value) {
    process(std::forward<decltype(value)>(value));
}
```

در این مثال، `process` تابعی فرضی است که باید در محیط واقعی تعریف شده باشد.

توجه کنید که `decltype(value)` در اینجا نوع Reference را نیز حفظ می‌کند و همین ویژگی برای Forwarding صحیح ضروری است.

## تفاوت میان `auto`، `auto&` و `auto&&`

انتخاب نوع پارامتر، بر نحوه اتصال به آرگومان و رفتار تابع تأثیر می‌گذارد.

| شکل پارامتر         | رفتار اصلی                            | کاربرد معمول                                |
| ------------------- | ------------------------------------- | ------------------------------------------- |
| `auto value`        | دریافت بر اساس Value                  | زمانی که نسخه مستقل از آرگومان لازم است     |
| `auto& value`       | دریافت با Lvalue Reference قابل تغییر | تغییر مستقیم شیء اصلی                       |
| `const auto& value` | دریافت با Reference فقط‌خواندنی       | مشاهده داده بدون کپی معمول                  |
| `auto&& value`      | دریافت با Forwarding Reference        | Wrapperها و Generic Forwarding              |
| `const auto value`  | دریافت Value با شیء محلی `const`      | موارد خاصی که تغییر پارامتر نباید مجاز باشد |

یک نکته ظریف این است که `const auto value` معمولاً `const` بودن آرگومان اصلی را تضمین نمی‌کند؛ بلکه پارامتر محلی را `const` می‌کند. اگر آرگومان یک شیء کپی‌پذیر باشد، نسخه‌ای مستقل ساخته می‌شود و تغییر ندادن پارامتر به معنای تغییر ندادن شیء اصلی نیست.

## استفاده از Concepts در Abbreviated Function Templates

### نقش Concepts در محدود کردن انواع

قابلیت `Concepts` در ++C20 امکان بیان محدودیت‌های معنایی و نحوی انواع Template را فراهم می‌کند.

به‌جای اینکه تابع برای هر نوعی تعریف شود و در صورت نامعتبر بودن عملیات داخل بدنه با خطاهای پیچیده مواجه شویم، می‌توان محدودیت را در خود امضای تابع مشخص کرد.

برای مثال:

```
#include <concepts>

void increment(std::integral auto& value) {
    ++value;
}
```

در این مثال، پارامتر فقط نوع‌هایی را می‌پذیرد که `std::integral` را برآورده کنند. این Concept در Header مربوط به `<concepts>` تعریف شده است.

این محدودیت شامل انواع صحیح استاندارد و انواع صحیح سفارشی سازگار با تعریف Concept می‌شود، اما انواع ممیز شناور را نمی‌پذیرد.

### استفاده از Conceptهای سفارشی

می‌توان Concept اختصاصی تعریف کرد تا محدودیت مورد نیاز تابع روشن‌تر شود:

```
#include <concepts>

template <typename T>
concept Addable = requires(const T& lhs, const T& rhs) {
    lhs + rhs;
};

auto add(const Addable auto& lhs, const Addable auto& rhs) {
    return lhs + rhs;
}
```

این مثال از نظر نحوی معتبر نیست، زیرا دو پارامتر `Addable` به‌صورت مستقل بررسی می‌شوند و این Concept تضمین نمی‌کند که عملگر `+` برای ترکیب نوع آرگومان اول و نوع آرگومان دوم معتبر باشد.

برای بیان صحیح این شرط، باید نوع‌های دو آرگومان را در یک رابطه مشترک بررسی کنیم. یک راه مناسب، استفاده از Template Parameterهای صریح است:

```
template <typename T, typename U>
concept AddableWith = requires(const T& lhs, const U& rhs) {
    lhs + rhs;
};

template <typename T, typename U>
    requires AddableWith<T, U>
auto add(const T& lhs, const U& rhs) {
    return lhs + rhs;
}
```

در این تعریف، رابطه بین دو نوع به‌صورت صریح بررسی می‌شود.

همچنین می‌توان برای یک Abbreviated Function Template از یک Concept سفارشی استفاده کرد که محدودیت هر پارامتر را مستقل بیان کند. انتخاب میان این دو روش به این بستگی دارد که آیا محدودیت‌ها به هر نوع به‌تنهایی مربوط هستند یا رابطه میان چند نوع اهمیت دارد.

### استفاده از `std::same_as`

گاهی لازم است دو پارامتر از یک نوع باشند. در چنین شرایطی، `std::same_as` می‌تواند برای اعمال محدودیت مفید باشد:

```
#include <concepts>

void compare(std::same_as<int> auto lhs,
             std::same_as<int> auto rhs) {
    // Both parameters must satisfy the int constraint
}
```

این مثال فقط برای پارامترهایی مناسب است که نوع استنتاج‌شده آن‌ها با `int` سازگار باشد؛ اما اگر هدف این باشد که هر دو پارامتر از یک نوع دلخواه باشند، استفاده از `std::same_as` به این شکل کافی نیست، زیرا نوع مورد انتظار از قبل `int` تعیین شده است.

برای اعمال یک نوع مشترک دلخواه، بهتر است از Template Parameter صریح استفاده شود:

```
template <typename T>
void compare(T lhs, T rhs) {
    // Both parameters use the same deduced type
}
```

این تفاوت نشان می‌دهد که Abbreviated Function Templates برای بیان محدودیت‌های مستقل مناسب‌اند، اما محدودیت‌های وابسته به یک نوع مشترک معمولاً با Templateهای صریح بهتر بیان می‌شوند.

## استفاده از Trailing Return Type

### تعیین نوع بازگشتی

در Abbreviated Function Templates می‌توان نوع بازگشتی را با استفاده از `auto` استنتاج کرد:

```
auto multiply(auto lhs, auto rhs) {
    return lhs * rhs;
}
```

کامپایلر نوع بازگشتی را از عبارت‌های `return` استنتاج می‌کند.

اگر لازم باشد نوع بازگشتی به‌صورت صریح مشخص شود، می‌توان از Trailing Return Type استفاده کرد:

```
auto convert(auto value) -> long {
    return static_cast<long>(value);
}
```

این فرم به‌ویژه زمانی مفید است که نوع بازگشتی از نوع پارامترها مستقل باشد یا لازم باشد نوع بازگشتی به‌صورت مشخص در Interface تابع دیده شود.

### محدودیت در دسترسی به نوع پارامتر

یکی از تفاوت‌های مهم میان Templateهای صریح و Abbreviated Function Templates این است که در فرم دوم نام پارامتر Template در دسترس نیست.

برای مثال، در تعریف زیر نوع `T` را می‌توان مستقیماً در نوع بازگشتی استفاده کرد:

```
template <typename T>
auto identity(T value) -> T {
    return value;
}
```

اما در تعریف زیر، `T` نامی شناخته‌شده نیست:

```
auto identity(auto value) {
    return value;
}
```

اگر نوع بازگشتی دقیقاً باید همان نوع Template Parameter باشد، استنتاج `auto` معمولاً کافی است؛ اما در موارد پیچیده‌تر، به‌خصوص هنگام استفاده از `decltype`، `std::conditional_t` یا Traitهای نوعی، تعریف صریح Template می‌تواند خواناتر و مناسب‌تر باشد.

## تفاوت با Generic Lambdaها

### ارتباط میان دو قابلیت

قابلیت Generic Lambda از ++C14 معرفی شد و اجازه می‌دهد پارامترهای Lambda با `auto` تعریف شوند:

```
auto lambda = [](auto value) {
    return value;
};
```

در مقابل، Abbreviated Function Templates در ++C20 همین سبک را برای توابع معمولی فراهم می‌کنند:

```
auto identity(auto value) {
    return value;
}
```

هر دو قابلیت از Template برای پشتیبانی از انواع مختلف استفاده می‌کنند؛ اما Lambda علاوه بر رفتار Generic، یک Closure Type نیز ایجاد می‌کند.

### چه زمانی از Lambda استفاده کنیم؟

Generic Lambda زمانی مناسب است که رفتار تابع در محدوده‌ای محلی تعریف می‌شود، مثلاً برای استفاده در الگوریتم‌ها:

```
#include <algorithm>
#include <vector>

int main() {
    std::vector<int> values{1, 2, 3, 4, 5};

    std::ranges::for_each(values, [](auto value) {
        return value * 2;
    });
}
```

در این مثال، استفاده از Lambda برای تعریف رفتار محلی مناسب است؛ البته چون `std::ranges::for_each` نتیجه بازگشتی Lambda را برای جایگزینی عناصر استفاده نمی‌کند، اگر هدف تغییر عناصر باشد باید از یک الگوریتم مناسب دیگر یا حلقه استفاده شود.

در مقابل، زمانی که تابع باید یک Interface مستقل و قابل استفاده مجدد داشته باشد، تعریف یک Function Template یا Abbreviated Function Template معمولاً انتخاب مناسب‌تری است.

## تفاوت با `auto` در پارامترهای غیرقالبی

### کاربرد `auto` در تعریف متغیر

از ++C11 می‌توان از `auto` برای استنتاج نوع متغیر استفاده کرد:

```
auto value = 42;
```

در اینجا `auto` نوع متغیر را از مقدار اولیه استنتاج می‌کند.

اما در تعریف تابع زیر:

```
void process(auto value) {
    // Process value
}
```

`auto` باعث ایجاد یک Function Template می‌شود.

این دو کاربرد از یک Placeholder Type استفاده می‌کنند، اما جایگاه و نقش آن‌ها متفاوت است. `auto` در تعریف متغیر یک نوع استنتاج‌شده برای همان متغیر ایجاد می‌کند، درحالی‌که `auto` در پارامتر تابع باعث ایجاد پارامتر Template می‌شود.

## کاربردهای عملی در طراحی API

### تعریف توابع کمکی

در پروژه‌های بزرگ، توابع کمکی معمولاً برای پردازش داده‌های متنوع استفاده می‌شوند. Abbreviated Function Templates می‌توانند امضای چنین توابعی را ساده‌تر کنند:

```
#include <iostream>

void logValue(const auto& value) {
    std::cout << value << '\n';
}
```

این تابع می‌تواند برای انواعی استفاده شود که قابلیت ارسال به جریان خروجی را دارند.

اگر قرار است Interface عمومی کتابخانه طراحی شود، بهتر است محدودیت‌های لازم با `Concepts` بیان شوند تا خطاهای ناشی از انواع ناسازگار زودتر و با پیام‌های دقیق‌تری تشخیص داده شوند.

### پردازش Rangeها

در کدهای مدرن ++C، توابعی که روی Rangeها کار می‌کنند اغلب به انواع مختلف Container وابسته‌اند. برای مثال:

```
#include <iostream>
#include <ranges>
#include <vector>

void printRange(const auto& range) {
    for (const auto& value : range) {
        std::cout << value << ' ';
    }

    std::cout << '\n';
}

int main() {
    std::vector<int> values{1, 2, 3, 4, 5};
    printRange(values);
}
```

در این مثال، تابع بدون وابستگی به نوع مشخص Container تعریف شده است. بااین‌حال، محدودیت‌های واقعی تابع شامل پشتیبانی از Range-based for و قابلیت ارسال عناصر به جریان خروجی است.

اگر بخواهیم این الزامات را در Interface بیان کنیم، می‌توانیم از `std::ranges::input_range` استفاده کنیم:

```
#include <iostream>
#include <ranges>

void printRange(const std::ranges::input_range auto& range) {
    for (const auto& value : range) {
        std::cout << value << ' ';
    }

    std::cout << '\n';
}
```

این محدودیت تضمین می‌کند که نوع مورد نظر با Concept مربوط به Input Range سازگار باشد؛ اما همچنان تضمین نمی‌کند که عناصر Range برای `std::cout` قابل درج باشند.

### استفاده در Callbackها و الگوریتم‌ها

در APIهایی که Callback دریافت می‌کنند، Abbreviated Function Templates می‌توانند در ساخت توابع Generic مستقل مفید باشند. بااین‌حال، اگر نوع Callback بخشی از Interface پیچیده باشد یا لازم باشد چند نوع Template با یکدیگر ارتباط داشته باشند، Templateهای صریح معمولاً مناسب‌تر هستند.

برای نمونه:

```
template <typename F, typename T>
auto apply(F&& function, T&& value) {
    return std::forward<F>(function)(
        std::forward<T>(value)
    );
}
```

این تابع از Templateهای صریح استفاده می‌کند، زیرا باید `F` و `T` را به‌صورت مستقل نام‌گذاری کند و آن‌ها را در `std::forward` به کار ببرد.

اگر هدف فقط اجرای یک عملیات ساده روی یک پارامتر باشد، استفاده از Abbreviated Function Template ممکن است خواناتر باشد؛ اما برای Forwarding پیچیده، روش سنتی کنترل بیشتری فراهم می‌کند.

## نکات پیشرفته درباره Template Parameterها

### چند پارامتر مستقل

هر پارامتر `auto` در امضای تابع، یک پارامتر Template مستقل ایجاد می‌کند:

```
auto combine(auto first, auto second, auto third) {
    return first + second + third;
}
```

این تابع می‌تواند سه آرگومان با انواع متفاوت دریافت کند، به شرط آنکه عبارت جمع برای انواع استنتاج‌شده معتبر باشد.

در مقابل، اگر همه آرگومان‌ها باید از یک نوع باشند، استفاده از Template Parameter مشترک مناسب‌تر است:

```
template <typename T>
auto combine(T first, T second, T third) {
    return first + second + third;
}
```

این دو تعریف از نظر استنتاج نوع و مجموعه آرگومان‌های پذیرفته‌شده یکسان نیستند.

### وابستگی میان پارامترها

گاهی نوع یک پارامتر باید به نوع پارامتر دیگری وابسته باشد. در چنین مواردی، Templateهای صریح راه‌حل روشن‌تری ارائه می‌کنند:

```
template <typename T, typename U>
auto makePair(T first, U second) {
    return std::pair<T, U>{first, second};
}
```

در این مثال، استفاده از `T` و `U` برای تعریف نوع بازگشتی ضروری است. می‌توان در برخی موارد از `auto` برای نوع بازگشتی استفاده کرد، اما برای ساخت نوعی که مستقیماً به پارامترهای Template وابسته است، نام‌گذاری صریح آن‌ها معمولاً ساده‌تر خواهد بود.

### پارامترهای Template با مقادیر غیرنوعی

Abbreviated Function Templates فقط برای استنتاج نوع پارامترهای تابع کاربرد دارند و جایگزین تمام امکانات Template نیستند.

برای مثال، اگر تابع به یک پارامتر غیرنوعی مانند اندازه آرایه نیاز داشته باشد، می‌توان از Template Parameter صریح استفاده کرد:

```
template <typename T, std::size_t N>
void processArray(const T (&array)[N]) {
    // Process array
}
```

در این مثال، `N` یک Non-type Template Parameter است و تعداد عناصر آرایه را نگه می‌دارد.

استفاده از `auto` در فهرست پارامتر تابع نمی‌تواند جایگزین تعریف این پارامتر غیرنوعی شود.

## محدودیت‌ها و موارد نامناسب برای استفاده

### نبود نام صریح برای پارامتر Template

در Abbreviated Function Templates، پارامترهای Template به‌صورت ضمنی ایجاد می‌شوند. بنابراین، نمی‌توان به آن‌ها با نام‌هایی مانند `T` یا `U` ارجاع داد.

اگر پیاده‌سازی تابع به نام نوع نیاز داشته باشد، استفاده از Templateهای سنتی انتخاب مناسب‌تری است.

### محدودیت در بیان روابط میان انواع

زمانی که نوع پارامتر دوم باید دقیقاً با نوع پارامتر اول یکسان باشد، یا نوع بازگشتی بر اساس رابطه‌ای میان چند نوع تعیین شود، Templateهای صریح معمولاً خواناتر هستند.

در چنین شرایطی، استفاده از Abbreviated Function Templates ممکن است نیازمند محدودیت‌های پیچیده‌ای شود که در نهایت کد را دشوارتر از روش سنتی می‌کند.

### محدودیت در Partial Specialization

Function Templateها به‌طور مستقیم از Partial Specialization پشتیبانی نمی‌کنند؛ این محدودیت پیش از ++C20 نیز وجود داشته است.

اگر لازم باشد رفتار یک تابع بر اساس دسته خاصی از انواع تغییر کند، معمولاً از Overload، `Concepts`، `if constexpr` یا Class Templateهای کمکی استفاده می‌شود.

### محدودیت در کنترل دقیق نوع بازگشتی

نوع بازگشتی استنتاج‌شده با `auto` از قواعد مخصوص خود پیروی می‌کند. اگر لازم باشد نوع بازگشتی دقیقاً نوع مشخصی باشد یا Reference بودن آن حفظ شود، باید طراحی تابع را با دقت انجام داد.

برای مثال، در این تعریف:

```
auto getValue(auto& value) {
    return value;
}
```

نوع بازگشتی معمولاً از مقدار بدون Reference استنتاج می‌شود؛ بنابراین، Reference بودن پارامتر در نوع بازگشتی حفظ نمی‌شود.

اگر هدف بازگرداندن Reference باشد، می‌توان از `decltype(auto)` استفاده کرد:

```
decltype(auto) getValue(auto& value) {
    return value;
}
```

این فرم نوع بازگشتی را بر اساس قواعد `decltype` استنتاج می‌کند و در این مثال، Reference بودن مقدار بازگشتی حفظ می‌شود.

بااین‌حال، استفاده از `decltype(auto)` نیازمند دقت است، زیرا تفاوت‌های کوچک در عبارت `return` می‌توانند نوع بازگشتی را تغییر دهند.

## خطاهای رایج و روش جلوگیری از آن‌ها

### فرض اشتباه درباره یکسان بودن نوع پارامترها

یکی از اشتباهات رایج این است که تصور شود دو پارامتر `auto` الزاماً از یک نوع هستند.

درحالی‌که در تعریف زیر:

```
auto calculate(auto lhs, auto rhs) {
    return lhs + rhs;
}
```

دو پارامتر مستقل هستند و ممکن است نوع‌های متفاوتی داشته باشند.

اگر نوع مشترک لازم است، باید این محدودیت را صریحاً در طراحی تابع اعمال کرد.

### استفاده نادرست از Referenceها

استفاده از `auto value` می‌تواند باعث کپی شدن داده شود. این مسئله برای انواع بزرگ یا غیرقابل کپی ممکن است مشکل‌ساز باشد.

برای جلوگیری از کپی ناخواسته، می‌توان از `const auto&` استفاده کرد؛ اما اگر تابع باید داده را تغییر دهد، `auto&` مناسب‌تر است.

### فرض اینکه `auto&&` همیشه Forwarding کامل انجام می‌دهد

پارامتر `auto&&` می‌تواند Lvalueها و Rvalueها را بپذیرد، اما برای انتقال صحیح Value Category باید از `std::forward` استفاده شود.

استفاده از `std::move` در همه شرایط صحیح نیست، زیرا این تابع معمولاً آرگومان را به‌صورت Rvalue تبدیل می‌کند و ممکن است رفتار مورد انتظار برای Lvalueها را تغییر دهد.

### استفاده بیش از حد از Abbreviated Function Templates

کوتاه‌تر بودن کد همیشه به معنای طراحی بهتر نیست. اگر تابع به محدودیت‌های پیچیده، نوع بازگشتی وابسته یا روابط میان چند نوع نیاز داشته باشد، Templateهای صریح معمولاً خواناتر هستند.

بهترین انتخاب، روشی است که Interface تابع را واضح‌تر کند و محدودیت‌های آن را به شکل قابل فهم‌تری نشان دهد.

## ملاحظات سازگاری با کامپایلرها

قابلیت Abbreviated Function Templates بخشی از استاندارد ++C20 است. برای استفاده از آن باید کامپایلری در اختیار داشت که این بخش از استاندارد را پشتیبانی کند.

در کامپایلرهای متداول، فعال کردن حالت ++C20 معمولاً با گزینه‌های زیر انجام می‌شود:

```
g++ -std=c++20 main.cpp -o main
```

```
clang++ -std=c++20 main.cpp -o main
```

```
cl /std:c++20 /EHsc main.cpp
```

گزینه‌های بالا حالت زبان را برای کامپایلرهای مربوطه تنظیم می‌کنند؛ بااین‌حال، سطح پشتیبانی از ویژگی‌های ++C20 به نسخه کامپایلر و محیط ساخت وابسته است.

برای پروژه‌های واقعی، بهتر است از نسخه‌های جدید کامپایلر استفاده شود و پشتیبانی از ویژگی‌های مورد نیاز با مستندات رسمی همان پیاده‌سازی بررسی شود.

## جمع‌بندی

قابلیت Abbreviated Function Templates در ++C20 راهی ساده و خوانا برای تعریف توابع Generic فراهم می‌کند. با استفاده از `auto` در پارامترهای تابع، می‌توان بدون نوشتن صریح `template <typename T>` برای هر پارامتر، از استنتاج نوع و قابلیت‌های Template بهره برد.

این قابلیت در توابع کمکی، پردازش Rangeها، الگوریتم‌های Generic و APIهای ساده بسیار مفید است. همچنین ترکیب آن با `Concepts` می‌تواند محدودیت‌های تابع را به شکل روشن‌تری بیان کند.

بااین‌حال، Abbreviated Function Templates جایگزین کامل Templateهای سنتی نیستند. هنگامی که نام‌گذاری صریح پارامترهای Template، ارتباط میان چند نوع، کنترل دقیق نوع بازگشتی یا پارامترهای غیرنوعی لازم باشد، استفاده از Templateهای صریح معمولاً انتخاب مناسب‌تری خواهد بود.

در طراحی حرفه‌ای ++C، مهم‌ترین اصل این است که میان اختصار نحوی، خوانایی، کنترل نوع و شفافیت Interface تعادل برقرار شود. Abbreviated Function Templates زمانی بیشترین ارزش را دارند که بتوانند بدون پنهان کردن پیچیدگی‌های مهم، کد Generic را ساده‌تر و قابل نگهداری‌تر کنند.
