# بررسی ویژگی `[[likely]]` در ++C20

## مقدمه

ویژگی `[[likely]]` یکی از امکانات زبان ++C20 است که با هدف ارائه اطلاعات احتمالی درباره مسیرهای اجرای برنامه به Compiler معرفی شده است. این Attribute به Compiler اعلام می‌کند که یک مسیر اجرایی، مانند یک شاخه از شرط، به احتمال زیاد انتخاب خواهد شد.

در برنامه‌های ++C، تصمیم‌گیری درباره ترتیب اجرای دستورات و انتخاب شاخه‌های شرطی از بخش‌های مهم بهینه‌سازی کد است. Compilerها معمولاً با استفاده از اطلاعات آماری، تحلیل جریان کنترل و قابلیت‌هایی مانند Profile-Guided Optimization (PGO)، تلاش می‌کنند مسیرهای پرتکرار را به شکل مؤثرتری بهینه‌سازی کنند.

بااین‌حال، در برخی شرایط، اطلاعات کافی درباره الگوی اجرای برنامه در اختیار Compiler نیست. ویژگی `[[likely]]` امکان ارائه یک راهنمایی صریح توسط برنامه‌نویس را فراهم می‌کند.

این ویژگی بخشی از زبان ++C20 است و در گروه Standard Attributes قرار می‌گیرد.

نکته مهم این است که `[[likely]]` یک دستور برای کنترل جریان اجرا نیست؛ بلکه صرفاً یک Optimization Hint محسوب می‌شود. بنابراین، استفاده از آن نباید هیچ تغییری در رفتار قابل مشاهده برنامه ایجاد کند.

## مفهوم Attribute در ++C

در زبان ++C، Attributeها مکانیزمی استاندارد برای ارائه اطلاعات تکمیلی به Compiler هستند.

این اطلاعات می‌توانند به Compiler کمک کنند تا درباره نحوه پردازش کد، بهینه‌سازی یا بررسی برخی ویژگی‌های برنامه تصمیم‌گیری کند.

ساختار عمومی یک Attribute استاندارد به شکل زیر است:

```
[[attribute_name]]
```

برای مثال، ویژگی `[[nodiscard]]` به Compiler اعلام می‌کند که نادیده گرفتن مقدار بازگشتی یک تابع یا شیء مشخص‌شده ممکن است اشتباه باشد.

همچنین ویژگی `[[deprecated]]` برای علامت‌گذاری APIهایی استفاده می‌شود که استفاده از آن‌ها توصیه نمی‌شود.

ویژگی `[[likely]]` نیز در همین خانواده قرار دارد، اما هدف آن ارائه اطلاعات مربوط به احتمال اجرای مسیرهای مختلف برنامه است.

## معرفی ویژگی [[likely]]

ویژگی `[[likely]]` در استاندارد ++C20 معرفی شده است.

این ویژگی به Compiler اعلام می‌کند که مسیر اجرایی مشخص‌شده احتمالاً بیشتر از مسیرهای جایگزین اجرا خواهد شد.

ساختار استفاده از آن به شکل زیر است:

```
[[likely]]
```

این Attribute معمولاً در کنار Labelها یا دستورهای شرطی استفاده می‌شود.

### کاربرد در دستور if

یکی از رایج‌ترین کاربردهای `[[likely]]` مشخص کردن شاخه محتمل‌تر یک شرط است.

```
#include <iostream>

int main() {
    int value = 100;

    if (value > 0) [[likely]] {
        std::cout << "Positive value\n";
    } else {
        std::cout << "Non-positive value\n";
    }
}
```

در این مثال، برنامه‌نویس به Compiler اعلام می‌کند که انتظار دارد شرط `value > 0` معمولاً برقرار باشد.

در نتیجه، Compiler می‌تواند هنگام تولید کد ماشین، این اطلاعات را برای بهینه‌سازی مسیر محتمل‌تر در نظر بگیرد.

بااین‌حال، اگر مقدار `value` منفی باشد، شاخه `else` همچنان به‌درستی اجرا خواهد شد.

بنابراین، `[[likely]]` هیچ تأثیری بر نتیجه منطقی شرط ندارد.

### کاربرد در دستور else

در صورت تمایل می‌توان شاخه `else` را نیز به‌عنوان مسیر محتمل‌تر مشخص کرد.

```
#include <iostream>

int main() {
    int value = -10;

    if (value > 0) {
        std::cout << "Positive value\n";
    } else [[likely]] {
        std::cout << "Non-positive value\n";
    }
}
```

در این مثال، برنامه‌نویس پیش‌بینی می‌کند که شرط معمولاً برقرار نیست.

در نتیجه، شاخه `else` به‌عنوان مسیر محتمل‌تر معرفی شده است.

### کاربرد در switch

ویژگی `[[likely]]` در دستور `switch` نیز کاربرد دارد.

```
#include <iostream>

enum class Status {
    Success,
    Error,
    Pending
};

int main() {
    Status status = Status::Success;

    switch (status) {
        case Status::Success: [[likely]] {
            std::cout << "Operation completed\n";
            break;
        }

        case Status::Error: {
            std::cout << "Operation failed\n";
            break;
        }

        case Status::Pending: {
            std::cout << "Operation is pending\n";
            break;
        }
    }
}
```

در این مثال، مقدار `Status::Success` به‌عنوان مسیر محتمل‌تر معرفی شده است.

این موضوع می‌تواند برای Compiler در بهینه‌سازی مسیرهای مختلف دستور `switch` مفید باشد.

البته میزان تأثیر آن به پیاده‌سازی Compiler و ساختار کد ماشین تولیدشده بستگی دارد.

## معرفی ویژگی [[unlikely]]

ویژگی `[[unlikely]]` مکمل `[[likely]]` است و در ++C20 معرفی شده است.

این Attribute به Compiler اعلام می‌کند که مسیر اجرایی مشخص‌شده احتمالاً به‌ندرت انتخاب خواهد شد.

ساختار آن به شکل زیر است:

```
[[unlikely]]
```

برای مثال:

```
#include <iostream>

int main() {
    int value = -1;

    if (value < 0) [[unlikely]] {
        std::cerr << "Invalid value\n";
    } else {
        std::cout << "Valid value\n";
    }
}
```

در این مثال، برنامه‌نویس انتظار دارد که مقادیر منفی به‌ندرت رخ دهند.

بنابراین، شاخه مربوط به خطا با `[[unlikely]]` مشخص شده است.

این اطلاعات می‌تواند به Compiler کمک کند تا مسیر عادی اجرای برنامه را به شکل مؤثرتری بهینه‌سازی کند.

### مقایسه [[likely]] و [[unlikely]]

این دو Attribute از نظر هدف مکمل یکدیگر هستند.

| ویژگی          | مفهوم             | کاربرد                 |
| -------------- | ----------------- | ---------------------- |
| `[[likely]]`   | مسیر محتمل‌تر     | مسیر عادی و پرتکرار    |
| `[[unlikely]]` | مسیر کم‌احتمال‌تر | خطاها و شرایط استثنایی |

برای مثال، در یک تابع پردازش درخواست، ممکن است دریافت درخواست معتبر بسیار رایج‌تر از دریافت درخواست نامعتبر باشد.

```
#include <iostream>

bool processRequest(int request) {
    if (request < 0) [[unlikely]] {
        std::cerr << "Invalid request\n";
        return false;
    }

    [[likely]] return true;
}

int main() {
    processRequest(10);
}
```

در این مثال، مسیر نامعتبر به‌عنوان مسیر کم‌احتمال مشخص شده است.

همچنین مسیر بازگشت موفق به‌عنوان مسیر محتمل‌تر معرفی شده است.

بااین‌حال، استفاده از `[[likely]]` روی دستور `return` باید با توجه به قواعد Attributeها و ساختار واقعی کد انجام شود؛ در اینجا Attribute به statement مربوط است، نه به خود مقدار بازگشتی.

## نحوه عملکرد داخلی Attributeها

ویژگی‌های `[[likely]]` و `[[unlikely]]` مستقیماً نحوه اجرای برنامه را تغییر نمی‌دهند.

این ویژگی‌ها اطلاعاتی درباره احتمال اجرای مسیرهای مختلف در اختیار Compiler قرار می‌دهند.

### تأثیر بر Code Generation

Compiler می‌تواند از این اطلاعات برای تصمیم‌گیری درباره نحوه تولید کد ماشین استفاده کند.

برای مثال، در پردازنده‌های مدرن، ترتیب قرارگیری دستورها در حافظه می‌تواند بر کارایی اجرای برنامه تأثیر بگذارد.

یکی از اهداف بهینه‌سازی این است که مسیرهای پرتکرار در ساختار کد تولیدشده، دسترسی و اجرای مناسبی داشته باشند.

در چنین شرایطی، Compiler ممکن است از Hintهای ارائه‌شده برای موارد زیر استفاده کند:

- بهبود ترتیب قرارگیری Basic Blockها
- بهینه‌سازی Branch Layout
- کاهش هزینه اجرای مسیرهای پرتکرار
- بهبود Instruction Cache Locality
- بهینه‌سازی برخی تصمیم‌های مربوط به Branch Prediction

البته هیچ‌کدام از این موارد تضمین‌شده نیستند.

### ارتباط با Branch Prediction

در پردازنده‌های مدرن، Branch Prediction مکانیزمی سخت‌افزاری است که تلاش می‌کند مسیر بعدی اجرای برنامه را پیش‌بینی کند.

این قابلیت به پردازنده اجازه می‌دهد بخشی از دستورهای مسیر احتمالی را پیش از مشخص شدن قطعی نتیجه شرط پردازش کند.

اگر پیش‌بینی اشتباه باشد، پردازنده ممکن است مجبور شود بخشی از کار انجام‌شده را کنار بگذارد و مسیر صحیح را ادامه دهد.

این اتفاق می‌تواند باعث افزایش هزینه اجرای برنامه شود.

ویژگی `[[likely]]` ممکن است به Compiler در تولید کدی کمک کند که با مسیرهای پرتکرار سازگاری بیشتری داشته باشد.

بااین‌حال، باید توجه داشت که این Attribute مستقیماً دستور یا فرمانی برای تنظیم سخت‌افزار Branch Predictor نیست.

همچنین هیچ تضمینی وجود ندارد که Compiler این Hint را به یک دستور سخت‌افزاری خاص تبدیل کند.

### ارتباط با Basic Block

در Compilerها، کد برنامه معمولاً به بخش‌هایی به نام Basic Block تقسیم می‌شود.

هر Basic Block مجموعه‌ای از دستورهای متوالی است که ورود به آن از ابتدا انجام می‌شود و خروج از آن معمولاً در انتهای بلوک اتفاق می‌افتد.

دستورهای شرطی می‌توانند باعث ایجاد چند Basic Block و مسیر مختلف در Control Flow Graph شوند.

اطلاعات مربوط به احتمال اجرای مسیرها می‌تواند برای مرتب‌سازی و بهینه‌سازی این بلوک‌ها استفاده شود.

برای مثال، Compiler ممکن است مسیر پرتکرار را به شکلی قرار دهد که جریان اجرای برنامه کارآمدتر باشد.

## قواعد و محدودیت‌های استفاده

ویژگی‌های `[[likely]]` و `[[unlikely]]` دارای قواعد مشخصی در استاندارد ++C هستند.

این قواعد اهمیت زیادی دارند؛ زیرا Attributeها صرفاً نشانه‌های تزئینی نیستند و محل قرارگیری آن‌ها در ساختار کد اهمیت دارد.

### استفاده در Statement

این دو Attribute از نوع Statement Attribute هستند.

بنابراین، باید در موقعیتی قرار بگیرند که از نظر قواعد زبان به یک Statement یا Label مربوط باشند.

برای مثال:

```
if (condition) [[likely]] {
    performOperation();
}
```

همچنین می‌توان آن‌ها را در کنار `else` به کار برد:

```
if (condition) {
    handleError();
} else [[likely]] {
    performSuccess();
}
```

### استفاده در Labelها

این Attributeها را می‌توان برای Labelهای دستور `switch` نیز استفاده کرد.

```
switch (status) {
    case 0: [[likely]]
        handleSuccess();
        break;

    case 1: [[unlikely]]
        handleFailure();
        break;
}
```

در این مثال، مسیر مربوط به `case 0` محتمل‌تر و مسیر مربوط به `case 1` کم‌احتمال‌تر معرفی شده است.

### استفاده روی دستورات مستقل

این ویژگی‌ها محدود به دستورات شرطی نیستند و می‌توانند روی Statementهای مستقل نیز استفاده شوند.

```
#include <iostream>

int main() {
    [[likely]] std::cout << "Normal execution\n";
}
```

در این مثال، Attribute به Statement مربوط به چاپ پیام متصل شده است.

البته چنین استفاده‌ای معمولاً در مقایسه با مشخص کردن شاخه‌های شرطی، اطلاعات محدودتری برای بهینه‌سازی فراهم می‌کند.

### استفاده هم‌زمان از دو Attribute

نباید یک Statement یا Label را به‌صورت متناقض با هر دو Attribute مشخص کرد.

برای مثال:

```
// Do not use contradictory likelihood attributes.
```

استفاده هم‌زمان از `[[likely]]` و `[[unlikely]]` روی یک Statement از نظر معنایی متناقض است و نباید در کد استاندارد و قابل‌حمل استفاده شود.

## مقایسه با روش‌های قدیمی‌تر

پیش از معرفی `[[likely]]` و `[[unlikely]]` در ++C20، برخی Compilerها از امکانات اختصاصی خود برای ارائه Branch Prediction Hint پشتیبانی می‌کردند.

این امکانات معمولاً وابسته به Compiler بودند و قابلیت حمل‌پذیری یکسانی نداشتند.

### مقایسه با \_\_builtin_expect

در GCC و Clang، تابع داخلی `__builtin_expect` برای ارائه اطلاعات احتمالی به Compiler استفاده می‌شود.

نمونه:

```
#include <iostream>

int main() {
    int value = 10;

    if (__builtin_expect(value == 0, 0)) {
        std::cerr << "Unexpected zero\n";
    } else {
        std::cout << "Normal execution\n";
    }
}
```

در این مثال، آرگومان دوم به Compiler اعلام می‌کند که انتظار می‌رود عبارت اول مقدار صفر داشته باشد یا نداشته باشد.

در اینجا مقدار مورد انتظار صفر است؛ بنابراین شرط `value == 0` به‌عنوان مسیر کم‌احتمال معرفی شده است.

این Built-in بخشی از استاندارد ++C نیست.

در مقابل، `[[likely]]` و `[[unlikely]]` امکانات استاندارد زبان هستند.

### مقایسه روش‌ها

| ویژگی               | `[[likely]]` | `[[unlikely]]` | `__builtin_expect`       |
| ------------------- | ------------ | -------------- | ------------------------ |
| استاندارد           | ++C20        | ++C20          | Compiler-specific        |
| قابلیت حمل          | استاندارد    | استاندارد      | وابسته به Compiler       |
| خوانایی             | بالا         | بالا           | پایین‌تر                 |
| کاربرد اصلی         | مسیر پرتکرار | مسیر کم‌تکرار  | ارائه احتمال مورد انتظار |
| وابستگی به Compiler | ندارد        | ندارد          | دارد                     |

برای کدهای جدید و قابل‌حمل، استفاده از Attributeهای استاندارد معمولاً انتخاب مناسب‌تری است.

البته در پروژه‌هایی که به امکانات خاص Compiler وابسته هستند، ممکن است Built-inها همچنان کاربرد داشته باشند.

## ارتباط با Profile-Guided Optimization

یکی از مهم‌ترین موضوعات مرتبط با `[[likely]]`، قابلیت Profile-Guided Optimization یا PGO است.

این تکنیک به Compiler اجازه می‌دهد با استفاده از اطلاعات واقعی اجرای برنامه، تصمیم‌های بهینه‌سازی دقیق‌تری بگیرد.

### مفهوم PGO

در روش PGO، برنامه ابتدا با ابزارهای مخصوص Instrument می‌شود تا اطلاعاتی درباره رفتار واقعی آن جمع‌آوری شود.

این اطلاعات می‌تواند شامل موارد زیر باشد:

- تعداد دفعات اجرای توابع
- تعداد دفعات انتخاب شاخه‌های شرطی
- مسیرهای پرتکرار برنامه
- الگوی اجرای حلقه‌ها
- فراوانی مسیرهای مختلف Control Flow

سپس Compiler از این اطلاعات هنگام ساخت نسخه نهایی برنامه استفاده می‌کند.

### تفاوت PGO و [[likely]]

تفاوت اصلی این دو روش در منبع اطلاعات مورد استفاده است.

در `[[likely]]`، برنامه‌نویس بر اساس دانش خود درباره رفتار برنامه یک Hint ارائه می‌دهد.

اما در PGO، اطلاعات می‌تواند از اجرای واقعی برنامه و Workloadهای مشخص به دست آید.

| معیار                     | `[[likely]]`           | PGO                     |
| ------------------------- | ---------------------- | ----------------------- |
| منبع اطلاعات              | پیش‌بینی برنامه‌نویس   | داده واقعی اجرای برنامه |
| نیاز به اجرای آزمایشی     | خیر                    | معمولاً بله             |
| دقت بالقوه                | وابسته به صحت پیش‌بینی | وابسته به کیفیت Profile |
| هزینه آماده‌سازی          | پایین                  | بالاتر                  |
| قابلیت انطباق با Workload | محدود                  | بیشتر                   |

در پروژه‌های بزرگ و Performance-Critical، استفاده از PGO می‌تواند مؤثرتر از Hintهای دستی باشد.

البته PGO نیز در صورتی نتایج مناسبی ارائه می‌دهد که داده‌های Profile نماینده رفتار واقعی کاربران و محیط تولید باشند.

## کاربردهای عملی

ویژگی‌های `[[likely]]` و `[[unlikely]]` در برخی موقعیت‌های خاص می‌توانند مفید باشند.

### مدیریت خطا

یکی از کاربردهای مناسب، مشخص کردن مسیرهای خطا به‌عنوان مسیرهای کم‌احتمال است.

```
#include <iostream>
#include <stdexcept>

int divide(int numerator, int denominator) {
    if (denominator == 0) [[unlikely]] {
        throw std::invalid_argument("Division by zero");
    }

    return numerator / denominator;
}

int main() {
    std::cout << divide(20, 4) << '\n';
}
```

در این مثال، فرض شده است که تقسیم بر صفر به‌ندرت اتفاق می‌افتد.

بنابراین، مسیر خطا با `[[unlikely]]` مشخص شده است.

این روش ممکن است به Compiler در بهینه‌سازی مسیر عادی کمک کند.

### پردازش درخواست‌های شبکه

در سیستم‌های Network Server ممکن است بیشتر درخواست‌ها معتبر باشند و تنها درصد کمی از درخواست‌ها با خطا مواجه شوند.

```
#include <string_view>

bool validateRequest(std::string_view request) {
    if (request.empty()) [[unlikely]] {
        return false;
    }

    return true;
}
```

در این مثال، درخواست خالی به‌عنوان حالت کم‌احتمال در نظر گرفته شده است.

البته این فرض باید بر اساس رفتار واقعی سیستم باشد.

### پردازش داده‌های پرتکرار

در پردازش داده‌های حجیم ممکن است یک مقدار یا وضعیت خاص بسیار پرتکرارتر از سایر وضعیت‌ها باشد.

```
#include <cstdint>

std::uint32_t processValue(std::uint32_t value) {
    if (value != 0) [[likely]] {
        return value * 2;
    }

    return 0;
}
```

در این مثال، فرض شده است که بیشتر مقادیر ورودی غیرصفر هستند.

در نتیجه، مسیر پردازش مقادیر غیرصفر به‌عنوان مسیر محتمل‌تر معرفی شده است.

### حلقه‌های پردازشی

در الگوریتم‌هایی که تعداد زیادی تکرار دارند، ممکن است یک شرط در بیشتر دفعات به شکل مشخصی ارزیابی شود.

```
#include <cstddef>
#include <vector>

std::size_t countPositive(const std::vector<int>& values) {
    std::size_t count = 0;

    for (int value : values) {
        if (value > 0) [[likely]] {
            ++count;
        }
    }

    return count;
}
```

در این مثال، فرض شده است که بیشتر مقادیر مثبت هستند.

اگر این فرض با داده‌های واقعی سازگار باشد، Compiler می‌تواند از آن برای بهینه‌سازی استفاده کند.

بااین‌حال، تأثیر Attribute در حلقه‌های بزرگ باید با Benchmark بررسی شود.

## اشتباهات رایج

استفاده نادرست از Branch Prediction Hint می‌تواند نه‌تنها بی‌فایده باشد، بلکه در برخی شرایط موجب کاهش کارایی شود.

### استفاده بدون شناخت Workload

یکی از اشتباهات رایج، استفاده از `[[likely]]` بر اساس حدس شخصی است.

برای مثال، ممکن است برنامه‌نویس تصور کند که یک شرط تقریباً همیشه برقرار است؛ اما داده‌های واقعی نشان دهند که دو شاخه تقریباً به یک اندازه اجرا می‌شوند.

در چنین شرایطی، Hint ارائه‌شده می‌تواند با رفتار واقعی برنامه ناسازگار باشد.

بهتر است قبل از استفاده، رفتار برنامه با Profiling بررسی شود.

### تصور تضمین افزایش سرعت

ویژگی `[[likely]]` تضمین نمی‌کند که برنامه سریع‌تر اجرا شود.

Compiler می‌تواند این اطلاعات را نادیده بگیرد یا تصمیم بگیرد که روش دیگری برای بهینه‌سازی مناسب‌تر است.

بنابراین، نباید صرفاً با افزودن این Attribute انتظار بهبود Performance داشت.

### استفاده بیش‌ازحد

قرار دادن `[[likely]]` و `[[unlikely]]` روی تعداد زیادی از دستورات می‌تواند ارزش اطلاعاتی آن‌ها را کاهش دهد.

این Hintها زمانی مفیدتر هستند که برای مسیرهای مهم و دارای تفاوت احتمالی مشخص استفاده شوند.

### استفاده برای کنترل اجرای برنامه

یکی از اشتباهات مهم، تصور این است که `[[likely]]` باعث می‌شود یک شاخه حتماً زودتر یا بیشتر اجرا شود.

این تصور نادرست است.

برای مثال:

```
#include <iostream>

int main() {
    bool condition = false;

    if (condition) [[likely]] {
        std::cout << "First branch\n";
    } else {
        std::cout << "Second branch\n";
    }
}
```

در این مثال، با وجود استفاده از `[[likely]]`، شاخه دوم اجرا می‌شود؛ زیرا مقدار شرط `false` است.

رفتار منطقی برنامه همچنان توسط مقدار شرط تعیین می‌شود.

### جایگزین کردن Profiling با Hint دستی

در برنامه‌های پیچیده، رفتار واقعی کاربران ممکن است با پیش‌بینی توسعه‌دهندگان تفاوت داشته باشد.

در چنین پروژه‌هایی، اتکا به Hintهای دستی به‌جای Profiling می‌تواند تصمیم‌های بهینه‌سازی نامناسبی ایجاد کند.

برای بهینه‌سازی حرفه‌ای، اندازه‌گیری واقعی باید اولویت داشته باشد.

## محدودیت‌های ویژگی‌های Likelihood

ویژگی‌های `[[likely]]` و `[[unlikely]]` دارای محدودیت‌های مهمی هستند که باید هنگام طراحی نرم‌افزار در نظر گرفته شوند.

### عدم تضمین نتیجه

استاندارد ++C تضمین نمی‌کند که Compiler حتماً Hint ارائه‌شده را در Code Generation اعمال کند.

بنابراین، این ویژگی‌ها نباید برای دستیابی به یک رفتار مشخص در سطح ماشین استفاده شوند.

### وابستگی به Compiler و Target Architecture

نحوه استفاده از این اطلاعات ممکن است بین Compilerهای مختلف متفاوت باشد.

همچنین معماری پردازنده، قابلیت‌های سخت‌افزاری، Optimization Level و ساختار برنامه می‌توانند بر میزان تأثیر این Hintها اثر بگذارند.

### وابستگی به داده‌های ورودی

اگر الگوی داده‌های ورودی تغییر کند، مسیر محتمل برنامه نیز ممکن است تغییر کند.

برای مثال، برنامه‌ای که در محیط توسعه معمولاً درخواست‌های معتبر دریافت می‌کند، ممکن است در محیط تولید با حجم زیادی از درخواست‌های نامعتبر مواجه شود.

در چنین شرایطی، Hintهای دستی قدیمی ممکن است دیگر مناسب نباشند.

### عدم تغییر در Semantics

این Attributeها نباید بر موارد زیر تأثیر بگذارند:

- نتیجه منطقی شرط‌ها
- ترتیب معنایی اجرای دستورات
- قوانین Exception Handling
- صحت محاسبات
- رفتار قابل مشاهده برنامه

هر کدی که تنها به دلیل وجود `[[likely]]` یا `[[unlikely]]` رفتار متفاوتی داشته باشد، از نظر استفاده صحیح از این Attributeها مشکل دارد.

## بررسی Performance با Benchmark

بهترین روش برای تشخیص مفید بودن `[[likely]]`، مقایسه عملکرد برنامه در شرایط یکسان است.

برای این کار باید نسخه‌ای از برنامه بدون Hint و نسخه‌ای با Hint مناسب ساخته شود.

### نمونه کد برای آزمایش

```
#include <cstddef>
#include <cstdint>
#include <vector>

std::uint64_t countWithoutHint(const std::vector<int>& values) {
    std::uint64_t count = 0;

    for (int value : values) {
        if (value > 0) {
            ++count;
        }
    }

    return count;
}

std::uint64_t countWithHint(const std::vector<int>& values) {
    std::uint64_t count = 0;

    for (int value : values) {
        if (value > 0) [[likely]] {
            ++count;
        }
    }

    return count;
}
```

در این مثال، دو تابع رفتار یکسانی دارند؛ اما یکی از آن‌ها از Hint استفاده می‌کند.

برای ارزیابی دقیق باید شرایط زیر رعایت شوند:

- داده‌های ورودی در هر دو آزمایش یکسان باشند.
- تعداد تکرارهای Benchmark کافی باشد.
- نتایج چندین بار اندازه‌گیری شوند.
- تأثیر Cache و سایر عوامل سخت‌افزاری در نظر گرفته شود.
- Compiler و Optimization Level یکسان باشند.
- از حذف محاسبات توسط Optimizer جلوگیری شود.

همچنین بهتر است آزمایش در شرایطی انجام شود که الگوی داده‌ها نماینده Workload واقعی باشد.

نکته مهم این است که Compiler ممکن است در هر دو نسخه کد ماشین مشابهی تولید کند. در این حالت، تفاوت عملکردی قابل‌اندازه‌گیری وجود نخواهد داشت.

## پشتیبانی Compilerها

ویژگی‌های `[[likely]]` و `[[unlikely]]` از امکانات استاندارد ++C20 هستند.

برای استفاده از آن‌ها باید Compiler از ++C20 و Attributeهای مربوطه پشتیبانی کند.

در Compilerهای رایج مانند موارد زیر، این قابلیت در نسخه‌های مدرن وجود دارد:

- GCC
- Clang
- Microsoft Visual C++

برای فعال‌سازی حالت ++C20 در GCC و Clang معمولاً می‌توان از دستور زیر استفاده کرد:

```
g++ -std=c++20 main.cpp -O2 -o app
```

یا:

```
clang++ -std=c++20 main.cpp -O2 -o app
```

در Microsoft Visual C++ نیز می‌توان از گزینه زیر استفاده کرد:

```
cl /std:c++20 /O2 main.cpp
```

نکته مهم این است که پشتیبانی از استاندارد ++C20 و میزان استفاده واقعی Compiler از Hintها دو موضوع متفاوت هستند.

حتی اگر Compiler این Attributeها را به‌درستی بپذیرد، لزوماً به این معنا نیست که در تمام شرایط بهینه‌سازی قابل‌اندازه‌گیری انجام خواهد داد.

## توصیه‌های طراحی و استفاده حرفه‌ای

برای استفاده صحیح از `[[likely]]` و `[[unlikely]]` بهتر است اصول زیر رعایت شوند:

- از `[[likely]]` برای مسیرهایی استفاده کنید که واقعاً پرتکرار هستند.
- از `[[unlikely]]` برای مسیرهای استثنایی و کم‌تکرار استفاده کنید.
- در صورت امکان، از داده‌های Profiling برای تعیین احتمال مسیرها استفاده کنید.
- در کدهای Performance-Critical، نتیجه استفاده از Hintها را با Benchmark بررسی کنید.
- از استفاده غیرضروری و گسترده از این Attributeها خودداری کنید.
- برای کنترل رفتار برنامه از شرط‌ها و سازوکارهای استاندارد زبان استفاده کنید، نه از Likelihood Attributeها.
- در کتابخانه‌های عمومی، از فرض‌های غیرواقعی درباره الگوی داده‌های مصرف‌کنندگان اجتناب کنید.
- هنگام تغییر Workload برنامه، مناسب بودن Hintهای قبلی را دوباره بررسی کنید.

## جمع‌بندی

ویژگی‌های `[[likely]]` و `[[unlikely]]` در استاندارد ++C20 معرفی شده‌اند تا برنامه‌نویسان بتوانند اطلاعاتی درباره احتمال اجرای مسیرهای مختلف برنامه در اختیار Compiler قرار دهند.

این Attributeها به‌ترتیب برای مشخص کردن مسیرهای محتمل‌تر و کم‌احتمال‌تر استفاده می‌شوند.

مهم‌ترین مزیت آن‌ها ارائه یک روش استاندارد، خوانا و قابل‌حمل برای بیان Branch Prediction Hint است.

بااین‌حال، این ویژگی‌ها هیچ تضمینی برای افزایش سرعت برنامه ندارند و رفتار منطقی برنامه را نیز تغییر نمی‌دهند.

در پروژه‌های حرفه‌ای، بهتر است این Attributeها در کنار Profiling، Benchmark و تکنیک‌های مناسب Performance Optimization استفاده شوند.

**نکته نهایی:** استفاده از `[[likely]]` و `[[unlikely]]` باید نتیجه شناخت رفتار واقعی برنامه باشد، نه صرفاً یک حدس درباره مسیرهای اجرایی. در بهینه‌سازی ++C، اندازه‌گیری و تحلیل عملکرد واقعی همیشه از فرضیات ذهنی قابل‌اعتمادتر است.
