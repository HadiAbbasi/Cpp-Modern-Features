# معرفی `char8_t` در ++C20

نوع `char8_t` در استاندارد ++C20 برای نمایش واحدهای کدگذاری‌شدهٔ متن در قالب UTF-8 معرفی شد. این نوع، تفاوت میان داده‌های متنی UTF-8 و داده‌های متنی مبتنی بر `char` را در سطح سیستم نوع زبان مشخص می‌کند و به توسعه‌دهندگان اجازه می‌دهد متن UTF-8 را به‌شکل صریح‌تری در APIها، کتابخانه‌ها و ساختارهای داده مدیریت کنند.

## مفهوم و هدف اصلی `char8_t`

پیش از استاندارد ++C20، برنامه‌نویسان معمولاً برای نگهداری داده‌های UTF-8 از `char` و `std::string` استفاده می‌کردند. این روش رایج بود، اما نوع داده به‌تنهایی مشخص نمی‌کرد که محتوای رشته از UTF-8، یک encoding دیگر یا داده‌های باینری تشکیل شده است.

برای مثال، رشتهٔ زیر از نظر نوع داده تفاوتی با رشته‌ای شامل داده‌های متنی با encoding دیگر ندارد:

```
#include <string>

int main() {
    std::string text = "Hello";
}
```

در این مثال، نوع `std::string` فقط مجموعه‌ای از اشیای `char` را نگهداری می‌کند و تضمینی دربارهٔ encoding متن ارائه نمی‌دهد.

استاندارد ++C20 نوع مستقل `char8_t` را معرفی کرد تا واحدهای کد UTF-8 از نوع عمومی `char` متمایز شوند. این جداسازی به کامپایلر اجازه می‌دهد برخی اشتباهات مربوط به ترکیب ناخواستهٔ انواع متنی را در زمان کامپایل تشخیص دهد.

```
#include <string>

int main() {
    std::u8string text = u8"Hello";
}
```

در این مثال، پیشوند `u8` مشخص می‌کند که literal متنی از نوع UTF-8 است و `std::u8string` برای نگهداری واحدهای کد آن به کار می‌رود.

## تعریف نوع و ویژگی‌های زبانی

نوع `char8_t` از ++C20 یک نوع صحیح مستقل است که برای نگهداری یک واحد کد UTF-8 طراحی شده است. این نوع از نظر ساختار زبانی، یک نوع صحیح متمایز است و صرفاً نام مستعار `char` محسوب نمی‌شود.

ویژگی‌های مهم این نوع عبارت‌اند از:

- معرفی در استاندارد: این نوع از ++C20 در دسترس است.
- اندازه: اندازهٔ `char8_t` دقیقاً یک بایت زبان ++C است؛ یعنی `sizeof(char8_t) == 1`.
- متمایز بودن نوع: این نوع با `char` یکسان نیست و تبدیل ضمنی میان آن‌ها انجام نمی‌شود.
- هدف اصلی: نمایش واحدهای کد UTF-8، نه نمایش یک نویسهٔ کامل Unicode.
- قابلیت استفاده در آرایه‌ها و رشته‌ها: می‌توان از آن برای ساخت آرایه‌های متنی، اشاره‌گرها و انواع رشته‌ای استاندارد استفاده کرد.

نوع `char8_t` با `unsigned char` نیز یکسان نیست، هرچند هر دو برای کاربردهایی که با مقادیر بایتی سروکار دارند می‌توانند مفید باشند. انتخاب نوع مناسب باید بر اساس معنای داده و قرارداد API انجام شود.

## تفاوت `char8_t` با `char` و `unsigned char`

برای انتخاب صحیح نوع داده، باید تفاوت میان این سه نوع را از نظر معنای داده، تبدیل‌ها و کاربردهای عملی در نظر گرفت.

| ویژگی                     | `char`                                   | `unsigned char`                         | `char8_t`                                     |
| ------------------------- | ---------------------------------------- | --------------------------------------- | --------------------------------------------- |
| زمان معرفی                | نسخه‌های اولیهٔ ++C                      | نسخه‌های اولیهٔ ++C                     | ++C20                                         |
| نوع مستقل                 | بله                                      | بله                                     | بله                                           |
| نوع صحیح بدون علامت       | خیر؛ signedness وابسته به پیاده‌سازی است | بله                                     | بله                                           |
| هدف اصلی                  | داده‌های نویسه‌ای و متنی عمومی           | داده‌های بایتی و مقادیر صحیح بدون علامت | واحدهای کد UTF-8                              |
| تبدیل ضمنی با دو نوع دیگر | مطابق قواعد تبدیل صحیح                   | مطابق قواعد تبدیل صحیح                  | تبدیل ضمنی به `char` یا `unsigned char` ندارد |
| نوع عناصر `std::string`   | `char`                                   | قابل استفاده در `std::basic_string`     | `char8_t` در `std::u8string`                  |

توجه داشته باشید که `char8_t` برای نمایش یک واحد کد UTF-8 تعریف شده است، نه برای نمایش مستقیم یک نویسهٔ کامل. در UTF-8، یک نویسه ممکن است با یک تا چهار واحد کد نمایش داده شود.

### بررسی تفاوت نوع‌ها در زمان کامپایل

کد زیر نشان می‌دهد که `char8_t` و `char` دو نوع متمایز هستند:

```
#include <type_traits>

static_assert(!std::is_same_v<char8_t, char>);
static_assert(!std::is_same_v<char8_t, unsigned char>);
static_assert(sizeof(char8_t) == 1);

int main() {
    char ch = 'A';
    char8_t utf8 = u8'A';

    // Explicit conversion is required.
    unsigned char byte = static_cast<unsigned char>(utf8);

    (void)ch;
    (void)byte;
}
```

در این مثال، تبدیل صریح به `unsigned char` مقدار عددی واحد کد را منتقل می‌کند؛ بااین‌حال، چنین تبدیلی به‌تنهایی هیچ تضمینی دربارهٔ اعتبار یک رشتهٔ UTF-8 ایجاد نمی‌کند.

## معرفی literalهای متنی UTF-8

در ++C، پیشوند `u8` برای تعریف literalهای متنی UTF-8 استفاده می‌شود. رفتار نوع این literalها در ++C20 تغییر مهمی داشته است.

```
auto text = u8"Hello";
```

نوع `text` در این مثال `const char8_t*` است؛ زیرا literal متنی به آرایه‌ای از `const char8_t` تبدیل می‌شود که در عبارت معمولی به اشاره‌گر به اولین عنصر تبدیل می‌شود.

### تفاوت نسخه‌های استاندارد

| استاندارد               | نوع عناصر literal متنی `u8` |
| ----------------------- | --------------------------- |
| ++C11 و ++C14           | `char`                      |
| ++C17                   | `char`                      |
| ++C20 و نسخه‌های جدیدتر | `char8_t`                   |

این تغییر برای سازگاری کدهای قدیمی اهمیت زیادی دارد. برنامه‌ای که در ++C17 از `u8"Hello"` به‌عنوان `const char*` استفاده می‌کرد، ممکن است پس از انتقال به ++C20 دیگر کامپایل نشود.

### انواع مختلف literal متنی

زبان ++C چند پیشوند متنی برای encodingهای متفاوت ارائه می‌دهد:

| پیشوند      | نوع عنصر در ++C20 | هدف                                     |
| ----------- | ----------------- | --------------------------------------- |
| بدون پیشوند | `char`            | literal متنی معمولی                     |
| `u8`        | `char8_t`         | UTF-8                                   |
| `u`         | `char16_t`        | UTF-16                                  |
| `U`         | `char32_t`        | UTF-32                                  |
| `L`         | `wchar_t`         | نوع نویسهٔ گستردهٔ وابسته به پیاده‌سازی |

نکتهٔ مهم این است که `u8` به‌تنهایی تضمین نمی‌کند فایل منبع با encoding صحیح ذخیره شده یا دادهٔ دریافتی از شبکه UTF-8 معتبر است. رفتار encoding فایل منبع و نحوهٔ تفسیر نویسه‌های آن نیز به قواعد استاندارد و تنظیمات مربوط به پیاده‌سازی وابسته است.

## معرفی `std::u8string` و انواع مرتبط

کتابخانهٔ استاندارد ++C20 نوع‌های رشته‌ای متناظر با `char8_t` را در اختیار برنامه‌نویس قرار می‌دهد.

| نوع                               | مفهوم                                        |
| --------------------------------- | -------------------------------------------- |
| `std::u8string`                   | رشته‌ای از عناصر `char8_t`                   |
| `std::u8string_view`              | نمای غیرمالک بر دنباله‌ای از عناصر `char8_t` |
| `std::basic_string<char8_t>`      | قالب عمومی رشته با عنصر `char8_t`            |
| `std::basic_string_view<char8_t>` | قالب عمومی نمای رشته با عنصر `char8_t`       |

برای استفاده از این نوع‌ها می‌توان از هدرهای استاندارد `<string>` و `<string_view>` بهره گرفت.

```
#include <iostream>
#include <string>
#include <string_view>

int main() {
    std::u8string text = u8"Hello";
    std::u8string_view view = text;

    std::cout << "Code units: " << view.size() << '\n';
}
```

در این مثال، رشتهٔ `text` مالک حافظه است، درحالی‌که `view` فقط نمایی از داده‌های آن را نگهداری می‌کند. طول رشته برحسب تعداد عناصر `char8_t` محاسبه می‌شود، نه تعداد نویسه‌های Unicode.

همچنین `std::cout` در این مثال فقط متن ASCII ثابت را چاپ می‌کند؛ چاپ مستقیم رشتهٔ `char8_t` از طریق جریان‌های معمولی `char` به این شکل پشتیبانی نمی‌شود.

### تفاوت طول رشته و تعداد نویسه‌ها

در UTF-8، مقدار بازگشتی از `size()` تعداد واحدهای کد است. این مقدار الزاماً با تعداد code pointها یا تعداد نویسه‌های قابل مشاهده برابر نیست.

```
#include <iostream>
#include <string>

int main() {
    std::u8string text = u8"é";

    std::cout << text.size() << '\n';
}
```

در این مثال، اگر `é` به شکل نویسهٔ Unicode با مقدار `U+00E9` در literal منبع حضور داشته باشد، encoding استاندارد UTF-8 آن دو واحد کد دارد؛ بنابراین مقدار `size()` برابر با `2` خواهد بود.

اما شکل ظاهری مشابه ممکن است با ترکیب `e` و علامت ترکیبی accent نیز ساخته شود. در این حالت تعداد واحدهای کد متفاوت خواهد بود، هرچند متن ممکن است از نظر بصری یکسان دیده شود.

برای شمارش code pointها یا محاسبهٔ تعداد نویسه‌های قابل مشاهده، باید از الگوریتم‌های آگاه از Unicode استفاده کرد؛ `std::u8string` به‌تنهایی چنین قابلیتی ندارد.

## مفهوم encoding و واحد کد در UTF-8

برای استفادهٔ صحیح از `char8_t` باید میان سه مفهوم زیر تفاوت قائل شد:

- Code unit: واحدی که encoding برای ذخیره‌سازی استفاده می‌کند. در UTF-8، هر واحد کد یک بایت زبان ++C است.
- Code point: مقدار عددی یک نویسه در فضای کد Unicode، مانند `U+0041` برای `A`.
- Grapheme cluster: واحدی که معمولاً به‌صورت یک نویسهٔ قابل مشاهده در متن ظاهر می‌شود و ممکن است از چند code point تشکیل شده باشد.

برای نمونه، نویسهٔ `A` در UTF-8 با یک واحد کد نمایش داده می‌شود، اما برخی نویسه‌های دیگر به چند واحد کد نیاز دارند.

```
#include <iostream>
#include <string>

int main() {
    std::u8string ascii = u8"A";
    std::u8string non_ascii = u8"€";
    std::u8string supplementary = u8"😀";

    std::cout << ascii.size() << '\n';
    std::cout << non_ascii.size() << '\n';
    std::cout << supplementary.size() << '\n';
}
```

با فرض آنکه literalهای منبع دقیقاً شامل همین نویسه‌ها باشند، خروجی به‌ترتیب `1`، `3` و `4` خواهد بود.

بنابراین، نباید از `size()` برای محاسبهٔ تعداد نویسه‌های یک متن چندزبانه استفاده کرد.

## مفهوم تبدیل نوع و سازگاری با APIهای قدیمی

یکی از مهم‌ترین تفاوت‌های `char8_t` با `char`، نبود تبدیل ضمنی میان این دو نوع است.

کد زیر در ++C20 معتبر نیست:

```
#include <string>

int main() {
    std::string text = u8"Hello";
}
```

دلیل این مسئله آن است که `u8"Hello"` از نوع آرایه‌ای از `const char8_t` است، درحالی‌که `std::string` عناصر `char` را نگهداری می‌کند.

برای حل این مسئله، باید مشخص شود که API مورد استفاده واقعاً چه نوع داده‌ای انتظار دارد.

### تبدیل صریح برای APIهای بایتی

اگر یک API قدیمی صرفاً به دنباله‌ای از بایت‌ها نیاز داشته باشد، می‌توان نمایش بایتی متن UTF-8 را به آن ارائه کرد. این کار با فرض آنکه API فقط بایت‌ها را مصرف می‌کند و هیچ تبدیل encoding ناخواسته‌ای انجام نمی‌دهد، امکان‌پذیر است.

```
#include <cstddef>
#include <iostream>
#include <string>

void writeBytes(const char* data, std::size_t size) {
    std::cout.write(data, static_cast<std::streamsize>(size));
}

int main() {
    std::u8string text = u8"Hello";

    writeBytes(
        reinterpret_cast<const char*>(text.data()),
        text.size()
    );
}
```

در این مثال، `reinterpret_cast` فقط نوع اشاره‌گر را تغییر می‌دهد؛ محتوای رشته به encoding دیگری تبدیل نمی‌شود. اندازه نیز صریحاً منتقل شده است تا مصرف‌کننده به خاتمه‌یافتن رشته با `'\0'` وابسته نباشد.

این روش زمانی مناسب است که قرارداد API بر مبنای بایت‌ها تعریف شده باشد. اگر API انتظار متن با encoding مشخص دیگری را داشته باشد، تبدیل اشاره‌گر کافی نیست و باید encoding به‌درستی تبدیل شود.

### نکات مهم دربارهٔ تبدیل اشاره‌گر

استفاده از `reinterpret_cast` به معنای تبدیل واقعی UTF-8 به یک encoding دیگر نیست. همچنین این روش نباید برای پنهان کردن ناسازگاری معنایی میان APIها به کار رود.

در طراحی یک API جدید، بهتر است نوع دادهٔ مورد انتظار را صریح مشخص کنید. اگر API با UTF-8 سروکار دارد، استفاده از `std::u8string_view` یا `std::u8string` می‌تواند قرارداد روشن‌تری ایجاد کند.

## بررسی تعامل با `std::string_view`

نوع `std::string_view` برای نمای غیرمالک از رشته‌های `char` طراحی شده است و به‌صورت مستقیم جایگزین `std::u8string_view` نیست.

```
#include <string_view>

int main() {
    std::u8string_view utf8 = u8"Hello";

    // std::string_view text = utf8;
}
```

خط کامنت‌شده را نمی‌توان بدون تبدیل صریح یا ایجاد یک نمای سازگار از نوع دیگر، فعال کرد؛ زیرا نوع عناصر دو نما متفاوت است.

برای APIهای UTF-8، امضای تابع زیر مناسب‌تر است:

```
#include <string_view>

void processUtf8(std::u8string_view text) {
    // Process UTF-8 code units.
}

int main() {
    processUtf8(u8"Hello");
}
```

این API در سطح نوع داده مشخص می‌کند که ورودی باید از واحدهای کد `char8_t` تشکیل شده باشد. بااین‌حال، برای اعتبارسنجی واقعی UTF-8 همچنان به بررسی محتوای ورودی نیاز است.

از آنجا که `std::u8string_view` مالک حافظه نیست، باید از معتبر ماندن طول عمر دادهٔ مرجع اطمینان حاصل کرد. نگهداری یک نمای اشاره‌گرمانند پس از پایان طول عمر رشتهٔ اصلی می‌تواند به رفتار تعریف‌نشده منجر شود.

## معرفی literalهای نویسه‌ای UTF-8

در ++C20، پیشوند `u8` برای literalهای نویسه‌ای نیز با `char8_t` ارتباط دارد.

```
#include <type_traits>

int main() {
    constexpr char8_t ch = u8'A';

    static_assert(std::is_same_v<decltype(ch), const char8_t>);
}
```

در این مثال، `u8'A'` یک literal نویسه‌ای UTF-8 است و نوع آن `char8_t` خواهد بود.

باید توجه داشت که یک literal نویسه‌ای UTF-8 برای نمایش یک واحد کد طراحی شده است. از این رو، نباید فرض کرد که می‌توان هر نویسهٔ Unicode را بدون توجه به تعداد واحدهای UTF-8 آن در قالب یک literal نویسه‌ای `u8'...'` نمایش داد.

برای متن‌هایی که به چند واحد کد نیاز دارند، باید از literal رشته‌ای UTF-8 مانند `u8"..."` استفاده کرد.

## کاربرد در طراحی APIهای مدرن

یکی از مهم‌ترین کاربردهای `char8_t` ایجاد مرز مشخص میان متن UTF-8 و سایر انواع داده است.

فرض کنید کتابخانه‌ای تابعی برای پردازش متن ارائه می‌کند. اگر این تابع از `std::string_view` استفاده کند، نوع ورودی به‌تنهایی مشخص نمی‌کند که داده UTF-8 است.

```
#include <string_view>

void processText(std::string_view text) {
    // The encoding is defined by the API contract.
}
```

در این حالت، قرارداد API باید encoding مورد انتظار را مستند کند.

در مقابل، استفاده از نوع اختصاصی UTF-8 قرارداد را در امضای تابع نیز منعکس می‌کند:

```
#include <string_view>

void processUtf8(std::u8string_view text) {
    // The input is intended to contain UTF-8 code units.
}
```

این طراحی می‌تواند از برخی خطاهای رایج جلوگیری کند، به‌ویژه زمانی که یک پروژه هم‌زمان با داده‌های UTF-8، داده‌های باینری و رشته‌های مبتنی بر `char` کار می‌کند.

البته نوع داده به‌تنهایی اعتبار encoding را تضمین نمی‌کند. اگر داده از شبکه، فایل یا منبع غیرقابل اعتماد دریافت می‌شود، اعتبارسنجی باید بخشی از فرایند پردازش باشد.

## کاربرد در فایل‌ها و شبکه

داده‌های UTF-8 معمولاً از فایل‌ها، APIهای وب، پایگاه‌های داده یا پروتکل‌های شبکه دریافت می‌شوند. در این موقعیت‌ها، تفاوت میان متن و بایت‌های خام اهمیت زیادی دارد.

اگر داده به‌صورت یک دنبالهٔ بایتی دریافت شود، ابتدا باید قرارداد منبع مشخص کند که داده واقعاً UTF-8 است یا خیر. سپس می‌توان آن را به ساختار مناسب منتقل کرد.

برای مثال، اگر یک API داخلی فقط دنبالهٔ بایت‌ها را نگهداری کند، ممکن است استفاده از `std::vector<std::byte>` مناسب باشد. اگر داده به‌عنوان متن UTF-8 پردازش می‌شود، `std::u8string` می‌تواند معنای نوع را بهتر منعکس کند.

این دو نوع برای هدف‌های متفاوت طراحی شده‌اند و نباید صرفاً به دلیل آنکه هر دو داده‌ای بایتی را نگهداری می‌کنند، جایگزین یکدیگر تلقی شوند.

### نکات مهم دربارهٔ صحت داده

- نوع `char8_t` معتبر بودن UTF-8 را تضمین نمی‌کند.
- وجود `'\0'` در داده ممکن است باعث توقف زودهنگام برخی APIهای رشته‌ای مبتنی بر خاتمه‌دهنده شود.
- دادهٔ UTF-8 ممکن است شامل نویسه‌های چندواحدی باشد؛ بنابراین تقسیم رشته بر اساس یک بایت می‌تواند encoding را خراب کند.
- اعتبارسنجی ورودی‌های خارجی باید در لایهٔ مناسب برنامه انجام شود.
- اگر پروتکل با بایت‌های خام سروکار دارد، بهتر است قرارداد داده مستقل از قرارداد متن تعریف شود.

## بررسی تعامل با `std::filesystem`

در ++C20، تعامل میان `char8_t` و کتابخانهٔ فایل‌سیستم نیز اهمیت پیدا می‌کند. نوع مسیرهای فایل‌سیستم `std::filesystem::path` به‌صورت مستقل از نوع رشتهٔ ورودی طراحی شده است، اما encoding رشته‌های ورودی و خروجی همچنان باید با دقت مدیریت شود.

برای مثال، در ++C20، تابع `u8string()` از نوع `std::u8string` نتیجه می‌دهد:

```
#include <filesystem>
#include <string>

int main() {
    std::filesystem::path path = "example.txt";

    std::u8string utf8Path = path.u8string();
}
```

این رفتار با نسخه‌های قدیمی‌تر استاندارد متفاوت است؛ در نسخه‌های پیش از ++C20، نتیجهٔ `u8string()` از نوع `std::string` بود.

در نتیجه، کدی که پیش‌تر نتیجهٔ `u8string()` را مستقیماً به `std::string` اختصاص می‌داد، ممکن است هنگام مهاجرت به ++C20 نیازمند اصلاح باشد.

همچنین باید توجه کرد که نمایش مسیر فایل در سطح سیستم‌عامل و encoding مورد استفاده برای مسیرها می‌تواند میان پیاده‌سازی‌ها تفاوت داشته باشد. بنابراین، نباید صرفاً بر اساس نوع C++ فرض کرد که تمام سیستم‌عامل‌ها مسیرها را با UTF-8 مدیریت می‌کنند.

## مقایسهٔ `char8_t` با `wchar_t`

نوع `wchar_t` برای نویسه‌های گسترده تعریف شده است و اندازه و encoding آن به پیاده‌سازی وابسته است. در مقابل، `char8_t` برای واحدهای کد UTF-8 در استاندارد ++C20 معرفی شده است.

این دو نوع هدف یکسانی ندارند:

- `char8_t` برای داده‌های UTF-8 طراحی شده است.
- `wchar_t` به سازوکار نویسه‌های گستردهٔ پیاده‌سازی مربوط می‌شود.
- استفاده از `wchar_t` به‌تنهایی تضمین نمی‌کند که متن در قالب UTF-16 یا UTF-32 ذخیره شده باشد.
- تبدیل میان `char8_t` و `wchar_t` ممکن است به تبدیل واقعی encoding نیاز داشته باشد.

به همین دلیل، انتخاب `char8_t` زمانی منطقی است که قرارداد داده به‌طور مشخص UTF-8 باشد؛ درحالی‌که انتخاب `wchar_t` باید بر اساس نیازهای API و محیط اجرا انجام شود.

## محدودیت‌ها و اشتباهات رایج

### فرض برابر بودن نوع رشته‌ها

نوع `std::u8string` با `std::string` یکسان نیست. این تفاوت در ++C20 عمدی است و نباید با تبدیل‌های ضمنی یا تغییر نوع ظاهری نادیده گرفته شود.

### فرض برابر بودن تعداد واحدهای کد و نویسه‌ها

مقدار `size()` در `std::u8string` تعداد واحدهای کد را نشان می‌دهد. برای شمارش code pointها یا grapheme clusterها باید از الگوریتم‌های مناسب Unicode استفاده کرد.

### فرض تضمین اعتبار UTF-8

داشتن نوع `char8_t` یا `std::u8string` به معنای معتبر بودن تمام داده‌های داخلی نیست. داده می‌تواند از ورودی خارجی یا عملیات بایتی نامعتبر ایجاد شده باشد.

### استفاده از تبدیل اشاره‌گر به‌جای تبدیل encoding

تبدیل یک `char8_t*` به `char*` محتوا را به encoding دیگری تبدیل نمی‌کند. چنین تبدیلی فقط در سناریوهای مشخص تعامل با APIهای بایتی قابل توجیه است.

### نادیده گرفتن تغییرات ++C17 و ++C20

یکی از مشکلات رایج در مهاجرت به ++C20، تغییر نوع literalهای `u8` از `char` به `char8_t` است. این تغییر می‌تواند بر overload resolution، انتساب رشته‌ها و امضای توابع اثر بگذارد.

### فرض خاتمه‌یافتن داده با نویسهٔ صفر

رشته‌های C-style معمولاً از `'\0'` برای پایان استفاده می‌کنند، اما داده‌های بایتی ممکن است در میانهٔ خود نیز مقدار صفر داشته باشند. برای انتقال امن داده، بهتر است طول آن نیز به‌صورت صریح منتقل شود.

## نکات سازگاری و مهاجرت به ++C20

هنگام انتقال یک پروژه از ++C17 به ++C20، بهتر است تمام نقاطی که از literalهای `u8` استفاده می‌کنند بررسی شوند.

موارد زیر از جمله بخش‌هایی هستند که احتمالاً نیاز به بازبینی دارند:

- توابعی که پارامتر `const char*` دریافت می‌کنند.
- متغیرهایی که مقدار literalهای `u8` را در `std::string` نگهداری می‌کنند.
- overloadهایی که میان انواع `char` و `char8_t` تمایز دارند.
- APIهایی که رشته‌ها را به کتابخانه‌های خارجی منتقل می‌کنند.
- کدهایی که مسیر فایل را از `std::filesystem::path::u8string()` دریافت می‌کنند.

برای استفاده از این قابلیت‌ها، کامپایلر باید از ++C20 و نوع `char8_t` پشتیبانی کند. فعال‌سازی استاندارد مناسب در ابزار ساخت پروژه نیز ضروری است.

برای نمونه، در GCC و Clang معمولاً می‌توان از گزینهٔ زیر استفاده کرد:

```
g++ -std=c++20 main.cpp -o main
```

در MSVC نیز می‌توان استاندارد زبان را با گزینهٔ مناسب کامپایلر فعال کرد:

```
cl /std:c++20 /EHsc main.cpp
```

البته پشتیبانی کامل از کتابخانهٔ استاندارد و ویژگی‌های مرتبط به نسخهٔ کامپایلر و محیط توسعه وابسته است.

## جمع‌بندی نهایی

نوع `char8_t` در ++C20 برای نمایش واحدهای کد UTF-8 و متمایز کردن آن‌ها از داده‌های عمومی `char` معرفی شده است. این نوع با ارائهٔ یک مرز مشخص در سیستم نوع زبان، طراحی APIهای متنی را روشن‌تر می‌کند و می‌تواند از برخی خطاهای ناشی از ترکیب ناخواستهٔ انواع داده جلوگیری کند.

در پروژه‌های مدرن، استفاده از `std::u8string` و `std::u8string_view` برای داده‌هایی که قرارداد آن‌ها UTF-8 است، انتخاب مناسبی محسوب می‌شود. بااین‌حال، برای تعامل با APIهای قدیمی، پردازش بایت‌های خام، اعتبارسنجی encoding و مدیریت مسیرهای فایل باید تفاوت‌های نوعی و رفتاری را در نظر گرفت.

مهم‌ترین نکته این است که `char8_t` نوع داده را صریح می‌کند، اما به‌تنهایی صحت UTF-8، تعداد نویسه‌های متن یا سازگاری با تمام APIهای خارجی را تضمین نمی‌کند.
