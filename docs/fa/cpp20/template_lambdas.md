#  لامبداهای قالبی در ++C20

## مقدمه و جایگاه این قابلیت

لامبداهای قالبی یا Template Lambdas یکی از قابلیت‌های مهم زبان ++C هستند که امکان ترکیب مزایای Lambda Expressions با انعطاف‌پذیری Function Templates را فراهم می‌کنند. این قابلیت به برنامه‌نویس اجازه می‌دهد پارامترهای قالبی را به‌صورت صریح در تعریف یک Lambda مشخص کند و در نتیجه، کنترل بیشتری بر نوع پارامترها، محدودیت‌های آن‌ها و نحوه استنتاج نوع داشته باشد.

در استاندارد ++C14، قابلیت Generic Lambdas معرفی شد تا بتوان Lambdaهایی با پارامترهای وابسته به نوع تعریف کرد. در این روش، معمولاً از `auto` در فهرست پارامترهای تابع استفاده می‌شد. استاندارد ++C20 این قابلیت را توسعه داد و اجازه داد فهرست پارامترهای قالبی صریح مستقیماً پس از بخش Capture نوشته شود.

برای مثال، در کد زیر یک Lambda با پارامتر قالبی صریح تعریف شده است:

```
#include <iostream>

int main() {
    auto identity = []<typename T>(T value) {
        return value;
    };

    std::cout << identity(42) << '\n';
    std::cout << identity(3.14) << '\n';
}
```

در این مثال، پارامتر قالبی `T` در زمان فراخوانی از نوع آرگومان استنتاج می‌شود. در نتیجه، یک Lambda می‌تواند برای چندین نوع متفاوت استفاده شود، بدون اینکه لازم باشد برای هر نوع، تابع جداگانه‌ای بنویسیم.

نکته مهم این است که Template Lambdas یک قابلیت زبانی استانداردشده در ++C20 هستند، نه یک ویژگی اختصاصی کامپایلر یا یک API متعلق به کتابخانه استاندارد. این قابلیت بر اساس پیشنهاد استانداردسازی [P0428R2](https://www.open-std.org/jtc1/sc22/wg21/docs/papers/2017/p0428r2.html?utm_source=chatgpt.com) به زبان اضافه شد.

## آشنایی با تکامل Lambdaها در استانداردهای مختلف

برای درک بهتر Lambdaهای قالبی، ابتدا باید تفاوت میان Lambdaهای معمولی، Generic Lambdas و Template Lambdas را بشناسیم.

### لامبداهای معمولی در ++C11

در ++C11، پارامترهای یک Lambda معمولی با نوع مشخص تعریف می‌شوند.

```
auto add = [](int a, int b) {
    return a + b;
};
```

این Lambda فقط با آرگومان‌هایی قابل استفاده است که مطابق قواعد تبدیل نوع و فراخوانی تابع با پارامترهای `int` سازگار باشند. نوع پارامترها در تعریف Lambda ثابت است.

### لامبداهای عمومی در ++C14

در ++C14، استفاده از `auto` در پارامترهای Lambda امکان‌پذیر شد.

```
auto add = [](auto a, auto b) {
    return a + b;
};
```

در این مثال، کامپایلر هنگام فراخوانی Lambda نوع پارامترها را استنتاج می‌کند. در عمل، کامپایلر برای هر نوع پارامتر مناسب، یک نمونه از الگوی فراخوانی قالبی را ایجاد می‌کند.

برای مثال، اگر `a` از نوع `int` و `b` از نوع `double` باشد، نوع پارامترها مستقل از یکدیگر استنتاج می‌شود و عبارت جمع بر اساس قواعد معمول ++C ارزیابی خواهد شد.

بااین‌حال، این شکل نوشتاری محدودیت‌هایی دارد. برنامه‌نویس نمی‌تواند به‌صورت مستقیم نام نوع استنتاج‌شده را مانند یک پارامتر قالبی معمولی در بخش‌های مختلف تعریف Lambda به کار ببرد. همچنین، الگوهای خاصی مانند دریافت مرجع به آرایه با اندازه ثابت یا اعمال یک Constraint مستقیماً روی پارامتر قالبی نام‌گذاری‌شده، با این روش دشوارتر هستند.

### معرفی Template Lambdas در ++C20

در ++C20، می‌توان فهرست پارامترهای قالبی را مستقیماً در تعریف Lambda مشخص کرد.

```
auto add = []<typename T>(T a, T b) {
    return a + b;
};
```

تفاوت مهم با نمونه قبلی این است که هر دو پارامتر تابع از یک نوع قالبی مشترک به نام `T` استفاده می‌کنند.

بنابراین، استنتاج نوع پارامترها دیگر به‌صورت دو استنتاج مستقل انجام نمی‌شود. کامپایلر باید بتواند هر دو آرگومان را با یک نوع قالبی سازگار کند.

برای مثال، فراخوانی با دو آرگومان `int` معتبر است، اما فراخوانی با آرگومان‌های `int` و `double` معمولاً باعث شکست Template Argument Deduction می‌شود؛ زیرا نوع `T` از دو آرگومان متفاوت استنتاج می‌شود.

```
auto add = []<typename T>(T a, T b) {
    return a + b;
};

auto result = add(10, 20);

// The following call fails template argument deduction:
// auto invalid = add(10, 2.5);
```

این قابلیت باعث می‌شود بتوانیم Lambdaهایی طراحی کنیم که نه‌فقط از چند نوع پشتیبانی می‌کنند، بلکه روابط دقیق‌تری میان نوع پارامترهای خود برقرار می‌سازند.

## مفهوم Generic Lambda و ساختار داخلی آن

هر Lambda در ++C یک نوع ناشناس به نام Closure Type دارد. شیء حاصل از ارزیابی عبارت Lambda نمونه‌ای از این نوع است و می‌تواند داده‌های Capture‌شده را نگهداری کند.

در یک Lambda معمولی، Closure Type دارای یک عملگر فراخوانی با امضای مشخص است. در یک Generic Lambda، عملگر فراخوانی به‌صورت Function Template تعریف می‌شود.

برای نمونه:

```
auto printer = []<typename T>(T value) {
    return value;
};
```

از دید مفهومی، عملگر فراخوانی این Lambda تقریباً رفتاری مشابه قالب زیر دارد:

```
template <typename T>
auto operator()(T value) const {
    return value;
}
```

این قطعه صرفاً نمایش مفهومی ساختار داخلی است و کدی نیست که بتوان آن را به همین شکل مستقیماً به‌عنوان پیاده‌سازی Closure Type نوشت.

کامپایلر نوع Closure را تولید می‌کند و عملگر فراخوانی قالبی را مطابق قواعد زبان در اختیار قرار می‌دهد.

چند نکته مهم درباره این ساختار وجود دارد:

- نکته نخست: Closure Type برای هر عبارت Lambda یکتا است؛ حتی اگر دو Lambda بدنه و پارامترهای یکسانی داشته باشند.
- نکته دوم: صریح بودن فهرست پارامترهای قالبی باعث نمی‌شود نوع Closure به یک Template Class قابل نام‌گذاری تبدیل شود.
- نکته سوم: در Lambdaهای Capture‌شده، داده‌های Capture متعلق به شیء Closure هستند و پارامترهای قالبی بخشی از سازوکار Template Argument Deduction برای عملگر فراخوانی محسوب می‌شوند.
- نکته چهارم: عملگر فراخوانی یک Generic Lambda می‌تواند برای نوع‌های مختلف Instantiate شود، اما این موضوع به معنی ایجاد یک شیء Lambda مجزا برای هر نوع نیست.

## بررسی ساختار نحوی Template Lambdas

ساختار کلی یک Template Lambda به شکل زیر است:

```
[captures]<template_parameters>(parameters) {
    // Function body
}
```

در این ساختار، بخش Capture اختیاری است و می‌تواند متغیرهای محیط پیرامون را ذخیره کند. فهرست پارامترهای قالبی نیز شامل Type Parameters، Non-Type Template Parameters یا سایر انواع مجاز پارامترهای قالبی است.

فهرست پارامترهای معمولی تابع پس از فهرست قالبی قرار می‌گیرد و از طریق آن‌ها می‌توان آرگومان‌های زمان اجرا را دریافت کرد.

### بررسی پارامترهای قالبی نوعی

رایج‌ترین شکل Template Lambda، استفاده از پارامترهای نوعی است.

```
auto make_pair_sum = []<typename T, typename U>(T first, U second) {
    return first + second;
};
```

در این نمونه، نوع `T` برای پارامتر اول و نوع `U` برای پارامتر دوم به‌صورت مستقل استنتاج می‌شوند.

در مقایسه با Lambda زیر، هر پارامتر نوع مشخص و نام‌گذاری‌شده‌ای دارد:

```
auto make_pair_sum = [](auto first, auto second) {
    return first + second;
};
```

از نظر توانایی استنتاج نوع، این دو تعریف در مثال بالا رفتار مشابهی دارند. مزیت اصلی شکل صریح زمانی نمایان می‌شود که لازم باشد از `T` و `U` در Constraintها، اعلان نوع، الگوهای پارامتری یا محاسبات زمان کامپایل استفاده کنیم.

### بررسی پارامترهای غیرنوعی

Template Lambdas می‌توانند Non-Type Template Parameters یا پارامترهای قالبی غیرنوعی داشته باشند. این پارامترها به‌جای دریافت یک نوع، مقدارهایی مانند اعداد صحیح ثابت را دریافت می‌کنند.

```
#include <cstddef>

auto repeat_value = []<typename T, std::size_t N>(T value) {
    return value * static_cast<T>(N);
};

auto result = repeat_value.operator()<int, 5>(10);
```

در این مثال، `T` مشخص‌کننده نوع مقدار ورودی و `N` مشخص‌کننده یک مقدار قالبی است. فراخوانی مستقیم عضو `operator()` امکان تعیین صریح آرگومان‌های قالبی را فراهم می‌کند.

البته، در اغلب کاربردهای معمول نیازی به تعیین دستی تمام آرگومان‌های قالبی نیست و می‌توان استنتاج نوع را به کامپایلر واگذار کرد.

### بررسی پارامترهای قالبی Variadic

در Template Lambdas می‌توان از Parameter Pack نیز استفاده کرد.

```
auto print_values = []<typename... Ts>(Ts... values) {
    ((std::cout << values << ' '), ...);
};
```

در این نمونه، تعداد پارامترها محدود نیست و نوع هر پارامتر در مجموعه `Ts` قرار می‌گیرد.

عبارت داخل بدنه از Fold Expression استفاده می‌کند تا تمام مقادیر به‌ترتیب در خروجی نوشته شوند. برای استفاده از این مثال باید هدر `<iostream>` در دسترس باشد.

استفاده از Packها زمانی ارزشمند است که بخواهیم یک عملیات را روی تعداد متغیری از آرگومان‌ها انجام دهیم یا نوع تمام پارامترهای دریافتی را در زمان کامپایل بررسی کنیم.

## کاربرد Template Parameter List در حل محدودیت‌های Generic Lambdas

دلیل اصلی معرفی این قابلیت، صرفاً کوتاه‌تر شدن نحو نوشتاری نیست. فهرست قالبی صریح امکان بیان الگوهای نوعی‌ای را فراهم می‌کند که با `auto` به‌تنهایی دشوار هستند یا به‌سادگی نمی‌توان آن‌ها را بیان کرد.

### دسترسی مستقیم به نوع استنتاج‌شده

در یک Generic Lambda ساده، اگر از `auto` استفاده کنیم و به نوع پارامتر نیاز داشته باشیم، معمولاً باید از ابزارهایی مانند `decltype` استفاده کنیم.

```
auto inspect = [](auto value) {
    using T = decltype(value);
    return sizeof(T);
};
```

در مقابل، در Template Lambda می‌توان نوع را مستقیماً نام‌گذاری کرد.

```
auto inspect = []<typename T>(T value) {
    return sizeof(T);
};
```

روش دوم در مثال‌هایی که چند بار به نوع نیاز داریم، ساده‌تر است. همچنین، هنگامی که لازم باشد نوع پایه، نوع اشاره‌گر یا نوع عضوهای داخلی یک Type را بررسی کنیم، داشتن نام قالبی می‌تواند خوانایی کد را افزایش دهد.

البته، `decltype` همچنان ابزار مهم و ضروری زبان است. Template Lambdas جایگزین آن نیستند، بلکه در موقعیت‌هایی که نوع بخشی از الگوی قالبی است، روش مستقیم‌تری ارائه می‌کنند.

### دریافت الگوهای پیچیده‌تر نوعی

یکی از محدودیت‌های شناخته‌شده در استفاده از پارامترهای `auto` این است که نمی‌توان به‌سادگی یک الگوی نوعی مشخص مانند اشاره‌گر یا مرجع به آرایه با اندازه ثابت را با نام‌گذاری مستقیم نوع استنتاج‌شده ترکیب کرد.

برای مثال، می‌توان یک Lambda نوشت که فقط اشاره‌گر دریافت کند:

```
auto dereference = []<typename T>(T* pointer) -> T& {
    return *pointer;
};
```

در اینجا، امضای Lambda مستقیماً مشخص می‌کند که آرگومان باید با الگوی `T*` سازگار باشد. همچنین، نوع `T` در بدنه قابل استفاده است.

این ساختار در مقایسه با دریافت یک مقدار با `auto` و بررسی نوع آن پس از استنتاج، بیان دقیق‌تری دارد.

### حفظ اندازه آرایه در زمان کامپایل

در یک پارامتر تابع از نوع آرایه، تفاوت مهمی میان دریافت آرایه با مقدار و دریافت آن با مرجع وجود دارد. پارامترهای تابعی از نوع آرایه که به شکل معمول دریافت می‌شوند، در اعلان تابع به اشاره‌گر تبدیل می‌شوند؛ بنابراین، اندازه آرایه معمولاً به این روش حفظ نمی‌شود.

با استفاده از پارامترهای قالبی صریح می‌توان اندازه آرایه را به‌عنوان یک پارامتر قالبی استنتاج کرد.

```
#include <cstddef>

auto get_extent = []<typename T, std::size_t N>(
    T const (&array)[N]
) {
    return N;
};

int numbers[] = {10, 20, 30, 40};

auto size = get_extent(numbers);
```

در این مثال، `N` در زمان کامپایل از نوع آرگومان استنتاج می‌شود. در نتیجه، مقدار بازگشتی برابر اندازه آرایه است.

این الگو برای نوشتن توابع کمکی مرتبط با آرایه‌های با اندازه ثابت کاربرد دارد. البته، برای Containerهای مدرن، معمولاً استفاده از `std::array`، `std::span` یا Interfaceهای مبتنی بر Range می‌تواند طراحی مناسب‌تری باشد؛ انتخاب میان این گزینه‌ها به نیازهای برنامه بستگی دارد.

## استفاده از Concepts و Constraints در Template Lambdas

یکی از کاربردهای مهم Template Lambdas در ++C20، ترکیب آن‌ها با Concepts و Constraints است.

Concepts امکان تعریف محدودیت‌هایی را فراهم می‌کنند که مشخص می‌سازند یک پارامتر قالبی باید چه ویژگی‌هایی داشته باشد. این قابلیت به‌جای اتکا به خطاهای پیچیده هنگام Instantiate شدن قالب، شرایط معتبر بودن یک فراخوانی را شفاف‌تر می‌کند.

### محدود کردن نوع پارامتر با Concept

برای مثال، می‌توان یک Lambda تعریف کرد که فقط برای نوع‌های صحیح معتبر باشد.

```
#include <concepts>

auto square = []<std::integral T>(T value) {
    return value * value;
};
```

در این نمونه، `std::integral` یک Concept استاندارد است که در هدر `<concepts>` تعریف شده است.

کامپایلر تنها زمانی می‌تواند این عملگر فراخوانی قالبی را برای یک نوع Instantiate کند که آن نوع با Constraint تعیین‌شده سازگار باشد.

این روش، در مقایسه با نوشتن یک شرط طولانی با `std::enable_if` یا ساختارهای SFINAE، بیان مستقیم‌تر و معمولاً خواناتری دارد.

### استفاده از Requires Clause

علاوه بر Constrained Type Parameters، می‌توان از `requires` در انتهای اعلان پارامترهای تابع استفاده کرد.

```
#include <concepts>

auto add_integral = []<typename T>(T first, T second)
    requires std::integral<T>
{
    return first + second;
};
```

در این مثال، نوع `T` از آرگومان‌ها استنتاج می‌شود و سپس Constraint بررسی می‌شود.

این شکل نوشتاری زمانی مفید است که Constraint پیچیده‌تر باشد یا به چند پارامتر قالبی وابسته باشد.

### محدود کردن رابطه میان چند نوع

گاهی هدف این نیست که هر پارامتر به‌تنهایی ویژگی خاصی داشته باشد، بلکه لازم است نوع پارامترها با یکدیگر رابطه مشخصی داشته باشند.

```
#include <concepts>
#include <type_traits>

auto same_type_add = []<typename T, typename U>(
    T first,
    U second
)
    requires std::same_as<
        std::remove_cvref_t<T>,
        std::remove_cvref_t<U>
    >
{
    return first + second;
};
```

در این نمونه، استفاده از `std::remove_cvref_t` باعث می‌شود ارزیابی Constraint نسبت به تفاوت‌های `const`، `volatile` و Reference حساس نباشد.

با این طراحی می‌توان دو پارامتر را طوری محدود کرد که نوع پایه آن‌ها یکسان باشد، درحالی‌که نوع‌های قالبی مستقل از یکدیگر استنتاج می‌شوند.

نکته مهم این است که `std::same_as` و `std::remove_cvref_t` متعلق به کتابخانه استاندارد هستند، اما نحو `requires` و سازوکار Constraints بخشی از زبان ++C20 محسوب می‌شوند.

### تفاوت Requires Clause در سرآیند قالب و اعلان تابع

در Template Lambdas ممکن است Constraint در دو محل قرار بگیرد:

```
#include <concepts>

auto first = []<typename T>
    requires std::integral<T>
(T value) {
    return value;
};

auto second = []<typename T>(T value)
    requires std::integral<T>
{
    return value;
};
```

در نمونه نخست، Constraint پس از فهرست پارامترهای قالبی قرار دارد. در نمونه دوم، Constraint پس از اعلان پارامترهای تابع و در قالب Trailing Requires Clause نوشته شده است.

هر دو حالت در این مثال، فراخوانی را به نوع‌های صحیح محدود می‌کنند؛ اما از نظر جایگاه نحوی به دو بخش متفاوت Grammar مربوط هستند.

انتخاب محل مناسب باید با توجه به ساختار Constraint و هدف طراحی انجام شود. در کدهای ساده، Constrained Type Parameters معمولاً خواناتر هستند؛ برای Constraintهای مرکب یا وابسته به چند پارامتر، استفاده از `requires` انعطاف بیشتری دارد.

## ترکیب پارامترهای قالبی صریح و Auto Parameters

یکی از ویژگی‌های کاربردی Template Lambdas این است که لازم نیست تمام پارامترهای تابع با نوع‌های قالبی صریح تعریف شوند. می‌توان پارامترهای صریح را با پارامترهای مبتنی بر `auto` ترکیب کرد.

```
auto process = []<typename T>(T first, auto second) {
    return first + second;
};
```

در این نمونه، نوع پارامتر اول با نام `T` مشخص شده است، درحالی‌که نوع پارامتر دوم به‌طور مستقل استنتاج می‌شود.

این ترکیب زمانی مفید است که یک بخش از Interface باید کنترل دقیق‌تری داشته باشد، اما سایر بخش‌ها می‌توانند از Type Deduction معمول استفاده کنند.

برای مثال، اگر نوع اولین آرگومان باید در بخش‌های مختلف بدنه Lambda استفاده شود، تعریف `T` منطقی است. اگر پارامتر دوم صرفاً برای انجام یک عملیات عمومی استفاده می‌شود، `auto` می‌تواند کد را ساده‌تر کند.

### تفاوت Auto Parameters با Type Parameters صریح

پارامتر `auto` در یک Generic Lambda باعث ایجاد یک پارامتر قالبی استنتاج‌شده می‌شود، اما نام مستقلی مانند `T` در فهرست پارامترهای قالبی در اختیار برنامه‌نویس قرار نمی‌دهد.

برای مثال، در کد زیر نوع پارامتر دوم با `T` یکسان است:

```
auto compare = []<typename T>(T first, T second) {
    return first == second;
};
```

در مقابل، کد زیر اجازه می‌دهد دو نوع مستقل استنتاج شوند:

```
auto compare = [](auto first, auto second) {
    return first == second;
};
```

اگر نیاز باشد نوع دو پارامتر مستقل بماند اما بتوان رابطه‌ای میان آن‌ها تعریف کرد، می‌توان از دو Type Parameter استفاده کرد:

```
auto compare = []<typename T, typename U>(T first, U second) {
    return first == second;
};
```

انتخاب میان این الگوها باید بر مبنای قرارداد مورد انتظار از Lambda انجام شود، نه صرفاً کوتاه‌تر بودن نحو نوشتاری.

## کاربرد Parameter Packs و Fold Expressions

Template Lambdas برای طراحی عملیات Variadic نیز بسیار مناسب هستند؛ به‌ویژه زمانی که لازم باشد نوع آرگومان‌ها در زمان کامپایل در دسترس باشد.

### بررسی همه آرگومان‌ها با یک Fold Expression

کد زیر تمام آرگومان‌های صحیح را بررسی می‌کند تا مشخص شود آیا همه آن‌ها زوج هستند یا خیر.

```
#include <concepts>

auto all_even = []<std::integral... Ts>(Ts... values) {
    return ((values % 2 == 0) && ...);
};
```

در این نمونه، عبارت `std::integral... Ts` یک پارامتر قالبی از نوع Pack تعریف می‌کند که تمام اعضای آن باید با Concept مشخص‌شده سازگار باشند.

همچنین، Fold Expression روی عملگر `&&` برای تمام مقادیر توسعه پیدا می‌کند. به همین دلیل، تعداد پارامترها می‌تواند متفاوت باشد.

در حالت Pack خالی، Fold Expression با عملگر `&&` به مقدار `true` ارزیابی می‌شود؛ این رفتار از قواعد Fold Expressions در زبان ناشی می‌شود.

### ساخت تابع Forwarding عمومی

یکی از کاربردهای حرفه‌ای Template Lambdas، ساخت Callableهای عمومی است که یک تابع دیگر و آرگومان‌های آن را دریافت کرده و فراخوانی را به تابع مقصد منتقل می‌کنند.

```
#include <concepts>
#include <functional>
#include <utility>

auto invoke_forward = []<typename F, typename... Args>(
    F&& function,
    Args&&... args
) -> decltype(auto)
    requires std::invocable<F, Args...>
{
    return std::invoke(
        std::forward<F>(function),
        std::forward<Args>(args)...
    );
};
```

این نمونه چند قابلیت مهم را ترکیب می‌کند:

- نخست، پارامترهای `F` و `Args` نوع تابع و آرگومان‌ها را استنتاج می‌کنند.
- دوم، Reference Collapsing و قواعد Forwarding Reference اجازه می‌دهند Value Category آرگومان‌ها به‌درستی حفظ شود.
- سوم، `std::forward` از تبدیل ناخواسته آرگومان‌ها به Lvalue جلوگیری می‌کند.
- چهارم، `std::invoke` امکان فراخوانی شکل‌های مختلف Callable را از طریق یک Interface مشترک فراهم می‌کند.
- پنجم، `decltype(auto)` نوع بازگشتی را بر اساس عبارت `return` حفظ می‌کند و می‌تواند برای بازگرداندن Reference یا مقدار مناسب باشد.
- ششم، Constraint مبتنی بر `std::invocable` باعث می‌شود Lambda برای ترکیب‌های نامعتبر از Callable و آرگومان‌ها قابل استفاده نباشد.

نکته مهم این است که این Wrapper باید با دقت استفاده شود. بازگرداندن Reference به شیئی که عمر آن در بدنه تابع یا تابع مقصد پایان می‌یابد، همچنان می‌تواند باعث Dangling Reference شود. همچنین، استفاده از Perfect Forwarding به‌خودی‌خود تضمین نمی‌کند که یک Wrapper از نظر مدیریت منابع، Lifetime یا Exception Safety درست طراحی شده باشد.

## کاربرد در الگوریتم‌ها و APIهای عمومی

Template Lambdas در بسیاری از موقعیت‌ها به‌عنوان تابع‌های کمکی محلی استفاده می‌شوند. مزیت آن‌ها زمانی بیشتر می‌شود که به نوع پارامترها برای انتخاب رفتار یا اعمال محدودیت نیاز داشته باشیم.

### پردازش نوع‌ها در زمان کامپایل

در مثال زیر، یک Lambda با کمک `if constexpr` رفتار متفاوتی را براساس ویژگی نوع ورودی انتخاب می‌کند.

```
#include <concepts>
#include <type_traits>

auto process_value = []<typename T>(T value) {
    using U = std::remove_cvref_t<T>;

    if constexpr (std::integral<U>) {
        return value + 1;
    } else {
        return value;
    }
};
```

در این مثال، `if constexpr` هنگام Instantiate شدن قالب ارزیابی می‌شود و شاخه غیرمعتبر برای نوع مربوطه کنار گذاشته می‌شود.

این روش در طراحی الگوریتم‌های Generic مفید است؛ به‌ویژه هنگامی که لازم باشد برای نوع‌های مختلف، پیاده‌سازی متفاوتی داشته باشیم، بدون اینکه Interface عمومی تابع را تغییر دهیم.

البته، تفاوت نوع بازگشتی میان شاخه‌های `if constexpr` می‌تواند بر نوع نتیجه هر Instantiate اثر بگذارد. بنابراین، هنگام طراحی APIهایی که باید نوع بازگشتی ثابتی داشته باشند، لازم است این موضوع به‌صورت آگاهانه مدیریت شود.

### استفاده در الگوریتم‌های STL

در الگوریتم‌های کتابخانه استاندارد، بسیاری از Lambdaها صرفاً به `auto` احتیاج دارند. اما هنگامی که بخواهیم نوع مشخصی را محدود کنیم یا رابطه‌ای میان نوع‌ها ایجاد کنیم، Template Lambdas می‌توانند انتخاب بهتری باشند.

```
#include <concepts>
#include <ranges>
#include <vector>

int main() {
    std::vector<int> numbers = {5, 1, 8, 2, 4};

    std::ranges::sort(
        numbers,
        []<std::totally_ordered T>(T const& left, T const& right) {
            return left < right;
        }
    );
}
```

در این مثال، پارامتر قالبی `T` نام‌گذاری شده و با Concept `std::totally_ordered` محدود شده است.

این طراحی هنگامی مفید است که خود Lambda نیاز به اطلاعات نوعی داشته باشد یا بخواهیم Constraint مشخصی را در Interface آن بیان کنیم.

بااین‌حال، برای یک Comparator ساده که فقط روی مقادیر یک نوع مشخص کار می‌کند، استفاده از نوع صریح یا یک Lambda معمولی ممکن است خواناتر باشد. صریح بودن Template Parameter List به‌تنهایی تضمین‌کننده کد بهتر نیست.

## مدیریت Capture و وضعیت داخلی Lambda

Template Lambdas از همان قواعد Capture مربوط به Lambdaهای معمولی پیروی می‌کنند. پارامترهای قالبی، جایگزین Capture نیستند و متغیرهای محیط پیرامون باید از طریق قواعد معمول Capture در دسترس قرار بگیرند.

```
int offset = 10;

auto add_offset = [offset]<typename T>(T value) {
    return value + offset;
};
```

در این مثال، `offset` با مقدار در Closure ذخیره می‌شود و `T` نوع مقدار ورودی را مشخص می‌کند.

اگر بخواهیم نسخه ذخیره‌شده متغیر را در بدنه Lambda تغییر دهیم، باید از `mutable` استفاده کنیم.

```
auto counter = [count = 0]<typename T>(T increment) mutable {
    count += static_cast<int>(increment);
    return count;
};
```

در این نمونه، `count` بخشی از وضعیت داخلی Closure است. کلیدواژه `mutable` امکان تغییر این نسخه ذخیره‌شده را فراهم می‌کند، اما رفتار پارامترهای قالبی را تغییر نمی‌دهد.

همچنین، Capture با Reference به متغیرهای محلی باید با ملاحظات Lifetime انجام شود. اگر Closure پس از پایان عمر متغیر مرجع نگه‌داری‌شده فراخوانی شود، احتمال دسترسی به حافظه نامعتبر وجود دارد.

این مسئله ارتباطی به Template Lambdas ندارد و در Lambdaهای معمولی نیز باید به آن توجه کرد.

## پیاده‌سازی Lambdaهای بازگشتی

بازگشت یا Recursion در Lambdaها موضوعی جدا از Template Lambdas است، اما پارامترهای قالبی صریح می‌توانند در پیاده‌سازی الگوهای بازگشتی مفید باشند.

در ++C20، تعریف مستقیم یک نام برای خود Lambda در بدنه آن به‌صورت خودکار انجام نمی‌شود. یکی از روش‌های متداول این است که خود Closure به‌عنوان یک پارامتر به Lambda منتقل شود.

```
auto factorial = []<typename Self>(
    Self const& self,
    unsigned int n
) -> unsigned int {
    return n <= 1
        ? 1U
        : n * self(self, n - 1);
};

auto result = factorial(factorial, 5);
```

در این مثال، پارامتر `Self` نوع Closure را دریافت می‌کند و از طریق آن می‌توان همان Lambda را مجدداً فراخوانی کرد.

این الگو در ++C20 معتبر است، اما باید توجه داشت که پارامتر `self` به‌صورت دستی به Lambda داده شده است. این قابلیت به معنی وجود یک مکانیزم ویژه برای Recursion در Template Lambdas نیست.

در ++C23، Explicit Object Parameters نیز امکان تعریف الگوهای بازگشتی و برخی Callableهای عمومی را فراهم می‌کنند. آن قابلیت از نظر نحوی با Template Lambdas در ++C20 متفاوت است و نباید این دو را با یکدیگر اشتباه گرفت.

## استفاده از Template Lambdas در زمان کامپایل

Lambdaها می‌توانند در شرایط مناسب به‌صورت Compile-Time نیز استفاده شوند. از ++C17 به بعد، Lambdaهایی که شرایط لازم را داشته باشند می‌توانند به‌صورت ضمنی `constexpr` باشند؛ بنابراین، Lambdaهای قالبی نیز در صورت رعایت محدودیت‌های مربوطه می‌توانند در ارزیابی‌های زمان کامپایل به کار روند.

```
inline constexpr auto square = []<typename T>(T value) {
    return value * value;
};

static_assert(square(4) == 16);
```

در این مثال، عبارت `static_assert` نتیجه را در زمان کامپایل بررسی می‌کند. بدنه Lambda عملیاتی انجام می‌دهد که برای این ارزیابی ثابت معتبر است.

این ویژگی برای ابزارهای Compile-Time، سیاست‌های محاسباتی، بررسی‌های ایستا و ساختارهای Generic مفید است.

### استفاده از Lambda بدون Capture به‌عنوان Non-Type Template Argument

در ++C20، Closure Type یک Lambda بدون Capture می‌تواند در شرایط استانداردشده، یک Structural Type باشد. این موضوع اجازه می‌دهد شیء حاصل از چنین Lambdaای به‌عنوان Non-Type Template Argument استفاده شود.

```
template<auto Callable>
struct callable_policy {
    static constexpr auto value = Callable;
};

inline constexpr auto square = []<typename T>(T value) {
    return value * value;
};

using SquarePolicy = callable_policy<square>;

static_assert(SquarePolicy::value(4) == 16);
```

در این نمونه، `square` یک شیء ثابت از Closure Type بدون Capture است و به‌عنوان آرگومان قالبی به `callable_policy` داده می‌شود.

این روش می‌تواند در طراحی Compile-Time Policyها و برخی APIهای بدون نیاز به Type Erasure مفید باشد.

اما این قابلیت محدودیت مهمی دارد: Lambdaهای دارای Capture عموماً واجد شرایط Structural Type نیستند؛ بنابراین، نمی‌توان فرض کرد که هر Closure را می‌توان به همین روش به‌عنوان یک Non-Type Template Argument استفاده کرد.

## تعیین صریح آرگومان‌های قالبی هنگام فراخوانی

در بیشتر موارد، Template Argument Deduction به‌صورت خودکار نوع پارامترها را تعیین می‌کند. بااین‌حال، گاهی لازم است یک یا چند آرگومان قالبی را صریحاً مشخص کنیم.

```
auto identity = []<typename T>(T value) {
    return value;
};

auto first = identity(42);

auto second = identity.operator()<long>(42L);
```

در نمونه نخست، نوع `T` استنتاج می‌شود. در نمونه دوم، نوع `T` با استفاده از Syntax مربوط به عضو قالبی Closure صریحاً مشخص شده است.

این شیوه ممکن است در بعضی APIها مفید باشد، اما نسبت به فراخوانی عادی پیچیده‌تر است. در طراحی یک Lambda عمومی، بهتر است اگر استنتاج نوع به‌درستی نتیجه می‌دهد، آن را به کامپایلر واگذار کنیم.

نکته دیگر این است که پارامتر قالبی‌ای که از هیچ آرگومان یا زمینه‌ای قابل استنتاج نباشد، معمولاً باید به‌صورت صریح مشخص شود؛ در غیر این صورت، فراخوانی با شکست Template Argument Deduction مواجه خواهد شد.

برای مثال:

```
auto make_value = []<typename T>(int value) {
    return static_cast<T>(value);
};

auto result = make_value.operator()<double>(42);
```

در این Lambda، نوع `T` از پارامتر `int` قابل استنتاج نیست. به همین دلیل، فراخوانی مستقیم عضو قالبی با آرگومان نوعی صریح ضروری است.

## محدودیت‌ها و خطاهای متداول

اگرچه Template Lambdas انعطاف‌پذیری قابل توجهی ایجاد می‌کنند، استفاده از آن‌ها باید با شناخت محدودیت‌های زبان همراه باشد.

### اشتباه گرفتن قابلیت C++20 با Auto Parameters

استفاده از `auto` در پارامترهای Lambda از ++C14 امکان‌پذیر است. اما فهرست پارامترهای قالبی صریح مانند `<typename T>` برای Lambdaها به ++C20 تعلق دارد.

در پروژه‌هایی که با استاندارد قدیمی‌تر کامپایل می‌شوند، استفاده از این نحو می‌تواند باعث خطای کامپایل شود.

### تصور اینکه صریح بودن نوع همیشه باعث بهبود عملکرد می‌شود

Template Lambdas از نظر ساختاری همچنان به Template Instantiation وابسته هستند. تعداد زیاد ترکیب‌های نوعی ممکن است زمان کامپایل را افزایش دهد و در بعضی طراحی‌ها بر اندازه فایل اجرایی اثر بگذارد.

به همین دلیل، استفاده از پارامتر قالبی صریح نباید صرفاً با هدف بهینه‌سازی عملکرد انجام شود. ابتدا باید مشخص شود که این قابلیت چه مزیت طراحی یا نوعی به کد اضافه می‌کند.

### نادیده گرفتن قواعد Deduction و Forwarding

در پارامترهای معمولی، استنتاج نوع می‌تواند Qualifierها و Referenceها را تحت تأثیر قرار دهد. به همین دلیل، برای نوشتن Wrapperهای عمومی باید با Template Argument Deduction، Forwarding Reference و Reference Collapsing آشنا بود.

صرف استفاده از `typename T` یا `T&&` تضمین نمی‌کند که یک Lambda برای تمام Value Categoryها رفتار صحیحی داشته باشد.

### استفاده بیش از حد از Constraints

هرچند Concepts می‌توانند Interface را دقیق‌تر کنند، Constraintهای پیچیده و تودرتو ممکن است خوانایی کد را کاهش دهند.

اگر شرط نوعی ساده است، استفاده از یک Concept استاندارد معمولاً کافی است. اگر الگوی پیچیده‌ای از Constraints لازم است، بهتر است آن منطق به یک Concept نام‌گذاری‌شده منتقل شود تا هم Lambda خواناتر باشد و هم منطق محدودسازی قابل استفاده مجدد باقی بماند.

### انتظار Overloadهای مستقل داخل یک Lambda

Template Lambda با یک Template Parameter List، به‌خودی‌خود یک مجموعه از چند عملگر فراخوانی مستقل با رفتارهای مختلف ایجاد نمی‌کند.

اگر هدف، تعریف Overloadهای مستقل است، باید از الگوهای مناسب مانند `if constexpr`، Constraints یا مجموعه‌های Callable مبتنی بر Overloaded Function Objects استفاده کرد.

در این موارد، انتخاب الگوی مناسب به میزان پیچیدگی رفتار و نیازهای Interface بستگی دارد.

### نادیده گرفتن Capture و Lifetime

Template Lambdas همان خطرهای مربوط به Capture را دارند. اگر یک Closure دارای Reference به متغیر محلی باشد، نگه‌داری آن پس از پایان عمر متغیر می‌تواند باعث رفتار نامعین شود.

پارامترهای قالبی هیچ تغییری در Lifetime داده‌های Capture‌شده ایجاد نمی‌کنند. این موضوع باید در طراحی Callableهایی که از Scope تعریف خود خارج می‌شوند، جدی گرفته شود.

## مقایسه Template Lambdas با Function Templates

Lambdaهای قالبی و Function Templates از یک سازوکار پایه مشترک استفاده می‌کنند، اما از نظر طراحی و کاربرد با یکدیگر تفاوت دارند.

| ویژگی                  | Template Lambda                                  | Function Template                                                                                              |
| ---------------------- | ------------------------------------------------ | -------------------------------------------------------------------------------------------------------------- |
| نوع                    | یک Closure Object با عملگر فراخوانی قالبی        | یک تابع قالبی                                                                                                  |
| Capture                | امکان Capture متغیرهای محیط پیرامون              | Capture مستقل وجود ندارد                                                                                       |
| Interface محلی         | مناسب برای تعریف Callable در یک Scope            | معمولاً مناسب برای APIهای تابعی نام‌گذاری‌شده                                                                  |
| استفاده در الگوریتم‌ها | مستقیماً به‌عنوان Callable قابل استفاده است      | تابع قالبی نیز می‌تواند به‌عنوان Callable استفاده شود، اما در بعضی موقعیت‌ها نیاز به انتخاب یا تطبیق امضا دارد |
| نوع Closure            | دارای یک Closure Type ناشناس                     | Closure Type ندارد                                                                                             |
| استفاده از قالب‌ها     | از Type Parameters و Constraints پشتیبانی می‌کند | از Type Parameters و Constraints پشتیبانی می‌کند                                                               |

در عمل، اگر نیاز به یک Callable محلی با Capture وجود داشته باشد، Template Lambda می‌تواند بسیار مناسب باشد. اگر هدف، طراحی یک تابع عمومی با نام مشخص و Interface مستقل از یک محیط محلی باشد، Function Template معمولاً انتخاب روشن‌تری است.

این دو روش رقیب مطلق یکدیگر نیستند. هر کدام برای دسته‌ای از مسائل طراحی شده‌اند و می‌توانند در یک پروژه واحد در کنار یکدیگر استفاده شوند.

## بررسی پشتیبانی کامپایلر و Feature-Test Macro

از آنجا که فهرست قالبی صریح برای Generic Lambdas در ++C20 معرفی شده است، بهتر است در پروژه‌های قابل حمل، پشتیبانی آن بررسی شود.

برای این منظور می‌توان از Feature-Test Macro استاندارد زبان استفاده کرد.

```
#if !defined(__cpp_generic_lambdas) || __cpp_generic_lambdas < 201707L
#error "Explicit template parameter lists for generic lambdas are not supported"
#endif
```

مقدار `201707L` برای پشتیبانی از Explicit Template Parameter Lists در Generic Lambdas تعریف شده است. این ماکرو در کنار تنظیم استاندارد زبان، راه مناسبی برای بررسی قابلیت کامپایلر محسوب می‌شود.

برای استفاده از این قابلیت، پروژه باید با حالت ++C20 یا استاندارد جدیدتر کامپایل شود. بااین‌حال، تعیین استاندارد زبان و وجود یک Feature-Test Macro جایگزین بررسی سایر قابلیت‌های موردنیاز پروژه نیست؛ به‌ویژه زمانی که کد از Concepts، Library Features جدید یا امکانات استانداردهای بعدی نیز استفاده می‌کند.

## جمع‌بندی

Template Lambdas در ++C20 امکان استفاده مستقیم از فهرست پارامترهای قالبی صریح در Lambda Expressions را فراهم می‌کنند. این قابلیت، Generic Lambdas را به Function Templates نزدیک‌تر می‌کند و در عین حال مزایای Closureها و Capture را حفظ می‌کند.

مهم‌ترین کاربردهای این قابلیت عبارت‌اند از نام‌گذاری مستقیم نوع‌های استنتاج‌شده، تعریف الگوهای نوعی دقیق‌تر، استفاده از Concepts و Constraints، طراحی Callableهای Variadic، نوشتن Wrapperهای عمومی و استفاده از Lambdaها در ساختارهای Compile-Time.

در کدهای ساده، Generic Lambda مبتنی بر `auto` همچنان می‌تواند انتخاب مناسبی باشد. اما هنگامی که نوع پارامتر باید در بخش‌های مختلف تعریف قابل استفاده باشد یا محدودیت‌های مشخصی بر نوع‌ها اعمال شود، Template Lambda معمولاً Interface روشن‌تر و کنترل بیشتری ارائه می‌کند.

بهترین رویکرد این است که از قابلیت‌های قالبی صریح زمانی استفاده شود که واقعاً به کنترل نوعی یا محدودسازی دقیق‌تر نیاز داریم؛ در غیر این صورت، یک Lambda ساده می‌تواند خواناتر و کافی باشد.
