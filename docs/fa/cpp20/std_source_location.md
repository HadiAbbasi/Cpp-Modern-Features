# معرفی `std::source_location` در ++C20

قابلیت `std::source_location` در استاندارد ++C20 راهکاری استاندارد برای دسترسی به اطلاعات محل قرارگیری کد در فایل منبع است. این قابلیت به برنامه‌نویسان اجازه می‌دهد اطلاعاتی مانند نام فایل، شماره خط، نام تابع و نام فایل منبع را در زمان اجرا به دست آورند؛ بدون آنکه مجبور باشند این اطلاعات را به‌صورت دستی به توابع ارسال کنند یا برای هر فراخوانی از Macroهای سفارشی استفاده کنند.

یکی از مهم‌ترین کاربردهای این قابلیت، توسعه سیستم‌های Logging، ثبت خطاها، ساخت ابزارهای تشخیصی و بهبود قابلیت نگهداری کد است. برای مثال، یک تابع ثبت گزارش می‌تواند به‌صورت خودکار مشخص کند که از کدام خط برنامه فراخوانی شده است؛ در نتیجه، هنگام بررسی خطاها دیگر نیازی نیست توسعه‌دهنده شماره خط و نام فایل را به‌صورت دستی مشخص کند.

## آشنایی با مفهوم `std::source_location`

در بسیاری از برنامه‌های ++C، دانستن محل دقیق وقوع یک رویداد برای عیب‌یابی اهمیت زیادی دارد. برای نمونه، وقتی یک تابع خطایی را ثبت می‌کند، ممکن است لازم باشد بدانیم کدام فایل، کدام خط و کدام تابع باعث ایجاد آن گزارش شده‌اند.

پیش از استاندارد ++C20، یکی از روش‌های رایج استفاده از Macroهای ازپیش‌تعریف‌شده زیر بود:

- `__FILE__` برای دریافت نام فایل منبع.
- `__LINE__` برای دریافت شماره خط جاری.
- `__func__` برای دریافت نام تابع جاری.
- `__DATE__` و `__TIME__` برای دریافت تاریخ و زمان ترجمه؛ این دو مورد اطلاعات مربوط به زمان کامپایل هستند، نه محل فراخوانی.

روش استفاده از این Macroها معمولاً به طراحی رابط‌های اختصاصی نیاز داشت و گاهی باعث پیچیدگی کد، وابستگی به Macroها و دشواری نگهداری می‌شد.

از طرف دیگر، اگر یک تابع معمولی را مستقیماً با `__FILE__` و `__LINE__` فراخوانی کنیم، اطلاعات محل فراخوانی به تابع منتقل می‌شوند؛ اما اگر این مقادیر داخل بدنه خود تابع محاسبه شوند، معمولاً محل تعریف یا پیاده‌سازی تابع را نشان خواهند داد، نه محل فراخوانی آن.

قابلیت `std::source_location` این مشکل را با ارائه یک نوع استاندارد در کتابخانه استاندارد ++C حل می‌کند.

### ساختار کلی این قابلیت

نوع `std::source_location` در Header استاندارد زیر تعریف شده است:

```
#include <source_location>
```

این نوع اطلاعات مربوط به محل قرارگیری یک بخش از کد را در قالب یک شیء در اختیار برنامه قرار می‌دهد. رابط عمومی آن شامل توابع زیر است:

| تابع عضو          | کاربرد                                              |
| ----------------- | --------------------------------------------------- |
| `line()`          | دریافت شماره خط منبع                                |
| `column()`        | دریافت شماره ستون منبع، در صورت پشتیبانی پیاده‌سازی |
| `file_name()`     | دریافت نام فایل منبع                                |
| `function_name()` | دریافت نام تابع مرتبط با محل ثبت‌شده                |
| `current()`       | ساخت شیء حاوی اطلاعات محل جاری کد                   |

چهار تابع نخست، اطلاعات ثبت‌شده در شیء را به‌صورت مقدارهای قابل‌خواندن ارائه می‌کنند. تابع `current()` نیز برای ثبت اطلاعات محل کد استفاده می‌شود و رفتار آن به محل قرارگیری فراخوانی در متن برنامه وابسته است.

نکته مهم این است که `std::source_location` یک قابلیت کتابخانه استاندارد است که در ++C20 معرفی شده است؛ بنابراین، برای استفاده از آن باید کامپایلر و کتابخانه استاندارد مورد استفاده، پشتیبانی لازم را داشته باشند.

## درک نحوه عملکرد `std::source_location`

ویژگی اصلی این قابلیت، توانایی ثبت محل فراخوانی در زمان استفاده از تابع `current()` است. درک این رفتار برای استفاده صحیح از آن ضروری است.

### مثال ساده برای دریافت محل کد

کد زیر یک نمونه ساده از دریافت اطلاعات محل جاری را نشان می‌دهد:

```
#include <iostream>
#include <source_location>

int main() {
    const auto location = std::source_location::current();

    std::cout << "File: " << location.file_name() << '\n';
    std::cout << "Line: " << location.line() << '\n';
    std::cout << "Column: " << location.column() << '\n';
    std::cout << "Function: " << location.function_name() << '\n';
}
```

در این مثال، فراخوانی `std::source_location::current()` درون تابع `main` قرار دارد؛ بنابراین، اطلاعات ثبت‌شده به محل همین فراخوانی در فایل منبع مربوط می‌شوند.

خروجی احتمالی برنامه ممکن است به شکل زیر باشد:

```
File: main.cpp
Line: 6
Column: 48
Function: int main()
```

خروجی دقیق به کامپایلر، نحوه فراخوانی و پیاده‌سازی کتابخانه استاندارد بستگی دارد. برای مثال، قالب نام تابع ممکن است در کامپایلرهای مختلف متفاوت باشد و نام فایل نیز ممکن است یک مسیر نسبی یا مطلق باشد.

همچنین، مقدار `column()` در صورت پشتیبانی پیاده‌سازی در دسترس است؛ بنابراین، نباید بدون بررسی الزامات محیط هدف، قالب دقیق آن را در ابزارهای تشخیصی تضمین‌شده فرض کرد.

## کاربرد مهم پارامتر پیش‌فرض در توابع

یکی از مهم‌ترین کاربردهای `std::source_location`، استفاده از آن به‌عنوان پارامتر پیش‌فرض یک تابع است. در این حالت، اگر فراخواننده آرگومان مربوط به محل کد را ارسال نکند، مقدار پیش‌فرض در محل فراخوانی تابع ارزیابی می‌شود.

این رفتار باعث می‌شود تابع بتواند محل فراخوانی‌کننده را ثبت کند، نه محل تعریف خودش.

### مثال ثبت خودکار محل فراخوانی

```
#include <iostream>
#include <source_location>
#include <string_view>

void log_message(
    std::string_view message,
    const std::source_location& location =
        std::source_location::current()
) {
    std::cout
        << location.file_name()
        << ':'
        << location.line()
        << " in "
        << location.function_name()
        << " -> "
        << message
        << '\n';
}

void process_data() {
    log_message("Processing started");
}

int main() {
    log_message("Application started");
    process_data();
}
```

در این برنامه، فراخوانی تابع `log_message` در دو محل متفاوت انجام می‌شود. در هر دو مورد، مقدار پیش‌فرض پارامتر `location` در محل فراخوانی همان تابع ارزیابی می‌شود.

در نتیجه، گزارش اول به خط فراخوانی در `main` و گزارش دوم به خط فراخوانی در `process_data` اشاره می‌کند.

این تفاوت، هسته اصلی کاربرد `std::source_location` در سیستم‌های Logging است.

### چرا پارامتر باید مقدار پیش‌فرض داشته باشد؟

در صورتی که تابع به شکل زیر تعریف شود، رفتار متفاوتی خواهیم داشت:

```
void log_message(std::string_view message) {
    const auto location = std::source_location::current();

    std::cout << location.file_name()
              << ':' << location.line()
              << " -> " << message << '\n';
}
```

در این حالت، `current()` درون بدنه تابع اجرا می‌شود. بنابراین، اطلاعات ثبت‌شده به محل فراخوانی `current()` در پیاده‌سازی `log_message` مربوط هستند؛ نه به محل فراخوانی `log_message` توسط کدهای دیگر.

این نکته یکی از رایج‌ترین اشتباهات هنگام استفاده از `std::source_location` است.

قاعده کاربردی این است که اگر هدف ثبت محل فراخوانی‌کننده باشد، معمولاً باید `std::source_location::current()` را در مقدار پیش‌فرض پارامتر تابع قرار داد.

## بررسی توابع عضو و اطلاعات قابل دریافت

نوع `std::source_location` رابطی کوچک دارد، اما هر یک از توابع آن کاربرد مشخصی در ابزارهای تشخیصی دارند.

### دریافت شماره خط با `line()`

تابع `line()` شماره خطی را برمی‌گرداند که اطلاعات محل منبع به آن مربوط است.

```
#include <iostream>
#include <source_location>

void inspect_location(
    const std::source_location& location =
        std::source_location::current()
) {
    std::cout << "Line: " << location.line() << '\n';
}

int main() {
    inspect_location();
}
```

این مقدار برای اتصال پیام‌های خطا به محل دقیق کد و بررسی گزارش‌های طولانی بسیار مفید است.

باید توجه داشت که شماره خط به محتوای فایل منبع و فرایند پیش‌پردازش وابسته است. تغییر خطوط فایل یا استفاده از دستور پیش‌پردازنده `#line` می‌تواند بر اطلاعاتی که کامپایلر ثبت می‌کند تأثیر بگذارد.

### دریافت نام فایل با `file_name()`

تابع `file_name()` نام فایل منبع مرتبط با محل ثبت‌شده را برمی‌گرداند.

```
#include <iostream>
#include <source_location>

void print_file(
    const std::source_location& location =
        std::source_location::current()
) {
    std::cout << location.file_name() << '\n';
}

int main() {
    print_file();
}
```

نام بازگشتی ممکن است شامل مسیر کامل، مسیر نسبی یا صرفاً نام فایل باشد. استاندارد، یکسان بودن قالب مسیر میان کامپایلرها و سیستم‌عامل‌های مختلف را تضمین نمی‌کند.

برای پروژه‌هایی که خروجی Logging را در محیط‌های مختلف تولید می‌کنند، نباید فرض کرد نام فایل همیشه یکسان خواهد بود.

همچنین، اگر مسیرهای کامل فایل در خروجی برنامه قرار بگیرند، ممکن است ساختار داخلی سیستم توسعه یا مسیرهای محرمانه محیط Build افشا شوند. در چنین شرایطی بهتر است پیش از انتشار گزارش، مسیرها به شکل مناسبی محدود یا پاک‌سازی شوند.

### دریافت نام تابع با `function_name()`

تابع `function_name()` نام تابع مرتبط با محل ثبت‌شده را ارائه می‌دهد.

```
#include <iostream>
#include <source_location>

void inspect(
    const std::source_location& location =
        std::source_location::current()
) {
    std::cout << location.function_name() << '\n';
}

int main() {
    inspect();
}
```

مقدار خروجی برای ابزارهای تشخیصی مفید است، اما قالب آن به پیاده‌سازی وابسته است. برای مثال، ممکن است اطلاعاتی مانند نوع بازگشتی، پارامترها، نام فضای نام یا مشخصات دیگر در رشته وجود داشته باشند.

بنابراین، `function_name()` نباید به‌عنوان یک API قابل‌حمل برای تجزیه نام تابع یا استخراج ساختار دقیق امضای تابع استفاده شود.

اگر برنامه به نام‌های استانداردشده برای ثبت رویدادها، ذخیره‌سازی در پایگاه داده یا ارتباط میان سرویس‌ها نیاز دارد، بهتر است شناسه‌های صریح و پایدار تعریف شوند.

### دریافت ستون با `column()`

تابع `column()` شماره ستون محل منبع را برمی‌گرداند.

```
#include <iostream>
#include <source_location>

void print_column(
    const std::source_location& location =
        std::source_location::current()
) {
    std::cout << location.column() << '\n';
}

int main() {
    print_column();
}
```

این قابلیت در ابزارهای تحلیل کد، گزارش خطاهای دقیق‌تر و محیط‌های توسعه مفید است. بااین‌حال، پشتیبانی و مقداردهی اطلاعات ستون به پیاده‌سازی وابسته است و ممکن است اطلاعات قابل‌اتکایی در همه محیط‌ها فراهم نشود.

برای برنامه‌هایی که به شماره ستون به‌عنوان بخشی از قرارداد خروجی وابسته هستند، باید رفتار کامپایلرها و نسخه‌های هدف به‌طور جداگانه آزمایش شود.

## طراحی توابع با `std::source_location`

برای استفاده حرفه‌ای از این قابلیت، باید به نحوه طراحی رابط توابع توجه کرد. محل قرارگیری پارامتر، نوع پارامتر و شیوه انتقال آن می‌توانند بر خوانایی و رفتار API تأثیر بگذارند.

### انتخاب نوع پارامتر مناسب

از آنجا که `std::source_location` یک شیء کوچک با رابطی ساده است، معمولاً می‌توان آن را به‌صورت مقداری یا با ارجاع ثابت دریافت کرد.

نمونه متداول زیر از ارجاع ثابت استفاده می‌کند:

```
#include <iostream>
#include <source_location>
#include <string_view>

void report(
    std::string_view message,
    const std::source_location& location =
        std::source_location::current()
) {
    std::cout << location.file_name()
              << ':' << location.line()
              << ": " << message << '\n';
}
```

این شکل رابط، خوانایی مناسبی دارد و از کپی غیرضروری در سطح API جلوگیری می‌کند؛ هرچند هزینه واقعی کپی یک شیء `std::source_location` به پیاده‌سازی وابسته است و معمولاً نباید بدون اندازه‌گیری بهینه‌سازی بیش از حد انجام داد.

استفاده از ارجاع ثابت همچنین به این معنا نیست که شیء محل منبع باید تا پایان اجرای تابع زنده بماند؛ پارامتر پیش‌فرض یک مقدار معتبر برای فراخوانی تولید می‌کند و تابع می‌تواند در طول اجرای همان فراخوانی از آن استفاده کند.

### انتخاب محل پارامتر در امضای تابع

اگر پارامتر `std::source_location` به‌صورت پیش‌فرض تعریف شده باشد، تمام پارامترهای معمولی بعد از آن نیز باید مقدار پیش‌فرض داشته باشند.

برای مثال، شکل زیر معتبر نیست:

```
void report(
    std::string_view message,
    const std::source_location& location =
        std::source_location::current(),
    int level
);
```

در این تعریف، پارامتر `level` بدون مقدار پیش‌فرض پس از پارامتری قرار گرفته است که مقدار پیش‌فرض دارد. چنین ترتیبی در اعلان معمول تابع مجاز نیست.

در عوض، می‌توان پارامتر محل منبع را در انتهای فهرست پارامترها قرار داد:

```
#include <source_location>
#include <string_view>

void report(
    std::string_view message,
    int level,
    const std::source_location& location =
        std::source_location::current()
);
```

در این طراحی، پارامترهای اصلی تابع پیش از پارامتر اختیاری محل منبع قرار می‌گیرند و استفاده از تابع ساده باقی می‌ماند.

### استفاده از مقدار پیش‌فرض در APIهای عمومی

برای توابع عمومی یک کتابخانه، افزودن پارامتر `std::source_location` می‌تواند اطلاعات تشخیصی ارزشمندی فراهم کند. بااین‌حال، بهتر است این قابلیت به‌عنوان بخشی از طراحی رابط در نظر گرفته شود، نه صرفاً یک جزئیات پیاده‌سازی.

اگر تابع یک API عمومی و پایدار است، باید بررسی شود که آیا اضافه کردن پارامتر جدید با نسخه‌های قبلی کتابخانه سازگار خواهد بود یا خیر. تغییر امضای تابع ممکن است بر سازگاری ABI، اشاره‌گرهای تابع، Overloadها و کدهای مصرف‌کننده تأثیر بگذارد.

در کتابخانه‌های پرکاربرد، می‌توان این قابلیت را از ابتدا در طراحی API لحاظ کرد تا در آینده نیازی به تغییرهای ناسازگار نباشد.

## مقایسه با Macroهای پیش‌پردازنده

قابلیت `std::source_location` بسیاری از نیازهایی را که پیش‌تر با Macroهای پیش‌پردازنده برطرف می‌شدند، پوشش می‌دهد؛ اما این دو روش از نظر سازوکار و کاربرد کاملاً یکسان نیستند.

### مقایسه با `__FILE__` و `__LINE__`

Macroهای `__FILE__` و `__LINE__` از امکانات استاندارد پیش‌پردازنده هستند و به استاندارد ++C20 محدود نمی‌شوند.

```
#include <iostream>

void log_message(const char* message) {
    std::cout << __FILE__ << ':' << __LINE__
              << ": " << message << '\n';
}

int main() {
    log_message("Started");
}
```

در این مثال، `__FILE__` و `__LINE__` درون بدنه تابع قرار دارند؛ بنابراین، معمولاً اطلاعات مربوط به محل تعریف این Macroها در متن تابع را نشان می‌دهند.

برای ثبت محل فراخوانی‌کننده، می‌توان آن‌ها را در یک Macro قرار داد:

```
#include <iostream>

void log_message(
    const char* message,
    const char* file,
    int line
) {
    std::cout << file << ':' << line
              << ": " << message << '\n';
}

#define LOG_MESSAGE(message) \
    log_message(message, __FILE__, __LINE__)

int main() {
    LOG_MESSAGE("Started");
}
```

در این طراحی، Macro در محل فراخوانی گسترش می‌یابد و اطلاعات محل فراخوانی را به تابع منتقل می‌کند.

همین مسئله یکی از دلایل مهم معرفی `std::source_location` است؛ زیرا می‌توان بدون تعریف Macro اختصاصی، رابطی معمولی و خوانا طراحی کرد.

### مقایسه ویژگی‌ها

| ویژگی                          | Macroهای پیش‌پردازنده                      | `std::source_location`                  |
| ------------------------------ | ------------------------------------------ | --------------------------------------- |
| نیاز به Macro اختصاصی          | معمولاً برای ثبت محل فراخوانی لازم است     | خیر                                     |
| پشتیبانی استاندارد             | در استانداردهای قدیمی‌تر نیز وجود دارد     | از ++C20                                |
| ثبت محل فراخوانی               | با گسترش Macro در محل فراخوانی             | با `current()` در مقدار پیش‌فرض پارامتر |
| نام تابع                       | با `__func__` و طراحی مناسب                | با `function_name()`                    |
| شماره ستون                     | Macro استاندارد مستقیمی ندارد              | با `column()`                           |
| تعامل با APIهای معمولی         | ممکن است به Macroهای پوششی نیاز داشته باشد | به‌صورت پارامتر معمولی تابع             |
| انعطاف‌پذیری پیش‌پردازنده      | بالا                                       | محدود به اطلاعات محل منبع               |
| قابلیت استفاده در APIهای عمومی | امکان‌پذیر، اما گاهی پیچیده                | معمولاً خواناتر و مناسب‌تر              |

البته Macroها همچنان کاربردهای خاص خود را دارند؛ برای مثال، تولید کد در زمان پیش‌پردازش، ساخت رابط‌های شرطی و پیاده‌سازی برخی الگوهای خاصی که به پیش‌پردازنده وابسته‌اند.

بنابراین، `std::source_location` جایگزین تمام Macroها نیست؛ بلکه برای دریافت اطلاعات محل کد، در بسیاری از طراحی‌ها گزینه‌ای استانداردتر و تمیزتر است.

## کاربرد در سیستم‌های Logging

یکی از بهترین موارد استفاده از `std::source_location`، ساخت سیستم ثبت گزارش است. در چنین سیستمی، گزارش‌ها معمولاً باید علاوه بر پیام، اطلاعاتی مانند سطح اهمیت، نام فایل، شماره خط و نام تابع را نیز ذخیره کنند.

### ساخت یک Logger ساده

```
#include <iostream>
#include <source_location>
#include <string_view>

enum class LogLevel {
    Info,
    Warning,
    Error
};

void log(
    LogLevel level,
    std::string_view message,
    const std::source_location& location =
        std::source_location::current()
) {
    const char* level_name = "INFO";

    switch (level) {
        case LogLevel::Info:
            level_name = "INFO";
            break;
        case LogLevel::Warning:
            level_name = "WARNING";
            break;
        case LogLevel::Error:
            level_name = "ERROR";
            break;
    }

    std::cerr
        << '[' << level_name << "] "
        << location.file_name() << ':'
        << location.line() << " in "
        << location.function_name() << " - "
        << message << '\n';
}

int main() {
    log(LogLevel::Info, "Application started");
    log(LogLevel::Warning, "Configuration is incomplete");
    log(LogLevel::Error, "Failed to load resource");
}
```

این طراحی اطلاعات محل فراخوانی را بدون نیاز به ارسال دستی نام فایل و شماره خط ثبت می‌کند.

در یک سیستم Logging واقعی، می‌توان قابلیت‌های دیگری مانند Timestamp، شناسه Thread، شناسه درخواست، خروجی ساختاریافته JSON و انتقال پیام به فایل یا سرویس خارجی را نیز اضافه کرد.

### طراحی توابع سطح بالاتر برای Logging

در سیستم‌های بزرگ، معمولاً توابع سطح بالاتری برای ثبت پیام‌های مشخص وجود دارند؛ مانند `log_info`، `log_warning` و `log_error`.

نکته مهم این است که اگر تابع سطح بالاتر خودش پارامتر پیش‌فرض `std::source_location::current()` را داشته باشد، محل ثبت‌شده معمولاً به محل فراخوانی همان تابع سطح بالاتر مربوط می‌شود.

اما اگر تابع سطح بالاتر، محل منبع را به تابع داخلی ارسال کند، اطلاعات ثبت‌شده می‌توانند محل فراخواننده اصلی را حفظ کنند.

```
#include <iostream>
#include <source_location>
#include <string_view>

void log_impl(
    std::string_view level,
    std::string_view message,
    const std::source_location& location
) {
    std::cout << '[' << level << "] "
              << location.file_name() << ':'
              << location.line() << ": "
              << message << '\n';
}

void log_error(
    std::string_view message,
    const std::source_location& location =
        std::source_location::current()
) {
    log_impl("ERROR", message, location);
}

void load_resource() {
    log_error("Resource loading failed");
}

int main() {
    load_resource();
}
```

در این نمونه، مقدار `location` در محل فراخوانی `log_error` تولید می‌شود و سپس بدون جایگزینی با اطلاعات جدید به `log_impl` منتقل می‌شود.

این الگو برای حفظ محل اصلی وقوع رویداد در لایه‌های مختلف یک سیستم بسیار مهم است.

### مدیریت Wrapperها و توابع کمکی

در طراحی‌های پیچیده‌تر، ممکن است چند لایه تابع بین کد اصلی و سیستم Logging قرار بگیرند. اگر هر لایه محل منبع را دوباره با `current()` تولید کند، ممکن است گزارش به جای محل فراخوانی‌کننده اصلی، به یکی از توابع واسط اشاره کند.

قاعده مناسب این است که محل منبع را در مرزی ثبت کنیم که واقعاً قصد داریم آن محل را گزارش دهیم و سپس همان شیء را در لایه‌های داخلی منتقل کنیم.

این روش به‌ویژه برای سیستم‌های Logging مشترک میان چند ماژول یا کتابخانه مفید است.

## استفاده در توابع کمکی و ابزارهای تشخیصی

علاوه بر Logging، این قابلیت در ساخت ابزارهای تشخیصی و توابعی که خطاهای ورودی را گزارش می‌کنند نیز کاربرد دارد.

### ثبت محل فراخوانی در اعتبارسنجی ورودی

```
#include <iostream>
#include <source_location>
#include <stdexcept>
#include <string_view>

void require(
    bool condition,
    std::string_view message,
    const std::source_location& location =
        std::source_location::current()
) {
    if (!condition) {
        std::cerr << "Validation failed at "
                  << location.file_name() << ':'
                  << location.line() << '\n';

        throw std::runtime_error(std::string(message));
    }
}

int main() {
    require(10 > 0, "Value must be positive");
    require(5 < 0, "Unexpected value");
}
```

در این مثال، تابع `require` در صورت نامعتبر بودن شرط، محل فراخوانی‌کننده را ثبت می‌کند و سپس یک استثنا پرتاب می‌کند.

برای کامپایل این نمونه باید Header مربوط به `std::string` نیز اضافه شود:

```
#include <string>
```

این مثال نشان می‌دهد که چگونه می‌توان اطلاعات تشخیصی را به یک ابزار اعتبارسنجی عمومی اضافه کرد، بدون آنکه هر فراخواننده مجبور باشد نام فایل و شماره خط را ارسال کند.

### استفاده در قراردادهای برنامه

در برخی پروژه‌ها، توابعی برای بررسی پیش‌شرط‌ها، پس‌شرط‌ها و فرضیات داخلی تعریف می‌شوند. ثبت محل فراخوانی در این توابع می‌تواند تشخیص خطاهای طراحی را آسان‌تر کند.

بااین‌حال، `std::source_location` به‌خودی‌خود هیچ شرطی را بررسی نمی‌کند، هیچ استثنایی پرتاب نمی‌کند و هیچ رفتار اعتبارسنجی را ارائه نمی‌دهد. این نوع فقط اطلاعات محل کد را در اختیار برنامه قرار می‌دهد؛ تصمیم‌گیری درباره نحوه برخورد با خطا بر عهده طراحی برنامه است.

## رفتار در توابع قالبی و Generic Programming

استفاده از `std::source_location` در توابع قالبی نیز امکان‌پذیر است. در این شرایط، باید تفاوت میان محل تعریف قالب، محل نمونه‌سازی قالب و محل فراخوانی تابع را در نظر گرفت.

### نمونه‌ای از تابع قالبی

```
#include <iostream>
#include <source_location>

template <typename T>
void inspect_value(
    const T& value,
    const std::source_location& location =
        std::source_location::current()
) {
    std::cout << "Value: " << value << '\n';
    std::cout << "File: " << location.file_name() << '\n';
    std::cout << "Line: " << location.line() << '\n';
}

int main() {
    inspect_value(42);
    inspect_value(3.14);
}
```

در این مثال، پارامتر پیش‌فرض محل منبع به محل فراخوانی تابع قالبی مربوط می‌شود. اطلاعات ثبت‌شده به‌طور خودکار به محل تعریف قالب یا خطی که کامپایلر نمونه خاص قالب را تولید می‌کند تبدیل نمی‌شوند.

این ویژگی برای کتابخانه‌های Generic Programming مفید است؛ زیرا می‌توان اطلاعات محل استفاده از یک ابزار عمومی را در اختیار پیاده‌سازی داخلی آن قرار داد.

### استفاده در کلاس‌های قالبی

همین رویکرد در توابع عضو کلاس‌های قالبی نیز قابل استفاده است:

```
#include <iostream>
#include <source_location>

template <typename T>
class Container {
public:
    void inspect(
        const std::source_location& location =
            std::source_location::current()
    ) const {
        std::cout << "Type-specific operation\n";
        std::cout << location.file_name() << ':'
                  << location.line() << '\n';
    }
};

int main() {
    Container<int> first;
    Container<double> second;

    first.inspect();
    second.inspect();
}
```

در اینجا، اطلاعات محل کد از محل فراخوانی تابع عضو دریافت می‌شود. این موضوع می‌تواند در بررسی استفاده از APIهای قالبی و تشخیص رفتارهای غیرمنتظره مفید باشد.

## تعامل با Lambdaها و توابع بازگشتی

در کدهای مدرن ++C، Lambdaها و توابع بازگشتی بخش مهمی از طراحی برنامه هستند. `std::source_location` در این ساختارها نیز قابل استفاده است؛ اما باید مشخص باشد که کدام محل کد مورد نظر است.

### استفاده در Lambda

```
#include <iostream>
#include <source_location>

int main() {
    auto report = [](
        const std::source_location& location =
            std::source_location::current()
    ) {
        std::cout << location.file_name() << ':'
                  << location.line() << '\n';
    };

    report();
}
```

در این مثال، مقدار پیش‌فرض پارامتر Lambda در محل فراخوانی آن ارزیابی می‌شود. بنابراین، اطلاعات به محل فراخوانی `report()` مربوط هستند، نه صرفاً به محل تعریف بدنه Lambda.

این قابلیت برای توابع Callback و ابزارهای تشخیصی که در چند محل فراخوانی می‌شوند مفید است.

### انتقال محل منبع در توابع بازگشتی

در یک تابع بازگشتی، اگر هدف ثبت محل شروع عملیات باشد، بهتر است محل منبع یک بار در ورودی تابع دریافت شود و در صورت نیاز به فراخوانی‌های بازگشتی منتقل شود.

اگر در هر مرحله محل منبع جدیدی تولید شود، گزارش‌ها ممکن است به محل فراخوانی داخلی یا بازگشتی اشاره کنند، نه به محلی که عملیات اصلی آغاز شده است.

این مسئله بیشتر به طراحی جریان اطلاعات در برنامه مربوط است تا محدودیتی در خود `std::source_location`.

## نکات مهم درباره طول عمر و نگهداری اطلاعات

یکی از نکاتی که هنگام استفاده از `std::source_location` باید در نظر گرفت، تفاوت میان نگهداری خود شیء و نگهداری اشاره‌گرها یا رشته‌های به‌دست‌آمده از آن است.

### ذخیره‌سازی شیء محل منبع

می‌توان شیء `std::source_location` را در یک متغیر ذخیره کرد و بعداً از آن استفاده کرد:

```
#include <iostream>
#include <source_location>

std::source_location saved_location;

void capture_location(
    const std::source_location& location =
        std::source_location::current()
) {
    saved_location = location;
}

int main() {
    capture_location();

    std::cout << saved_location.file_name() << ':'
              << saved_location.line() << '\n';
}
```

در این مثال، شیء محل منبع پس از بازگشت تابع `capture_location` نیز قابل استفاده است. این موضوع با نگهداری ارجاع به یک پارامتر محلی متفاوت است؛ زیرا خود شیء ذخیره می‌شود.

در کاربردهای هم‌زمان، اگر چند Thread بتوانند متغیر مشترک `saved_location` را بدون هماهنگی بخوانند و بنویسند، باید قواعد معمول هم‌زمانی و Data Race در ++C رعایت شوند.

### ذخیره‌سازی رشته‌های مربوط به محل منبع

توابع `file_name()` و `function_name()` اشاره‌گر `const char*` برمی‌گردانند. این رشته‌ها را نباید بدون بررسی قرارداد طول عمر، برای نگهداری طولانی‌مدت به یک اشاره‌گر خام تبدیل کرد.

برای مثال، اگر اطلاعات باید در صف ناهم‌زمان Logging ذخیره شوند یا پس از پایان عملیات فعلی پردازش شوند، می‌توان رشته‌ها را در `std::string` کپی کرد.

```
#include <source_location>
#include <string>

struct SourceInfo {
    std::string file;
    std::string function;
    unsigned int line;
    unsigned int column;
};

SourceInfo copy_source_info(
    const std::source_location& location
) {
    return {
        location.file_name(),
        location.function_name(),
        location.line(),
        location.column()
    };
}
```

این ساختار، اطلاعات را در قالب رشته‌های مالکیت‌دار ذخیره می‌کند و برای صف‌های Logging، ذخیره‌سازی رویدادها و انتقال داده میان Threadها مناسب‌تر است.

## بررسی محدودیت‌ها و نکات طراحی

اگرچه `std::source_location` استفاده از اطلاعات محل کد را ساده می‌کند، محدودیت‌های آن باید در طراحی حرفه‌ای در نظر گرفته شوند.

### وابستگی به پیاده‌سازی

نام فایل، قالب نام تابع و جزئیات مربوط به ستون ممکن است بین کامپایلرها و محیط‌های Build متفاوت باشند. بنابراین، خروجی این قابلیت نباید بدون لایه‌ای از استانداردسازی، یک قالب متنی ثابت و قابل‌حمل فرض شود.

### نبود اطلاعات مربوط به Stack Trace

این نوع فقط اطلاعات یک محل در کد منبع را ارائه می‌دهد. `std::source_location` به‌تنهایی Stack Trace، زنجیره فراخوانی توابع، وضعیت Thread یا تاریخچه اجرای برنامه را ثبت نمی‌کند.

اگر هدف بررسی زنجیره کامل فراخوانی‌ها باشد، به ابزارهای Debugger، قابلیت‌های اختصاصی سیستم‌عامل یا کتابخانه‌های مناسب برای Stack Tracing نیاز خواهد بود.

### نبود تضمین برای رفتار یکسان در همه محیط‌ها

اگر برنامه در چند محیط مختلف Build می‌شود، باید پشتیبانی از Header استاندارد `<source_location>` و رفتار کامپایلرها بررسی شود. صرف انتخاب گزینه استاندارد ++C20 در کامپایلر، به‌تنهایی تضمین نمی‌کند که همه اجزای کتابخانه استاندارد به‌طور کامل در دسترس باشند.

### ملاحظات امنیتی

مسیر فایل‌های منبع ممکن است اطلاعات داخلی محیط توسعه یا زیرساخت Build را افشا کند. برای نمونه، مسیرهای کامل می‌توانند نام حساب‌های کاربری، ساختار دایرکتوری‌ها یا مسیرهای داخلی CI را نشان دهند.

اگر گزارش‌ها برای کاربران نهایی ارسال می‌شوند یا در سرویس‌های خارجی ذخیره می‌شوند، بهتر است اطلاعات مسیر بر اساس سیاست امنیتی پروژه پاک‌سازی شوند.

### ملاحظات مربوط به کارایی

هزینه استفاده از `std::source_location` به‌تنهایی معمولاً دلیل مناسبی برای اجتناب از آن نیست؛ اما هزینه کل Logging می‌تواند به فرمت‌سازی رشته، قفل‌ها، عملیات ورودی و خروجی و انتقال داده وابسته باشد.

در مسیرهای بسیار پرتکرار، بهتر است به جای حذف بی‌دلیل اطلاعات تشخیصی، هزینه واقعی سیستم اندازه‌گیری شود و در صورت نیاز از Logging شرطی، ثبت ناهم‌زمان یا قالب‌بندی تنبل استفاده شود.

### محدودیت در بازسازی نام‌های قابل‌حمل

مقدار `function_name()` برای نمایش و عیب‌یابی مناسب است، اما قرارداد قابل‌حملی برای تبدیل آن به شناسه یکتای تابع ارائه نمی‌کند. استفاده از این مقدار به‌عنوان کلید پایگاه داده، شناسه پایدار API یا معیار تشخیص هویت تابع می‌تواند باعث مشکلات سازگاری شود.

برای چنین کاربردهایی، شناسه‌های صریح و کنترل‌شده انتخاب مطمئن‌تری هستند.

## نکات مهم در استفاده از `std::source_location`

در پروژه‌های واقعی، رعایت چند اصل می‌تواند از بیشتر اشتباهات رایج جلوگیری کند.

- برای ثبت محل فراخوانی‌کننده، معمولاً `std::source_location::current()` را به‌عنوان مقدار پیش‌فرض پارامتر تعریف کنید.
- در توابع واسط، اگر حفظ محل اصلی مهم است، شیء محل منبع را به توابع داخلی منتقل کنید.
- قالب خروجی `function_name()` و مسیر `file_name()` را وابسته به یک کامپایلر خاص فرض نکنید.
- برای ذخیره‌سازی طولانی‌مدت یا انتقال ناهم‌زمان، در صورت نیاز اطلاعات رشته‌ای را کپی کنید.
- در APIهای عمومی، سازگاری امضا، Overloadها و ABI را هنگام افزودن پارامتر محل منبع بررسی کنید.
- در سیستم‌های Logging، `std::source_location` را با سطح اهمیت، زمان رویداد و شناسه‌های مناسب ترکیب کنید.
- در محیط‌های حساس، مسیرهای فایل را پیش از انتشار گزارش‌ها بررسی یا پاک‌سازی کنید.
- اگر Stack Trace یا تاریخچه کامل اجرای برنامه لازم است، از ابزار مکمل مناسب استفاده کنید.

## جمع‌بندی نهایی

قابلیت `std::source_location` در استاندارد ++C20 روشی استاندارد و خوانا برای دریافت اطلاعات مربوط به محل کد در اختیار برنامه‌نویسان قرار می‌دهد. مهم‌ترین مزیت آن، امکان ثبت محل فراخوانی‌کننده بدون نیاز به Macroهای اختصاصی و ارسال دستی اطلاعاتی مانند نام فایل و شماره خط است.

استفاده از پارامتر پیش‌فرض حاوی `std::source_location::current()` به‌ویژه در سیستم‌های Logging، توابع اعتبارسنجی، ابزارهای تشخیصی و کتابخانه‌های عمومی بسیار مفید است.

بااین‌حال، باید تفاوت میان محل فراخوانی تابع و محل اجرای `current()`، وابستگی قالب خروجی به پیاده‌سازی، محدودیت اطلاعات رشته‌ای و نیازهای امنیتی و کارایی را در نظر گرفت.

در مجموع، برای پروژه‌هایی که از ++C20 یا نسخه‌های جدیدتر استفاده می‌کنند، `std::source_location` یکی از ابزارهای استاندارد و کاربردی برای بهبود قابلیت عیب‌یابی و نگهداری کد است؛ به‌خصوص زمانی که اطلاعات محل کد باید به شکلی ساده، قابل‌انتقال در لایه‌های برنامه و بدون وابستگی غیرضروری به Macroها در دسترس باشند.
