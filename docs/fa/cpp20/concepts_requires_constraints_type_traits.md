# آموزش جامع Concepts، Constraints و requires در ++C20

## مقدمه و ضرورت مفاهیم جدید

استاندارد ++C20 با معرفی قابلیت‌های `Concepts`، عبارت `requires` و سیستم `Constraints`، روش تعریف و استفاده از `Templates` را به‌طور اساسی بهبود داد. هدف این قابلیت‌ها آن است که محدودیت‌های مربوط به انواع داده و عملیات مجاز، به‌جای باقی ماندن در مستندات یا آشکار شدن در پیام‌های خطای پیچیده، به‌صورت بخشی از رابط برنامه‌نویسی و قراردادهای کامپایل‌پذیر بیان شوند.

پیش از ++C20، برنامه‌نویسان معمولاً برای محدود کردن `Template`ها از تکنیک‌هایی مانند `SFINAE`، ابزارهای `std::enable_if`، ویژگی‌های `Type Traits` و `static_assert` استفاده می‌کردند. این روش‌ها همچنان در برخی موقعیت‌ها کاربرد دارند، اما اغلب باعث پیچیدگی اعلان‌ها، دشواری نگهداری کد و پیام‌های خطای غیرشفاف می‌شوند.

با استفاده از قابلیت‌های جدید، می‌توان مشخص کرد که یک تابع یا کلاس قالبی دقیقاً به چه ویژگی‌هایی از نوع ورودی نیاز دارد؛ برای مثال، آیا نوع موردنظر قابل مقایسه است، آیا می‌توان دو مقدار از آن را با یکدیگر جمع کرد یا آیا یک نوع، عملیات لازم برای پیمایش یک محدوده را فراهم می‌کند.

سه اصطلاح اصلی این مبحث ارتباط نزدیکی با یکدیگر دارند، اما معنای یکسانی ندارند:

- Concepts: ابزار نام‌گذاری و تعریف مجموعه‌ای از الزامات نوعی و عملیاتی برای `Template`ها.
- Constraints: مجموعه‌ای از قواعد منطقی که مشخص می‌کنند آیا یک `Template` یا گزینهٔ overload واجد شرایط استفاده است یا خیر.
- requires: کلمهٔ کلیدی زبان که در دو ساختار `requires-expression` و `requires-clause` به کار می‌رود تا الزامات را بیان یا اعمال کند.

درک تفاوت این سه مفهوم برای طراحی APIهای عمومی، کتابخانه‌های قالبی، الگوریتم‌های Generic و سیستم‌های دارای چندین `Overload` ضروری است.

## مفهوم Constraints و نحوه ارزیابی آن‌ها

### تعریف Constraints

در ++C20، یک `Constraint` شرطی است که کامپایلر می‌تواند برای تعیین واجد شرایط بودن یک `Template` یا تابع قالبی بررسی کند. این شرط معمولاً به ویژگی‌های نوع، معتبر بودن یک عبارت، وجود یک عضو یا برقرار بودن یک رابطهٔ منطقی وابسته است.

برای مثال، فرض کنید تابعی تنها برای انواعی قابل استفاده است که عملگر جمع آن‌ها معتبر باشد:

```
#include <concepts>

template <typename T>
concept Addable = requires(T a, T b) {
    a + b;
};

template <typename T>
requires Addable<T>
T add(T a, T b) {
    return a + b;
}
```

در این مثال، مفهوم `Addable` مشخص می‌کند که عبارت `a + b` باید برای نوع `T` معتبر باشد. سپس تابع `add` تنها زمانی در مجموعهٔ گزینه‌های قابل انتخاب قرار می‌گیرد که شرط `Addable<T>` برقرار باشد.

نکتهٔ مهم این است که معتبر بودن عبارت `a + b` لزوماً به معنای بازگرداندن نوع `T` نیست. ممکن است نوع حاصل متفاوت باشد؛ این موضوع در تعریف مفهوم `Addable` بررسی نشده است.

### تفاوت Constraints با اعتبارسنجی زمان اجرا

محدودیت‌های قالبی در زمان کامپایل بررسی می‌شوند و جایگزین اعتبارسنجی ورودی‌های زمان اجرا نیستند.

برای مثال، شرط قابل‌مقایسه‌بودن دو مقدار را می‌توان در زمان کامپایل بررسی کرد؛ اما اینکه مقدار یک عدد مثبت باشد یا یک اندیس در محدودهٔ مجاز قرار بگیرد، معمولاً به داده‌های زمان اجرا وابسته است.

```
#include <concepts>
#include <stdexcept>

template <std::integral T>
T divide(T numerator, T denominator) {
    if (denominator == 0) {
        throw std::invalid_argument("Division by zero");
    }

    return numerator / denominator;
}
```

در این مثال، `std::integral` نوع‌های صحیح را محدود می‌کند، اما صفر نبودن مخرج همچنان در زمان اجرا بررسی می‌شود. همچنین این تابع به‌دلیل قواعد تقسیم صحیح، برای مقادیر صحیح مناسب است و برای تقسیم اعشاری باید طراحی متفاوتی در نظر گرفته شود.

### رابطه Constraints با Template Instantiation

در هنگام استفاده از یک `Template`، کامپایلر باید بررسی کند که الزامات وابسته به نوع موردنظر برقرار هستند یا خیر. اگر یک `Constraint` برقرار نباشد، گزینهٔ مربوط معمولاً از مجموعهٔ گزینه‌های واجد شرایط برای انتخاب حذف می‌شود.

این رفتار به‌ویژه در `Overload Resolution` اهمیت دارد؛ زیرا می‌توان چند پیاده‌سازی برای یک نام تابع داشت و با محدودیت‌های متفاوت، انتخاب آن‌ها را به ویژگی‌های آرگومان‌ها وابسته کرد.

بااین‌حال، `Constraints` به معنای تضمین معتبر بودن تمام عملیات داخل بدنهٔ تابع نیست. شرط‌ها باید با نیازهای واقعی پیاده‌سازی هماهنگ باشند. اگر بدنه به عملیاتی وابسته باشد که در محدودیت‌ها بیان نشده و برای نوع انتخاب‌شده معتبر نباشد، برنامه همچنان می‌تواند با خطای کامپایل مواجه شود.

## معرفی requires-expression

### ساختار و کاربرد اصلی

عبارت `requires-expression` یکی از امکانات اصلی ++C20 است که برای بررسی معتبر بودن مجموعه‌ای از عبارات و الزامات استفاده می‌شود. این عبارت معمولاً نتیجه‌ای از نوع `bool` در زمان کامپایل تولید می‌کند و می‌تواند مستقیماً در تعریف یک `Concept` یا یک شرط قالبی استفاده شود.

ساختار کلی آن به این شکل است:

```
requires (parameter-list) {
    requirement-sequence
}
```

فهرست پارامترها اختیاری است. پارامترهای این فهرست صرفاً برای بیان و بررسی الزامات استفاده می‌شوند و لازم نیست برای آن‌ها در زمان اجرا مقداری ساخته شود.

برای نمونه:

```
template <typename T>
concept HasSize = requires(const T& value) {
    value.size();
};
```

این مفهوم بررسی می‌کند که آیا فراخوانی `value.size()` برای یک شیء ثابت از نوع `T` معتبر است یا خیر. نوع بازگشتی، پیچیدگی زمانی و معنای واقعی این تابع بررسی نمی‌شوند.

### انواع Requirement در requires-expression

چهار نوع اصلی `Requirement` در این ساختار وجود دارد:

- `Simple requirement`
- `Type requirement`
- `Compound requirement`
- `Nested requirement`

هرکدام جنبهٔ متفاوتی از اعتبار یک نوع یا عبارت را بررسی می‌کنند.

#### بررسی Simple requirement

ساده‌ترین نوع الزام، بررسی معتبر بودن یک عبارت است. در این حالت، نتیجه یا نوع عبارت به‌صورت صریح محدود نمی‌شود؛ تنها معتبر بودن خود عبارت اهمیت دارد.

```
template <typename T>
concept Incrementable = requires(T value) {
    ++value;
    value++;
};
```

در این مثال، هر دو عبارت افزایش پیشوندی و پسوندی باید معتبر باشند. اگر یکی از آن‌ها برای نوع `T` تعریف نشده باشد، مفهوم `Incrementable` برقرار نخواهد بود.

نکتهٔ مهم آن است که هر عبارت باید از نظر نحوی و قواعد زبان معتبر باشد، اما لزوماً هنگام اجرای برنامه واقعاً اجرا نمی‌شود. این عبارات در اینجا برای بررسی قابلیت‌های نوع استفاده شده‌اند.

#### بررسی Type requirement

الزام نوعی برای بررسی معتبر بودن یک نام نوع استفاده می‌شود؛ به‌ویژه زمانی که نوع موردنظر یک عضو داخلی از نوع دیگر باشد.

```
template <typename T>
concept HasValueType = requires {
    typename T::value_type;
};
```

در این مثال، نوع `T` باید دارای عضوی به نام `value_type` باشد که بتوان آن را به‌عنوان یک نوع تفسیر کرد.

این الزام صرفاً وجود یک نام نوع معتبر را بررسی می‌کند و تضمین نمی‌کند که نوع معرفی‌شده با نیازهای الگوریتم سازگار باشد.

#### بررسی Compound requirement

الزام ترکیبی زمانی کاربرد دارد که علاوه بر معتبر بودن یک عبارت، لازم باشد ویژگی‌های دیگری مانند نوع نتیجه یا عدم پرتاب استثنا نیز بررسی شوند.

ساختار کلی این الزام به شکل زیر است:

```
requires {
    { expression } noexcept -> Concept;
}
```

در این ساختار، اجزای `noexcept` و `-> Concept` اختیاری هستند. بخش `noexcept` مشخص می‌کند که عبارت نباید بتواند استثنا پرتاب کند؛ بخش `-> Concept` نیز مفهوم موردنظر را روی نوع نتیجه اعمال می‌کند.

برای مثال:

```
#include <concepts>

template <typename T>
concept IntegerLikeResult = requires(const T& value) {
    { value.getValue() } -> std::integral;
};
```

در این مثال، عبارت `value.getValue()` باید معتبر باشد و نوع نتیجهٔ آن نیز باید مفهوم `std::integral` را برآورده کند.

نکتهٔ ظریف آن است که در Compound requirement، مفهوم پس از `->` روی نوع `decltype((expression))` اعمال می‌شود؛ یعنی نوع عبارت با قواعد `decltype` و پرانتزگذاری دوگانه تعیین می‌شود. بنابراین، نوع مرجع و ویژگی‌های `const` می‌توانند در نتیجه مؤثر باشند.

برای نمونه، اگر تابع `getValue` یک مرجع به عدد صحیح بازگرداند، نتیجه الزاماً با مفهوم `std::integral` سازگار نیست؛ زیرا این مفهوم نوع مرجع را به‌عنوان یک نوع صحیح مستقل نمی‌پذیرد.

#### بررسی Nested requirement

الزام تو‌در‌تو برای بیان یک شرط منطقی دیگر داخل `requires-expression` استفاده می‌شود. این شرط باید با `requires` معرفی شود.

```
#include <concepts>

template <typename T>
concept SmallIntegral = requires {
    requires std::integral<T>;
    requires (sizeof(T) <= 4);
};
```

در این مثال، نوع `T` باید یک نوع صحیح باشد و اندازهٔ آن نیز نباید از چهار بایت بیشتر باشد.

توجه کنید که اندازهٔ نوع‌ها به پیاده‌سازی وابسته است. عبارت `sizeof(T) <= 4` الزاماً به معنای محدود کردن نوع به یک عرض بیت مشخص در تمام پلتفرم‌ها نیست؛ همچنین `sizeof` اندازهٔ شیء را برحسب بایت تعریف‌شده توسط پیاده‌سازی گزارش می‌کند، نه الزاماً بایت هشت‌بیتی.

### استفاده از پارامترهای requires-expression

پارامترهای داخل فهرست پارامترهای `requires-expression` به بیان عبارت‌های وابسته به نوع کمک می‌کنند.

```
template <typename T>
concept ComparableWithSelf = requires(const T& a, const T& b) {
    a == b;
    a != b;
};
```

این پارامترها اعلان‌های محلی مخصوص بررسی هستند و نمی‌توان از آن‌ها مانند متغیرهای معمولی در بدنهٔ تابع استفاده کرد.

اگر `requires-expression` در یک بافت غیرقالبی قرار بگیرد و نتیجهٔ بررسی از همان ابتدا نامعتبر باشد، ممکن است به‌جای نتیجهٔ `false` خطای کامپایل رخ دهد. بنابراین، نباید تصور کرد که هر عبارت `requires` می‌تواند هر خطای نحوی یا معنایی را به یک شرط منطقی ناموفق تبدیل کند.

## مفهوم requires-clause و روش اعمال محدودیت

### ساختار کلی requires-clause

در مقابل `requires-expression`، ساختار `requires-clause` برای اعمال محدودیت به یک اعلان قالبی استفاده می‌شود.

این شرط می‌تواند پس از فهرست پارامترهای قالب یا پس از فهرست پارامترهای تابع قرار بگیرد.

```
#include <concepts>

template <typename T>
requires std::integral<T>
T twice(T value) {
    return value + value;
}
```

در این مثال، `requires std::integral<T>` یک `requires-clause` است و استفاده از تابع را به نوع‌های صحیح محدود می‌کند.

همین محدودیت را می‌توان با یک `Concept` به شکل کوتاه‌تری نوشت:

```
#include <concepts>

template <std::integral T>
T twice(T value) {
    return value + value;
}
```

این دو اعلان از نظر محدودیت نوعی معادل‌اند. در شیوهٔ دوم، از `Constrained Template Parameter` استفاده شده است؛ در شیوهٔ اول، محدودیت صریحاً با `requires-clause` نوشته شده است.

### مقایسه محل‌های قرارگیری requires-clause

در ++C20، یک `requires-clause` می‌تواند پس از پارامترهای قالب یا پس از پارامترهای تابع قرار گیرد.

```
#include <concepts>

template <typename T>
requires std::integral<T>
T first(T value) {
    return value;
}

template <typename T>
T second(T value)
    requires std::integral<T>
{
    return value;
}
```

هر دو تابع محدودیت یکسانی دارند. انتخاب محل نوشتن شرط بیشتر به خوانایی و ساختار اعلان بستگی دارد.

برای قالب‌هایی که محدودیت‌های پیچیده‌تری دارند، بهتر است محدودیت‌ها به‌صورت منظم و نزدیک به اعلان مربوطه قرار بگیرند تا قرارداد تابع به‌آسانی قابل مشاهده باشد.

### استفاده از requires برای محدود کردن کلاس‌ها

محدودیت‌ها تنها برای توابع کاربرد ندارند و می‌توان آن‌ها را روی `Class Template`ها نیز اعمال کرد.

```
#include <concepts>

template <std::integral T>
class Counter {
public:
    explicit Counter(T initial) : value_(initial) {}

    T value() const {
        return value_;
    }

private:
    T value_;
};
```

در این مثال، ایجاد نمونه از `Counter` با نوع‌های غیرصحیح مجاز نیست.

این روش برای طراحی کلاس‌هایی که به قرارداد مشخصی دربارهٔ نوع داده نیاز دارند، بسیار مناسب است. بااین‌حال، محدود کردن نوع به یک دستهٔ استاندارد همیشه کافی نیست؛ گاهی باید ویژگی‌های دقیق‌تری مانند قابل‌افزایش‌بودن، قابلیت تبدیل یا پشتیبانی از عملیات خاص نیز بررسی شوند.

## معرفی Concepts و نحوه تعریف آن‌ها

### مفهوم Concept در ++C20

یک `Concept` نامی برای یک مجموعه از محدودیت‌ها است که مشخص می‌کند یک نوع باید چه ویژگی‌هایی داشته باشد تا در یک بافت قالبی خاص قابل استفاده باشد.

`Concept`ها با استفاده از کلمهٔ کلیدی `concept` تعریف می‌شوند و نتیجهٔ تعریف آن‌ها باید یک شرط منطقی معتبر باشد.

```
#include <concepts>

template <typename T>
concept Arithmetic = std::integral<T> || std::floating_point<T>;
```

در این مثال، مفهوم `Arithmetic` نوع‌های صحیح و اعشاری استاندارد را پوشش می‌دهد.

این مفهوم برخلاف تصور رایج، تمام انواعی را که از نظر ریاضی می‌توان با آن‌ها محاسبه انجام داد پوشش نمی‌دهد؛ برای مثال، یک کلاس سفارشی برای اعداد مختلط ممکن است عملیات حسابی داشته باشد، اما به‌طور خودکار عضو `std::integral` یا `std::floating_point` محسوب نمی‌شود.

### استفاده از Conceptهای استاندارد

کتابخانهٔ استاندارد ++C20 مجموعه‌ای از مفهوم‌های عمومی را در هدر `<concepts>` تعریف کرده است. این مفهوم‌ها برای استفاده در APIهای قالبی طراحی شده‌اند و معمولاً نسبت به تعریف شرط‌های تکراری و دست‌ساز، خواناتر و استانداردتر هستند.

| مفهوم استاندارد              | کاربرد                                                         |
| ---------------------------- | -------------------------------------------------------------- |
| `std::same_as`               | بررسی یکسان بودن دو نوع                                        |
| `std::derived_from`          | بررسی رابطهٔ ارث‌بری عمومی و بدون ابهام                        |
| `std::convertible_to`        | بررسی قابلیت تبدیل ضمنی مورد انتظار                            |
| `std::integral`              | بررسی نوع‌های صحیح                                             |
| `std::floating_point`        | بررسی نوع‌های اعشاری استاندارد                                 |
| `std::signed_integral`       | بررسی نوع‌های صحیح علامت‌دار                                   |
| `std::unsigned_integral`     | بررسی نوع‌های صحیح بدون علامت                                  |
| `std::constructible_from`    | بررسی قابلیت ساخت یک نوع از آرگومان‌های مشخص                   |
| `std::default_initializable` | بررسی قابلیت مقداردهی اولیهٔ پیش‌فرض                           |
| `std::copy_constructible`    | بررسی الزامات کپی‌سازی                                         |
| `std::move_constructible`    | بررسی الزامات ساخت با استفاده از مقدار قابل انتقال             |
| `std::assignable_from`       | بررسی الزامات انتساب                                           |
| `std::destructible`          | بررسی الزامات تخریب                                            |
| `std::invocable`             | بررسی امکان فراخوانی یک شیء با آرگومان‌های مشخص                |
| `std::predicate`             | بررسی الزامات یک رابطهٔ محمولی                                 |
| `std::regular`               | بررسی مجموعه‌ای از الزامات متداول برای انواع منظم              |
| `std::semiregular`           | بررسی مجموعه‌ای از الزامات پایه برای انواع قابل مقداردهی و کپی |
| `std::equality_comparable`   | بررسی الزامات مقایسهٔ برابری                                   |
| `std::totally_ordered`       | بررسی الزامات ترتیب کامل                                       |
| `std::ranges::range`         | بررسی وجود الزامات پایهٔ یک Range                              |

برای استفاده از این مفهوم‌ها باید هدر مربوطه را وارد کرد. مفهوم‌های ذکرشده در این جدول همگی به استاندارد ++C20 تعلق دارند، اما برخی مفهوم‌های مرتبط با `Ranges` در فضای نام `std::ranges` تعریف شده‌اند.

### تفاوت Conceptهای مشابه

بعضی از مفهوم‌های استاندارد نام‌های نزدیک به یکدیگر دارند، اما قراردادهای یکسانی را بیان نمی‌کنند.

برای مثال، `std::convertible_to<From, To>` صرفاً به این معنا نیست که یک عبارت تبدیل به `To` برای کامپایلر قابل قبول است. این مفهوم الزامات مربوط به تبدیل ضمنی و `static_cast` را نیز بررسی می‌کند و قراردادهای معنایی مشخصی دارد.

همچنین `std::derived_from<Derived, Base>` از `std::is_base_of_v` محدودتر است؛ زیرا رابطهٔ ارث‌بری عمومی و بدون ابهام را می‌سنجد و در حالت‌هایی مانند ارث‌بری خصوصی، نتیجه می‌تواند متفاوت باشد.

به همین ترتیب، `std::move_constructible<T>` به معنای وجود سازنده‌ای اختصاصی با امضای دقیق `T(T&&)` نیست. یک نوع ممکن است از طریق سازنده‌ای با پارامتر `const T&` نیز از یک مقدار rvalue ساخته شود و در بررسی مفهوم پذیرفته شود.

### طراحی Conceptهای اختصاصی

در پروژه‌های واقعی، مفهوم‌های استاندارد همیشه تمام نیازهای یک API را پوشش نمی‌دهند. در چنین شرایطی می‌توان یک مفهوم اختصاصی تعریف کرد که قرارداد واقعی موردنیاز را به‌صورت مستقیم بیان کند.

```
#include <concepts>

template <typename T>
concept NumericAccumulator = requires(T a, T b) {
    { a + b } -> std::same_as<T>;
    { a += b } -> std::same_as<T&>;
    { T{} } -> std::same_as<T>;
};
```

در این مثال، نوع باید از جمع و جمع انتسابی پشتیبانی کند و نتیجهٔ این عملیات‌ها نیز باید با نوع‌های مورد انتظار مطابقت داشته باشد.

توجه کنید که این مفهوم هنوز تضمین نمی‌کند عملیات جمع از نظر ریاضی رفتار مناسبی داشته باشد، سرریز ایجاد نکند یا ویژگی‌های مورد انتظار از یک انباشت‌گر را حفظ کند. چنین خصوصیات معنایی معمولاً از طریق مستندات، طراحی نوع و آزمون‌های مناسب مشخص می‌شوند.

### مفهوم‌های مرکب و استفادهٔ مجدد

یکی از مزیت‌های اصلی `Concept`ها آن است که می‌توان مفهوم‌های ساده‌تر را ترکیب کرد و مفهوم‌های سطح بالاتر ساخت.

```
#include <concepts>

template <typename T>
concept Numeric = std::integral<T> || std::floating_point<T>;

template <typename T>
concept Additive = requires(T a, T b) {
    { a + b } -> std::same_as<T>;
};

template <typename T>
concept NumericAdditive = Numeric<T> && Additive<T>;
```

در این مثال، `NumericAdditive` تنها نوع‌هایی را می‌پذیرد که هم شرایط `Numeric` و هم شرایط `Additive` را داشته باشند.

این نوع ترکیب به‌ویژه در کتابخانه‌های بزرگ مفید است؛ زیرا می‌توان الزامات مشترک را یک‌بار تعریف کرد و سپس در الگوریتم‌ها و کلاس‌های متعدد به کار برد.

البته نباید مفهوم‌ها را بدون نیاز واقعی بیش از حد خرد کرد. تعریف مفهوم‌های بسیار کوچک و پراکنده، اگر هیچ استفادهٔ مجدد یا ارزش معنایی مشخصی نداشته باشند، ممکن است خوانایی کد را کاهش دهد.

## تفاوت Named Concepts و Constraintهای خام

### استفاده از مفهوم نام‌گذاری‌شده

زمانی که یک محدودیت معنای مستقلی در طراحی API دارد یا در چند نقطه استفاده می‌شود، بهتر است به‌صورت یک `Concept` نام‌گذاری شود.

```
#include <concepts>

template <typename T>
concept StringLike = requires(const T& value) {
    { value.data() } -> std::convertible_to<const char*>;
    { value.size() } -> std::convertible_to<std::size_t>;
};
```

در این مثال، فرض شده است که هدر `<cstddef>` نیز برای استفاده از `std::size_t` وارد شود؛ بنابراین، نسخهٔ کامل و قابل کامپایل باید آن را نیز شامل کند:

```
#include <concepts>
#include <cstddef>

template <typename T>
concept StringLike = requires(const T& value) {
    { value.data() } -> std::convertible_to<const char*>;
    { value.size() } -> std::convertible_to<std::size_t>;
};
```

مفهوم `StringLike` قرارداد مشخصی را معرفی می‌کند و استفاده از آن در امضای توابع، هدف محدودیت را بهتر از مجموعه‌ای از عبارت‌های پراکنده نشان می‌دهد.

البته نامی مانند `StringLike` باید با معنای واقعی محدودیت سازگار باشد. این مفهوم الزاماً تمام ویژگی‌های یک رشته، مانند خاتمه‌یافتن با نویسهٔ صفر، مالکیت حافظه یا پشتیبانی از encoding مشخص را تضمین نمی‌کند.

### چه زمانی Constraint خام مناسب است؟

اگر محدودیت فقط یک‌بار استفاده می‌شود و معنای مستقلی برای آن وجود ندارد، یک شرط مستقیم می‌تواند مناسب‌تر باشد.

```
template <typename T>
requires (sizeof(T) <= 16)
void processSmallObject(const T& value) {
    // Implementation
}
```

در این مثال، شرط اندازه مستقیماً در محل استفاده نوشته شده است.

البته این شرط باید با هدف تابع هماهنگ باشد. برای مثال، اندازهٔ کوچک نوع لزوماً به معنای هزینهٔ پایین کپی‌سازی یا پردازش سریع‌تر نیست.

## بررسی Overload Resolution با Constraints

### محدود کردن گزینه‌های تابع

یکی از کاربردهای مهم `Constraints`، تعریف چند overload برای یک نام تابع است که هرکدام قرارداد متفاوتی دارند.

```
#include <concepts>
#include <string>

template <std::integral T>
std::string describe(T value) {
    return "integral";
}

template <std::floating_point T>
std::string describe(T value) {
    return "floating point";
}
```

در این مثال، فراخوانی تابع با یک نوع صحیح به overload نخست و فراخوانی آن با یک نوع اعشاری استاندارد به overload دوم هدایت می‌شود.

```
auto a = describe(42);
auto b = describe(3.14);
```

اگر نوعی هر دو محدودیت را برآورده نکند، هیچ‌یک از این دو گزینه قابل انتخاب نخواهد بود؛ مگر آنکه overload دیگری با محدودیت مناسب وجود داشته باشد.

### اولویت‌بندی با Subsumption

قابلیت `Subsumption` مشخص می‌کند که رابطهٔ منطقی بین محدودیت‌ها چگونه در انتخاب overload مؤثر باشد. اگر یک محدودیت از نظر قواعد استاندارد، محدودیت دیگری را subsume کند، می‌توان از این رابطه برای تشخیص محدودیت دقیق‌تر استفاده کرد.

```
#include <concepts>
#include <string>

template <typename T>
requires std::integral<T>
std::string classify(T) {
    return "integral";
}

template <typename T>
requires std::signed_integral<T>
std::string classify(T) {
    return "signed integral";
}
```

در این مثال، مفهوم `std::signed_integral` خود شامل محدودیت `std::integral` است. بنابراین، برای یک نوع صحیح علامت‌دار، overload دوم محدودتر است و انتخاب می‌شود.

```
auto a = classify(10);
auto b = classify(10u);
```

در فراخوانی نخست، نتیجهٔ تابع `signed integral` و در فراخوانی دوم نتیجهٔ تابع `integral` خواهد بود.

نکتهٔ کلیدی این است که کامپایلر برای تعیین رابطهٔ subsumption صرفاً عبارات منطقی را مانند یک انسان ساده‌سازی جبری نمی‌کند. استاندارد برای این کار از قواعد مشخصی شامل `Atomic Constraints`، هم‌ارزی آن‌ها و ساختار منطقی محدودیت‌ها استفاده می‌کند.

### تفاوت Constraintهای ظاهراً یکسان

دو شرط ممکن است از نظر منطقی معادل باشند، اما لزوماً در قواعد subsumption معادل محسوب نشوند.

```
#include <concepts>

template <typename T>
concept IsIntegral = std::integral<T>;

template <typename T>
requires IsIntegral<T>
void handle(T) {}

template <typename T>
requires std::integral<T>
void handle(T) {}
```

این مثال را نباید به‌عنوان یک overload طراحی‌شدهٔ معتبر برای استفادهٔ روزمره در نظر گرفت؛ دو محدودیت با وجود معنای مشابه، الزاماً رابطهٔ subsumption موردنیاز برای انتخاب یکتا را برقرار نمی‌کنند و ممکن است فراخوانی با ابهام مواجه شود.

علت این رفتار به هویت `Atomic Constraint`ها مربوط است. هویت آن‌ها صرفاً بر اساس یکسان بودن نتیجهٔ منطقی یا متن ظاهری بررسی نمی‌شود؛ منشأ عبارت و قواعد نگاشت پارامترها نیز اهمیت دارند.

برای جلوگیری از چنین مشکلاتی، بهتر است محدودیت مشترک را در یک `Concept` تعریف کنید و در تمام overloadهایی که باید رابطهٔ اولویت مشخصی داشته باشند، همان مفهوم را به شکل سازگار به کار ببرید.

### مفهوم‌های نام‌گذاری‌شده و طراحی API

استفاده از `Concept` مشترک فقط به خوانایی محدود نمی‌شود؛ بلکه می‌تواند در رفتار انتخاب overload نیز اهمیت داشته باشد.

```
#include <concepts>

template <typename T>
concept IntegralType = std::integral<T>;

template <IntegralType T>
void process(T) {}

template <IntegralType T>
requires std::signed_integral<T>
void process(T) {}
```

در این طراحی، overload دوم محدودیت‌های overload نخست را به همراه شرط اضافی مربوط به علامت‌دار بودن نوع دارد. برای نوع‌های صحیح علامت‌دار، overload دوم محدودتر است.

هنگام توسعهٔ کتابخانه‌های عمومی، بهتر است روابط بین overloadها به‌صورت عمدی طراحی و با نمونه‌های مختلف نوعی آزمایش شوند؛ به‌خصوص اگر چند شرط ترکیبی یا مفهوم اختصاصی درگیر باشند.

## شناخت Atomic Constraints و Constraint Normalization

### مفهوم Atomic Constraint

یک `Atomic Constraint` کوچک‌ترین واحدی است که در الگوریتم subsumption نقش مستقیم دارد. این واحد معمولاً از یک عبارت منطقی وابسته به پارامترهای قالب و نگاشت پارامترهای مربوط به آن تشکیل می‌شود.

برای مثال، در شرط زیر:

```
template <typename T>
concept SmallAndIntegral =
    std::integral<T> && (sizeof(T) <= 4);
```

محدودیت نهایی از ترکیب دو شرط منطقی ساخته شده است. در فرایند `Constraint Normalization`، ساختار محدودیت‌ها به شکلی تبدیل می‌شود که روابط بین واحدهای اتمی قابل بررسی باشند.

این فرایند یکی از دلایلی است که استفادهٔ سازگار از مفهوم‌های نام‌گذاری‌شده در طراحی overloadها اهمیت دارد.

### مفهوم Constraint Normalization

`Constraint Normalization` فرایندی است که محدودیت‌ها را مطابق قواعد استاندارد به ساختار منطقی نرمال‌شده تبدیل می‌کند. این فرایند هنگام بررسی مفهوم‌ها و محدودیت‌های مرکب، نحوهٔ گسترش محدودیت‌های دیگر و نگاشت پارامترهای قالب را در نظر می‌گیرد.

این فرایند با ساده‌سازی معمول عبارت‌های منطقی یکسان نیست. برای مثال، دو عبارت ممکن است از نظر ریاضی معادل باشند، اما در ساختار اتمی و رابطهٔ subsumption یکسان نباشند.

در طراحی عملی، بهتر است به‌جای تکیه بر ساده‌سازی‌های ظاهری، محدودیت‌های مشترک را به‌صورت مفهوم‌های استاندارد یا اختصاصی تعریف کنید و از همان تعریف در تمام اعلان‌های مرتبط استفاده کنید.

### ترکیب منطقی Constraintها

محدودیت‌ها می‌توانند با عملگرهای منطقی `&&` و `||` ترکیب شوند.

```
#include <concepts>

template <typename T>
concept IntegerOrFloatingPoint =
    std::integral<T> || std::floating_point<T>;

template <typename T>
concept SignedOrSmall =
    std::signed_integral<T> || (sizeof(T) <= 2);
```

در مثال نخست، یک نوع باید یا صحیح باشد یا از نوع‌های اعشاری استاندارد باشد.

در مثال دوم، نوع باید صحیح علامت‌دار باشد یا اندازه‌ای حداکثر برابر دو بایت داشته باشد. توجه کنید که این شرط دوم به‌تنهایی تضمین نمی‌کند نوع موردنظر عددی، علامت‌دار یا مناسب عملیات حسابی باشد.

از آنجا که `Constraints` با قواعد زبان ارزیابی می‌شوند، ترتیب ظاهری شرط‌ها و ساختار وابستگی آن‌ها در بررسی معتبر بودن عبارات می‌تواند اهمیت داشته باشد. به‌ویژه در عبارت‌های `requires-expression`، شرط‌ها را طوری بنویسید که از بررسی عملیاتی که پیش‌نیاز آن‌ها برقرار نیست جلوگیری شود.

## کاربرد Constraintها در انواع Generic

### بررسی قابلیت فراخوانی

در الگوریتم‌های عمومی، گاهی لازم است مطمئن شویم یک شیء با آرگومان‌های مشخص قابل فراخوانی است. برای این منظور، مفهوم `std::invocable` در کتابخانهٔ استاندارد وجود دارد.

```
#include <concepts>
#include <utility>

template <typename F, typename... Args>
requires std::invocable<F, Args...>
decltype(auto) invokeCallable(F&& callable, Args&&... args) {
    return std::forward<F>(callable)(
        std::forward<Args>(args)...
    );
}
```

در این مثال، محدودیت بررسی می‌کند که آیا شیء `callable` با نوع آرگومان‌های موردنظر قابل فراخوانی است یا خیر.

استفاده از `std::forward` برای حفظ ویژگی‌های مقدارهای ورودی در انتقال آن‌ها به فراخوانی نهایی است. بااین‌حال، این پیاده‌سازی یک جایگزین کامل برای `std::invoke` نیست؛ زیرا `std::invoke` علاوه بر callableهای معمولی، سازوکارهای مرتبط با اشاره‌گر به تابع عضو و اشاره‌گر به دادهٔ عضو را نیز پشتیبانی می‌کند.

### بررسی قابلیت ساخت و کپی

در طراحی کلاس‌های عمومی، مفهوم‌هایی مانند `std::constructible_from`، `std::copy_constructible` و `std::movable` می‌توانند قرارداد ساخت و جابه‌جایی اشیا را بیان کنند.

```
#include <concepts>

template <std::copy_constructible T>
T duplicate(const T& value) {
    return value;
}
```

این تابع تنها برای نوع‌هایی قابل استفاده است که الزامات `std::copy_constructible` را برآورده می‌کنند.

البته مفهوم‌های استاندارد گاهی از یک بررسی سادهٔ وجود سازنده فراتر می‌روند و مجموعه‌ای از الزامات مرتبط با تبدیل‌ها، انتساب‌ها یا ویژگی‌های معنایی را بیان می‌کنند. بنابراین، انتخاب مفهوم باید براساس قرارداد موردنیاز باشد، نه صرفاً شباهت نام آن با عملیات موردنظر.

### طراحی الگوریتم‌های مبتنی بر Range

در ++C20، کتابخانهٔ `Ranges` از مفهوم‌ها برای بیان الزامات الگوریتم‌ها و محدوده‌های داده استفاده می‌کند. این قابلیت به الگوریتم‌ها امکان می‌دهد انواع ورودی را بر اساس ویژگی‌های موردنیاز بپذیرند، نه فقط بر اساس نوع مشخص اشاره‌گر یا iterator.

```
#include <concepts>
#include <ranges>

template <std::ranges::input_range R>
void inspectRange(R&& range) {
    for (auto&& element : range) {
        (void)element;
    }
}
```

در این مثال، پارامتر باید الزامات `std::ranges::input_range` را برآورده کند. این الزام به وجود عملیات لازم برای پیمایش ورودی از طریق رابط Range مربوط است.

نکتهٔ مهم آن است که `input_range` الزاماً به معنای پشتیبانی از چند بار پیمایش مستقل، دسترسی تصادفی یا تغییر عناصر نیست. اگر الگوریتم به قابلیت قوی‌تری نیاز دارد، باید از مفهوم مناسب‌تری مانند `forward_range`، `bidirectional_range` یا `random_access_range` استفاده کند.

### استفاده از Iterator Concepts

مفهوم‌های مربوط به iteratorها در ++C20 تفاوت بین قابلیت‌های مختلف پیمایش را به‌صورت صریح بیان می‌کنند.

| مفهوم                         | کاربرد                           |
| ----------------------------- | -------------------------------- |
| `std::input_iterator`         | پیمایش و خواندن ورودی            |
| `std::output_iterator`        | نوشتن خروجی                      |
| `std::forward_iterator`       | پیمایش چندباره و حرکت رو به جلو  |
| `std::bidirectional_iterator` | حرکت رو به جلو و عقب             |
| `std::random_access_iterator` | دسترسی تصادفی و محاسبات فاصله‌ای |
| `std::contiguous_iterator`    | ترتیب پیوستهٔ عناصر در حافظه     |

این مفهوم‌ها را باید با توجه به نیاز واقعی الگوریتم انتخاب کرد. برای مثال، اگر یک الگوریتم تنها یک‌بار داده‌ها را از ابتدا تا انتها می‌خواند، الزام به `random_access_iterator` بی‌دلیل است و می‌تواند استفاده از الگوریتم را محدود کند.

### مفهوم‌های مربوط به Containerها

در کتابخانهٔ استاندارد، مفهوم عمومی `std::ranges::range` بررسی می‌کند که آیا برای شیء موردنظر، عملیات آغاز و پایان پیمایش مطابق الزامات مربوطه معتبر است یا خیر.

اما این مفهوم به‌تنهایی تضمین نمی‌کند که شیء یک Container کامل باشد، حافظهٔ عناصر را مالک باشد یا عملیات مشخصی مانند درج و حذف را پشتیبانی کند.

در طراحی الگوریتم‌ها بهتر است به‌جای درخواست یک نوع Container خاص، دقیقاً قابلیت موردنیاز را بیان کنید. چنین رویکردی امکان استفاده از آرایه‌ها، `std::vector`، `std::array`، viewها و انواع سفارشی سازگار را افزایش می‌دهد.

## مقایسه Concepts با SFINAE و Type Traits

### روش قدیمی محدود کردن Templateها

پیش از ++C20، یکی از روش‌های رایج برای محدود کردن قالب‌ها استفاده از `SFINAE` بود. این اصطلاح مخفف Substitution Failure Is Not An Error است و به این معنا اشاره دارد که در برخی شرایط، شکست جایگزینی نوع‌ها یا عبارت‌ها هنگام بررسی یک گزینهٔ قالبی، به‌جای ایجاد خطای فوری، باعث کنار گذاشته شدن آن گزینه می‌شود.

برای مثال، در استاندارد ++C17 می‌توان یک تابع را با استفاده از `std::enable_if_t` محدود کرد:

```
#include <type_traits>

template <typename T,
          std::enable_if_t<std::is_integral_v<T>, int> = 0>
T doubleValue(T value) {
    return value + value;
}
```

این روش معتبر است، اما در مقایسه با مفهوم‌های جدید، محدودیت را به شکل غیرمستقیم‌تری بیان می‌کند.

همان هدف را می‌توان در ++C20 به شکل زیر بیان کرد:

```
#include <concepts>

template <std::integral T>
T doubleValue(T value) {
    return value + value;
}
```

نسخهٔ دوم خواناتر است و هدف محدودیت را مستقیماً نشان می‌دهد.

### تفاوت‌های اساسی دو روش

| ویژگی                                | `SFINAE`                                    | `Concepts` و `Constraints`                               |
| ------------------------------------ | ------------------------------------------- | -------------------------------------------------------- |
| خوانایی اعلان                        | معمولاً پیچیده‌تر                           | معمولاً روشن‌تر                                          |
| بیان الزامات چندگانه                 | اغلب نیازمند ترکیب چند تکنیک                | پشتیبانی مستقیم از منطق محدودیت‌ها                       |
| انتخاب overload                      | مبتنی بر قواعد SFINAE و overload resolution | علاوه بر overload resolution، مبتنی بر قواعد subsumption |
| پیام‌های خطا                         | در بسیاری از موارد دشوارتر برای فهم         | معمولاً دقیق‌تر و مرتبط‌تر با محدودیت                    |
| محدودیت‌های معنایی                   | اغلب مبتنی بر نوع‌ها و عبارت‌های قابل بررسی | امکان بیان قراردادهای نوعی و عملیاتی خواناتر             |
| سازگاری با استانداردهای قدیمی        | مناسب برای ++C11 و نسخه‌های بعدی            | نیازمند ++C20                                            |
| امکان استفاده در کتابخانهٔ استاندارد | همچنان وجود دارد                            | در APIهای جدید و `Ranges` کاربرد گسترده دارد             |

توجه کنید که `Concepts` جایگزین تمام کاربردهای `SFINAE` نیست. برخی تکنیک‌های قدیمی همچنان در کدهای سازگار با استانداردهای پیشین یا در طراحی‌های خاص مفید هستند. همچنین مفهوم‌ها خودشان در فرایند بررسی قالب‌ها با قواعد جایگزینی و اعتبارسنجی عبارات تعامل دارند.

### مقایسه با Type Traits

قابلیت `Type Traits` از استاندارد ++C11 در کتابخانهٔ استاندارد وجود داشته و امکان بررسی ویژگی‌هایی مانند صحیح بودن نوع، قابلیت ساخت، ارث‌بری و بسیاری از خصوصیات دیگر را فراهم کرده است.

```
#include <type_traits>

template <typename T>
constexpr bool isInteger = std::is_integral_v<T>;
```

در این مثال، `isInteger` یک متغیر `constexpr` است که نتیجهٔ بررسی نوع را در زمان کامپایل در اختیار قرار می‌دهد.

در ++C20 می‌توان همین ویژگی را در یک مفهوم استفاده کرد:

```
#include <concepts>

template <typename T>
concept IntegerType = std::integral<T>;
```

تفاوت مهم آن است که `Type Traits` معمولاً اطلاعاتی دربارهٔ نوع را به‌صورت مقدار یا نوع کمکی ارائه می‌کنند، درحالی‌که `Concept` برای بیان مستقیم محدودیت‌های یک قالب طراحی شده است.

این دو ابزار مکمل یکدیگرند. اگر به اطلاعاتی مانند `std::is_trivially_copyable_v<T>` نیاز دارید، همچنان می‌توانید از `Type Traits` استفاده کنید؛ لازم نیست تمام ویژگی‌ها را با `requires-expression` دوباره پیاده‌سازی کنید.

## تفاوت Constraintها با static_assert

### نقش متفاوت اعتبارسنجی ایستا

قابلیت `static_assert` از استاندارد ++C11 وجود دارد و برای اعلام یک خطای کامپایل در صورت برقرار نبودن یک شرط مناسب است.

```
#include <type_traits>

template <typename T>
T identity(T value) {
    static_assert(std::is_integral_v<T>,
                  "T must be an integral type");

    return value;
}
```

در این مثال، تابع برای نوع غیرصحیح یک خطای صریح ایجاد می‌کند، اما محدودیت در مرحلهٔ انتخاب overload اعمال نشده است.

در مقابل، نسخهٔ زیر محدودیت را مستقیماً به اعلان قالب متصل می‌کند:

```
#include <concepts>

template <std::integral T>
T identity(T value) {
    return value;
}
```

در این حالت، استفاده از تابع با یک نوع غیرصحیح باعث می‌شود گزینهٔ محدودشده واجد شرایط انتخاب نباشد.

### چه زمانی static_assert بهتر است؟

ابزار `static_assert` همچنان برای بررسی ناوردایی‌های داخلی، پیکربندی‌های زمان کامپایل و شرایطی که باید صریحاً خطا ایجاد کنند مناسب است.

برای مثال، اگر یک پیاده‌سازی فقط در پلتفرم‌هایی با اندازهٔ مشخص برای یک نوع قابل استفاده باشد، ممکن است بررسی این شرط در داخل پیاده‌سازی مناسب باشد.

در مقابل، اگر هدف این است که یک تابع عمومی فقط برای گروه خاصی از انواع در overload resolution قابل انتخاب باشد، استفاده از `Concept` یا `requires-clause` معمولاً طراحی بهتری ایجاد می‌کند.

## بررسی وابستگی‌ها و قواعد اعتبارسنجی

### عبارت‌های وابسته به Template Parameters

در قالب‌ها، اعتبار یک عبارت ممکن است به نوع پارامترهای قالب وابسته باشد. برای مثال، عبارت `value.size()` تنها در صورتی معتبر است که نوع واقعی `value` چنین عضوی را فراهم کند.

```
template <typename T>
concept HasSize = requires(const T& value) {
    value.size();
};
```

در این مثال، اعتبار عبارت برای نوع‌های مختلف بررسی می‌شود و نتیجهٔ آن در ارزیابی مفهوم نقش دارد.

بااین‌حال، باید بین نام‌های وابسته و نام‌های غیر وابسته تفاوت گذاشت. نام‌های غیر وابسته ممکن است پیش از آنکه قالب برای یک نوع مشخص نمونه‌سازی شود بررسی شوند؛ بنابراین، `requires-expression` را نباید ابزاری برای پنهان کردن هر نوع خطای نحوی یا نامعتبر دانست.

### مدیریت ترتیب بررسی شرط‌ها

در عبارت‌های منطقی، ترتیب شرط‌ها می‌تواند برای جلوگیری از ارزیابی یک عبارت وابسته و نامعتبر اهمیت داشته باشد.

```
#include <concepts>

template <typename T>
concept HasNestedTypeAndValue = requires {
    typename T::value_type;
    requires std::integral<typename T::value_type>;
};
```

در این مثال، وجود `T::value_type` ابتدا بررسی می‌شود و شرط تو‌در‌تو به نوع آن وابسته است.

ساختار شرط‌ها باید طوری طراحی شود که وابستگی‌ها به‌درستی مشخص باشند. به‌خصوص هنگام ترکیب مفهوم‌های اختصاصی، از نوشتن شرط‌هایی که به نوع یا عضوی ناموجود وابسته‌اند بدون در نظر گرفتن قواعد کوتاه‌سازی منطقی و اعتبارسنجی قالب پرهیز کنید.

### مفهوم‌های بازگشتی و وابستگی متقابل

تعریف مفهوم‌هایی که به یکدیگر وابستگی بازگشتی دارند، می‌تواند با قواعد تعریف و نرمال‌سازی محدودیت‌ها تداخل پیدا کند. مفهوم‌ها برای ترکیب الزامات طراحی شده‌اند، اما این به معنای مجاز بودن هر نوع چرخهٔ وابستگی نیست.

در طراحی کتابخانه، بهتر است مفهوم‌های پایه مستقل باشند و مفهوم‌های سطح بالاتر از آن‌ها ساخته شوند. این ساختار هم خواناتر است و هم تحلیل روابط منطقی را ساده‌تر می‌کند.

## بررسی محدودیت‌های معنایی Concepts

### تفاوت معتبر بودن عبارت با درست بودن رفتار

یکی از مهم‌ترین نکته‌ها دربارهٔ مفهوم‌ها این است که بسیاری از بررسی‌های آن‌ها دربارهٔ معتبر بودن عبارت‌ها هستند، نه صحت معنایی رفتار برنامه.

```
template <typename T>
concept AddableToSelf = requires(T a, T b) {
    a + b;
};
```

این مفهوم تنها بررسی می‌کند که عبارت جمع معتبر باشد. دربارهٔ اینکه نتیجه با جمع ریاضی مطابقت دارد، عملگر برای ورودی‌های خاص رفتار معقولی دارد یا نتیجه تحت سرریز چه وضعیتی پیدا می‌کند، تضمینی نمی‌دهد.

برای نمونه، یک نوع سفارشی ممکن است عملگر `operator+` را طوری تعریف کند که به‌جای جمع، الحاق رشته‌ای یا عملیات دیگری انجام دهد. از دید کامپایلر، عبارت همچنان می‌تواند معتبر باشد.

### قراردادهای معنایی در مفهوم‌های استاندارد

بعضی مفهوم‌های استاندارد، علاوه بر بررسی‌های نحوی، الزامات معنایی نیز دارند. برای مثال، `std::equality_comparable` و `std::totally_ordered` بر قراردادهایی دربارهٔ روابط مقایسه‌ای تکیه می‌کنند.

کامپایلر نمی‌تواند تمام این قراردادها را به‌صورت عمومی اثبات کند. بنابراین، برآورده کردن الزامات یک مفهوم استاندارد ممکن است به رعایت قواعد معنایی مستندشده نیز نیاز داشته باشد.

در نتیجه، صرف عبور از بررسی‌های کامپایلر برای اثبات درست بودن یک نوع سفارشی کافی نیست. آزمون‌ها و مستندات باید رفتار مورد انتظار را نیز پوشش دهند.

### مفهوم‌های بیش از حد محدودکننده

اگر یک الگوریتم تنها به عملیات `a + b` نیاز دارد، محدود کردن پارامتر آن به `std::integral` می‌تواند غیرضروری باشد؛ زیرا کلاس‌های سفارشی یا انواع عددی دیگر نیز ممکن است این عملیات را فراهم کنند.

برای مثال:

```
template <typename T>
requires requires(const T& a, const T& b) {
    a + b;
}
auto sum(const T& a, const T& b) {
    return a + b;
}
```

این نسخه تنها معتبر بودن عملیات جمع را می‌خواهد و نوع‌های بیشتری را می‌پذیرد.

البته این انعطاف‌پذیری باید با نیازهای واقعی تابع هماهنگ باشد. اگر بدنه به بازگشت نتیجه از نوع مشخص، رفتار عددی معین یا عملیات دیگری نیاز دارد، محدودیت باید آن الزامات را نیز منعکس کند.

## روش‌های نگارش و سازمان‌دهی Constraints

### انتخاب بین سه شکل رایج

در ++C20 می‌توان محدودیت را با یک مفهوم در پارامتر قالب، با `requires-clause` یا در برخی موارد با `requires-expression` بیان کرد.

```
#include <concepts>

template <std::integral T>
T first(T value) {
    return value;
}

template <typename T>
requires std::integral<T>
T second(T value) {
    return value;
}

template <typename T>
T third(T value)
    requires requires(T x) {
        x + x;
    }
{
    return value;
}
```

هرکدام از این شکل‌ها برای هدف متفاوتی مناسب است:

- در حالت نخست، محدودیت ساده و مستقیماً قابل نام‌گذاری است.
- در حالت دوم، محدودیت صریحاً در محل اعلان نوشته شده است.
- در حالت سوم، الزام عملیاتی مستقیماً در محدودیت تابع قرار دارد و برای شرایط خاص مناسب است.

در کدهای کتابخانه‌ای، اگر یک شرط بارها استفاده می‌شود یا معنای مشخصی دارد، تعریف `Concept` اختصاصی معمولاً بهترین گزینه است.

### پرهیز از تکرار محدودیت‌ها

تکرار شرط‌های طولانی در چند تابع می‌تواند نگهداری کد را دشوار کند. اگر تعریف یک شرط تغییر کند، لازم است تمام اعلان‌های وابسته نیز سازگار بمانند.

```
#include <concepts>

template <typename T>
concept IncrementableValue = requires(T value) {
    ++value;
};

template <IncrementableValue T>
void advanceOnce(T& value) {
    ++value;
}

template <IncrementableValue T>
void advanceTwice(T& value) {
    ++value;
    ++value;
}
```

در این مثال، قرارداد مربوط به قابلیت افزایش تنها یک‌بار تعریف شده و در دو تابع استفاده شده است.

البته این مفهوم فقط معتبر بودن عملگر افزایش پیشوندی را بررسی می‌کند؛ اگر الگوریتم به نوع نتیجهٔ این عملگر یا ویژگی‌های معنایی آن نیاز دارد، باید آن الزامات نیز صریحاً بیان شوند.

### جلوگیری از Constraints ناسازگار

اگر چند overload با شرط‌هایی طراحی شوند که هم‌پوشانی دارند اما رابطهٔ محدودتر بودن آن‌ها روشن نیست، ممکن است انتخاب تابع مبهم شود.

برای جلوگیری از این مشکل، ابتدا گروه‌های نوعی مورد پشتیبانی را مشخص کنید و سپس روابط بین محدودیت‌ها را طراحی کنید. اگر هدف آن است که یک overload در تمام شرایط خاص بر دیگری اولویت داشته باشد، این رابطه را با مفهوم‌های مشترک و محدودیت‌های منطقی سازگار بیان کنید.

## کاربردهای عملی در طراحی کتابخانه

### طراحی APIهای عددی

در کتابخانه‌های محاسباتی، مفهوم‌ها می‌توانند تفاوت بین نوع‌های صحیح، اعشاری و نوع‌های عددی سفارشی را روشن کنند. این کار باعث می‌شود خطاهای ناشی از استفاده از نوع نامناسب، زودتر و با پیام‌های مرتبط‌تر مشخص شوند.

بااین‌حال، اگر الگوریتم به ویژگی‌هایی مانند دقت محدود، رفتار سرریز یا عملیات تقسیم نیاز دارد، مفهوم سادهٔ `std::integral` یا `std::floating_point` لزوماً تمام الزامات را بیان نمی‌کند.

### طراحی APIهای مبتنی بر Callable

در سیستم‌هایی که تابع‌ها، lambdaها و اشیای قابل فراخوانی را دریافت می‌کنند، `std::invocable` و `std::predicate` می‌توانند قرارداد ورودی را روشن کنند.

برای مثال، الگوریتم مرتب‌سازی ممکن است به یک تابع مقایسه نیاز داشته باشد که برای دو عنصر قابل فراخوانی باشد و نتیجه‌ای سازگار با الزامات predicate ارائه دهد. استفاده از مفهوم مناسب در اعلان قالب می‌تواند خطاهای مربوط به comparator نامعتبر را زودتر مشخص کند.

### طراحی کلاس‌های مدیریت منابع

در کلاس‌هایی که منابع را مالک می‌شوند یا انتقال می‌دهند، مفهوم‌هایی مانند `std::movable` و `std::move_constructible` می‌توانند به بیان الزامات نوع کمک کنند.

البته باید بین قابل انتقال بودن یک نوع و درست بودن انتقال مالکیت تفاوت گذاشت. مفهوم‌ها به‌تنهایی تضمین نمی‌کنند که یک نوع سفارشی پس از انتقال در وضعیت معنایی مناسبی قرار می‌گیرد یا منابع را به‌درستی آزاد می‌کند.

### طراحی الگوریتم‌های عمومی

در الگوریتم‌های عمومی، مفهوم‌های `Ranges` و iteratorها کمک می‌کنند الزامات دقیق عملیات موردنیاز بیان شوند. این کار از محدود کردن بی‌دلیل الگوریتم به یک Container خاص جلوگیری می‌کند و استفاده از viewها، محدوده‌های تنبل و انواع سفارشی را آسان‌تر می‌سازد.

برای مثال، الگوریتمی که فقط به پیمایش رو به جلو نیاز دارد بهتر است از `std::forward_iterator` یا مفهوم Range مناسب استفاده کند، نه اینکه بی‌دلیل دسترسی تصادفی را الزامی کند.

## بررسی پیام‌های خطا و عیب‌یابی

### درک پیام‌های خطای Constraints

یکی از مزیت‌های مهم مفهوم‌ها این است که در بسیاری از موارد، کامپایلر می‌تواند مشخص کند کدام محدودیت برقرار نشده است. بااین‌حال، شکل و جزئیات پیام‌های خطا به کامپایلر و نسخهٔ آن وابسته است.

برای مثال، در کد زیر:

```
#include <concepts>

template <std::integral T>
T square(T value) {
    return value * value;
}

int main() {
    auto result = square(3.14);
}
```

آرگومان `3.14` از نوع `double` است و مفهوم `std::integral` را برآورده نمی‌کند. بنابراین، قالب محدودشده برای این فراخوانی قابل انتخاب نیست.

برای عیب‌یابی چنین خطاهایی، بهتر است بررسی را به‌ترتیب زیر انجام دهید:

- ابتدا مشخص کنید کدام overload یا قالب برای فراخوانی موردنظر انتخاب شده است.
- سپس بررسی کنید که آیا نوع آرگومان‌ها محدودیت‌های تعریف‌شده را برآورده می‌کنند.
- در صورت استفاده از مفهوم اختصاصی، الزامات داخل `requires-expression` را جداگانه بررسی کنید.
- اگر چند overload وجود دارد، رابطهٔ subsumption و احتمال ابهام را نیز بررسی کنید.
- در نهایت، مطمئن شوید که بدنهٔ تابع به عملیاتی نیاز ندارد که در محدودیت‌ها بیان نشده است.

### استفاده از ابزارهای توسعه

برای توسعهٔ کتابخانه‌های مبتنی بر مفهوم‌ها، استفاده از نسخه‌های جدید GCC، Clang یا MSVC توصیه می‌شود. هرچند این کامپایلرها از ++C20 پشتیبانی می‌کنند، میزان کامل بودن پیاده‌سازی و کیفیت تشخیص خطا ممکن است بین نسخه‌ها متفاوت باشد.

همچنین استفاده از گزینهٔ استاندارد زبان برای فعال‌سازی ++C20 مفید است:

```
g++ -std=c++20 -Wall -Wextra -Wpedantic main.cpp -o main
```

برای Clang نیز می‌توان از گزینهٔ `-std=c++20` استفاده کرد. این گزینه‌ها مربوط به کامپایلر هستند و جزو نحو زبان محسوب نمی‌شوند.

## تفاوت قابلیت‌های زبان و کتابخانهٔ استاندارد

### تشخیص مرز میان زبان و کتابخانه

برای استفادهٔ صحیح از مفهوم‌ها، باید تفاوت قابلیت‌های خود زبان با امکانات کتابخانهٔ استاندارد را در نظر داشت.

| قابلیت                      | دسته‌بندی           | نسخه  |
| --------------------------- | ------------------- | ----- |
| کلمهٔ کلیدی `concept`       | قابلیت زبان         | ++C20 |
| عبارت `requires-expression` | قابلیت زبان         | ++C20 |
| عبارت `requires-clause`     | قابلیت زبان         | ++C20 |
| `Constraint Normalization`  | قواعد زبان          | ++C20 |
| `Constraint Subsumption`    | قواعد زبان          | ++C20 |
| `std::integral`             | کتابخانهٔ استاندارد | ++C20 |
| `std::same_as`              | کتابخانهٔ استاندارد | ++C20 |
| `std::invocable`            | کتابخانهٔ استاندارد | ++C20 |
| `std::ranges::range`        | کتابخانهٔ استاندارد | ++C20 |
| `std::is_integral_v`        | کتابخانهٔ استاندارد | ++C17 |

این تفاوت از نظر فنی مهم است؛ زیرا ممکن است یک کامپایلر نحو `requires` را پشتیبانی کند، اما نسخهٔ کتابخانهٔ استاندارد یا پیاده‌سازی یک قابلیت مشخص از `Ranges` با سطح پشتیبانی مورد انتظار متفاوت باشد.

همچنین گزینهٔ `-std=c++20` به‌تنهایی تضمین نمی‌کند که تمام قابلیت‌های استاندارد در همهٔ نسخه‌های کامپایلر بدون نقص پیاده‌سازی شده‌اند.

### بررسی قابلیت پشتیبانی کامپایلر

در پروژه‌های چندپلتفرمی، بهتر است قابلیت‌های موردنیاز را با کامپایلرها و کتابخانه‌های استاندارد هدف آزمایش کنید. در صورت نیاز، می‌توان از ماکروهای ویژگی‌های زبان مانند `__cpp_concepts` برای بررسی سطح پشتیبانی استفاده کرد.

```
#ifndef __cpp_concepts
#error "This project requires C++20 Concepts support"
#endif
```

این بررسی وجود ماکرو را کنترل می‌کند، اما به‌تنهایی تضمین‌کنندهٔ پشتیبانی کامل و بدون نقص از تمام قابلیت‌های مرتبط نیست.

برای پروژه‌های عمومی، استفاده از سیستم ساختی مانند CMake و تعیین استاندارد موردنیاز در پیکربندی پروژه، روش مناسب‌تری برای مدیریت نیازمندی‌های کامپایل است.

## نکات مهم برای طراحی حرفه‌ای

### انتخاب محدودیت متناسب با نیاز واقعی

بهترین محدودیت، محدودیتی است که دقیقاً نیازهای پیاده‌سازی را بیان کند. اگر الگوریتم تنها به یک عملیات نیاز دارد، محدود کردن آن به یک دستهٔ نوعی خاص ممکن است انعطاف‌پذیری غیرضروری را کاهش دهد.

در مقابل، محدودیت بیش از حد ضعیف نیز می‌تواند باعث شود خطاهای کامپایل از بدنهٔ تابع و با پیام‌های پیچیده ظاهر شوند. بنابراین، باید بین انعطاف‌پذیری و بیان دقیق قرارداد تعادل برقرار کرد.

### استفاده از مفهوم‌های استاندارد در اولویت

اگر مفهوم استانداردی وجود دارد که قرارداد موردنیاز را به‌درستی بیان می‌کند، معمولاً استفاده از آن انتخاب مناسبی است. تعریف مفهوم اختصاصی زمانی ارزشمند است که قرارداد پروژه با مفهوم‌های موجود به‌طور دقیق بیان نشود یا نام‌گذاری آن ارزش معنایی داشته باشد.

برای نمونه، به‌جای تعریف دوبارهٔ محدودیت مربوط به نوع‌های صحیح، استفاده از `std::integral` روشن‌تر و سازگارتر است.

### پرهیز از ادعاهای معنایی اثبات‌نشده

یک `Concept` می‌تواند معتبر بودن عملیات را بررسی کند، اما معمولاً نمی‌تواند تمام خصوصیات رفتاری را اثبات کند. اگر الگوریتم به ویژگی‌هایی مانند ترتیب کامل، رفتار عددی خاص یا حفظ ناورداها نیاز دارد، این الزامات باید در مستندات و آزمون‌ها نیز پوشش داده شوند.

### طراحی منظم Overloadها

در APIهایی که چند overload دارند، روابط بین محدودیت‌ها باید از ابتدا طراحی شوند. اگر دو overload محدودیت‌های هم‌پوشان داشته باشند، صرفاً متفاوت بودن متن `requires-clause`ها تضمین نمی‌کند که کامپایلر بتواند گزینهٔ مناسب را انتخاب کند.

استفاده از مفهوم‌های مشترک، پرهیز از تکرار بی‌دلیل محدودیت‌ها و آزمایش حالت‌های مرزی، احتمال بروز ابهام را کاهش می‌دهد.

### در نظر گرفتن سازگاری با نسخه‌های قبلی

اگر کتابخانه باید با ++C17 یا استانداردهای قدیمی‌تر نیز سازگار باشد، نمی‌توان مستقیماً از قابلیت‌های زبانی ++C20 در تمام مسیرهای ساخت استفاده کرد.

در چنین پروژه‌هایی می‌توان از `Type Traits` و `SFINAE` برای پیاده‌سازی سازگار با نسخه‌های قدیمی استفاده کرد یا نسخه‌های متفاوتی از API را بر اساس استاندارد هدف در نظر گرفت. انتخاب این روش به نیازهای کاربران کتابخانه و سیاست پشتیبانی پروژه بستگی دارد.

## جمع‌بندی نهایی

قابلیت‌های `Concepts`، `Constraints` و `requires` در ++C20 ابزارهایی برای طراحی قالب‌های خواناتر، بیان دقیق‌تر قراردادها و بهبود انتخاب overloadها هستند. این قابلیت‌ها امکان می‌دهند نیازمندی‌های یک الگوریتم یا کلاس عمومی، به‌جای پنهان ماندن در بدنهٔ پیاده‌سازی، به‌صورت بخشی از اعلان آن مشخص شوند.

مهم‌ترین نکته‌های این مبحث عبارت‌اند از:

- مفهوم `Concept` نامی برای مجموعه‌ای از محدودیت‌های نوعی و عملیاتی است.
- محدودیت `Constraint` تعیین می‌کند که آیا یک قالب یا overload واجد شرایط استفاده است یا خیر.
- عبارت `requires-expression` برای بررسی معتبر بودن عبارت‌ها و الزامات استفاده می‌شود.
- ساختار `requires-clause` محدودیت را به یک اعلان قالبی متصل می‌کند.
- قواعد `Constraint Normalization` و `Subsumption` در انتخاب overloadهای محدودشده نقش مهمی دارند.
- مفهوم‌های استاندارد کتابخانهٔ ++C20 معمولاً نسبت به تعریف دوبارهٔ محدودیت‌های متداول انتخاب مناسب‌تری هستند.
- `Concepts` جایگزین کامل `SFINAE`، `Type Traits` یا `static_assert` نیست؛ هرکدام کاربردهای مشخص خود را دارند.
- معتبر بودن یک عبارت به‌تنهایی صحت معنایی رفتار نوع را تضمین نمی‌کند.
- محدودیت‌ها باید دقیقاً با نیازهای الگوریتم هماهنگ باشند تا از محدود کردن بی‌دلیل کاربران یا پذیرش نوع‌های نامناسب جلوگیری شود.

در نهایت، استفادهٔ مؤثر از این امکانات تنها به یادگیری نحو `requires` محدود نمی‌شود. درک روابط منطقی محدودیت‌ها، شناخت قراردادهای معنایی مفهوم‌های استاندارد و طراحی آگاهانهٔ overloadها، بخش اصلی بهره‌گیری حرفه‌ای از قابلیت‌های قالبی ++C20 است.
