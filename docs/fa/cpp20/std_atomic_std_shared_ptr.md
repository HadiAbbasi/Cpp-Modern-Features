# راهنمای جامع `std::atomic<std::shared_ptr<T>>` در ++C20

## مقدمه

در برنامه‌های چندریسمانی، گاهی لازم است چند `thread` به یک شیء مشترک دسترسی داشته باشند و هم‌زمان امکان جایگزین‌کردن نسخهٔ آن شیء نیز وجود داشته باشد. نوع `std::shared_ptr<T>` مالکیت مشترک و مدیریت طول عمر شیء را فراهم می‌کند، اما خودِ یک متغیر `shared_ptr` را نمی‌توان بدون همگام‌سازی از چند `thread` به‌طور هم‌زمان خواند و نوشت.

قابلیت `std::atomic<std::shared_ptr<T>>` که در استاندارد ++C20 اضافه شد، راهی استاندارد برای بارگذاری و جایگزینی اتمیک یک `shared_ptr` فراهم می‌کند. این ابزار به‌ویژه برای الگوهایی مانند انتشار تنظیمات تغییرناپذیر، تعویض snapshotها، جدول‌های راهنمایی و داده‌هایی که بیشتر خوانده می‌شوند تا نوشته شوند، مفید است.

نکتهٔ اساسی این است که اتمیک‌بودن متغیر اشاره‌گر، به‌معنای thread-safe بودن خود شیء اشاره‌شده نیست. این نوع، هم‌زمانی در دسترسی به جایگاه `shared_ptr` و مدیریت مالکیت آن را پوشش می‌دهد؛ همگام‌سازی تغییرات درون شیء همچنان مسئولیت طراحی برنامه است.

## مسئله‌ای که این قابلیت حل می‌کند

فرض کنید یک متغیر سراسری به تنظیمات برنامه اشاره می‌کند و چند `thread` آن را می‌خوانند، درحالی‌که یک `thread` دیگر هر از گاهی نسخهٔ جدید تنظیمات را منتشر می‌کند. دسترسی هم‌زمان خواندن و نوشتن به همان شیء `shared_ptr` بدون همگام‌سازی، در ++C یک `data race` ایجاد می‌کند و رفتار برنامه تعریف‌نشده خواهد بود.

```cpp
#include <memory>

struct Config {
    int timeout_ms;
};

std::shared_ptr<const Config> current_config;

// Unsafe if one thread writes current_config while another reads it.
void update_config() {
    current_config = std::make_shared<const Config>(Config{500});
}

void read_config() {
    auto snapshot = current_config;
    (void)snapshot;
}
```

در نمونهٔ بالا، مشکل از `shared_ptr` بودن یا نبودن شیء مقصد نیست؛ مشکل این است که خود متغیر `current_config` بدون همگام‌سازی خوانده و نوشته می‌شود. افزایش و کاهش شمارندهٔ مالکیت در یک پیاده‌سازی استاندارد معمولاً برای کنترل‌های مالکیت مشترک به‌شکل thread-safe طراحی شده است، اما این موضوع اجازه نمی‌دهد همان نمونهٔ متغیر `shared_ptr` را هم‌زمان از یک `thread` بخوانیم و از `thread` دیگر تغییر دهیم.

## معرفی نوع اتمیک در ++C20

در ++C20، تخصصی‌سازی زیر برای `std::atomic` در دسترس است:

```cpp
std::atomic<std::shared_ptr<T>>
```

برای استفاده از آن، هدرهای `<atomic>` و `<memory>` را وارد کنید. این تخصصی‌سازی از همان رابط کلی عملیات اتمیک پیروی می‌کند، اما به‌طور ویژه برای `std::shared_ptr` تعریف شده است.

```cpp
#include <atomic>
#include <memory>

struct Config {
    int timeout_ms;
};

std::atomic<std::shared_ptr<const Config>> current_config{
    std::make_shared<const Config>(Config{250})
};
```

این تعریف یک جایگاه اتمیک برای مقدار `shared_ptr` ایجاد می‌کند. عملیات‌هایی مانند `load`، `store`، `exchange` و `compare_exchange` روی این جایگاه به‌شکل اتمیک انجام می‌شوند.

### تفاوت با رابط قدیمی `atomic_load` و `atomic_store`

پیش از ++C20، کتابخانهٔ استاندارد توابع آزاد ویژه‌ای مانند `std::atomic_load`، `std::atomic_store`، `std::atomic_exchange` و نسخه‌های `compare_exchange` برای کار با `shared_ptr` ارائه می‌کرد. این توابع در ++C11 معرفی شده بودند و در ++C20 منسوخ (deprecated) شدند؛ تخصصی‌سازی `std::atomic<std::shared_ptr<T>>` جایگزین مدرن آن‌هاست. توابع قدیمی در استانداردهای مربوطه همچنان ممکن است در دسترس باشند، اما برای کد جدید ++C20 معمولاً بهتر است از رابط تخصصی‌سازی اتمیک استفاده شود.

## عملیات اصلی

### بارگذاری با `load`

عملیات `load` یک نسخه از اشاره‌گر مشترک را به‌صورت اتمیک دریافت می‌کند. نسخهٔ برگردانده‌شده، مالکیت مشترک خود را حفظ می‌کند؛ بنابراین اگر مقدار اتمیک بعداً با شیء دیگری جایگزین شود، شیء قبلی تا زمانی که مالکیت‌های فعال آن باقی‌اند از بین نمی‌رود.

```cpp
auto snapshot = current_config.load();
```

برای تعیین ترتیب حافظه می‌توان یک `std::memory_order` نیز به `load` داد:

```cpp
auto snapshot = current_config.load(std::memory_order_acquire);
```

در کد ساده، استفاده از ترتیب پیش‌فرض `std::memory_order_seq_cst` معتبر و اغلب خواناتر است. انتخاب ترتیب ضعیف‌تر باید بر اساس مدل انتشار داده و تحلیل دقیق همگام‌سازی انجام شود، نه صرفاً برای تلاش جهت بهبود کارایی.

### ذخیره‌سازی با `store`

عملیات `store` مقدار فعلی را به‌صورت اتمیک با یک `shared_ptr` جدید جایگزین می‌کند:

```cpp
auto next = std::make_shared<const Config>(Config{750});
current_config.store(next);
```

مقدار پیش‌فرض ترتیب حافظه برای `store`، یعنی `std::memory_order_seq_cst`، مجاز است. برای `store` نمی‌توان از `std::memory_order_acquire` یا `std::memory_order_acq_rel` استفاده کرد؛ این ترتیب‌ها برای ذخیره‌سازی ساده معتبر نیستند.

### جایگزینی و دریافت مقدار قبلی با `exchange`

عملیات `exchange` مقدار جدید را به‌صورت اتمیک نصب می‌کند و مقدار قبلی را برمی‌گرداند:

```cpp
auto next = std::make_shared<const Config>(Config{1000});
auto previous = current_config.exchange(next);
```

این عملیات وقتی مفید است که برنامه علاوه بر انتشار نسخهٔ جدید، بخواهد نسخهٔ قبلی را نیز نگه دارد، ثبت کند یا پس از اتمام استفادهٔ دیگران دربارهٔ آزادسازی منابع آن تصمیم بگیرد. خود `exchange` تضمین نمی‌کند که دیگر هیچ `thread`ای از مقدار قبلی استفاده نمی‌کند؛ نسخهٔ برگردانده‌شده و نسخه‌های بارگذاری‌شدهٔ قبلی ممکن است همچنان زنده باشند.

### به‌روزرسانی شرطی با `compare_exchange`

عملیات‌های `compare_exchange_weak` و `compare_exchange_strong` مقدار اتمیک را با مقدار مورد انتظار مقایسه می‌کنند. اگر مقایسه موفق باشد، مقدار جدید نصب می‌شود؛ اگر موفق نباشد، متغیر `expected` با مقدار فعلی به‌روزرسانی می‌شود.

```cpp
auto expected = current_config.load();
auto desired = std::make_shared<const Config>(Config{1500});

if (current_config.compare_exchange_strong(expected, desired)) {
    // The replacement succeeded.
} else {
    // expected now contains the value observed by the failed operation.
}
```

مقایسهٔ `shared_ptr` در این عملیات بر اساس مالکیت و اشاره‌گر ذخیره‌شده مطابق قواعد مشخص‌شده برای این تخصصی‌سازی انجام می‌شود؛ آن را با مقایسهٔ محتوای شیء مقصد اشتباه نگیرید. در نتیجه، دو شیء با فیلدهای یکسان لزوماً برای این مقایسه معادل نیستند.

نسخهٔ `weak` ممکن است حتی بدون تفاوت واقعی مقدار، شکست کاذب (spurious failure) داشته باشد؛ به همین دلیل معمولاً در حلقه‌های retry استفاده می‌شود. نسخهٔ `strong` شکست کاذب ندارد، اما در بعضی الگوها نسخهٔ `weak` مناسب‌تر است.

## مثال کاربردی کامل: انتشار تنظیمات تغییرناپذیر

یکی از الگوهای روشن استفاده از این نوع، ساختن نسخهٔ جدیدی از داده در یک `thread` و انتشار آن برای خوانندگان است. در این الگو، خوانندگان یک snapshot محلی می‌گیرند و سپس بدون قفل روی خود snapshot کار می‌کنند. استفاده از `const` کمک می‌کند که داده پس از انتشار تغییر نکند.

```cpp
#include <atomic>
#include <iostream>
#include <memory>
#include <thread>

struct Config {
    int timeout_ms;
    int retry_count;
};

std::atomic<std::shared_ptr<const Config>> config{
    std::make_shared<const Config>(Config{200, 3})
};

void reader() {
    auto snapshot = config.load(std::memory_order_acquire);

    std::cout << "timeout=" << snapshot->timeout_ms
              << ", retries=" << snapshot->retry_count << '\n';
}

void writer() {
    auto next = std::make_shared<const Config>(Config{800, 5});
    config.store(std::move(next), std::memory_order_release);
}

int main() {
    std::thread r1(reader);
    std::thread w(writer);
    std::thread r2(reader);

    r1.join();
    w.join();
    r2.join();
}
```

در این مثال، هر خواننده یا نسخهٔ قدیمی را می‌بیند یا نسخهٔ جدید را؛ خواننده یک `shared_ptr` محلی دارد که طول عمر همان snapshot را تا پایان استفاده تضمین می‌کند. اگر ذخیره‌سازی با `memory_order_release` انجام شود و بارگذاری موفق با `memory_order_acquire` مقدار منتشرشده را مشاهده کند، نوشتن‌های پیش از انتشار می‌توانند از طریق رابطهٔ `synchronizes-with` و در نتیجه `happens-before` برای خواننده قابل مشاهده باشند.

توجه کنید که این برنامه تضمین نمی‌کند ترتیب چاپ خطوط ثابت باشد. همچنین `std::cout` در این مثال برای نمایش استفاده شده و ترتیب خروجی، معیاری برای ترتیب انتشار تنظیمات نیست.

## مدل حافظه و ترتیب عملیات

### ترتیب پیش‌فرض

عملیات‌های اتمیک این نوع، مانند دیگر عملیات‌های اتمیک، در صورت حذف آرگومان ترتیب حافظه از `std::memory_order_seq_cst` استفاده می‌کنند. این ترتیب یک ترتیب کلی سازگار با قواعد sequential consistency برای عملیات‌های مربوط فراهم می‌کند، اما به‌خودی‌خود جایگزین طراحی صحیح دسترسی به داده‌های غیراتمیک نیست.

### استفاده از `release` و `acquire`

در الگوی انتشار داده، معمولاً نویسنده یک شیء را کامل می‌سازد و سپس آن را با `store(memory_order_release)` منتشر می‌کند. خواننده با `load(memory_order_acquire)` مقدار را می‌گیرد. اگر بارگذاری مقدار منتشرشده را مشاهده کند، عملیات‌های پیش از ذخیره‌سازی release در برابر عملیات‌های پس از بارگذاری acquire مرتب می‌شوند.

```cpp
auto next = std::make_shared<const Config>(Config{600, 4});
config.store(std::move(next), std::memory_order_release);

auto snapshot = config.load(std::memory_order_acquire);
```

در یک مثال واقعی، دو خط بالا معمولاً در `thread`های جداگانه قرار می‌گیرند؛ اگر در یک تابع و به همین ترتیب اجرا شوند، ارزش آموزشی دارند اما به‌تنهایی سناریوی هم‌زمانی را نشان نمی‌دهند.

### محدودیت‌های `memory_order`

قواعد مجاز ترتیب حافظه برای عملیات‌های مختلف یکسان نیستند:

- `load` نمی‌تواند از `std::memory_order_release` یا `std::memory_order_acq_rel` استفاده کند.
- `store` نمی‌تواند از `std::memory_order_acquire` یا `std::memory_order_acq_rel` استفاده کند.
- `exchange` و عملیات‌های `compare_exchange` می‌توانند ترتیب‌های قوی‌تری مانند `acq_rel` را بپذیرند، با رعایت محدودیت‌های ترتیب موفقیت و شکست در `compare_exchange`.
- ترتیب شکست در `compare_exchange` نمی‌تواند `release` یا `acq_rel` باشد و نباید از ترتیب موفقیت قوی‌تر باشد.

در کدهای حساس به کارایی، ترتیب حافظه را فقط پس از مشخص‌کردن رابطه‌های لازم بین داده‌ها انتخاب کنید. یک `shared_ptr` اتمیک، صرفاً با اتمیک‌کردن اشاره‌گر، تمام متغیرهای دیگر برنامه را ایمن نمی‌کند.

## تضمین طول عمر و مالکیت

### زنده‌ماندن شیء مقصد

وقتی `load` یک `shared_ptr` برمی‌گرداند، مقدار برگردانده‌شده مالکیت مشترک را حفظ می‌کند. اگر نویسنده بلافاصله مقدار اتمیک را جایگزین کند، snapshot خواننده همچنان می‌تواند شیء قدیمی را زنده نگه دارد.

```cpp
auto old_snapshot = config.load();
config.store(std::make_shared<const Config>(Config{900, 2}));

// old_snapshot still keeps the old Config alive.
std::cout << old_snapshot->timeout_ms << '\n';
```

این رفتار برای دسترسی بدون قفل به snapshotهای تغییرناپذیر سودمند است؛ بااین‌حال، اگر خواننده یک snapshot را مدت زیادی نگه دارد، حافظهٔ نسخه‌های قدیمی نیز ممکن است دیرتر آزاد شود.

### تفاوت thread-safety شمارنده و شیء مقصد

مدیریت شمارندهٔ مالکیت مشترک با thread-safety داده‌های شیء تفاوت دارد. این الگو از نظر انتشار و طول عمر مناسب است:

```cpp
std::atomic<std::shared_ptr<Config>> current;

void reader() {
    auto p = current.load();
    if (p) {
        // Reading is safe only if no concurrent unsynchronized write
        // modifies the same fields of *p.
        int value = p->timeout_ms;
        (void)value;
    }
}
```

اگر thread دیگری هم‌زمان `p->timeout_ms` را تغییر دهد، `shared_ptr` اتمیک از آن فیلد محافظت نمی‌کند. برای شیء قابل‌تغییر، باید قفل، اتمیک‌های جداگانه، یا یک پروتکل همگام‌سازی معتبر دیگر به کار رود. در طراحی snapshot، معمولاً پس از انتشار داده را تغییرناپذیر نگه می‌دارند.

### احتیاط دربارهٔ چرخه‌های مالکیت

`std::shared_ptr` چرخه‌های مالکیت را به‌صورت خودکار جمع‌آوری نمی‌کند. اگر شیء مقصد به‌طور مستقیم یا غیرمستقیم مالکیت مشترکی ایجاد کند که به خودش بازمی‌گردد، شمارنده ممکن است هرگز به صفر نرسد. استفاده از `std::weak_ptr` در روابطی که مالکیت نباید چرخه بسازد، می‌تواند این مشکل را حل کند. اتمیک‌بودن جایگاه `shared_ptr` این مسئله را تغییر نمی‌دهد.

## آیا عملیات‌ها lock-free هستند؟

وجود `std::atomic<std::shared_ptr<T>>` به این معنی نیست که همهٔ عملیات‌های آن الزاماً lock-free هستند. پیاده‌سازی کتابخانهٔ استاندارد می‌تواند برای تضمین اتمیک‌بودن از قفل داخلی یا سازوکارهای دیگر استفاده کند. برای بررسی ویژگی در زمان اجرا، رابط `is_lock_free()` ارائه نشده است؛ این تخصصی‌سازی متد `is_lock_free` ندارد. بنابراین نباید از `std::atomic_is_lock_free` یا فرض lock-free بودن نوع‌های اتمیک ساده، نتیجه گرفت که عملیات `atomic<shared_ptr>` بدون قفل است.

در عمل، عملیات‌های `shared_ptr` نیازمند مدیریت شمارندهٔ مالکیت‌اند و ممکن است هزینه‌هایی فراتر از تعویض یک اشاره‌گر خام داشته باشند. اگر تأخیر قابل پیش‌بینی یا کارایی بسیار بالا ضروری است، باید روی کتابخانه و پلتفرم هدف benchmark انجام دهید و هزینهٔ تخصیص حافظه، افزایش و کاهش شمارنده و آزادسازی شیء را نیز در نظر بگیرید.

## تفاوت با `std::mutex`

دو رویکرد رایج، استفاده از `std::atomic<std::shared_ptr<T>>` و حفاظت از یک `shared_ptr` معمولی با `std::mutex` است. هیچ‌کدام در همهٔ شرایط برنده نیستند.

| معیار | `std::atomic<std::shared_ptr<T>>` | `std::mutex` همراه با `shared_ptr` |
|---|---|---|
| اتمیک‌بودن جایگاه اشاره‌گر | از طریق عملیات تخصصی‌سازی | با قفل‌گرفتن در تمام دسترسی‌های مرتبط |
| خواندن snapshot | معمولاً ساده با `load` | نیازمند رعایت قرارداد قفل |
| قفل داخلی | ممکن است در پیاده‌سازی وجود داشته باشد | قفل صریح و قابل مشاهده |
| کار با چند متغیر مرتبط | به‌تنهایی کافی نیست | می‌تواند چند داده را زیر یک قفل محافظت کند |
| مناسب برای | انتشار یک مقدار مستقل یا snapshot | invariantهای چندمتغیره و عملیات مرکب |
| طول عمر snapshot | با کپی `shared_ptr` حفظ می‌شود | می‌توان آن را زیر قفل کپی و سپس بیرون قفل استفاده کرد |

اگر عملیات نیاز دارد چند متغیر همیشه با هم سازگار بمانند، قفل معمولاً راه‌حل ساده‌تر و روشن‌تری است. اگر مسئله صرفاً تعویض یک اشاره‌گر به دادهٔ تغییرناپذیر باشد، نوع اتمیک می‌تواند رابط مناسبی ارائه کند.

## الگوهای کاربردی

### انتشار snapshot تنظیمات

برنامه می‌تواند تنظیمات جدید را خارج از مسیر خواندن بسازد و پس از تکمیل، با یک `store` منتشر کند. خوانندگان فقط یک بار `load` می‌کنند و از snapshot محلی استفاده می‌کنند. این الگو وقتی مناسب است که خواندن بسیار بیشتر از نوشتن انجام شود و داده پس از انتشار تغییر نکند.

### تعویض جدول راهنمایی یا دادهٔ cache

در یک cache یا registry، ممکن است ساختار دادهٔ جدید به‌طور کامل آماده شود و سپس جایگزین نسخهٔ قبلی گردد. اتمیک‌بودن جایگاه اشاره‌گر از مشاهدهٔ یک `shared_ptr` نیمه‌جایگزین‌شده جلوگیری می‌کند؛ اما سازوکار ساخت و تغییر خود ساختار باید جداگانه ایمن باشد.

### انتشار سیاست یا مدل قابل‌تعویض

یک سرویس می‌تواند یک شیء سیاست، جدول مسیریابی یا مدل خواندنی را با نسخهٔ تازه جایگزین کند. خواننده‌ای که نسخهٔ قبلی را گرفته است، تا پایان کار مالکیت آن را نگه می‌دارد. این روش از آزادشدن زودهنگام شیء جلوگیری می‌کند و نیاز به هماهنگی دستی طول عمر را کاهش می‌دهد.

## الگوی به‌روزرسانی با حلقهٔ `compare_exchange`

گاهی لازم است مقدار جدید بر اساس نسخهٔ فعلی محاسبه شود. در این وضعیت، یک بار `load` و سپس `store` کافی نیست، چون نویسندهٔ دیگری ممکن است بین این دو عملیات مقدار را تغییر دهد. می‌توان از حلقهٔ compare-exchange استفاده کرد:

```cpp
#include <atomic>
#include <memory>

struct Settings {
    int limit;
};

std::atomic<std::shared_ptr<const Settings>> settings{
    std::make_shared<const Settings>(Settings{10})
};

void increase_limit(int delta) {
    auto expected = settings.load(std::memory_order_acquire);

    for (;;) {
        auto desired = std::make_shared<const Settings>(
            Settings{expected->limit + delta}
        );

        if (settings.compare_exchange_weak(
                expected,
                desired,
                std::memory_order_release,
                std::memory_order_acquire)) {
            break;
        }

        // On failure, expected is updated to the currently observed value.
    }
}
```

در این مثال، مقدار پیشنهادی در هر تلاش بر اساس `expected` همان تلاش ساخته می‌شود. اگر عملیات شکست بخورد، `expected` به مقدار مشاهده‌شده به‌روزرسانی می‌شود و حلقه مقدار تازه را مبنا قرار می‌دهد. ترتیب موفقیت `release` و ترتیب شکست `acquire` با محدودیت‌های `compare_exchange` سازگارند.

این الگو فقط زمانی درست است که عملیات محاسبه‌شده را بتوان در صورت شکست دوباره انجام داد. ساختن شیء جدید در هر تلاش ممکن است هزینهٔ تخصیص حافظه داشته باشد. همچنین اگر محاسبه اثر جانبی خارجی داشته باشد، retry ممکن است آن اثر را چند بار اجرا کند؛ در آن صورت باید طراحی بازنگری شود.

## نکات ظریف دربارهٔ `compare_exchange`

### مقایسهٔ اشاره‌گر و مالکیت

عملیات compare-exchange برای `shared_ptr` بر مبنای قواعد مقایسهٔ مشخص‌شده برای تخصصی‌سازی انجام می‌شود، نه برابری محتوای شیء. در کدهای قدیمی‌تر یا پیاده‌سازی‌های متفاوت، نباید بدون توجه به نسخهٔ استاندارد، فرض کنید که تنها مقایسهٔ آدرس ذخیره‌شده تمام معنای مقایسه را بیان می‌کند. در ++C20، قواعد این تخصصی‌سازی برای مقایسهٔ مقدار مورد انتظار تعریف شده‌اند و در استانداردهای بعدی نیز جزئیات کتابخانه ممکن است تکامل یابد؛ هنگام تکیه بر موارد مرزی، مرجع استاندارد هدف را بررسی کنید.

### مسئلهٔ ABA

مسئلهٔ ABA زمانی مطرح می‌شود که مقدار از A به B و سپس دوباره به A تغییر کند و الگوریتم فقط برابری مقدار فعلی را بسنجد. مالکیت مشترک می‌تواند در بعضی سناریوها طول عمر اشیاء را حفظ کند، اما به‌تنهایی یک نسخه‌شمار یا پروتکل تشخیص همهٔ تغییرات ایجاد نمی‌کند. اگر صحت الگوریتم به این وابسته است که هیچ تغییر میانی رخ نداده باشد، از یک شمارندهٔ نسل، شناسهٔ نسخه یا طرحی استفاده کنید که این تغییر را قابل تشخیص کند.

### شکست و به‌روزرسانی `expected`

پس از شکست compare-exchange، `expected` دیگر لزوماً همان مقدار اولیه نیست؛ مقدار فعلی مشاهده‌شده در عملیات شکست در آن قرار می‌گیرد. فراموش‌کردن این نکته می‌تواند باعث محاسبهٔ مجدد بر اساس snapshot قدیمی و ایجاد خطاهای منطقی شود.

## نکات مربوط به `nullptr` و مقادیر خالی

مقدار اتمیک می‌تواند یک `shared_ptr` خالی نگه دارد. بنابراین، مانند هر `shared_ptr` دیگری، قبل از dereference باید معتبر بودن آن بررسی شود.

```cpp
std::atomic<std::shared_ptr<const Config>> config;

auto snapshot = config.load();
if (snapshot) {
    std::cout << snapshot->timeout_ms << '\n';
}
```

مقداردهی اولیهٔ پیش‌فرض یک `std::atomic<std::shared_ptr<T>>` آن را با `shared_ptr` خالی مقداردهی می‌کند. اگر برنامه انتظار دارد مقدار همیشه موجود باشد، بهتر است این invariant را هنگام ساخت برقرار کند و در عین حال رفتار حالت خالی را در مسیرهای خطا یا shutdown مشخص کند.

## مدیریت آزادسازی و اثرات جانبی destructor

وقتی یک عملیات اتمیک جایگاه `shared_ptr` را تغییر می‌دهد، شمارندهٔ مالکیت مقدار قبلی ممکن است کاهش یابد. اگر این کاهش آخرین مالکیت باشد، تخریب شیء و آزادسازی حافظه می‌تواند در همان مسیری رخ دهد که عملیات را انجام می‌دهد، مطابق قواعد استاندارد و جزئیات پیاده‌سازی. بنابراین، عملیات‌هایی مانند `store` یا `exchange` را نباید بدون بررسی در مسیرهایی قرار داد که destructor سنگین، آزادسازی منابع گران‌قیمت یا callbackهای غیرقابل پیش‌بینی دارند.

اگر زمان و محل آزادسازی منابع مهم است، می‌توان مقدار قبلی را با `exchange` دریافت کرد و سیاست آزادسازی را جداگانه طراحی نمود؛ با این حال، نسخه‌های دیگری که خوانندگان نگه داشته‌اند همچنان می‌توانند آزادسازی نهایی را به تأخیر بیندازند. صرف استفاده از `exchange` تضمین نمی‌کند destructor دقیقاً در همان نقطه یا در thread خاصی اجرا شود.

## ساخت و مقداردهی اولیه

برای مقداردهی اولیه می‌توان یک `shared_ptr` موجود را به سازنده داد:

```cpp
auto initial = std::make_shared<const Config>(Config{300});
std::atomic<std::shared_ptr<const Config>> config{initial};
```

همچنین می‌توان آن را با `shared_ptr` ساخته‌شده در همان عبارت مقداردهی کرد. نوع `std::atomic<std::shared_ptr<T>>` قابل کپی‌کردن نیست؛ یک شیء اتمیک را نمی‌توان مانند یک `shared_ptr` معمولی کپی کرد. برای انتقال مقدار بین جایگاه‌ها، باید از عملیات‌های بارگذاری، ذخیره‌سازی یا جایگزینی استفاده کرد.

## محدودیت‌ها و مواردی که بهتر است استفاده نشود

- اگر چند فیلد یا چند شیء باید به‌عنوان یک invariant واحد تغییر کنند، یک جایگاه اتمیک به‌تنهایی کافی نیست.
- اگر مقصد پس از انتشار به‌شکل هم‌زمان تغییر می‌کند، باید همگام‌سازی جداگانه‌ای برای محتوای آن در نظر گرفته شود.
- اگر هر بار خواندن یا نوشتن بسیار پرتکرار است و هزینهٔ شمارندهٔ `shared_ptr` قابل توجه است، benchmark و گزینه‌های دیگر را بررسی کنید.
- اگر مدیریت مالکیت مشترک ضروری نیست و طول عمر شیء از قبل با پروتکل دیگری تضمین می‌شود، `shared_ptr` ممکن است سربار غیرضروری ایجاد کند.
- اگر نیاز به تضمین سخت‌گیرانهٔ latency یا رفتار lock-free دارید، فرض نکنید این تخصصی‌سازی چنین تضمینی ارائه می‌کند.
- اگر چند writer هم‌زمان تغییرات وابسته به مقدار قبلی انجام می‌دهند، استفادهٔ ساده از `load` سپس `store` می‌تواند به lost update منجر شود؛ در این حالت از compare-exchange یا قفل استفاده کنید.

## خطاهای رایج

### اشتباه گرفتن اتمیک‌بودن اشاره‌گر با اتمیک‌بودن شیء

این نوع فقط عملیات روی جایگاه `shared_ptr` را همگام می‌کند. خواندن و نوشتن هم‌زمان یک فیلد غیراتمیک در شیء مقصد همچنان می‌تواند data race باشد.

### نگه‌داشتن مرجع خام پس از پایان مالکیت

اگر یک اشاره‌گر خام یا reference از snapshot گرفته شود و `shared_ptr` مالک آن از بین برود، دسترسی بعدی می‌تواند به dangling pointer منجر شود. تا زمانی که استفاده ادامه دارد، یک `shared_ptr` محلی نگه دارید یا طول عمر را با روشی معتبر تضمین کنید.

### فرض‌کردن lock-free بودن

نام `atomic` تضمین نمی‌کند که پیاده‌سازی بدون قفل باشد. مشخصات کارایی را روی پلتفرم هدف اندازه‌گیری کنید.

### استفاده از `store` برای به‌روزرسانی مبتنی بر مقدار فعلی

الگوی `load`، محاسبه و سپس `store` در حضور چند نویسنده می‌تواند به از دست رفتن به‌روزرسانی منجر شود. برای تغییر شرطی یا مبتنی بر مقدار قبلی، از compare-exchange یا قفل استفاده کنید.

### نگه‌داشتن snapshotها برای مدت طولانی

مالکیت مشترک، طول عمر را ایمن می‌کند اما ممکن است حافظهٔ نسخه‌های قدیمی را برای مدت طولانی نگه دارد. مدت نگهداری snapshotها و اندازهٔ داده‌ها را در طراحی حافظه لحاظ کنید.

## راهنمای انتخاب

برای انتخاب بین چند گزینه، ابتدا مشخص کنید چه چیزی باید اتمیک باشد:

- اگر فقط یک اشاره‌گر به یک snapshot تغییرناپذیر باید جایگزین شود، `std::atomic<std::shared_ptr<const T>>` گزینه‌ای روشن و کاربردی است.
- اگر چند داده باید با هم تغییر کنند، یک `std::mutex` یا طراحی همگام‌سازی جامع‌تر را در نظر بگیرید.
- اگر مالکیت مشترک لازم نیست، شاید یک اشاره‌گر خام یا نوع مالکیت دیگری با پروتکل طول عمر دقیق مناسب‌تر باشد؛ اما حذف `shared_ptr` بدون اثبات ایمنی طول عمر خطرناک است.
- اگر کارایی مهم است، معیار را با benchmark واقعی، ابزارهای تشخیص data race و بار کاری مشابه محیط تولید تعیین کنید.

## جمع‌بندی

نوع `std::atomic<std::shared_ptr<T>>` در ++C20 امکان بارگذاری، ذخیره‌سازی، جایگزینی و compare-exchange اتمیک برای یک `shared_ptr` را فراهم می‌کند. این قابلیت به‌خصوص برای انتشار snapshotهای تغییرناپذیر و تعویض داده‌هایی مناسب است که تعداد خواندن آن‌ها زیاد و تعداد به‌روزرسانی‌شان کم است.

مهم‌ترین اصل طراحی این است که سه مسئله را از هم جدا نگه دارید: اتمیک‌بودن جایگاه اشاره‌گر، طول عمر شیء مقصد و همگام‌سازی دسترسی به محتوای شیء. `std::atomic<std::shared_ptr<T>>` دو مورد اول را در سطح عملیات مالکیت و انتشار به شکل مفیدی پشتیبانی می‌کند، اما برای تغییرات هم‌زمان داخل شیء یا invariantهای چندمتغیره به راهکارهای دیگری نیاز دارید. در نهایت، کارایی، رفتار آزادسازی و نیاز واقعی به مالکیت مشترک باید با توجه به پیاده‌سازی و بار کاری هدف ارزیابی شوند.
