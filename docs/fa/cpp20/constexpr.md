# بهبودهای `constexpr` در ++C20

## مقدمه

قابلیت `constexpr` به کامپایلر اجازه می‌دهد در صورت فراهم بودن شرایط، عبارت‌ها و توابع را هنگام ترجمه ارزیابی کند. هدف این قابلیت صرفاً سریع‌تر کردن برنامه نیست؛ ارزیابی زمان ترجمه می‌تواند برای ساخت مقادیر ثابت، اعتبارسنجی ورودی‌ها، تولید جدول‌های داده، پیاده‌سازی الگوریتم‌های عمومی و تشخیص خطاها پیش از اجرای برنامه نیز به کار رود.

استاندارد ++C20 این قابلیت را به‌طور چشمگیری گسترش داد. محدودیت‌های قدیمی‌تر درباره بدنهٔ توابع `constexpr` کاهش یافتند، تخصیص حافظهٔ پویا در ارزیابی زمان ترجمه امکان‌پذیر شد و بخش بزرگی از کتابخانهٔ استاندارد برای استفاده در عبارت‌های ثابت آماده شد. در کنار این تغییرات، قابلیت‌هایی مانند `consteval`، `constinit` و `std::is_constant_evaluated` ابزارهای دقیق‌تری برای کنترل زمان ارزیابی در اختیار برنامه‌نویس قرار می‌دهند.

نکتهٔ مهم این است که `constexpr` به معنای «حتماً اجرا شدن در زمان کامپایل» نیست. یک تابع `constexpr` می‌تواند در زمان اجرا نیز فراخوانی شود؛ تنها وقتی از نتیجه در زمینه‌ای استفاده شود که به عبارت ثابت نیاز دارد، ارزیابی زمان ترجمه الزامی می‌شود.

## مفهوم ارزیابی زمان ترجمه

### تفاوت میان `constexpr` و اجرای عادی

تابع `constexpr` تابعی است که در صورت رعایت قواعد عبارت ثابت، امکان ارزیابی در زمان ترجمه را دارد. کامپایلر آزاد است فراخوانی‌های دیگر همان تابع را در زمان اجرا انجام دهد.

```cpp
constexpr int square(int value) {
    return value * value;
}

constexpr int compile_time_result = square(8);

int runtime_square(int value) {
    return square(value);
}
```

در مثال بالا، مقدار `compile_time_result` باید یک عبارت ثابت معتبر باشد؛ بنابراین نتیجهٔ `square(8)` در زمان ترجمه محاسبه می‌شود. در مقابل، فراخوانی داخل `runtime_square` به ورودی زمان اجرا وابسته است و می‌تواند هنگام اجرای برنامه ارزیابی شود.

### سه مفهوم متفاوت: `constexpr`، `consteval` و `constinit`

این سه کلیدواژه به مسائل مرتبط، اما متفاوتی پاسخ می‌دهند:

- `constexpr` امکان ارزیابی زمان ترجمه را فراهم می‌کند و برای متغیرها نیز ثابت بودن مقدار را الزام می‌کند.
- `consteval` که در ++C20 معرفی شد، یک تابع `immediate function` تعریف می‌کند؛ فراخوانی‌های مجاز آن باید در زمینهٔ ارزیابی فوری و زمان ترجمه انجام شوند.
- `constinit` که در ++C20 معرفی شد، تضمین می‌کند متغیر دارای مدت‌زمان ذخیره‌سازی ایستا یا thread-local به‌صورت ایستای مقداردهی اولیه شود؛ اما متغیر را `const` نمی‌کند و به‌تنهایی به معنی قابل‌استفاده بودن مقدار آن در همهٔ عبارت‌های ثابت نیست.

```cpp
constexpr int multiply(int a, int b) {
    return a * b;
}

consteval int compile_time_multiply(int a, int b) {
    return a * b;
}

constinit int global_counter = 0;

int main() {
    constexpr int a = multiply(3, 4);
    constexpr int b = compile_time_multiply(5, 6);

    global_counter = a + b;
}
```

در این مثال، `global_counter` پس از مقداردهی اولیه همچنان قابل تغییر است. همچنین `consteval` برای توابعی مناسب است که نتیجهٔ زمان ترجمه بخشی از قرارداد طراحی آن‌هاست، نه صرفاً یک بهینه‌سازی احتمالی.

## مهم‌ترین تغییرات زبانی در ++C20

### کاهش محدودیت‌های بدنهٔ تابع `constexpr`

در استانداردهای قدیمی‌تر، تابع `constexpr` باید بدنه‌ای بسیار محدود داشته باشد. این محدودیت‌ها در نسخه‌های مختلف استاندارد به‌تدریج کاهش یافتند و ++C20 این روند را ادامه داد. در ++C20، تابع `constexpr` می‌تواند از سازوکارهای متداول‌تری مانند متغیرهای محلی، حلقه‌ها، شاخه‌بندی، مدیریت استثنا و بعضی عملیات حافظهٔ پویا استفاده کند؛ البته ارزیابی واقعی همچنان باید با قواعد عبارت ثابت سازگار باشد.

```cpp
constexpr int sum_until(int limit) {
    int total = 0;

    for (int i = 0; i <= limit; ++i) {
        if (i % 2 == 0) {
            total += i;
        }
    }

    return total;
}

static_assert(sum_until(6) == 12);
```

این نمونه از متغیر محلی قابل‌تغییر، حلقه و شرط استفاده می‌کند. چنین ساختاری برای توابع `constexpr` مدرن طبیعی است و نیازی به بازنویسی الگوریتم به شکل بازگشتی ندارد.

### مقداردهی اولیهٔ پیش‌فرض در توابع `constexpr`

تغییر مرتبط با `P1331R2` در ++C20 اجازه می‌دهد برخی متغیرهای محلی از نوع‌های ساده بدون مقداردهی اولیهٔ فوری تعریف شوند، به شرط آنکه مسیر اجرایی پیش از خواندن مقدار، آن را مقداردهی کند.

```cpp
constexpr int first_positive(const int* values, int count) {
    int result;

    for (int i = 0; i < count; ++i) {
        if (values[i] > 0) {
            result = values[i];
            return result;
        }
    }

    return 0;
}

constexpr int values[] = {-3, 0, 7, 9};
static_assert(first_positive(values, 4) == 7);
```

این امکان به معنای مجاز شدن خواندن متغیر مقداردهی‌نشده نیست. اگر یک مسیر اجرایی پیش از نوشتن در `result` آن را بخواند، برنامه دچار رفتار تعریف‌نشده خواهد شد و آن مسیر نمی‌تواند ارزیابی ثابت معتبر ایجاد کند. در طراحی عمومی، مقداردهی اولیهٔ صریح معمولاً خوانایی بیشتری دارد؛ از این ویژگی فقط زمانی استفاده کنید که ساختار الگوریتم آن را توجیه کند.

### استفاده از `try` و `catch` در تابع `constexpr`

استاندارد ++C20 اجازه می‌دهد بدنهٔ تابع `constexpr` شامل ساختارهای `try` و `catch` باشد. این تغییر به‌تنهایی به معنی قابل‌پرتاب بودن هر استثنا در ارزیابی ثابت نیست؛ مسیر ارزیابی ثابت باید همچنان قواعد عبارت ثابت را رعایت کند. به‌ویژه، مسیری که در زمان ترجمه استثنا پرتاب می‌کند معمولاً نمی‌تواند برای تولید یک عبارت ثابت معتبر استفاده شود.

```cpp
constexpr int safe_divide(int numerator, int denominator) {
    try {
        if (denominator == 0) {
            throw "division by zero";
        }

        return numerator / denominator;
    } catch (...) {
        return 0;
    }
}

static_assert(safe_divide(12, 3) == 4);
```

فراخوانی بالا مسیر بدون استثنا را طی می‌کند و برای عبارت ثابت معتبر است. نباید از این مثال نتیجه گرفت که پرتاب و گرفتن استثنا در زمان ترجمه جایگزینی عمومی برای اعتبارسنجی ورودی‌هاست. در کدی که خطا باید در زمان ترجمه تشخیص داده شود، می‌توان از `static_assert`، `consteval` یا طراحی‌ای استفاده کرد که ورودی نامعتبر را از ابتدا ناممکن کند.

### پشتیبانی از توابع مجازی `constexpr`

در ++C20 محدودیت‌های مربوط به تابع مجازی `constexpr` کاهش یافتند و این توابع می‌توانند در طراحی‌های چندریختی نیز نقش داشته باشند. بااین‌حال، هر فراخوانی مجازی الزاماً در زمان ترجمه قابل ارزیابی نیست؛ نوع پویای شیء، مسیر فراخوانی و قواعد عبارت ثابت همچنان تعیین‌کننده‌اند.

```cpp
struct Base {
    constexpr virtual int value() const {
        return 1;
    }

    constexpr virtual ~Base() = default;
};

struct Derived : Base {
    constexpr int value() const override {
        return 2;
    }
};

constexpr int read_value(const Base& object) {
    return object.value();
}

constexpr Derived derived{};
static_assert(read_value(derived) == 2);
```

این قابلیت می‌تواند برای مدل‌های دادهٔ ثابت و سلسله‌مراتب کوچک مفید باشد، اما پیچیدگی چندریختی را به‌صورت خودکار از بین نمی‌برد. برای طراحی‌هایی که به ارزیابی زمان ترجمهٔ قابل‌پیش‌بینی نیاز دارند، نوع‌های ساده، `std::variant` یا الگوهای مبتنی بر templates ممکن است انتخاب مناسب‌تری باشند.

### تخریب‌گرهای `constexpr`

در ++C20 می‌توان تخریب‌گر را با `constexpr` مشخص کرد. این ویژگی برای نوع‌هایی مهم است که در طول ارزیابی زمان ترجمه منابعی را مدیریت می‌کنند و باید پیش از پایان ارزیابی، به‌درستی تخریب شوند.

```cpp
struct Measurement {
    int value;

    constexpr Measurement(int v) : value(v) {}

    constexpr ~Measurement() = default;
};

constexpr int get_measurement() {
    Measurement item{42};
    return item.value;
}

static_assert(get_measurement() == 42);
```

قابل‌استفاده بودن تخریب‌گر در زمان ترجمه به معنی مجاز بودن هر عملیات درون آن نیست. عملیات تخریب نیز باید در زمینهٔ ثابت مجاز باشد و منابع موقت ایجادشده در ارزیابی باید طبق قواعد مربوط آزاد شوند.

## تخصیص حافظهٔ پویا در زمان ترجمه

### پشتیبانی از `new` و `delete`

یکی از تغییرات مهم ++C20، با پیشنهاد `P0784R7`، امکان استفاده از تخصیص و آزادسازی حافظهٔ پویا در ارزیابی ثابت است. حافظه‌ای که در جریان ارزیابی ثابت با سازوکار مجاز تخصیص داده می‌شود، باید پیش از پایان همان ارزیابی آزاد شود؛ به این ویژگی معمولاً `transient allocation` گفته می‌شود.

```cpp
constexpr int sum_dynamic(int count) {
    int* values = new int[count];

    int sum = 0;
    for (int i = 0; i < count; ++i) {
        values[i] = i + 1;
        sum += values[i];
    }

    delete[] values;
    return sum;
}

static_assert(sum_dynamic(5) == 15);
```

در این نمونه، حافظه در همان ارزیابی تخصیص داده و پیش از بازگشت آزاد می‌شود. اگر تخصیص با `new` انجام شود اما حافظه در پایان ارزیابی ثابت همچنان زنده بماند، آن ارزیابی معمولاً عبارت ثابت معتبری نخواهد بود.

### چرا تخصیص پویا در زمان ترجمه مفید است؟

پیش از ++C20، بسیاری از الگوریتم‌های زمان ترجمه باید از آرایه‌های ثابت، ظرفیت‌های از پیش تعیین‌شده یا بازگشت‌های پیچیده استفاده می‌کردند. تخصیص پویا اجازه می‌دهد ساختارهای دادهٔ موقت با اندازهٔ وابسته به ورودی بسازیم؛ برای نمونه، می‌توان یک الگوریتم را با حافظهٔ موقت اجرا کرد و در نهایت فقط یک عدد یا نتیجهٔ ثابت برگرداند.

این قابلیت برای تولید جدول‌های ثابت، تجزیهٔ رشته‌ها، اعتبارسنجی پیکربندی و محاسباتی که به حافظهٔ موقت نیاز دارند مفید است. بااین‌حال، محدودیت‌های کامپایلر و سقف منابع ارزیابی ثابت همچنان مهم‌اند؛ الگوریتمی که در زمان اجرا مناسب است ممکن است در زمان ترجمه بسیار پرهزینه باشد.

### محدودیت‌های حافظهٔ پویا در عبارت‌های ثابت

قواعد ++C20 به این معنا نیستند که هر منبع حافظه‌ای می‌تواند از زمان ترجمه به برنامهٔ اجراشونده منتقل شود. تخصیص‌های موقت باید در طول ارزیابی ثابت به‌درستی آزاد شوند و نتیجهٔ نهایی باید از نوعی باشد که قواعد عبارت ثابت اجازه می‌دهند.

```cpp
constexpr int* invalid_escape() {
    return new int(10);
}

// This is not a valid constant expression:
// constexpr int* ptr = invalid_escape();
```

نمونهٔ بالا عمداً به‌صورت کامنت توضیح داده شده است، زیرا بازگرداندن اشاره‌گر به حافظه‌ای که در این ارزیابی تخصیص داده شده و آزاد نشده، برای ساخت مقدار ثابت مجاز نیست. اگر داده باید در برنامه باقی بماند، از ساختاری مناسب برای دادهٔ ثابت استفاده کنید؛ برای مثال، `std::array` با اندازهٔ معلوم یا یک شیء دارای ذخیره‌سازی ایستا که به‌درستی مقداردهی اولیه شده باشد.

## پشتیبانی کتابخانهٔ استاندارد از `constexpr`

### استفاده از `std::vector` در زمان ترجمه

در ++C20 بسیاری از عملیات `std::vector` برای ارزیابی `constexpr` آماده شدند. این تغییر استفاده از ظرفی با اندازهٔ متغیر را در محاسبات زمان ترجمه ممکن می‌کند، مشروط بر اینکه تخصیص‌های پویا در پایان ارزیابی ثابت آزاد شوند.

```cpp
#include <vector>

constexpr int sum_vector() {
    std::vector<int> values;

    values.push_back(10);
    values.push_back(20);
    values.push_back(30);

    int sum = 0;
    for (int value : values) {
        sum += value;
    }

    return sum;
}

static_assert(sum_vector() == 60);
```

این مثال به پیاده‌سازی کتابخانهٔ استانداردی نیاز دارد که پشتیبانی `constexpr` مربوط به ++C20 را ارائه کند. استفاده از `std::vector` در محاسبهٔ ثابت به این معنی نیست که می‌توان یک `std::vector` معمولی را با حافظهٔ تخصیص‌یافته در زمان ترجمه به‌طور دلخواه در خروجی نهایی نگه داشت؛ محدودیت عمر تخصیص‌ها همچنان پابرجاست.

### استفاده از `std::string` در زمان ترجمه

در ++C20 بسیاری از توابع `std::string` نیز `constexpr` شدند. در نتیجه، ساخت، تغییر و بررسی رشته‌ها می‌تواند بخشی از محاسبات زمان ترجمه باشد.

```cpp
#include <string>

constexpr bool has_expected_size() {
    std::string text = "compile-time";
    text += "-string";
    return text.size() == 18;
}

static_assert(has_expected_size());
```

رفتار و امکان ارزیابی ثابت باید با پیاده‌سازی کتابخانه و قواعد حافظهٔ پویا سازگار باشد. برای داده‌های ثابت و کوچک، `std::string_view` اغلب گزینه‌ای سبک‌تر است؛ اما این نوع مالک حافظه نیست و نباید به داده‌ای اشاره کند که عمر آن تمام شده است.

### الگوریتم‌های کتابخانهٔ استاندارد

استاندارد ++C20 قابلیت `constexpr` را به تعداد زیادی از الگوریتم‌ها و توابع کتابخانه گسترش داد. برای نمونه، بسیاری از الگوریتم‌های `<algorithm>` مانند `std::sort` و `std::find` در ++C20 قابل ارزیابی ثابت شدند، به شرط آنکه نوع‌ها، iteratorها و عملیات مورد استفاده نیز با ارزیابی ثابت سازگار باشند.

```cpp
#include <algorithm>
#include <array>

constexpr bool sorted_values() {
    std::array<int, 5> values{5, 1, 4, 2, 3};
    std::sort(values.begin(), values.end());

    return values == std::array<int, 5>{1, 2, 3, 4, 5};
}

static_assert(sorted_values());
```

این قابلیت نیاز به پیاده‌سازی دستی الگوریتم‌های ساده را کاهش می‌دهد و امکان استفادهٔ مجدد از الگوریتم‌های استاندارد را افزایش می‌دهد. بااین‌حال، باید بررسی کرد که همهٔ عملیات مورد استفاده در مسیر ارزیابی ثابت پشتیبانی می‌شوند؛ `constexpr` بودن یک الگوریتم به‌تنهایی هر نوع iterator یا تابع مقایسه‌ای را قابل‌استفاده در زمان ترجمه نمی‌کند.

### بررسی نوع‌ها و توابع کتابخانه

پشتیبانی `constexpr` در کتابخانه به‌صورت یکپارچه برای تمام اجزا اضافه نشد. بعضی نوع‌ها و توابع از استانداردهای قدیمی‌تر `constexpr` بودند و بعضی دیگر در ++C20 گسترش یافتند. بنابراین، هنگام هدف‌گیری چند کامپایلر یا کتابخانه، مستندات پیاده‌سازی و وضعیت پشتیبانی استاندارد را بررسی کنید؛ صرف فعال کردن حالت `-std=c++20` تضمین نمی‌کند که همهٔ امکانات کتابخانه در نسخهٔ نصب‌شده کامل باشند.

## تشخیص زمینهٔ ارزیابی با `std::is_constant_evaluated`

### معرفی `std::is_constant_evaluated`

تابع `std::is_constant_evaluated` در ++C20 و در سرآیند `<type_traits>` معرفی شد. این تابع مشخص می‌کند که فراخوانی در زمینه‌ای انجام می‌شود که ارزیابی ثابت در حال بررسی است یا خیر.

```cpp
#include <type_traits>

constexpr int choose_value(int value) {
    if (std::is_constant_evaluated()) {
        return value * 2;
    }

    return value * 3;
}

static_assert(choose_value(10) == 20);

int main() {
    int result = choose_value(10);
    return result == 30 ? 0 : 1;
}
```

در عبارت `static_assert` مسیر ارزیابی ثابت انتخاب می‌شود. فراخوانی زمان اجرا در `main` مسیر دیگر را طی می‌کند. این امکان گاهی برای انتخاب الگوریتمی مناسب‌تر در زمان ترجمه یا زمان اجرا مفید است.

### موارد استفادهٔ مناسب

از این تابع می‌توان زمانی استفاده کرد که دو پیاده‌سازی از نظر معنایی نتیجهٔ یکسانی تولید می‌کنند، اما یکی برای ارزیابی ثابت مناسب‌تر است. برای نمونه، مسیر زمان ترجمه ممکن است از الگوریتمی ساده و کم‌هزینه از نظر منابع کامپایلر استفاده کند، در حالی که مسیر زمان اجرا از بهینه‌سازی سخت‌افزاری یا روش سریع‌تری بهره ببرد.

نباید از آن برای ایجاد تفاوت معنایی غیرمنتظره در API استفاده کرد. اگر نتیجهٔ یک تابع به این بستگی داشته باشد که فراخوانی در زمان ترجمه رخ داده یا زمان اجرا، این تفاوت باید بخشی آگاهانه و مستند از قرارداد تابع باشد.

### نکتهٔ ظریف دربارهٔ ارزیابی احتمالی

در بعضی زمینه‌ها، کامپایلر ممکن است عبارت را برای بررسی امکان ارزیابی ثابت ارزیابی کند، حتی اگر در نهایت همان عبارت به‌عنوان مقدار ثابت استفاده نشود. به همین دلیل، نباید `std::is_constant_evaluated` را معادل پرسش ساده‌ای دربارهٔ تصمیم نهایی کامپایلر برای تولید کد دانست. این تابع دربارهٔ زمینهٔ ارزیابی است، نه یک ابزار عمومی برای تشخیص همهٔ بهینه‌سازی‌های کامپایلر.

## توابع `consteval` و محاسبات اجباری زمان ترجمه

### تفاوت `consteval` با `constexpr`

تابع `constexpr` می‌تواند هم در زمان ترجمه و هم در زمان اجرا استفاده شود. در مقابل، تابع `consteval` در ++C20 یک `immediate function` است و فراخوانی آن باید در زمینه‌ای انجام شود که شرایط ارزیابی فوری را برآورده کند.

```cpp
consteval int checked_port(int port) {
    if (port < 1 || port > 65535) {
        throw "invalid port";
    }

    return port;
}

constexpr int server_port = checked_port(8080);
```

این مثال برای مقدار معتبر قابل ارزیابی است. اگر آرگومان در زمان ترجمه معلوم نباشد یا مسیر فراخوانی شرایط لازم را رعایت نکند، برنامه نامعتبر خواهد بود. پرتاب استثنا در مسیر نامعتبر نیز باعث نمی‌شود مقدار نامعتبر به‌طور عادی به دست آید؛ در این مثال، چنین فراخوانی‌ای نمی‌تواند یک ارزیابی فوری معتبر را کامل کند.

### زمان مناسب برای استفاده از `consteval`

این کلیدواژه برای ساخت APIهایی مناسب است که مقدار آن‌ها باید حتماً هنگام ترجمه محاسبه شود؛ مانند تولید شناسه‌ها، اعتبارسنجی قالب‌های ثابت یا محاسبهٔ مقادیر پیکربندی. در مقابل، اگر تابع باید بتواند ورودی زمان اجرا را نیز پردازش کند، `constexpr` معمولاً انتخاب منعطف‌تری است.

## الگوهای عملی طراحی

### اعتبارسنجی پیکربندی در زمان ترجمه

ترکیب `constexpr` با `static_assert` اجازه می‌دهد بعضی خطاهای پیکربندی پیش از اجرای برنامه تشخیص داده شوند.

```cpp
constexpr bool valid_buffer_size(int size) {
    return size >= 64 && size <= 65536 && (size & (size - 1)) == 0;
}

constexpr int buffer_size = 1024;
static_assert(valid_buffer_size(buffer_size),
              "buffer_size must be a supported power of two");
```

این روش برای مقادیری مناسب است که از تنظیمات ثابت، پارامترهای template یا ثابت‌های برنامه به دست می‌آیند. اگر مقدار از ورودی کاربر یا فایل پیکربندی در زمان اجرا خوانده می‌شود، اعتبارسنجی زمان اجرا همچنان ضروری است.

### تولید جدول دادهٔ ثابت

محاسبات زمان ترجمه می‌توانند داده‌هایی تولید کنند که در زمان اجرا فقط خوانده می‌شوند. این الگو برای جدول‌های تبدیل، lookup tableها و مقادیر از پیش محاسبه‌شده کاربرد دارد.

```cpp
#include <array>
#include <cstddef>

constexpr std::array<int, 8> make_squares() {
    std::array<int, 8> result{};

    for (std::size_t i = 0; i < result.size(); ++i) {
        result[i] = static_cast<int>(i * i);
    }

    return result;
}

constexpr auto squares = make_squares();
static_assert(squares[5] == 25);
```

در این مثال اندازهٔ جدول ثابت است و `std::array` مالکیت ساده و قابل‌پیش‌بینی دارد. برای جدول‌های بزرگ، هزینهٔ ترجمه، اندازهٔ فایل شیء و میزان حافظهٔ مورد نیاز برنامه را نیز بسنجید.

### استفاده از الگوریتم‌های استاندارد به‌جای کد دست‌ساز

اگر الگوریتم استاندارد موردنیاز در ++C20 برای ارزیابی ثابت پشتیبانی می‌شود، معمولاً بهتر است از همان الگوریتم استفاده شود تا یک پیاده‌سازی سفارشی صرفاً برای زمان ترجمه نوشته شود. این انتخاب خوانایی، قابلیت نگهداری و اعتماد به پیاده‌سازی کتابخانه را بهبود می‌دهد؛ البته شرط آن است که نوع‌ها و عملیات ورودی با ارزیابی ثابت سازگار باشند.

## محدودیت‌ها و خطاهای رایج

### اشتباه گرفتن `constexpr` با تضمین اجرای زمان ترجمه

برچسب `constexpr` به‌تنهایی تضمین نمی‌کند که هر فراخوانی در زمان ترجمه اجرا شود. اگر نتیجه به ورودی زمان اجرا وابسته باشد و زمینهٔ استفاده عبارت ثابت نباشد، فراخوانی می‌تواند در زمان اجرا انجام شود. برای الزام به ارزیابی فوری، `consteval` را بررسی کنید.

### فرض کردن پشتیبانی یکسان همهٔ کتابخانه‌ها

قابلیت‌های زبان و کتابخانه دو موضوع جدا هستند. ممکن است کامپایلر از نحو زبان ++C20 پشتیبانی کند، اما کتابخانهٔ استاندارد همراه آن هنوز تمام عملیات `constexpr` موردنیاز را پیاده‌سازی نکرده باشد. تست روی ترکیب واقعی کامپایلر و کتابخانهٔ هدف ضروری است.

### نگه‌داشتن تخصیص پویا پس از پایان ارزیابی

تخصیص موقت برای محاسبات زمان ترجمه مفید است، اما نمی‌توان هر اشاره‌گر یا منبع تخصیص‌یافته را از ارزیابی ثابت بیرون برد. منابع موقت باید در همان ارزیابی آزاد شوند. برای نتیجهٔ پایدار، از نوع‌هایی با ذخیره‌سازی و طول عمر مناسب استفاده کنید.

### هزینهٔ بالای کامپایل

محاسبهٔ زمان ترجمه رایگان نیست. الگوریتم‌های پیچیده، حلقه‌های بزرگ، ساختارهای دادهٔ حجیم و بازگشت‌های عمیق می‌توانند زمان کامپایل و مصرف حافظهٔ کامپایلر را افزایش دهند. محاسباتی را به زمان ترجمه منتقل کنید که سود آن در اعتبارسنجی زودهنگام، کاهش کار زمان اجرا یا تولید دادهٔ ثابت قابل‌توجه باشد.

### رفتار وابسته به پیاده‌سازی

استاندارد قواعد زبان و کتابخانه را مشخص می‌کند، اما محدودیت‌های منابع کامپایلر و میزان کامل بودن پشتیبانی در نسخه‌های مختلف یکسان نیست. اگر پروژه چند پلتفرم را هدف می‌گیرد، نمونه‌های `static_assert` و تست‌های کامپایل را در زنجیرهٔ ساخت هر پلتفرم اجرا کنید.

### تفاوت بین `constexpr` و `const`

متغیر `const` صرفاً از طریق همان نام قابل‌تغییر نیست؛ این ویژگی به‌تنهایی مقداردهی اولیهٔ زمان ترجمه را تضمین نمی‌کند. در مقابل، متغیر محلی یا شیء‌ای که با `constexpr` تعریف می‌شود باید مقداردهی اولیهٔ معتبر و قابل‌ارزیابی ثابت داشته باشد. انتخاب میان این دو باید بر اساس نیاز واقعی به مقدار ثابت زمان ترجمه انجام شود.

## راهنمای انتخاب ابزار مناسب

| نیاز طراحی | ابزار پیشنهادی | نکته |
|---|---|---|
| امکان استفاده در زمان ترجمه و زمان اجرا | `constexpr` | انتخاب عمومی و منعطف |
| الزام به ارزیابی زمان ترجمه | `consteval` | فراخوانی باید شرایط ارزیابی فوری را رعایت کند |
| تضمین مقداردهی اولیهٔ ایستا برای متغیر | `constinit` | متغیر را به‌خودی‌خود `const` نمی‌کند |
| تشخیص زمینهٔ ارزیابی | `std::is_constant_evaluated` | برای انتخاب آگاهانهٔ مسیر اجرا |
| بررسی شرط در زمان ترجمه | `static_assert` | پیام خطای صریح برای شرط نامعتبر |
| ساخت آرایهٔ ثابت با اندازهٔ مشخص | `std::array` | مالکیت و اندازهٔ ثابت |
| ساخت ظرف موقت با اندازهٔ متغیر | `std::vector` در ++C20 | تخصیص‌ها باید با قواعد ارزیابی ثابت سازگار باشند |
| پردازش رشته در زمان ترجمه | `std::string` در ++C20 | توجه به تخصیص موقت و عمر داده |

## سازگاری و ساخت پروژه

برای فعال کردن حالت ++C20 باید گزینهٔ استاندارد مناسب را در کامپایلر انتخاب کنید. برای نمونه، در GCC و Clang معمولاً می‌توان از `-std=c++20` و در نسخه‌های جدید MSVC از گزینهٔ استاندارد متناظر استفاده کرد. نام دقیق گزینه‌ها و میزان پشتیبانی به نسخهٔ ابزار وابسته است.

نمونه‌ای از کامپایل با GCC یا Clang:

```bash
g++ -std=c++20 -Wall -Wextra -pedantic main.cpp -o app
```

گزینهٔ استاندارد به‌تنهایی تضمین‌کنندهٔ پشتیبانی کامل تمام ویژگی‌های زبان و کتابخانه نیست. برای قابلیت‌های مهم پروژه، نسخهٔ کامپایلر و کتابخانهٔ استاندارد را در مستندات رسمی بررسی کنید و مثال‌های کوچک قابل‌آزمون با `static_assert` در فرایند ساخت نگه دارید.

## جمع‌بندی

استاندارد ++C20، `constexpr` را از ابزاری محدود برای عبارت‌ها و توابع ساده به سازوکاری کاربردی‌تر برای محاسبات زمان ترجمه تبدیل کرد. کاهش محدودیت‌های بدنهٔ توابع، پشتیبانی از تخریب‌گرهای `constexpr`، تخصیص حافظهٔ پویا در ارزیابی ثابت، و گسترش پشتیبانی کتابخانه‌هایی مانند `std::vector`، `std::string` و الگوریتم‌های استاندارد، امکان نوشتن کدهای عمومی‌تر و قابل‌آزمون‌تر را فراهم می‌کنند.

در طراحی حرفه‌ای، مهم است که میان امکان ارزیابی ثابت و الزام به ارزیابی ثابت تفاوت بگذاریم. برای حالت نخست `constexpr`، برای الزام به محاسبهٔ فوری `consteval` و برای تضمین مقداردهی اولیهٔ ایستا `constinit` ابزارهای مناسبی هستند. همچنین باید هزینهٔ زمان کامپایل، محدودیت عمر تخصیص‌های موقت و تفاوت پشتیبانی کتابخانه‌ها را در نظر گرفت. بهترین استفاده از این قابلیت‌ها زمانی است که محاسبهٔ زمان ترجمه مزیت روشن و قابل‌اندازه‌گیری برای صحت، طراحی یا کارایی برنامه ایجاد کند.
