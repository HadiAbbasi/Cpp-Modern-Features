# معرفی `std::shared_timed_mutex` در ++C14

## مقدمه

در برنامه‌نویسی چندنخی (Multithreaded Programming)، یکی از چالش‌های اصلی، دسترسی هم‌زمان چند `Thread` به داده‌های مشترک (Shared Data) است. هنگامی که چند نخ به‌صورت هم‌زمان یک متغیر یا ساختار داده را تغییر می‌دهند، یا یک نخ داده‌ای را تغییر می‌دهد که نخ‌های دیگر در حال خواندن آن هستند، ممکن است شرایط رقابتی (Race Condition) ایجاد شود.

برای مدیریت این وضعیت، کتابخانه استاندارد ++C ابزارهای همگام‌سازی (Synchronization) مختلفی ارائه می‌دهد. یکی از این ابزارها، کلاس `std::shared_timed_mutex` است که از استاندارد ++C14 به کتابخانه استاندارد اضافه شد.

این کلاس نوعی Mutex است که علاوه بر قفل انحصاری (Exclusive Lock)، امکان قفل اشتراکی (Shared Lock) و تلاش برای دریافت قفل با محدودیت زمانی (Timed Locking) را فراهم می‌کند.

ویژگی اصلی این Mutex آن است که چند نخ می‌توانند به‌صورت هم‌زمان قفل اشتراکی دریافت کنند، اما در حالت عادی فقط یک نخ می‌تواند قفل انحصاری داشته باشد. همچنین، قفل انحصاری با قفل‌های اشتراکی ناسازگار است؛ بنابراین، تا زمانی که قفل‌های اشتراکی فعال هستند، نخ دیگری نمی‌تواند قفل انحصاری را دریافت کند.

این قابلیت برای سیستم‌هایی مفید است که عملیات خواندن داده‌ها در آن‌ها بسیار بیشتر از عملیات نوشتن است؛ مانند Cacheها، جدول‌های پیکربندی، Registryهای داخلی و ساختارهای داده‌ای که معمولاً توسط چندین نخ خوانده می‌شوند.

## معرفی مفهوم Shared Mutex

### تفاوت قفل انحصاری و قفل اشتراکی

در یک Mutex معمولی مانند `std::mutex`، هر بار تنها یک نخ می‌تواند قفل را در اختیار داشته باشد. این رفتار برای محافظت از عملیات نوشتن ضروری است، اما در سناریوهایی که چند نخ صرفاً قصد خواندن داده را دارند، ممکن است محدودکننده باشد.

در مقابل، یک Shared Mutex دو نوع مالکیت اصلی ارائه می‌دهد:

- Exclusive Ownership: تنها یک نخ می‌تواند قفل انحصاری را در اختیار داشته باشد. این حالت معمولاً برای تغییر داده‌های مشترک استفاده می‌شود.
- Shared Ownership: چند نخ می‌توانند به‌صورت هم‌زمان قفل اشتراکی داشته باشند. این حالت معمولاً برای خواندن داده‌های مشترک استفاده می‌شود.

قوانین مالکیت به‌صورت زیر خلاصه می‌شوند:

| وضعیت فعلی قفل               | دریافت قفل اشتراکی              | دریافت قفل انحصاری                  |
| ---------------------------- | ------------------------------- | ----------------------------------- |
| بدون مالک                    | مجاز                            | مجاز                                |
| دارای یک یا چند مالک اشتراکی | مجاز، با رعایت سیاست پیاده‌سازی | غیرمجاز تا آزاد شدن قفل‌های اشتراکی |
| دارای مالک انحصاری           | غیرمجاز                         | غیرمجاز                             |

نکته مهم این است که در هر لحظه، نمی‌توان قفل انحصاری را هم‌زمان با قفل اشتراکی یا قفل انحصاری دیگری در اختیار داشت.

همچنین، استاندارد تضمین نمی‌کند که نخ‌های منتظر همیشه به ترتیب ورود به صف قفل دسترسی پیدا کنند. بنابراین، نباید از رفتار خاص یک پیاده‌سازی برای تضمین Fairness یا جلوگیری قطعی از Starvation استفاده کرد.

### چرا به Shared Mutex نیاز داریم؟

فرض کنید یک سرویس چندنخی، اطلاعات کاربران را در یک ساختار داده نگهداری می‌کند. صدها نخ ممکن است اطلاعات را بخوانند، در حالی که فقط تعداد محدودی از نخ‌ها در زمان‌های مشخص داده‌ها را تغییر می‌دهند.

اگر برای تمام عملیات از `std::mutex` استفاده شود، حتی خواندن‌های مستقل نیز باید به‌صورت انحصاری انجام شوند. این موضوع ممکن است باعث کاهش Parallelism شود.

با استفاده از `std::shared_timed_mutex`، چند نخ می‌توانند هم‌زمان اطلاعات را بخوانند، در حالی که عملیات نوشتن همچنان به محافظت انحصاری نیاز دارد.

البته، این طراحی همیشه سریع‌تر نیست. هزینه داخلی Shared Mutex ممکن است از یک Mutex معمولی بیشتر باشد و مزیت آن به الگوی دسترسی، تعداد نخ‌ها، سخت‌افزار و مدت نگهداری قفل بستگی دارد.

## معرفی قابلیت‌های اصلی کلاس

کلاس `std::shared_timed_mutex` در Header استاندارد `<shared_mutex>` تعریف شده است.

نمونه‌ای از تعریف و استفاده اولیه آن:

```
#include <shared_mutex>
#include <iostream>

int main() {
    std::shared_timed_mutex mutex;

    mutex.lock();

    std::cout << "Exclusive lock acquired\n";

    mutex.unlock();

    return 0;
}
```

در این مثال، نخ اصلی قفل انحصاری را دریافت می‌کند و پس از اجرای عملیات، آن را آزاد می‌کند.

برای استفاده در برنامه‌های واقعی، معمولاً بهتر است به‌جای مدیریت دستی قفل، از ابزارهای RAII مانند `std::unique_lock` و `std::shared_lock` استفاده شود.

## بررسی تفاوت `std::shared_timed_mutex` و `std::shared_mutex`

هر دو کلاس برای پشتیبانی از مالکیت اشتراکی و انحصاری طراحی شده‌اند، اما تفاوت مهمی در قابلیت‌های آن‌ها وجود دارد.

کلاس `std::shared_timed_mutex` از ++C14 در دسترس است و علاوه بر عملیات قفل‌گذاری معمول، عملیات زمان‌دار را نیز پشتیبانی می‌کند.

کلاس `std::shared_mutex` در ++C17 معرفی شد و رابط کاربری ساده‌تری برای قفل اشتراکی و انحصاری دارد، اما توابع زمان‌دار اختصاصی ندارد.

| ویژگی                          | `std::shared_timed_mutex` | `std::shared_mutex` |
| ------------------------------ | ------------------------- | ------------------- |
| نسخه استاندارد                 | ++C14                     | ++C17               |
| قفل انحصاری                    | دارد                      | دارد                |
| قفل اشتراکی                    | دارد                      | دارد                |
| قفل‌گذاری زمان‌دار             | دارد                      | ندارد               |
| پشتیبانی از `std::unique_lock` | دارد                      | دارد                |
| پشتیبانی از `std::shared_lock` | دارد                      | دارد                |
| استفاده با `try_lock_for`      | دارد                      | ندارد               |
| استفاده با `try_lock_until`    | دارد                      | ندارد               |

اگر برنامه به Timeout برای دریافت قفل نیاز داشته باشد، `std::shared_timed_mutex` انتخاب مناسبی است. در غیر این صورت، در ++C17 و نسخه‌های جدیدتر، `std::shared_mutex` می‌تواند انتخاب ساده‌تری باشد.

## معرفی عملیات قفل‌گذاری

کلاس `std::shared_timed_mutex` چند گروه از عملیات را برای کنترل دسترسی ارائه می‌دهد.

### بررسی عملیات انحصاری

عملیات انحصاری برای زمانی استفاده می‌شوند که نخ باید داده را تغییر دهد یا به دسترسی انحصاری نیاز داشته باشد.

| تابع               | کاربرد                                    |
| ------------------ | ----------------------------------------- |
| `lock()`           | انتظار تا دریافت قفل انحصاری              |
| `try_lock()`       | تلاش برای دریافت فوری قفل انحصاری         |
| `unlock()`         | آزاد کردن قفل انحصاری                     |
| `try_lock_for()`   | تلاش برای دریافت قفل انحصاری تا مدت مشخص  |
| `try_lock_until()` | تلاش برای دریافت قفل انحصاری تا زمان مشخص |

تابع `lock()` ممکن است تا زمانی که قفل در دسترس شود منتظر بماند. تابع `try_lock()` بدون انتظار برای آزاد شدن قفل، تلاش می‌کند مالکیت انحصاری را دریافت کند.

اگر `try_lock()` موفق نباشد، مقدار `false` برمی‌گرداند. اگر موفق شود، مقدار `true` برمی‌گرداند.

### بررسی عملیات اشتراکی

عملیات اشتراکی برای دسترسی هم‌زمان چند نخ به داده‌های مشترک طراحی شده‌اند.

| تابع                      | کاربرد                                    |
| ------------------------- | ----------------------------------------- |
| `lock_shared()`           | انتظار تا دریافت قفل اشتراکی              |
| `try_lock_shared()`       | تلاش برای دریافت فوری قفل اشتراکی         |
| `unlock_shared()`         | آزاد کردن قفل اشتراکی                     |
| `try_lock_shared_for()`   | تلاش برای دریافت قفل اشتراکی تا مدت مشخص  |
| `try_lock_shared_until()` | تلاش برای دریافت قفل اشتراکی تا زمان مشخص |

در حالت اشتراکی، چند نخ می‌توانند به‌صورت هم‌زمان مالک قفل باشند، مشروط بر اینکه قفل انحصاری در اختیار نخ دیگری نباشد و محدودیت‌های پیاده‌سازی اجازه دهند.

## استفاده از قفل انحصاری با RAII

استفاده مستقیم از `lock()` و `unlock()` ممکن است در صورت وقوع Exception یا خروج زودهنگام از تابع، به آزاد نشدن قفل منجر شود.

برای جلوگیری از این مشکل، می‌توان از `std::unique_lock` استفاده کرد.

```
#include <shared_mutex>
#include <mutex>
#include <iostream>

class Counter {
public:
    void increment() {
        std::unique_lock<std::shared_timed_mutex> lock(mutex_);
        ++value_;
    }

    int get() {
        std::unique_lock<std::shared_timed_mutex> lock(mutex_);
        return value_;
    }

private:
    std::shared_timed_mutex mutex_;
    int value_ = 0;
};

int main() {
    Counter counter;

    counter.increment();
    counter.increment();

    std::cout << counter.get() << '\n';
}
```

در این مثال، `std::unique_lock` قفل انحصاری را هنگام ساخت دریافت می‌کند و هنگام خروج از محدوده عمر شیء آن را آزاد می‌کند.

هرچند تابع `get()` صرفاً داده را می‌خواند، در این نمونه از قفل انحصاری استفاده شده است. در ادامه می‌توان آن را با قفل اشتراکی بهینه کرد.

## استفاده از قفل اشتراکی با `std::shared_lock`

کلاس `std::shared_lock` از ++C14 معرفی شده و برای مدیریت RAII قفل اشتراکی طراحی شده است.

این کلاس به یک Mutex سازگار با Shared Locking نیاز دارد؛ از جمله `std::shared_timed_mutex`.

نمونه زیر، خواندن داده را با قفل اشتراکی انجام می‌دهد:

```
#include <shared_mutex>
#include <mutex>
#include <iostream>

class Counter {
public:
    void increment() {
        std::unique_lock<std::shared_timed_mutex> lock(mutex_);
        ++value_;
    }

    int get() const {
        std::shared_lock<std::shared_timed_mutex> lock(mutex_);
        return value_;
    }

private:
    mutable std::shared_timed_mutex mutex_;
    int value_ = 0;
};

int main() {
    Counter counter;

    counter.increment();
    counter.increment();

    std::cout << counter.get() << '\n';
}
```

در این نسخه، تابع `get()` با استفاده از `std::shared_lock` می‌تواند هم‌زمان با خواندن نخ‌های دیگر اجرا شود.

کلمه کلیدی `mutable` برای Mutex ضروری است، زیرا تابع `get()` از نوع `const` است، اما برای همگام‌سازی باید بتواند وضعیت داخلی Mutex را تغییر دهد.

نکته مهم این است که قفل اشتراکی تنها زمانی ایمن است که داده مورد حفاظت در طول مدت قفل به‌شکل ناسازگار تغییر نکند. در این مثال، تمام تغییرات `value_` تحت قفل انحصاری انجام می‌شوند.

## استفاده از قفل زمان‌دار

یکی از قابلیت‌های مهم `std::shared_timed_mutex` امکان تلاش برای دریافت قفل با محدودیت زمانی است.

این قابلیت برای سیستم‌هایی مفید است که نمی‌خواهند یک نخ برای مدت نامحدود منتظر دریافت قفل بماند.

### استفاده از `try_lock_for()`

تابع `try_lock_for()` مدت زمانی نسبی را دریافت می‌کند. اگر قفل در این مدت قابل دریافت باشد، مقدار `true` برمی‌گرداند؛ در غیر این صورت، مقدار `false` برمی‌گرداند.

نمونه زیر از قفل انحصاری زمان‌دار استفاده می‌کند:

```
#include <shared_mutex>
#include <mutex>
#include <chrono>
#include <iostream>

int main() {
    std::shared_timed_mutex mutex;

    if (mutex.try_lock_for(std::chrono::milliseconds(100))) {
        std::cout << "Lock acquired\n";
        mutex.unlock();
    } else {
        std::cout << "Lock acquisition timed out\n";
    }

    return 0;
}
```

در این مثال، نخ برای دریافت قفل انحصاری تا حدود ۱۰۰ میلی‌ثانیه تلاش می‌کند. مقدار واقعی زمان انتظار می‌تواند به زمان‌بندی سیستم و جزئیات پیاده‌سازی وابسته باشد.

برای جلوگیری از فراموش شدن آزادسازی قفل، بهتر است از `std::unique_lock` با `std::defer_lock` استفاده شود.

```
#include <shared_mutex>
#include <mutex>
#include <chrono>
#include <iostream>

int main() {
    std::shared_timed_mutex mutex;

    std::unique_lock<std::shared_timed_mutex> lock(
        mutex, std::defer_lock
    );

    if (lock.try_lock_for(std::chrono::milliseconds(100))) {
        std::cout << "Lock acquired\n";
    } else {
        std::cout << "Lock acquisition timed out\n";
    }

    return 0;
}
```

در این نسخه، شیء `lock` در ابتدا مالک Mutex نیست. در صورت موفقیت عملیات `try_lock_for()`، مالکیت قفل به آن منتقل می‌شود و در پایان محدوده عمر، قفل به‌صورت خودکار آزاد خواهد شد.

### استفاده از `try_lock_until()`

تابع `try_lock_until()` به‌جای مدت نسبی، یک زمان مطلق دریافت می‌کند. معمولاً این زمان با `std::chrono::steady_clock` یا یک Clock مناسب دیگر ساخته می‌شود.

```
#include <shared_mutex>
#include <mutex>
#include <chrono>
#include <iostream>

int main() {
    std::shared_timed_mutex mutex;

    const auto deadline =
        std::chrono::steady_clock::now() +
        std::chrono::milliseconds(200);

    std::unique_lock<std::shared_timed_mutex> lock(
        mutex, std::defer_lock
    );

    if (lock.try_lock_until(deadline)) {
        std::cout << "Lock acquired\n";
    } else {
        std::cout << "Deadline reached\n";
    }

    return 0;
}
```

استفاده از `std::chrono::steady_clock` برای محاسبه Deadline معمولاً مناسب است، زیرا این ساعت برای اندازه‌گیری زمان سپری‌شده طراحی شده و با تغییر ساعت سیستم عقب یا جلو نمی‌رود.

### استفاده از قفل اشتراکی زمان‌دار

عملیات زمان‌دار برای قفل اشتراکی نیز در دسترس هستند.

```
#include <shared_mutex>
#include <mutex>
#include <chrono>
#include <iostream>

int main() {
    std::shared_timed_mutex mutex;

    std::shared_lock<std::shared_timed_mutex> lock(
        mutex, std::defer_lock
    );

    if (lock.try_lock_for(std::chrono::milliseconds(100))) {
        std::cout << "Shared lock acquired\n";
    } else {
        std::cout << "Shared lock unavailable\n";
    }

    return 0;
}
```

در این مثال، نخ برای دریافت قفل اشتراکی تلاش می‌کند. اگر قفل انحصاری در اختیار نخ دیگری باشد یا قفل در مدت مشخص قابل دریافت نشود، عملیات ناموفق خواهد بود.

## کاربرد در ساختارهای داده‌ای خواندنی

یکی از رایج‌ترین کاربردهای Shared Mutex، محافظت از ساختارهای داده‌ای است که تعداد عملیات خواندن در آن‌ها بیشتر از عملیات نوشتن است.

برای مثال، یک Registry می‌تواند اطلاعاتی را نگهداری کند که نخ‌های متعدد آن‌ها را می‌خوانند، اما فقط گاهی تغییر می‌کنند.

```
#include <shared_mutex>
#include <mutex>
#include <unordered_map>
#include <string>
#include <optional>

class UserRegistry {
public:
    void setUser(int id, const std::string& name) {
        std::unique_lock<std::shared_timed_mutex> lock(mutex_);
        users_[id] = name;
    }

    std::optional<std::string> getUser(int id) const {
        std::shared_lock<std::shared_timed_mutex> lock(mutex_);

        const auto it = users_.find(id);
        if (it == users_.end()) {
            return std::nullopt;
        }

        return it->second;
    }

private:
    mutable std::shared_timed_mutex mutex_;
    std::unordered_map<int, std::string> users_;
};
```

این مثال از `std::optional` استفاده می‌کند که از ++C17 در دسترس است. بنابراین، این کد به‌طور کامل با ++C14 سازگار نیست، هرچند کلاس اصلی `std::shared_timed_mutex` در ++C14 موجود است.

برای نسخه ++C14، می‌توان نتیجه جست‌وجو را با `bool` و یک پارامتر خروجی مدیریت کرد:

```
#include <shared_mutex>
#include <mutex>
#include <unordered_map>
#include <string>

class UserRegistry {
public:
    void setUser(int id, const std::string& name) {
        std::unique_lock<std::shared_timed_mutex> lock(mutex_);
        users_[id] = name;
    }

    bool getUser(int id, std::string& result) const {
        std::shared_lock<std::shared_timed_mutex> lock(mutex_);

        const auto it = users_.find(id);
        if (it == users_.end()) {
            return false;
        }

        result = it->second;
        return true;
    }

private:
    mutable std::shared_timed_mutex mutex_;
    std::unordered_map<int, std::string> users_;
};
```

در این طراحی، عملیات خواندن تا زمانی که قفل اشتراکی نگهداری می‌شود به داده‌های داخلی دسترسی دارد و نتیجه را به‌صورت کپی در اختیار فراخواننده قرار می‌دهد. در نتیجه، فراخواننده برای استفاده از نتیجه به نگهداری قفل داخلی نیاز ندارد.

## بررسی محدودیت‌ها و نکات مهم

### مسئله Starvation

در برخی پیاده‌سازی‌ها، ممکن است نخ‌های خواننده به دلیل ورود مکرر خواننده‌های جدید، مدت زیادی منتظر دریافت قفل انحصاری بمانند. وضعیت معکوس نیز بسته به سیاست پیاده‌سازی ممکن است رخ دهد.

استاندارد ++C ترتیب عادلانه و تضمین عمومی برای جلوگیری از Starvation ارائه نمی‌کند. بنابراین، اگر سیستم به تأخیر قابل پیش‌بینی نیاز داشته باشد، باید رفتار پیاده‌سازی هدف و نیازهای زمان‌بندی را جداگانه بررسی کرد.

### مسئله Deadlock

مانند سایر Mutexها، استفاده نادرست از `std::shared_timed_mutex` می‌تواند به Deadlock منجر شود.

برای مثال، اگر یک نخ قفل اشتراکی را دریافت کند و بدون آزاد کردن آن تلاش کند قفل انحصاری همان Mutex را دریافت کند، ممکن است منتظر وضعیتی بماند که خودش مانع تحقق آن شده است.

به‌طور کلی، نباید فرض کرد که این Mutex امکان ارتقای مستقیم و اتمیک از Shared Ownership به Exclusive Ownership را فراهم می‌کند.

### مدیریت طول عمر داده

قفل‌گذاری تنها زمانی از داده محافظت می‌کند که تمام دسترسی‌های مرتبط با آن از قرارداد همگام‌سازی یکسان پیروی کنند.

اگر یک اشاره‌گر یا Reference به داده داخلی پس از آزاد شدن قفل در اختیار فراخواننده قرار گیرد، ممکن است دسترسی بعدی به داده بدون محافظت انجام شود. در چنین وضعیتی، وجود Mutex به‌تنهایی ایمنی حافظه را تضمین نمی‌کند.

### هزینه عملکرد

Shared Mutex الزاماً از `std::mutex` سریع‌تر نیست. هزینه مدیریت چند مالک اشتراکی، رقابت بر سر قفل و رفتار زمان‌بندی می‌تواند باعث شود که در برخی بارهای کاری، Mutex معمولی عملکرد بهتری داشته باشد.

بنابراین، انتخاب این ابزار باید بر اساس اندازه‌گیری واقعی، الگوی خواندن و نوشتن، مدت نگهداری قفل و تعداد نخ‌ها انجام شود.

## مقایسه با `std::mutex`

کلاس `std::mutex` برای همگام‌سازی انحصاری طراحی شده است و رابط ساده‌تری دارد. در مقابل، `std::shared_timed_mutex` امکان قفل اشتراکی و عملیات زمان‌دار را نیز فراهم می‌کند.

| معیار                       | `std::mutex`    | `std::shared_timed_mutex` |
| --------------------------- | --------------- | ------------------------- |
| قفل انحصاری                 | دارد            | دارد                      |
| قفل اشتراکی                 | ندارد           | دارد                      |
| عملیات زمان‌دار             | ندارد           | دارد                      |
| پیچیدگی استفاده             | کمتر            | بیشتر                     |
| مناسب برای خواندن هم‌زمان   | به‌صورت انحصاری | بله                       |
| مناسب برای همه الگوهای کاری | وابسته به نیاز  | وابسته به نیاز            |

اگر ساختار داده بیشتر تغییر می‌کند یا بخش محافظت‌شده بسیار کوتاه است، `std::mutex` ممکن است گزینه مناسب‌تری باشد. اگر چند نخ اغلب داده را می‌خوانند و نوشتن نسبتاً نادر است، بررسی Shared Mutex منطقی خواهد بود.

## نکات کاربردی برای استفاده حرفه‌ای

- برای مدیریت معمول قفل انحصاری، از `std::unique_lock` یا در موارد ساده‌تر از `std::lock_guard` استفاده کنید.
- برای مدیریت قفل اشتراکی، از `std::shared_lock` استفاده کنید.
- برای Timeout، از عملیات زمان‌دار خود Mutex یا متدهای متناظر در `std::unique_lock` و `std::shared_lock` استفاده کنید.
- از نگهداری قفل در طول عملیات ورودی و خروجی، فراخوانی‌های شبکه‌ای یا پردازش‌های طولانی، مگر در صورت ضرورت، اجتناب کنید.
- برای جلوگیری از Deadlock، ترتیب دریافت چند قفل را در کل برنامه به‌صورت سازگار تعریف کنید.
- برای تصمیم‌گیری درباره استفاده از Shared Mutex، Benchmarkهایی متناسب با الگوی واقعی برنامه اجرا کنید.
- به‌جای تکیه بر فرض‌های مربوط به Fairness، رفتار زمان‌بندی و نیازهای تأخیر سیستم را بررسی کنید.

## جمع‌بندی

کلاس `std::shared_timed_mutex` از ++C14 ابزاری برای همگام‌سازی دسترسی به داده‌های مشترک است که هم قفل انحصاری و هم قفل اشتراکی را پشتیبانی می‌کند. قابلیت مهم دیگر آن، امکان تلاش برای دریافت قفل با محدودیت زمانی است.

این کلاس برای ساختارهایی که تعداد خواندن‌های هم‌زمان در آن‌ها زیاد و تعداد نوشتن‌ها نسبتاً کم است، می‌تواند مفید باشد. با این حال، انتخاب آن باید بر اساس نیاز واقعی برنامه، هزینه همگام‌سازی و اندازه‌گیری عملکرد انجام شود.

در برنامه‌های مدرن، استفاده از ابزارهای RAII مانند `std::unique_lock` و `std::shared_lock` به مدیریت صحیح طول عمر قفل کمک می‌کند و احتمال خطاهای ناشی از آزاد نکردن قفل را کاهش می‌دهد.
