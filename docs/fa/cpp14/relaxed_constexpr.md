# قابلیت Relaxed `constexpr` در ++C14

## مقدمه

قابلیت `constexpr` در ++C11 به برنامه‌نویس اجازه داد تابع‌ها و متغیرهایی تعریف کند که بتوانند در زمان کامپایل ارزیابی شوند؛ البته این امکان به محدودیت‌های نسبتاً سخت‌گیرانه‌ای وابسته بود. برای نمونه، بدنهٔ یک تابع `constexpr` در ++C11 عملاً باید به یک عبارت `return` محدود می‌شد و نمی‌توانست مانند یک تابع معمولی از متغیرهای محلی، حلقه‌ها و ساختارهای کنترلی متداول استفاده کند.

استاندارد ++C14 این محدودیت‌ها را کاهش داد. این تغییر که معمولاً با نام **Relaxed `constexpr`** شناخته می‌شود، نوشتن تابع‌های قابل ارزیابی در زمان کامپایل را طبیعی‌تر کرد و اجازه داد الگوریتم‌هایی با چند مرحله محاسبه، متغیرهای محلی و حلقه‌ها نیز در صورت برآورده‌کردن قواعد ارزیابی ثابت، در زمان کامپایل اجرا شوند.

نکتهٔ مهم این است که Relaxed `constexpr` به این معنا نیست که هر تابع `constexpr` الزاماً در زمان کامپایل اجرا می‌شود. چنین تابعی می‌تواند در زمان اجرا هم فراخوانی شود؛ زمان ارزیابی به زمینهٔ استفاده و امکان‌پذیری ارزیابی ثابت بستگی دارد.

## مفهوم `constexpr` پیش از ++C14

در ++C11، تابع `constexpr` با محدودیت‌های شدیدی تعریف می‌شد تا ارزیابی آن در زمان کامپایل قابل کنترل باشد. به‌طور معمول، بدنهٔ چنین تابعی باید شامل یک دستور `return` و یک عبارت مناسب برای ارزیابی ثابت می‌بود.

برای مثال، تابع زیر در ++C11 معتبر است:

```cpp
constexpr int square(int value)
{
    return value * value;
}
```

در این نمونه، اگر آرگومان تابع یک عبارت ثابت باشد، نتیجه نیز می‌تواند در زمان کامپایل محاسبه شود:

```cpp
constexpr int result = square(5);

static_assert(result == 25);
```

اما پیاده‌سازی همین محاسبه با یک متغیر محلی در ++C11 مجاز نبود:

```cpp
constexpr int square(int value)
{
    int result = value * value; // Not allowed in C++11 constexpr function bodies
    return result;
}
```

علت این محدودیت آن بود که قواعد اولیهٔ `constexpr` عمداً بدنهٔ تابع را به شکل بسیار ساده‌ای محدود می‌کردند. این طراحی برای محاسبات ساده مناسب بود، اما برای الگوریتم‌های واقعی انعطاف کافی نداشت.

## تغییرات اصلی در ++C14

در ++C14، بدنهٔ تابع `constexpr` می‌تواند شامل بسیاری از دستورهایی باشد که در تابع‌های معمولی به کار می‌روند. از جمله:

- تعریف متغیرهای محلی با نوع‌های مناسب؛
- استفاده از شرط‌های `if` و `else`؛
- استفاده از حلقه‌های `for`، `while` و `do-while`؛
- استفاده از چند دستور متوالی و انتساب به متغیرهای محلی؛
- استفاده از عبارت‌های بازگشت متعدد، در مسیرهای اجرایی متفاوت.

بااین‌حال، این آزادی نامحدود نیست. تابع همچنان باید قواعد مربوط به ارزیابی ثابت را رعایت کند و نمی‌تواند در یک ارزیابی ثابت، عملیاتی انجام دهد که طبق استاندارد در چنین زمینه‌ای مجاز نیست.

### مثال: محاسبهٔ مربع با متغیر محلی

در ++C14، می‌توان تابع قبلی را به شکل زیر نوشت:

```cpp
constexpr int square(int value)
{
    int result = value * value;
    return result;
}

constexpr int result = square(5);
static_assert(result == 25);
```

در این نسخه، تعریف متغیر محلی `result` مجاز است. در صورت استفاده از تابع در یک عبارت ثابت، کامپایلر می‌تواند محاسبه را در زمان کامپایل انجام دهد.

### مثال: استفاده از شرط

تابع زیر مقدار بزرگ‌تر از دو عدد را برمی‌گرداند:

```cpp
constexpr int maxValue(int a, int b)
{
    if (a > b)
        return a;

    return b;
}

static_assert(maxValue(7, 4) == 7);
static_assert(maxValue(2, 9) == 9);
```

وجود شرط `if` باعث نمی‌شود تابع دیگر `constexpr` نباشد. در ++C14، مسیر اجرایی انتخاب‌شده می‌تواند در ارزیابی ثابت اجرا شود، به شرط آن‌که عملیات همان مسیر مجاز باشند.

### مثال: استفاده از حلقه

یکی از مهم‌ترین بهبودها، امکان نوشتن محاسبات تکراری با حلقه است. برای نمونه، تابع زیر فاکتوریل یک عدد نامنفی را محاسبه می‌کند:

```cpp
constexpr unsigned long long factorial(unsigned int n)
{
    unsigned long long result = 1;

    for (unsigned int i = 2; i <= n; ++i)
        result *= i;

    return result;
}

static_assert(factorial(0) == 1);
static_assert(factorial(5) == 120);
```

این تابع در ++C14 می‌تواند در زمان کامپایل ارزیابی شود. توجه داشته باشید که نوع بازگشتی ظرفیت محدودی دارد؛ برای ورودی‌های بزرگ، سرریز حسابی می‌تواند نتیجه را نامعتبر کند. همچنین تعداد تکرارها و محدودیت منابع کامپایلر ممکن است بر امکان ارزیابی ثابت اثر بگذارد.

## تفاوت ارزیابی در زمان کامپایل و زمان اجرا

وجود کلیدواژهٔ `constexpr` به‌تنهایی تضمین نمی‌کند که تمام فراخوانی‌های تابع در زمان کامپایل انجام شوند. این کلیدواژه تابع را واجد شرایط ارزیابی ثابت می‌کند، اما زمینهٔ فراخوانی تعیین می‌کند که ارزیابی ثابت لازم است یا خیر.

```cpp
constexpr int square(int value)
{
    int result = value * value;
    return result;
}

constexpr int compileTimeValue = square(6);

int runtimeInput = 6;
int runtimeValue = square(runtimeInput);
```

در این مثال، مقدار `compileTimeValue` باید به‌صورت یک عبارت ثابت قابل محاسبه باشد. اما فراخوانی‌ای که مقدار آن از `runtimeInput` می‌آید، به زمان اجرا وابسته است و معمولاً در زمان اجرا ارزیابی می‌شود؛ کامپایلر ممکن است در صورت امکان بهینه‌سازی انجام دهد، ولی این موضوع با الزام زبان به ارزیابی ثابت یکسان نیست.

برای اجبار به ارزیابی ثابت می‌توان از زمینه‌هایی استفاده کرد که به عبارت ثابت نیاز دارند؛ برای نمونه، مقداردهی یک متغیر `constexpr` یا شرط `static_assert`.

## قواعد و محدودیت‌های مهم

Relaxed `constexpr` محدودیت‌های بدنهٔ تابع را کاهش می‌دهد، اما قواعد ارزیابی ثابت همچنان پابرجا هستند.

### متغیرهای محلی و مقداردهی آن‌ها

متغیرهای محلی در تابع `constexpr` می‌توانند در محاسبات استفاده شوند، مشروط بر آن‌که عملیات و نوع‌های به‌کاررفته با قواعد ارزیابی ثابت سازگار باشند.

```cpp
constexpr int sumTo(int n)
{
    int sum = 0;

    for (int i = 1; i <= n; ++i)
        sum += i;

    return sum;
}

static_assert(sumTo(4) == 10);
```

در این تابع، متغیرهای `sum` و `i` برای ساخت محاسبهٔ مرحله‌ای استفاده شده‌اند. این الگو در ++C14 بسیار کاربردی‌تر از محدودکردن تابع به یک عبارت `return` است.

### مسیرهای اجرایی و عملیات نامعتبر

در ارزیابی ثابت، فقط عملیات مسیر اجرایی انتخاب‌شده اهمیت دارند. وجود عملیاتی که در یک مسیر دیگر مجاز به ارزیابی ثابت نیستند، لزوماً هر فراخوانی تابع را نامعتبر نمی‌کند؛ مسئله این است که آیا همان فراخوانی مشخص می‌تواند یک ارزیابی ثابت معتبر باشد یا خیر.

به‌عنوان مثال، تقسیم بر صفر در مسیر اجراشده، ارزیابی ثابت معتبر ایجاد نمی‌کند:

```cpp
constexpr int divideOrZero(int value, int divisor)
{
    if (divisor == 0)
        return 0;

    return value / divisor;
}

static_assert(divideOrZero(10, 2) == 5);
static_assert(divideOrZero(10, 0) == 0);
```

در این نمونه، شرط از اجرای تقسیم بر صفر جلوگیری می‌کند. اگر تابع مستقیماً عبارت `value / divisor` را با مقسوم‌علیه صفر ارزیابی کند، آن ارزیابی ثابت معتبر نخواهد بود.

### محدودیت‌های نوع و عملیات

قابل‌استفاده‌بودن یک نوع در تابع `constexpr` به قواعد همان استاندارد و عملیات مورد استفاده بستگی دارد. در ++C14 هنوز محدودیت‌هایی نسبت به استانداردهای جدیدتر وجود دارد؛ به‌ویژه در زمینهٔ تغییر وضعیت اشیای پویا، استفاده از کتابخانهٔ استاندارد و عملیات جانبی.

برای نمونه، Relaxed `constexpr` به این معنا نیست که در ++C14 می‌توان هر عملیات ورودی/خروجی، هر تخصیص حافظه یا هر تابع کتابخانه‌ای را در زمان کامپایل اجرا کرد. هر عملیات باید جداگانه با قواعد ارزیابی ثابت استاندارد سازگار باشد.

## کاربردهای عملی

### محاسبهٔ مقادیر ثابت

برای محاسباتی که نتیجهٔ آن‌ها باید در زمان کامپایل مشخص باشد، `constexpr` می‌تواند از محاسبهٔ تکراری در زمان اجرا جلوگیری کند و مقدار لازم را در دسترس سازوکارهایی مانند `static_assert` قرار دهد.

```cpp
constexpr unsigned int powerOfTwo(unsigned int exponent)
{
    unsigned int result = 1;

    for (unsigned int i = 0; i < exponent; ++i)
        result *= 2;

    return result;
}

static_assert(powerOfTwo(0) == 1);
static_assert(powerOfTwo(8) == 256);
```

این پیاده‌سازی برای ورودی‌هایی مناسب است که نتیجه در محدودهٔ `unsigned int` باقی بماند. در طراحی واقعی باید رفتار ورودی‌های بزرگ نیز مشخص شود.

### اعتبارسنجی در زمان کامپایل

می‌توان از توابع `constexpr` برای بررسی ویژگی‌های مقادیر ثابت و استفاده از نتیجه در `static_assert` کمک گرفت:

```cpp
constexpr bool isEven(int value)
{
    return value % 2 == 0;
}

static_assert(isEven(10));
static_assert(!isEven(7));
```

این الگو به‌ویژه برای ثابت‌های پیکربندی، اندازه‌ها، ویژگی‌های عددی و شروطی مفید است که باید هنگام کامپایل بررسی شوند.

### پیاده‌سازی الگوریتم‌های ساده

حلقه‌ها و متغیرهای محلی امکان پیاده‌سازی الگوریتم‌هایی مانند جمع عناصر، جست‌وجوی ساده، محاسبهٔ توان و بررسی ویژگی‌های عددی را فراهم می‌کنند. البته امکان ارزیابی یک الگوریتم در زمان کامپایل به نوع داده‌ها، عملیات مجاز و منابع کامپایلر بستگی دارد.

## نکات طراحی و اشتباهات رایج

### تصور اجباری‌بودن اجرای زمان کامپایل

اشتباه رایج این است که تصور شود تابع `constexpr` همیشه در زمان کامپایل اجرا می‌شود. در واقع، چنین تابعی ممکن است در زمان اجرا فراخوانی شود. اگر اجرای زمان کامپایل الزام طراحی است، نتیجه باید در زمینه‌ای استفاده شود که به عبارت ثابت نیاز دارد.

### نادیده‌گرفتن سرریز و دامنهٔ ورودی

قابل ارزیابی‌بودن تابع در زمان کامپایل به معنی درست‌بودن الگوریتم برای تمام ورودی‌ها نیست. محاسباتی مانند فاکتوریل و توان ممکن است از محدودهٔ نوع عددی خارج شوند. برای نوع‌های صحیح علامت‌دار، سرریز معمولاً رفتار تعریف‌نشده دارد؛ برای نوع‌های صحیح بدون علامت، محاسبه به‌صورت پیمانه‌ای انجام می‌شود. دامنهٔ ورودی و رفتار در مرزها باید صریحاً بررسی شوند.

### استفادهٔ بی‌دلیل از `constexpr`

اگر تابع قرار نیست در زمینهٔ عبارت ثابت استفاده شود و چنین قابلیتی ارزش طراحی مشخصی ایجاد نمی‌کند، افزودن `constexpr` ممکن است سود عملی چندانی نداشته باشد. بااین‌حال، برای تابع‌های کوچک و محاسباتی که منطقی است در زمان کامپایل نیز قابل ارزیابی باشند، این قابلیت می‌تواند مفید باشد.

### اشتباه‌گرفتن قابلیت زبان با بهینه‌سازی کامپایلر

ارزیابی ثابت یک مفهوم زبانی است؛ بهینه‌سازی کامپایلر موضوع دیگری است. کامپایلر ممکن است فراخوانی یک تابع معمولی را نیز به‌صورت بهینه محاسبه کند، اما این به معنی مجازبودن استفاده از نتیجهٔ آن در هر زمینهٔ نیازمند عبارت ثابت نیست.

## مقایسهٔ `constexpr` در ++C11 و ++C14

| قابلیت | ++C11 | ++C14 |
|---|---|---|
| بدنهٔ بسیار محدود با یک `return` | بله | محدودیت برداشته شد |
| تعریف متغیر محلی در تابع `constexpr` | عموماً مجاز نبود | مجاز است، با رعایت قواعد |
| استفاده از شرط‌های `if` و `else` | محدودیت شدید | پشتیبانی می‌شود |
| استفاده از حلقه‌ها | مجاز نبود | پشتیبانی می‌شود |
| چند مرحله محاسبه و انتساب محلی | بسیار محدود | پشتیبانی می‌شود |
| تضمین اجرای همهٔ فراخوانی‌ها در زمان کامپایل | خیر | خیر |

این جدول تفاوت اصلی را نشان می‌دهد: ++C14 شیوهٔ نوشتن توابع `constexpr` را به توابع معمولی نزدیک‌تر کرد، اما الزامات ارزیابی ثابت را حذف نکرد.

## تفاوت با قابلیت‌های استانداردهای جدیدتر

Relaxed `constexpr` به‌طور مشخص به تغییرات ++C14 اشاره دارد. استانداردهای بعدی نیز دامنهٔ کاربرد `constexpr` را گسترش داده‌اند؛ برای مثال، ++C17 و ++C20 تغییرات بیشتری در زبان و کتابخانهٔ استاندارد معرفی کردند. بنابراین، نباید محدودیت‌های ++C14 را بدون بررسی به استانداردهای جدیدتر تعمیم داد یا برعکس، قابلیت‌های جدیدتر را بخشی از ++C14 فرض کرد.

در پروژه‌هایی که باید با چند استاندارد کامپایل شوند، لازم است کد با استاندارد هدف بررسی شود و نباید صرفاً بر اساس پشتیبانی یک کامپایلر از یک قابلیت نتیجه گرفت که آن قابلیت در استاندارد موردنظر وجود دارد.

## جمع‌بندی

قابلیت Relaxed `constexpr` در ++C14 یکی از بهبودهای مهم نسبت به ++C11 بود. این قابلیت اجازه داد تابع‌های قابل ارزیابی در زمان کامپایل از متغیرهای محلی، شرط‌ها، حلقه‌ها و چندین مرحلهٔ محاسباتی استفاده کنند و در نتیجه، پیاده‌سازی الگوریتم‌های واقعی با `constexpr` بسیار ساده‌تر شود.

بااین‌حال، `constexpr` تضمین نمی‌کند که هر فراخوانی در زمان کامپایل انجام شود و همهٔ عملیات نیز برای ارزیابی ثابت مجاز نیستند. برای استفادهٔ حرفه‌ای، باید تفاوت میان قابلیت ارزیابی ثابت و اجرای زمان کامپایل اجباری، محدودیت‌های استاندارد هدف، دامنهٔ ورودی‌ها و رفتار محاسبات عددی را در نظر گرفت.
