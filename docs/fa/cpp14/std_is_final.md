# آموزش جامع `std::is_final` در ++C14

## معرفی قابلیت `std::is_final`

قابلیت `std::is_final` یکی از ابزارهای `Type Traits` در Standard Library زبان ++C است که از استاندارد **++C14** در دسترس قرار گرفت. این قابلیت مشخص می‌کند که آیا یک نوع، به‌صورت مستقیم یا از طریق تعریف نوع مورد بررسی، با کلیدواژهٔ `final` از ارث‌بری منع شده است یا خیر.

در ++C11، کلیدواژهٔ `final` برای جلوگیری از ارث‌بری از یک `class` یا `struct` معرفی شد. بااین‌حال، در این استاندارد ابزار استاندارد مستقیمی برای بررسی این ویژگی در زمان کامپایل وجود نداشت. استاندارد ++C14 این نیاز را با معرفی `std::is_final` برطرف کرد.

این قابلیت در سربرگ `<type_traits>` تعریف شده است و می‌توان از آن برای موارد زیر استفاده کرد:

- بررسی ویژگی‌های یک نوع در زمان کامپایل.
- پیاده‌سازی `Template Metaprogramming`.
- اعمال محدودیت‌های مرتبط با ارث‌بری در کتابخانه‌های عمومی.
- نوشتن ابزارهای عمومی برای تحلیل انواع و طراحی سلسله‌مراتب کلاس‌ها.
- ایجاد بررسی‌های ایستا برای اعتبارسنجی قراردادهای طراحی.

نکتهٔ مهم این است که `std::is_final` فقط وضعیت نوع مورد بررسی را گزارش می‌کند؛ این Trait به‌خودی‌خود مانع ارث‌بری نمی‌شود و هیچ تغییری در تعریف نوع ایجاد نمی‌کند.

## مفهوم کلیدواژهٔ `final`

کلیدواژهٔ `final` در ++C11 معرفی شد و می‌تواند برای جلوگیری از ارث‌بری از یک کلاس یا جلوگیری از Override شدن یک تابع مجازی استفاده شود.

### جلوگیری از ارث‌بری از کلاس

برای جلوگیری از ایجاد کلاس مشتق‌شده از یک کلاس مشخص، می‌توان `final` را در انتهای تعریف کلاس قرار داد.

```
class Base {
public:
    virtual void execute() {}
};

class FinalClass final : public Base {
public:
    void execute() override {}
};
```

در این مثال، کلاس `FinalClass` می‌تواند از `Base` ارث‌بری کند؛ اما کلاس دیگری اجازه ندارد از `FinalClass` مشتق شود.

نمونهٔ زیر نامعتبر است و باید توسط کامپایلر رد شود:

```
class InvalidDerived : public FinalClass {
};
```

### جلوگیری از Override شدن تابع مجازی

کلیدواژهٔ `final` محدود به تعریف کلاس نیست و برای توابع مجازی نیز کاربرد دارد.

```
class Base {
public:
    virtual void execute() {}
};

class Derived : public Base {
public:
    void execute() final {}
};
```

در این مثال، کلاس `Derived` مجاز است از `Base` ارث‌بری کند، اما کلاس‌های مشتق‌شده از `Derived` نمی‌توانند تابع `execute` را دوباره Override کنند.

```
class FurtherDerived : public Derived {
public:
    void execute() override {}
};
```

تعریف `FurtherDerived` نامعتبر است، زیرا تابع مجازی `execute` در کلاس پایهٔ مستقیم آن با `final` مشخص شده است.

**نکتهٔ کلیدی:** ویژگی `final` روی یک تابع مجازی با ویژگی `final` روی خود کلاس متفاوت است. تابع `std::is_final` تنها وضعیت نهایی بودن نوع را بررسی می‌کند، نه وضعیت توابع مجازی آن را.

## معرفی `std::is_final`

نوع `std::is_final` یک `Unary Type Trait` است که مشخص می‌کند آیا نوع بررسی‌شده یک نوع کلاس نهایی است یا خیر.

تعریف مفهومی آن به شکل زیر است:

```
template<class T>
struct is_final;
```

این تعریف صرفاً نمایش مفهومی رابط استاندارد است و نباید به‌عنوان پیاده‌سازی واقعی کتابخانه در نظر گرفته شود.

برای استفاده از این Trait باید سربرگ زیر را اضافه کرد:

```
#include <type_traits>
```

نتیجهٔ بررسی از طریق عضو `value` قابل دسترسی است و نوع آن `bool` است.

```
#include <type_traits>

class OrdinaryClass {
};

class FinalClass final {
};

static_assert(!std::is_final<OrdinaryClass>::value,
              "OrdinaryClass is not final");

static_assert(std::is_final<FinalClass>::value,
              "FinalClass is final");
```

در این مثال، هر دو بررسی در زمان کامپایل انجام می‌شوند. اگر نتیجهٔ هر بررسی با شرط `static_assert` مطابقت نداشته باشد، برنامه کامپایل نخواهد شد.

### نحوهٔ تفسیر نتیجه

نتیجهٔ `std::is_final<T>::value` به این صورت تفسیر می‌شود:

| نتیجه   | مفهوم                                                                     |
| ------- | ------------------------------------------------------------------------- |
| `true`  | نوع `T` یک نوع کلاس نهایی است.                                            |
| `false` | نوع `T` نهایی نیست یا اساساً از دستهٔ انواع کلاسی موردنظر این Trait نیست. |

در نتیجه، مقدار `false` الزاماً به این معنا نیست که نوع مورد بررسی قابلیت ارث‌بری دارد. برای مثال، انواع عددی مانند `int` و انواع اشاره‌گر نیز نتیجهٔ `false` تولید می‌کنند، درحالی‌که نمی‌توان از آن‌ها مانند یک کلاس ارث‌بری کرد.

## بررسی انواع مختلف

برای استفادهٔ حرفه‌ای از `std::is_final` باید بدانیم این Trait در مواجهه با انواع مختلف چه رفتاری دارد.

### بررسی کلاس‌های معمولی و نهایی

```
#include <type_traits>

class Base {
};

class Derived : public Base {
};

class Sealed final {
};

static_assert(!std::is_final<Base>::value, "");
static_assert(!std::is_final<Derived>::value, "");
static_assert(std::is_final<Sealed>::value, "");
```

در این مثال، کلاس `Derived` صرفاً به این دلیل که از کلاس دیگری ارث‌بری کرده است، نهایی محسوب نمی‌شود. نهایی بودن یک نوع به تعریف خود آن نوع بستگی دارد، نه به وضعیت کلاس پایه یا کلاس‌های مشتق‌شده از آن.

### بررسی `struct`

از نظر قواعد ارث‌بری، `struct` و `class` تفاوتی در نحوهٔ استفاده از `final` ندارند. تفاوت اصلی آن‌ها در سطح دسترسی پیش‌فرض اعضا و ارث‌بری است.

```
#include <type_traits>

struct OpenStruct {
};

struct ClosedStruct final {
};

static_assert(!std::is_final<OpenStruct>::value, "");
static_assert(std::is_final<ClosedStruct>::value, "");
```

بنابراین، `std::is_final` برای هر دو شکل تعریف کلاس قابل استفاده است.

### بررسی انواع غیرکلاسی

این Trait برای بررسی نهایی بودن انواعی طراحی شده است که قابلیت استفاده به‌عنوان کلاس را دارند. در انواع غیرکلاسی، نتیجه `false` است.

```
#include <type_traits>

static_assert(!std::is_final<int>::value, "");
static_assert(!std::is_final<double>::value, "");
static_assert(!std::is_final<int*>::value, "");
static_assert(!std::is_final<int&>::value, "");
static_assert(!std::is_final<void>::value, "");
```

این رفتار برای پیاده‌سازی ابزارهای عمومی اهمیت دارد؛ زیرا استفاده از Trait روی انواع مختلف لزوماً باعث خطای کامپایل نمی‌شود.

### بررسی انواع دارای `const` و `volatile`

ویژگی‌های `const` و `volatile` نهایی بودن کلاس را تغییر نمی‌دهند. Trait برای انواع دارای این Qualifierها نیز وضعیت نهایی بودن نوع اصلی را منعکس می‌کند.

```
#include <type_traits>

class FinalType final {
};

static_assert(std::is_final<FinalType>::value, "");
static_assert(std::is_final<const FinalType>::value, "");
static_assert(std::is_final<volatile FinalType>::value, "");
static_assert(std::is_final<const volatile FinalType>::value, "");
```

این رفتار با ماهیت `std::is_final` سازگار است؛ زیرا `const` و `volatile` ویژگی نهایی بودن کلاس را تغییر نمی‌دهند.

## بررسی تفاوت `std::is_final` با `std::is_base_of`

دو Trait استاندارد `std::is_final` و `std::is_base_of` اهداف متفاوتی دارند و نباید به‌جای یکدیگر استفاده شوند.

نوع `std::is_final<T>` بررسی می‌کند که آیا نوع `T` نهایی است یا خیر. در مقابل، `std::is_base_of<Base, Derived>` رابطهٔ ارث‌بری میان دو نوع را بررسی می‌کند.

```
#include <type_traits>

class Base {
};

class Derived : public Base {
};

class FinalDerived final : public Base {
};

static_assert(std::is_base_of<Base, Derived>::value, "");
static_assert(std::is_base_of<Base, FinalDerived>::value, "");

static_assert(!std::is_final<Derived>::value, "");
static_assert(std::is_final<FinalDerived>::value, "");
```

در این مثال، هر دو کلاس مشتق‌شده از `Base` هستند؛ اما فقط `FinalDerived` نهایی است.

نکتهٔ مهم این است که `std::is_base_of` نیز به‌تنهایی تضمین نمی‌کند که یک نوع مشخص بتواند در تمام شرایط به‌عنوان کلاس پایه استفاده شود. دسترسی به پایه، ابهام در ارث‌بری و محدودیت‌های ناشی از `final` می‌توانند در معتبر بودن یک رابطهٔ واقعی ارث‌بری نقش داشته باشند.

## بررسی تفاوت `std::is_final` با `std::is_abstract`

Trait دیگری به نام `std::is_abstract` مشخص می‌کند که آیا یک نوع کلاس Abstract است یا خیر.

این دو ویژگی مستقل از یکدیگر هستند:

- کلاس `final` الزاماً Abstract نیست.
- کلاس Abstract الزاماً `final` نیست.
- یک کلاس می‌تواند هم Abstract و هم `final` باشد.

مثال زیر این تفاوت را نشان می‌دهد:

```
#include <type_traits>

class AbstractBase {
public:
    virtual void execute() = 0;
};

class ConcreteFinal final : public AbstractBase {
public:
    void execute() override {}
};

static_assert(std::is_abstract<AbstractBase>::value, "");
static_assert(!std::is_final<AbstractBase>::value, "");

static_assert(!std::is_abstract<ConcreteFinal>::value, "");
static_assert(std::is_final<ConcreteFinal>::value, "");
```

در این مثال، `AbstractBase` یک کلاس Abstract غیرنهایی است و `ConcreteFinal` یک کلاس Concrete و نهایی است.

## بررسی ویژگی‌های استاندارد در نسخه‌های مختلف ++C

قابلیت `std::is_final` در استانداردهای مختلف ++C جایگاه مشخصی دارد.

| نسخهٔ استاندارد | وضعیت                                                                                                                                             |
| --------------- | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| ++C11           | کلیدواژهٔ `final` معرفی شد؛ `std::is_final` در Standard Library وجود نداشت.                                                                       |
| ++C14           | `std::is_final` به `<type_traits>` اضافه شد.                                                                                                      |
| ++C17           | امکان استفاده از متغیرهای `inline constexpr` و بهبودهای مرتبط با Traitها، از جمله `std::is_final_v`، فراهم شد.                                    |
| ++C20           | امکاناتی مانند Concepts و `consteval` راه‌های بیشتری برای بیان محدودیت‌های زمان کامپایل فراهم کردند؛ خود `std::is_final` همچنان قابل استفاده است. |
| ++C23           | قابلیت اصلی این Trait بدون تغییر مفهومی مهمی قابل استفاده باقی ماند.                                                                              |

برای پروژه‌هایی که باید با ++C14 سازگار باشند، استفاده از `std::is_final<T>::value` روش استاندارد و قابل‌حمل است.

### معرفی `std::is_final_v` در ++C17

از ++C17، بسیاری از Type Traitها دارای متغیرهای کمکی با پسوند `_v` شدند. این قابلیت، استفاده از Traitها را خواناتر می‌کند.

```
#include <type_traits>

class FinalClass final {
};

static_assert(std::is_final_v<FinalClass>, "");
```

در ++C14، شکل بالا در Standard Library وجود ندارد و باید از فرم زیر استفاده کرد:

```
#include <type_traits>

class FinalClass final {
};

static_assert(std::is_final<FinalClass>::value, "");
```

این تفاوت هنگام نگهداری کتابخانه‌هایی که از چند نسخهٔ استاندارد پشتیبانی می‌کنند، اهمیت دارد.

## کاربردهای عملی در Template Metaprogramming

یکی از کاربردهای مهم `std::is_final`، استفاده در Template Metaprogramming است. در این الگوها، تصمیم‌گیری دربارهٔ انواع و مسیرهای پیاده‌سازی می‌تواند هنگام کامپایل انجام شود.

### انتخاب پیاده‌سازی بر اساس نهایی بودن نوع

فرض کنید یک کتابخانهٔ عمومی، دو مسیر متفاوت برای پردازش انواع مختلف دارد. در ++C14 می‌توان با `std::enable_if` یک overload را برای کلاس‌های نهایی فعال کرد.

```
#include <type_traits>
#include <iostream>

template<class T>
typename std::enable_if<std::is_final<T>::value, void>::type
process(const T&) {
    std::cout << "Final type\n";
}

template<class T>
typename std::enable_if<!std::is_final<T>::value, void>::type
process(const T&) {
    std::cout << "Non-final or non-class type\n";
}

class FinalType final {
};

class OrdinaryType {
};

int main() {
    process(FinalType{});
    process(OrdinaryType{});
    process(42);
}
```

در این مثال، `std::enable_if` برای فعال‌سازی یا غیرفعال‌سازی overloadها در زمان کامپایل استفاده شده است. تابع اول برای انواع نهایی و تابع دوم برای سایر انواع انتخاب می‌شود.

این مثال از نظر فنی معتبر است؛ اما در طراحی واقعی باید توجه کرد که نهایی بودن کلاس همیشه معیار مناسبی برای انتخاب الگوریتم نیست. اگر تفاوت رفتار به قابلیت، قرارداد یا عملیات یک نوع مربوط است، استفاده از Trait اختصاصی یا یک Interface مناسب معمولاً طراحی روشن‌تری ایجاد می‌کند.

### استفاده در بررسی‌های ایستا

در برخی کتابخانه‌ها، ممکن است قرارداد طراحی الزام کند که یک نوع مشخص نهایی باشد. در چنین شرایطی می‌توان از `static_assert` استفاده کرد.

```
#include <type_traits>

template<class T>
class Registry {
    static_assert(std::is_final<T>::value,
                  "T must be a final class type");

public:
    void registerObject() {
    }
};

class FinalObject final {
};

Registry<FinalObject> registry;
```

در این مثال، نوع `FinalObject` شرط موردنظر را برآورده می‌کند.

البته پیام خطا در این مثال کمی کلی است؛ زیرا `std::is_final<T>::value` برای انواع غیرکلاسی نیز `false` است. در یک API عمومی، می‌توان با بررسی‌های جداگانه پیام خطای دقیق‌تری ایجاد کرد.

## محدودیت‌های `std::is_final`

با وجود سادگی این Trait، چند محدودیت مهم باید در طراحی کتابخانه‌ها و ابزارهای عمومی در نظر گرفته شود.

### عدم بررسی نهایی بودن توابع

نوع `std::is_final<T>` فقط ویژگی نهایی بودن نوع را بررسی می‌کند. این Trait مشخص نمی‌کند که آیا یک تابع مجازی درون کلاس با `final` تعریف شده است یا خیر.

برای مثال، در کلاس زیر تابع `execute` نهایی است، اما خود کلاس نهایی نیست:

```
class Base {
public:
    virtual void execute() final {}
};

class Derived : public Base {
};
```

تعریف `Derived` معتبر است؛ زیرا ممنوعیت فقط برای Override کردن تابع `execute` اعمال شده است.

### عدم تشخیص امکان ارث‌بری در تمام شرایط

نتیجهٔ `false` به معنی مجاز بودن ارث‌بری از نوع نیست. این موضوع به‌خصوص برای انواع غیرکلاسی و انواع ناقص اهمیت دارد.

همچنین، `std::is_final` رابطهٔ ارث‌بری واقعی را بررسی نمی‌کند؛ بلکه فقط ویژگی نهایی بودن نوع را گزارش می‌دهد.

### عدم جایگزینی قواعد زبان

حتی اگر یک بررسی ایستا نتیجهٔ `false` بدهد، این نتیجه به معنی معتبر بودن تمام کدهای ارث‌بری نیست. قواعد زبان دربارهٔ دسترسی، کامل بودن نوع، ابهام در کلاس‌های پایه و سایر محدودیت‌های ارث‌بری همچنان اعمال می‌شوند.

### وابستگی به تعریف نوع

نهایی بودن نوع بخشی از تعریف آن است. اگر یک نوع در یک کتابخانه با `final` تعریف شود، استفاده از آن به‌عنوان کلاس پایه نامعتبر خواهد بود؛ حتی اگر کد مصرف‌کننده هیچ اطلاعی از این Trait نداشته باشد.

در نتیجه، `std::is_final` برای بررسی ویژگی نوع مفید است، اما جایگزین طراحی صحیح سلسله‌مراتب کلاس‌ها یا بررسی قواعد ارث‌بری نیست.

## نکات مهم دربارهٔ انواع ناقص

یکی از جزئیات مهم در استفاده از Type Traitها، رفتار آن‌ها با `Incomplete Type` است.

در ++C، یک نوع کلاس می‌تواند پیش از تعریف کامل خود فقط با یک اعلان مقدماتی معرفی شود:

```
class ForwardDeclared;
```

در این مرحله، کامپایلر هنوز اطلاعات کافی برای بسیاری از بررسی‌های مرتبط با ساختار کامل کلاس را در اختیار ندارد.

استاندارد برای استفاده از `std::is_final` روی انواع ناقص، محدودیت‌هایی دارد و نباید فرض کرد که این Trait برای هر نوع ناقصی نتیجه‌ای قابل اتکا تولید می‌کند. استفاده از آن برای یک نوع کلاس ناقص، در شرایطی که کامل شدن نوع بتواند نتیجه را تغییر دهد، با الزامات استاندارد سازگار نیست و می‌تواند رفتار تعریف‌نشده به همراه داشته باشد.

بنابراین، اگر طراحی Template به بررسی نهایی بودن نوع نیاز دارد، بهتر است این بررسی پس از کامل شدن تعریف کلاس انجام شود.

نمونهٔ زیر الگوی مناسبی است:

```
#include <type_traits>

class ForwardDeclared;

class FinalType final {
};

static_assert(std::is_final<FinalType>::value, "");
```

در این مثال، Trait فقط روی نوع کامل `FinalType` اعمال شده است.

نکتهٔ مهم این است که صرف وجود یک اعلان مقدماتی برای یک کلاس، تضمین نمی‌کند که تمام Traitهای مرتبط با کلاس برای آن نوع قابل استفاده باشند.

## نکات طراحی و بهترین شیوه‌ها

برای استفادهٔ حرفه‌ای از `std::is_final`، رعایت چند اصل می‌تواند به طراحی بهتر APIها و کتابخانه‌ها کمک کند.

- **استفاده از Trait برای بررسی ویژگی واقعی نوع:** زمانی از `std::is_final` استفاده کنید که نهایی بودن کلاس مستقیماً بر صحت یا انتخاب پیاده‌سازی تأثیر می‌گذارد.
- **پرهیز از وابسته کردن منطق غیرضروری به `final`:** نهایی بودن یک کلاس همیشه به معنی سریع‌تر بودن، ایمن‌تر بودن یا مناسب‌تر بودن آن برای یک عملیات خاص نیست.
- **توجه به نسخهٔ استاندارد پروژه:** در کد ++C14، فرم `std::is_final<T>::value` انتخاب قابل‌حملی است؛ فرم `_v` به ++C17 نیاز دارد.
- **تفکیک ویژگی‌های مستقل:** برای بررسی Abstract بودن، رابطهٔ ارث‌بری یا ویژگی‌های دیگر، از Trait مناسب همان مفهوم استفاده کنید.
- **توجه به کامل بودن نوع:** بررسی نهایی بودن یک کلاس را به زمانی موکول کنید که تعریف نوع کامل شده باشد.
- **ارائهٔ پیام خطای روشن:** در کتابخانه‌های عمومی، بررسی‌های ایستا باید قرارداد مورد انتظار را به‌صورت دقیق بیان کنند تا اشکال‌زدایی ساده‌تر شود.
- **پرهیز از فرض دربارهٔ کامپایلر:** از Trait استاندارد استفاده کنید و به رفتارهای اختصاصی کامپایلر یا Extensionهای غیراستاندارد متکی نباشید.

## جمع‌بندی نهایی

قابلیت `std::is_final` در استاندارد ++C14 معرفی شد تا امکان بررسی ویژگی `final` یک نوع در زمان کامپایل فراهم شود. این Trait در سربرگ `<type_traits>` قرار دارد و نتیجهٔ آن از طریق عضو `value` با نوع `bool` قابل دسترسی است.

مهم‌ترین کاربردهای آن شامل Template Metaprogramming، اعتبارسنجی قراردادهای طراحی، انتخاب پیاده‌سازی‌های وابسته به ویژگی نوع و توسعهٔ کتابخانه‌های عمومی است.

بااین‌حال، باید توجه داشت که `std::is_final` فقط نهایی بودن نوع را بررسی می‌کند؛ این Trait نه امکان ارث‌بری را در تمام شرایط تضمین می‌کند و نه وضعیت نهایی بودن توابع مجازی را مشخص می‌سازد.

برای کدهای سازگار با ++C14، استفاده از `std::is_final<T>::value` روش استاندارد است. در نسخه‌های ++C17 و جدیدتر نیز می‌توان از `std::is_final_v<T>` برای نوشتن کدی خواناتر استفاده کرد.

دقت فنی دربارهٔ انواع ناقص را اصلاح کنتفاوت زبان و Standard Library را روشن‌تر کن
