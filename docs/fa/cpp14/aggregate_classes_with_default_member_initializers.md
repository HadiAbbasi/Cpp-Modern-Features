# کلاس‌های Aggregate همراه با مقداردهی اولیه اعضای کلاس در ++C14

## مقدمه

قابلیت `Aggregate Classes with Default Member Initializers` به تعامل دو مفهوم مهم در زبان ++C مربوط می‌شود: مفهوم `Aggregate` و قابلیت `Default Member Initializers` که در استاندارد ++C11 معرفی شد. این دو مفهوم به‌تنهایی مفید هستند، اما ترکیب آن‌ها در استانداردهای مختلف زبان، به‌ویژه ++C14 و ++C17، رفتارهای متفاوتی دارد که شناخت آن‌ها برای طراحی کلاس‌های ساده و قابل نگهداری ضروری است.

مفهوم `Aggregate` به نوعی اشاره می‌کند که می‌توان اعضای آن را بدون تعریف سازنده‌های اختصاصی، با استفاده از `Aggregate Initialization` مقداردهی اولیه کرد. از طرف دیگر، قابلیت `Default Member Initializers` اجازه می‌دهد مقادیر پیش‌فرض اعضای یک کلاس در محل تعریف آن‌ها مشخص شوند.

نکته مهم این است که در استاندارد ++C14، وجود `Default Member Initializers` باعث می‌شود یک کلاس واجد شرایط `Aggregate` نباشد. این محدودیت در ++C17 تغییر کرد و به همین دلیل، تفاوت میان این دو نسخه در کدهای قابل‌حمل و سازگار با استاندارد اهمیت زیادی دارد.

## مفهوم Aggregate در ++C

در زبان ++C، یک نوع `Aggregate` نوعی است که قواعد مشخصی برای مقداردهی اولیه اعضای آن وجود دارد. این قابلیت به توسعه‌دهنده اجازه می‌دهد بدون نوشتن سازنده اختصاصی، اعضای شیء را هنگام ایجاد آن مقداردهی کند.

برای مثال، ساختار زیر را در نظر بگیرید:

```
#include <iostream>

struct Point {
    int x;
    int y;
};

int main() {
    Point p{10, 20};

    std::cout << p.x << '\n';
    std::cout << p.y << '\n';
}
```

در این مثال، نوع `Point` یک `Aggregate` است و عبارت `Point p{10, 20};` اعضای آن را به‌ترتیب مقداردهی می‌کند.

مهم‌ترین ویژگی‌های این روش عبارت‌اند از:

- نیازی به تعریف constructor اختصاصی نیست.
- اعضا می‌توانند مستقیماً با استفاده از initializer list مقداردهی شوند.
- قواعد مقداردهی اولیه به ترتیب اعضای قابل‌مقداردهی نوع وابسته هستند.
- در صورت حذف برخی مقادیر از فهرست مقداردهی اولیه، قواعد مقداردهی اعضای باقی‌مانده اعمال می‌شوند.

در اینجا منظور از `initializer list`، فهرست مقادیر موجود در عبارت مقداردهی اولیه است؛ این مفهوم را نباید با کلاس استاندارد `std::initializer_list` یکسان دانست.

## مفهوم Default Member Initializers

قابلیت `Default Member Initializers` در استاندارد ++C11 معرفی شد و اجازه می‌دهد مقدار اولیه پیش‌فرض هر عضو غیر `static` در همان محل اعلان آن مشخص شود.

برای نمونه:

```
struct Configuration {
    int timeout = 30;
    bool enabled = true;
    double threshold = 0.75;
};
```

در این تعریف، اعضای `timeout`، `enabled` و `threshold` دارای مقدارهای اولیه پیش‌فرض هستند.

در نتیجه، هنگام ایجاد شیء بدون تعیین مقدار دیگری برای این اعضا، مقدارهای تعریف‌شده استفاده می‌شوند:

```
Configuration config;
```

در این حالت، مقدارهای اعضا به‌ترتیب `30`، `true` و `0.75` خواهند بود.

همچنین می‌توان هنگام ایجاد شیء، مقادیر متفاوتی تعیین کرد:

```
Configuration config{60, false, 0.9};
```

در این مثال، مقادیر ارائه‌شده برای اعضا جایگزین مقدارهای پیش‌فرض می‌شوند.

بااین‌حال، رفتار دقیق این نوع مقداردهی به این بستگی دارد که نوع موردنظر طبق استاندارد زبان، `Aggregate` محسوب شود یا خیر.

## تفاوت رفتار در استانداردهای ++C11، ++C14 و ++C17

برای درک صحیح این موضوع، باید قواعد تعریف `Aggregate` را در نسخه‌های مختلف زبان بررسی کرد.

### رفتار در ++C11

در استاندارد ++C11، وجود `Default Member Initializers` مانع `Aggregate` بودن کلاس می‌شد.

بنابراین، تعریف زیر یک `Aggregate` محسوب نمی‌شد:

```
struct Point {
    int x = 0;
    int y = 0;
};
```

این محدودیت باعث می‌شد نتوان با تکیه بر قواعد `Aggregate Initialization`، این نوع را به همان شکل یک ساختار ساده بدون مقداردهی اولیه اعضا مقداردهی کرد.

### رفتار در ++C14

در استاندارد ++C14 نیز این محدودیت برقرار بود.

بنابراین، اگر کلاسی دارای `Default Member Initializers` بود، طبق قواعد این استاندارد واجد شرایط `Aggregate` محسوب نمی‌شد.

برای مثال:

```
struct Settings {
    int retries = 3;
    bool verbose = false;
};
```

در ++C14، نوع `Settings` یک `Aggregate` نیست.

در نتیجه، عبارت زیر به‌دلیل نبود سازنده مناسب، در این استاندارد معتبر نیست:

```
Settings settings{5, true};
```

همچنین نباید فرض کرد که نوشتن `{}` یا حذف initializerها به‌تنهایی این محدودیت را برطرف می‌کند. مسئله اصلی، شرایط تعریف `Aggregate` در استاندارد مورد استفاده است.

### تغییر مهم در ++C17

در استاندارد ++C17، محدودیت مربوط به `Default Member Initializers` از تعریف `Aggregate` حذف شد.

بنابراین، کلاس زیر می‌تواند یک `Aggregate` باشد:

```
struct Settings {
    int retries = 3;
    bool verbose = false;
};
```

اکنون عبارت زیر معتبر است:

```
Settings settings{5, true};
```

در این حالت، مقادیر `5` و `true` به اعضای `retries` و `verbose` اختصاص داده می‌شوند.

همچنین می‌توان تنها برخی اعضا را مقداردهی کرد:

```
Settings settings{5};
```

در این مثال، مقدار `retries` برابر `5` و مقدار `verbose` برابر `false` خواهد بود.

پس باید توجه داشت که پشتیبانی از `Aggregate` همراه با `Default Member Initializers` ویژگی استاندارد ++C17 است، نه ++C14.

## بررسی یک مثال عملی در ++C14

فرض کنید قصد داریم ساختاری برای نگهداری اطلاعات یک کاربر تعریف کنیم:

```
struct User {
    int id;
    bool active;
};
```

این ساختار در ++C14 یک `Aggregate` است و می‌توان آن را به شکل زیر مقداردهی کرد:

```
User user{101, true};
```

اما اگر بخواهیم برای اعضای آن مقدارهای پیش‌فرض تعریف کنیم، باید محدودیت استاندارد را در نظر بگیریم:

```
struct User {
    int id = 0;
    bool active = true;
};
```

این تعریف در ++C14 دیگر یک `Aggregate` نیست.

بنابراین، برای استفاده از مقداردهی اولیه مستقیم با فهرست مقادیر، باید راهکار دیگری انتخاب شود.

## راهکارهای مناسب برای ++C14

اگر پروژه‌ای باید با ++C14 سازگار باشد، چند راهکار عملی وجود دارد. انتخاب روش مناسب به این بستگی دارد که آیا حفظ `Aggregate Initialization` مهم‌تر است یا تعیین مقدارهای پیش‌فرض در محل تعریف اعضا.

### راهکار نخست: حذف Default Member Initializers

اگر هدف اصلی حفظ `Aggregate` بودن کلاس باشد، می‌توان مقداردهی اولیه اعضا را حذف کرد:

```
struct User {
    int id;
    bool active;
};

int main() {
    User user{0, true};
}
```

در این روش، مقدارهای اولیه هنگام ایجاد شیء مشخص می‌شوند.

مزیت اصلی آن، سادگی و سازگاری با ++C14 است. بااین‌حال، مسئولیت تعیین مقدارهای اولیه به محل ایجاد شیء منتقل می‌شود.

### راهکار دوم: تعریف سازنده

اگر وجود مقدارهای پیش‌فرض مهم باشد، می‌توان سازنده تعریف کرد:

```
struct User {
    int id;
    bool active;

    User(int id = 0, bool active = true)
        : id(id), active(active) {}
};
```

اکنون می‌توان شیء را بدون آرگومان یا با آرگومان‌های مشخص ایجاد کرد:

```
User first;
User second{101, false};
```

در این روش، مقدارهای پیش‌فرض در پارامترهای سازنده تعریف می‌شوند.

البته تعریف سازنده باعث می‌شود کلاس دیگر `Aggregate` نباشد. در نتیجه، این راهکار جایگزینی برای مقداردهی اولیه با سازنده است، نه راهی برای حفظ هم‌زمان تمام ویژگی‌های `Aggregate`.

### راهکار سوم: استفاده از تابع کارخانه

گاهی بهتر است ساخت شیء از طریق یک تابع انجام شود تا منطق ایجاد شیء در یک نقطه متمرکز بماند:

```
struct User {
    int id;
    bool active;
};

User makeDefaultUser() {
    return User{0, true};
}

int main() {
    User user = makeDefaultUser();
}
```

این روش برای پروژه‌هایی مفید است که می‌خواهند قواعد ایجاد اشیا را در توابع مستقل نگه دارند.

بااین‌حال، تابع کارخانه به‌خودی‌خود امکان تعریف `Default Member Initializers` را بدون تغییر قواعد زبان فراهم نمی‌کند.

## تفاوت مقداردهی اولیه با مقدارهای پیش‌فرض

یکی از نکات مهم در استفاده از این قابلیت، تشخیص تفاوت میان مقدارهای پیش‌فرض اعضا و مقدارهایی است که هنگام ایجاد شیء به آن‌ها داده می‌شود.

فرض کنید در ++C17 ساختار زیر را داریم:

```
struct Server {
    int port = 8080;
    bool secure = false;
    int timeout = 30;
};
```

اکنون می‌توان از چند روش برای ایجاد شیء استفاده کرد:

```
Server first{};
Server second{443};
Server third{443, true};
Server fourth{443, true, 60};
```

نتیجه هر حالت به این صورت است:

| عبارت                          | `port` | `secure` | `timeout` |
| ------------------------------ | ------ | -------- | --------- |
| `Server first{}`               | 8080   | `false`  | 30        |
| `Server second{443}`           | 443    | `false`  | 30        |
| `Server third{443, true}`      | 443    | `true`   | 30        |
| `Server fourth{443, true, 60}` | 443    | `true`   | 60        |

این رفتار نشان می‌دهد که در `Aggregate Initialization`، مقدارهای ارائه‌شده برای اعضای متناظر استفاده می‌شوند و برای اعضای حذف‌شده، مقداردهی اولیه پیش‌فرض عضو در نظر گرفته می‌شود.

در مقابل، در ++C14 چنین کلاسی به دلیل وجود `Default Member Initializers` یک `Aggregate` نیست؛ بنابراین نباید همین قواعد را بدون تغییر به آن نسخه تعمیم داد.

## نکات طراحی و خطاهای رایج

در طراحی کلاس‌های ساده، چند نکته اهمیت ویژه‌ای دارند:

- سازگاری استاندارد: اگر پروژه با ++C14 کامپایل می‌شود، نباید فرض کنید کلاسی با `Default Member Initializers` همچنان `Aggregate` است.
- تفاوت سازنده و مقداردهی اولیه عضو: تعریف مقدار پیش‌فرض برای یک عضو، با تعریف سازنده‌ای که پارامتر پیش‌فرض دارد یکسان نیست.
- ترتیب اعضا: در `Aggregate Initialization`، مقادیر به‌ترتیب اعضای قابل‌مقداردهی اختصاص داده می‌شوند؛ بنابراین تغییر ترتیب اعضا می‌تواند معنای فراخوانی‌های موجود را تغییر دهد.
- تغییر استاندارد: ممکن است کدی که در ++C17 معتبر است، در ++C14 کامپایل نشود؛ در نتیجه، نسخه استاندارد پروژه باید در تنظیمات build مشخص باشد.
- سازگاری با API: اگر یک ساختار عمومی با مقداردهی اولیه ترتیبی استفاده می‌شود، افزودن یا جابه‌جایی اعضا می‌تواند بر کدهای مصرف‌کننده اثر بگذارد.

## جمع‌بندی

قابلیت `Default Member Initializers` امکان تعیین مقدارهای اولیه پیش‌فرض برای اعضای کلاس را فراهم می‌کند و از استاندارد ++C11 در دسترس است. بااین‌حال، در ++C14 وجود این مقداردهی‌های اولیه مانع `Aggregate` بودن کلاس می‌شود.

این محدودیت در ++C17 برطرف شد؛ ازاین‌رو، در نسخه‌های جدیدتر می‌توان هم مقدارهای پیش‌فرض اعضا را در محل تعریف آن‌ها مشخص کرد و هم از `Aggregate Initialization` بهره برد.

برای پروژه‌های مبتنی بر ++C14، انتخاب میان ساختار ساده بدون `Default Member Initializers`، تعریف سازنده و استفاده از تابع کارخانه باید بر اساس نیازهای طراحی انجام شود. مهم‌ترین اصل این است که قواعد نسخه استاندارد هدف را در نظر بگیرید و رفتار ++C17 را به ++C14 تعمیم ندهید.
