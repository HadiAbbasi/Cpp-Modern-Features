# Thread — نخ

> **نخ (Thread)** نمایشی از یک اجرای مستقل یا یک محاسبه در یک برنامه است. در C++11، مانند بسیاری از سیستم‌های محاسباتی مدرن، یک نخ می‌تواند — و معمولاً نیز چنین می‌کند — فضای آدرس مشترکی با سایر نخ‌ها داشته باشد. از این نظر، نخ با **فرآیند (Process)** متفاوت است؛ زیرا فرآیندها معمولاً داده‌های خود را مستقیماً با سایر فرآیندها به اشتراک نمی‌گذارند.
>
> زبان C++ در گذشته برای سخت‌افزارها و سیستم‌عامل‌های مختلف، پیاده‌سازی‌های متعددی برای نخ‌ها داشته است. ویژگی جدید در C++11، ارائه‌ی یک **کتابخانه استاندارد برای کار با نخ‌ها** است.

- استاندارد C++11 یک API استاندارد برای نخ‌ها و primitiveهای همگام‌سازی (Synchronization Primitives) تعریف کرد.
- از آنجا که این استاندارد توسط کامپایلرهای مدرن پشتیبانی می‌شود، کدهای مبتنی بر آن روی اکثر سیستم‌عامل‌ها قابل حمل هستند.
- نسبت به `pthreads` سطح بالاتری دارد و نوشتن کد تمیز و قابل نگهداری با آن ساده‌تر است.
- از اتمیک بودن (Atomicity) و ترتیب حافظه (Memory Ordering) پشتیبانی می‌کند.

**معایب:**

- همه‌ی primitiveهای همگام‌سازی در C++11 پیاده‌سازی نشده‌اند؛ برای مثال `barrier`، قفل‌های خواندن/نوشتن (Read-Write Locks)، `semaphore` و موارد مشابه.
- به یک کامپایلر مدرن نیاز دارد و در مقایسه با `pthreads` سابقه‌ی آزمایش و استفاده‌ی کمتری دارد.

## ایجاد نخ — Constructor

یک نخ با ساختن یک شیء از نوع `std::thread` و ارسال یک تابع یا شیء تابع (Function Object) به آن ایجاد و اجرا می‌شود:

```cpp
thread thread( Function&& f, Args&&... args );
```

**پارامترها:**

- `f`: تابعی که توسط نخ اجرا خواهد شد.
- `args`: آرگومان‌هایی که به تابع موردنظر ارسال می‌شوند.

```cpp
#include <thread>

void f();

struct F {
    void operator()();
};

int main()
{
    std::thread t1{f};    // f() در یک نخ جداگانه اجرا می‌شود
    std::thread t2{F()};  // F()() در یک نخ جداگانه اجرا می‌شود
}
```

## پایان اجرای نخ

یک نخ در شرایط زیر اجرای خود را به پایان می‌رساند:

- به انتهای تابع اصلی اجرای خود (`start_routine`) می‌رسد.
- دستور `return` را اجرا می‌کند.

**نکته:**

- نخ هنگام پایان اجرا، فضای Stack خود را آزاد می‌کند.
- نخ می‌تواند مقدار بازگشتی داشته باشد، اما...
- دریافت مستقیم مقدار بازگشتی از یک `std::thread` امکان‌پذیر نیست.

## Joining نخ‌ها

![join](../../en/cpp11/assets/thread.png)

```cpp
void thread.join();
```

- این تابع منتظر می‌ماند تا نخ موردنظر اجرای خود را به پایان برساند.
- یک نخ را نمی‌توان بیش از یک بار `join` کرد.

```cpp
bool thread.joinable();
```

- بررسی می‌کند که آیا نخ امکان `join` شدن دارد یا خیر.

مثال:

```cpp
int main()
{
    std::thread t1{f};    // f() در یک نخ جداگانه اجرا می‌شود
    std::thread t2{F()};  // F()() در یک نخ جداگانه اجرا می‌شود

    t1.join();  // منتظر پایان t1 می‌مانیم
    t2.join();  // منتظر پایان t2 می‌مانیم
}
```

### اگر نخ `join` نشود چه اتفاقی می‌افتد؟

پس از پایان اجرای نخ، برخی اطلاعات داخلی مربوط به آن برای استفاده‌ی بیشتر نگهداری می‌شوند.

تابع `thread.join()` این اطلاعات را برای دریافت وضعیت نخ خاتمه‌یافته استفاده می‌کند و پس از آن اطلاعات مربوطه آزاد می‌شوند.

اگر `thread.join()` فراخوانی نشود، باید به سیستم اعلام کنیم که دیگر به این نخ نیازی نداریم و می‌تواند منابع مربوط به آن را آزاد کند.

در صورت استفاده از تعداد بسیار زیادی نخ، یا زمانی که هر نخ اطلاعات و ساختار بزرگی تولید می‌کند، آزاد نشدن صحیح منابع می‌تواند باعث مصرف زیاد حافظه و مشکلات جدی شود.

## مثال‌ها

به‌طور کلی، معمولاً می‌خواهیم نتیجه‌ی یک وظیفه (Task) اجراشده را نیز دریافت کنیم. در `std::thread` ساده، مفهوم مستقیمی برای مقدار بازگشتی وجود ندارد؛ برای این کار، معمولاً `std::future` انتخاب مناسبی است.

روش دیگر این است که آرگومانی به نخ ارسال کنیم تا نخ نتیجه را در آن قرار دهد. برای مثال:

```cpp
void f(vector<double>&);

struct F {
    vector<double>& v;

    F(vector<double>& vv) : v{vv} { }

    void operator()();
};

int main()
{
    std::thread t1{std::bind(f, some_vec)};
    // f(some_vec) در یک نخ جداگانه اجرا می‌شود

    std::thread t2{F(some_vec)};
    // F(some_vec)() در یک نخ جداگانه اجرا می‌شود

    t1.join();
    t2.join();
}
```

به‌طور کلی، دریافت نتیجه‌ی یک Task اهمیت زیادی دارد. همان‌طور که گفته شد، `std::future` معمولاً انتخاب مناسبی برای انتقال نتیجه‌ی اجرای یک Task است.

روش دیگر این است که محل ذخیره‌ی نتیجه را به نخ بدهیم:

```cpp
void f(vector<double>&, double* res);
// نتیجه در res قرار می‌گیرد

struct F {
    vector<double>& v;
    double* res;

    F(vector<double>& vv, double* p) : v{vv}, res{p} { }

    void operator()();
    // نتیجه در res قرار می‌گیرد
};

int main()
{
    double res1;
    double res2;

    std::thread t1{
        std::bind(f, some_vec, &res1)
    };
    // f(some_vec, &res1) در یک نخ جداگانه اجرا می‌شود

    std::thread t2{
        F(some_vec, &res2)
    };
    // F(some_vec, &res2)() در یک نخ جداگانه اجرا می‌شود

    t1.join();
    t2.join();

    std::cout << res1 << ' ' << res2 << '\n';
}
```

### مدیریت خطاها

اما خطاها چه می‌شوند؟

اگر یک Task یک Exception پرتاب کند و خود نخ آن را مدیریت نکند، تابع `std::terminate()` فراخوانی می‌شود که معمولاً باعث پایان برنامه خواهد شد.

به همین دلیل، معمولاً باید از این وضعیت جلوگیری کنیم.

یک `std::future` می‌تواند Exception را از نخ اجراکننده به نخ فراخواننده (Parent/Calling Thread) منتقل کند. این یکی از دلایل مهم استفاده از `future` است.

راه دیگر این است که نوعی **کد خطا (Error Code)** را برگردانیم.

### اگر `thread` از Scope خارج شود چه می‌شود؟

اگر یک شیء `std::thread` از Scope خارج شود و هنوز `join` یا `detach` نشده باشد، تابع `std::terminate()` فراخوانی می‌شود.

بنابراین باید از چنین وضعیتی جلوگیری کنیم.

## متوقف کردن نخ

در C++11 راه مستقیمی برای درخواست از یک نخ جهت پایان دادن به اجرای خود وجود ندارد.

به عبارت دیگر:

- نمی‌توان مستقیماً از نخ درخواست کرد که هرچه سریع‌تر و به شکل مناسب اجرای خود را متوقف کند.
- نمی‌توان یک نخ را به‌صورت مستقیم Kill کرد.

در نتیجه، گزینه‌های ما عبارت‌اند از:

1. طراحی یک مکانیزم **توقف مشارکتی (Cooperative Interruption)**؛ مثلاً با استفاده از یک داده‌ی مشترک که نخ اصلی آن را تغییر دهد و نخ اجراکننده مرتباً آن را بررسی کند و در صورت فعال شدن، به‌شکل کنترل‌شده از اجرای خود خارج شود.

2. استفاده از امکانات Native سیستم‌عامل با کمک `thread::native_handle()` برای دسترسی به مفهوم نخ در سطح سیستم‌عامل.

3. خاتمه دادن به فرآیند با استفاده از:

```cpp
std::quick_exit()
```

4. خاتمه دادن به برنامه با استفاده از:

```cpp
std::terminate()
```

## Detached Threads — نخ‌های جداشده

![detach](../../en/cpp11/assets/detach_thread.png)

```cpp
void thread.detach();
```

تابع `detach()` نخ مربوط به شیء `thread` را به‌صورت **Detached** علامت‌گذاری می‌کند.

پس از اینکه یک نخ Detached اجرای خود را به پایان رساند، منابع مربوط به آن به‌صورت خودکار به سیستم بازگردانده می‌شوند و نیازی نیست نخ دیگری با آن `join` شود.

به زبان ساده:

- `join()` یعنی: «منتظر پایان این نخ بمان.»
- `detach()` یعنی: «این نخ را مستقل اجرا کن؛ دیگر منتظر پایان آن نخواهم ماند.»

## مثال — Counter

### مسئله

یک متغیر صحیح سراسری به نام `counter` ایجاد کنید.

سپس ۴ نخ ایجاد کنید که هر کدام:

- مقدار `counter` را ۱۰٬۰۰۰٬۰۰۰ بار افزایش دهند.
- پس از پایان همه‌ی نخ‌ها، مقدار نهایی `counter` چاپ شود.

کد:

```cpp
#include <iostream>
#include <thread>
#include <vector>

using namespace std;

int counter = 0;

void counterThread()
{
    for (int i = 0; i < 10000000; ++i) {
        counter++;
    }

    return;
}

int main()
{
    vector<thread> threads;

    for (int i = 0; i < 4; ++i) {
        threads.push_back(thread(counterThread));
    }

    for (int i = 0; i < 4; ++i) {
        threads[i].join();
    }

    cout << counter << endl;

    return 0;
}
```

**نکته مهم:** این برنامه از نظر Thread-Safety مشکل دارد. چون چند نخ به‌صورت هم‌زمان متغیر مشترک `counter` را تغییر می‌دهند، نتیجه لزوماً `40000000` نخواهد بود.

دلیل این مسئله وجود **Race Condition** است که در ادامه توضیح داده می‌شود.

## خطرات برنامه‌نویسی چندنخی

فرض کنید یک شرکت بانکی شناخته‌شده از شما خواسته است یک برنامه‌ی چندنخی برای انجام تراکنش‌های بانکی طراحی کنید.

ابتدا با یک هدف ساده شروع می‌کنیم: **امکان واریز وجه به حساب‌ها**.

مشتریان پول واریز می‌کنند و مبلغ موردنظر باید به موجودی حساب آن‌ها اضافه شود.

اما به دلیل اجرای هم‌زمان چند نخ، ممکن است اتفاق زیر رخ دهد:

| مرحله | Thread 0 | Thread 1 | موجودی حساب |
|---|---|---|---:|
| 1 | مشتری درخواست واریز می‌کند | مشتری درخواست واریز می‌کند | 0 CZK |
| 2 | موجودی فعلی را بررسی می‌کند = 0 CZK | موجودی فعلی را بررسی می‌کند = 0 CZK | 0 CZK |
| 3 | درخواست واریز 1000 CZK | درخواست واریز 2000 CZK | 0 CZK |
| 4 | موجودی جدید را محاسبه می‌کند = 1000 CZK | موجودی جدید را محاسبه می‌کند = 2000 CZK | 0 CZK |
| 5 | موجودی جدید را می‌نویسد = 1000 CZK | موجودی جدید را می‌نویسد = 2000 CZK | 2000 CZK |

در این مثال، مبلغ نهایی باید:

```text
0 + 1000 + 2000 = 3000 CZK
```

باشد، اما به دلیل اجرای هم‌زمان دو نخ، ممکن است مقدار نهایی فقط `2000 CZK` شود.

### Race Condition چیست؟

مشکل از اینجا ناشی می‌شود که بسیاری از عملیات زمان می‌برند و ممکن است در حین اجرای آن‌ها، نخ دیگری شروع به تغییر همان داده کند.

این وضعیت را **Race Condition (شرایط رقابتی)** می‌نامیم.

در Race Condition، نتیجه‌ی نهایی به ترتیب دقیق اجرای دستورهای نخ‌ها بستگی دارد.

در مثال بالا، اگر `Thread 0` قبل از `Thread 1` به‌طور کامل عملیات به‌روزرسانی موجودی را انجام دهد، یا برعکس، نتیجه صحیح خواهد بود.

اما اگر اجرای آن‌ها با یکدیگر تداخل پیدا کند، نتیجه ممکن است نادرست باشد.

### راه‌حل: Mutex

این مشکل با استفاده از **Mutex (Mutual Exclusion)** حل می‌شود.

Mutex تضمین می‌کند که بخش‌های مشخصی از داده‌ی مشترک، در یک لحظه فقط توسط **یک نخ** مورد دسترسی یا تغییر قرار بگیرند.

به این بخش از برنامه معمولاً **Critical Section** گفته می‌شود.

بنابراین با استفاده از Mutex می‌توانیم از تغییر هم‌زمان داده‌های مشترک توسط چند نخ جلوگیری کنیم.
