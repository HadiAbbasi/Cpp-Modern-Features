# قالب‌های پارامتری متغیر در ++C11

قابلیت Variadic Templates در استاندارد ++C11 امکان تعریف `function template`ها و `class template`هایی را فراهم می‌کند که می‌توانند تعداد متغیری از آرگومان‌ها یا پارامترهای نوع را دریافت کنند. این قابلیت یکی از پایه‌های مهم برنامه‌نویسی Generic در ++C مدرن است و در پیاده‌سازی ابزارهایی مانند `std::tuple`، `std::make_shared`، توابع قالبی عمومی و بسیاری از اجزای کتابخانه استاندارد نقش دارد.

پیش از معرفی این قابلیت، برای پشتیبانی از تعداد متفاوتی از آرگومان‌ها معمولاً باید چندین overload جداگانه تعریف می‌شد یا از راهکارهایی با انعطاف‌پذیری و ایمنی نوع کمتر استفاده می‌کردیم. قابلیت Variadic Templates این محدودیت را برطرف می‌کند و امکان می‌دهد یک الگوی عمومی برای مجموعه‌ای با طول متغیر از پارامترها طراحی کنیم.

در این مستند، ساختار داخلی این قابلیت، روش‌های پیاده‌سازی، قواعد deduction، تفاوت‌های آن با C-style variadic functions، محدودیت‌ها، خطاهای متداول و ارتباط آن با قابلیت‌های استانداردهای بعدی بررسی می‌شود.

## آشنایی با مفهوم Variadic Templates

در ++C11، یک `template parameter pack` مجموعه‌ای با تعداد متغیر از پارامترهای قالبی است. این مجموعه می‌تواند شامل پارامترهای نوع، پارامترهای مقدار یا پارامترهای قالبی باشد. همچنین یک `function parameter pack` مجموعه‌ای با تعداد متغیر از پارامترهای تابعی است.

برای تعریف یک parameter pack از علامت `...` استفاده می‌شود. محل قرارگیری این علامت تعیین می‌کند که با چه نوع packای سروکار داریم.

### معرفی پارامترهای نوع متغیر

در مثال زیر، پارامتر `Types` یک مجموعه از پارامترهای نوع است:

```
template <typename... Types>
struct TypeList {
};
```

در این تعریف، `Types` یک `template parameter pack` است. بسته به نحوه استفاده از `TypeList`، این مجموعه می‌تواند خالی باشد یا یک یا چند نوع را در بر بگیرد.

```
TypeList<> empty;
TypeList<int> one;
TypeList<int, double, char> several;
```

در این مثال، هر سه اعلان معتبر هستند؛ زیرا هیچ محدودیتی برای حداقل تعداد اعضای `Types` تعیین نشده است.

### معرفی پارامترهای متغیر تابع

در تابع زیر، `Args` یک `function parameter pack` را تشکیل می‌دهد:

```
template <typename... Args>
void printTypes(Args... args) {
}
```

در اینجا دو pack وجود دارد:

- `Args` مجموعه‌ای از پارامترهای نوع است.
- `args` مجموعه‌ای از پارامترهای تابعی است که نوع هر عضو متناظر با نوع عضو مربوط به `Args` خواهد بود.

برای نمونه، فراخوانی زیر سه آرگومان با سه نوع متفاوت به تابع ارسال می‌کند:

```
printTypes(10, 3.14, "hello");
```

کامپایلر نوع هر آرگومان را استنتاج می‌کند و specialization مناسب تابع را تولید می‌کند.

نکته مهم این است که تعریف تابع بالا به‌تنهایی هیچ عملیاتی روی آرگومان‌ها انجام نمی‌دهد. برای استفاده از اعضای pack باید از سازوکارهایی مانند `pack expansion` یا بازگشت بازگشتی تابع استفاده کنیم.

## تفاوت Template Parameter Pack و Function Parameter Pack

این دو مفهوم به یکدیگر مرتبط هستند، اما نقش متفاوتی دارند.

| ویژگی             | `Template Parameter Pack`   | `Function Parameter Pack`                          |
| ----------------- | --------------------------- | -------------------------------------------------- |
| کاربرد            | نگهداری پارامترهای قالبی    | نگهداری پارامترهای تابع                            |
| نمونه             | `typename... Types`         | `Args... args`                                     |
| محتوا             | نوع، مقدار یا پارامتر قالبی | پارامترهای تابع                                    |
| زمان تعیین اندازه | هنگام specialization قالب   | هنگام تعیین specialization تابع و تطبیق آرگومان‌ها |

در مثال زیر، یک template parameter pack برای تعیین نوع پارامترهای تابع استفاده شده است:

```
template <typename... Types>
void process(Types... values) {
}
```

پارامترهای `Types` و `values` از نظر تعداد با یکدیگر تطبیق دارند. اگر تابع با سه آرگومان فراخوانی شود، هر دو pack سه عضو خواهند داشت.

این ارتباط به این معنا نیست که هر pack الزاماً باید به شکل یک پارامتر تابع استفاده شود؛ packها می‌توانند در ساختارهای قالبی مختلف نیز حضور داشته باشند.

## سازوکار Pack Expansion

مهم‌ترین بخش کار با Variadic Templates، مفهوم `pack expansion` است. این سازوکار اجازه می‌دهد یک الگوی مشخص برای تمام اعضای یک pack گسترش پیدا کند.

برای مثال، عبارت زیر را در نظر بگیرید:

```
template <typename... Types>
void process(Types... values) {
}
```

در این تابع، عبارت `Types...` به این معناست که پارامتر `Types` برای هر عضو گسترش داده شود. اگر `Types` شامل `int`، `double` و `char` باشد، شکل مفهومی پارامترهای تابع چنین خواهد بود:

```
void process(int, double, char);
```

این نمایش صرفاً برای توضیح مفهوم است؛ کامپایلر تابع را با استفاده از سازوکار template instantiation تولید می‌کند.

### نحوه استفاده از الگوی گسترش

در یک pack expansion، بخش پیش از `...` الگوی گسترش را مشخص می‌کند. کامپایلر این الگو را برای اعضای متناظر pack اعمال می‌کند.

مثال زیر مقادیر آرگومان‌ها را چاپ می‌کند:

```
#include <iostream>

template <typename... Args>
void printAll(Args... args) {
    using expander = int[];
    (void)expander{0, ((std::cout << args << ' '), 0)...};
    std::cout << '\n';
}

int main() {
    printAll(10, 3.14, "hello");
}
```

خروجی:

```
10 3.14 hello
```

در این پیاده‌سازی، عبارت `((std::cout << args << ' '), 0)...` برای هر عضو `args` یک عنصر در آرایه تولید می‌کند. عملگر comma باعث می‌شود ابتدا چاپ انجام شود و سپس مقدار صفر به‌عنوان عنصر آرایه تولید شود.

این روش از تکنیک‌های رایج پیش از ++C17 برای اجرای یک عملیات روی اعضای pack بود. در ++C17، با معرفی `fold expression`، چنین کدی را می‌توان بسیار ساده‌تر نوشت که در ادامه بررسی خواهد شد.

### گسترش هم‌زمان چند Pack

گاهی لازم است دو pack با یکدیگر استفاده شوند. در این حالت، اگر هر دو pack در یک الگوی expansion ظاهر شوند، اعضای متناظر آن‌ها به‌صورت هم‌زمان گسترش پیدا می‌کنند.

```
#include <iostream>

template <typename... Types>
void printPairs(Types... values) {
    using expander = int[];
    (void)expander{0, ((std::cout << values << '\n'), 0)...};
}

int main() {
    printPairs(10, 20, 30);
}
```

مثال بالا فقط یک pack دارد؛ بنابراین هر مقدار جداگانه پردازش می‌شود. برای مشاهده گسترش هم‌زمان دو pack، نمونه زیر را در نظر بگیرید:

```
#include <iostream>

template <typename... Types>
void printPairs(Types... left, Types... right) {
    using expander = int[];
    (void)expander{
        0,
        ((std::cout << left << " : " << right << '\n'), 0)...
    };
}

int main() {
    printPairs<int>(1, 2, 10, 20);
}
```

این نمونه به دلیل قواعد deduction و تعیین مرز پارامترهای pack انتهایی، برای استفاده عمومی مناسب نیست و به شکل نوشته‌شده نیز الگوی فراخوانی مورد انتظار را به‌صورت قابل اتکا پیاده‌سازی نمی‌کند. برای پردازش دو مجموعه هم‌اندازه، بهتر است از دو pack مستقل در یک ساختار مناسب، مانند tupleها، استفاده شود.

نمونه معتبر زیر با کمک `std::index_sequence` در استانداردهای جدیدتر این کار را انجام می‌دهد؛ اما برای فهم پایه‌های ++C11، نکته اصلی آن است که تمام packهای ظاهرشده در یک expansion باید با قواعد تطبیق همان expansion سازگار باشند.

### نکات مهم درباره گسترش

- عبارت `...` به‌تنهایی یک عملیات کامل نیست؛ باید به یک الگوی قابل گسترش متصل باشد.
- گسترش pack می‌تواند در فهرست آرگومان‌های تابع، فهرست پارامترهای قالب، فهرست initializerها و چندین زمینه دیگر اتفاق بیفتد.
- گسترش یک pack خالی در زمینه‌هایی که مجاز است، می‌تواند به تولید هیچ عنصری منجر شود.
- در صورت استفاده هم‌زمان از چند pack در یک expansion، تعداد اعضای آن‌ها باید با قواعد آن expansion سازگار باشد؛ معمولاً تعداد متفاوت موجب خطای کامپایل می‌شود.

## پیاده‌سازی تابع‌های بازگشتی با Variadic Templates

در ++C11، یکی از متداول‌ترین روش‌های پردازش اعضای pack استفاده از `recursive variadic function` است. در این روش، تابع در هر مرحله یک آرگومان را پردازش می‌کند و سپس با آرگومان‌های باقی‌مانده خودش را فراخوانی می‌کند.

### تعریف تابع پایه

برای پایان دادن به بازگشت، معمولاً یک overload بدون آرگومان یا یک overload ویژه برای آخرین آرگومان تعریف می‌شود.

```
#include <iostream>

void printAll() {
    std::cout << '\n';
}

template <typename T, typename... Rest>
void printAll(const T& first, const Rest&... rest) {
    std::cout << first << ' ';
    printAll(rest...);
}

int main() {
    printAll(10, 3.14, "hello");
}
```

خروجی:

```
10 3.14 hello
```

در این طراحی:

- پارامتر `first` آرگومان فعلی را دریافت می‌کند.
- پارامتر `rest` آرگومان‌های باقی‌مانده را در قالب یک pack نگه می‌دارد.
- تابع در هر مرحله یک مقدار را چاپ کرده و با pack کوچک‌تر فراخوانی می‌شود.
- وقتی دیگر آرگومانی باقی نماند، overload بدون آرگومان اجرا می‌شود.

### استفاده از Overload برای آخرین آرگومان

در بعضی الگوریتم‌ها، لازم نیست حتماً یک overload بدون آرگومان داشته باشیم. می‌توانیم یک overload برای یک آرگومان و یک overload برای چند آرگومان تعریف کنیم.

```
#include <iostream>

template <typename T>
void printAll(const T& value) {
    std::cout << value << '\n';
}

template <typename T, typename... Rest>
void printAll(const T& first, const Rest&... rest) {
    std::cout << first << ' ';
    printAll(rest...);
}

int main() {
    printAll(1, 2, 3, 4);
}
```

در این نسخه، آخرین آرگومان توسط overload تک‌آرگومانی پردازش می‌شود. اگر تابع با یک آرگومان فراخوانی شود، overload عمومی‌تر نیازی به بازگشت نخواهد داشت.

### مزایا و محدودیت‌های بازگشت

روش بازگشتی برای ++C11 قابل استفاده است و با بسیاری از الگوریتم‌های متداول سازگاری دارد. با این حال، هر مرحله معمولاً باعث instantiation یک specialization دیگر می‌شود و عمق زیاد بازگشت می‌تواند محدودیت‌های کامپایلر را تحت تأثیر قرار دهد.

همچنین باید به هزینه واقعی عملیات توجه کرد. کامپایلر ممکن است بسیاری از لایه‌های فراخوانی را بهینه کند، اما این موضوع به معنای تضمین حذف تمام هزینه‌ها در هر شرایطی نیست.

برای کدهایی که فقط نیاز دارند یک عبارت روی تمام اعضای pack اجرا شود، روش‌های مبتنی بر expansion معمولاً ساده‌تر هستند.

## کاربرد Variadic Templates در توابع عمومی

یکی از کاربردهای اصلی این قابلیت، ساختن توابع عمومی است که تعداد و نوع آرگومان‌های آن‌ها از قبل مشخص نیست.

### ساخت تابعی برای انتقال آرگومان‌ها

فرض کنید می‌خواهیم تابعی بسازیم که یک شیء را با آرگومان‌های دلخواه ایجاد کند. تعریف overload جداگانه برای هر تعداد آرگومان، راهکار مناسبی نیست.

در ++C11 می‌توان از `std::forward` و forwarding referenceها استفاده کرد:

```
#include <utility>

template <typename T, typename... Args>
T createObject(Args&&... args) {
    return T(std::forward<Args>(args)...);
}
```

این تابع آرگومان‌های دریافتی را به سازنده نوع `T` منتقل می‌کند.

در اینجا دو قابلیت مهم با یکدیگر ترکیب شده‌اند:

- قابلیت Variadic Templates برای پذیرش تعداد متغیر آرگومان‌ها.
- قابلیت Perfect Forwarding برای حفظ ویژگی‌های مقداری آرگومان‌ها، از جمله lvalue یا rvalue بودن آن‌ها، در صورت رعایت قواعد مربوط.

نوع `Args&&` در این زمینه یک forwarding reference است، زیرا `Args` در فرایند deduction تعیین می‌شود. اگر `Args` از قبل به یک نوع مشخص محدود شده بود، تفسیر `T&&` می‌توانست متفاوت باشد.

البته تابع بالا صرفاً یک مثال آموزشی است؛ برای کاربردهای عمومی، استفاده از ابزار استاندارد `std::make_unique` در ++C14 یا `std::make_shared` در ++C11، بسته به نوع مالکیت مورد نیاز، معمولاً انتخاب بهتری است.

### انتقال آرگومان‌ها به تابع دیگر

یکی از الگوهای بسیار رایج، ساخت یک wrapper عمومی برای فراخوانی تابع دیگری است:

```
#include <utility>

template <typename Callable, typename... Args>
auto invokeWrapper(Callable&& callable, Args&&... args)
    -> decltype(
        std::forward<Callable>(callable)(
            std::forward<Args>(args)...
    )
) {
    return std::forward<Callable>(callable)(
        std::forward<Args>(args)...
    );
}
```

این کد در ++C11 از trailing return type استفاده می‌کند تا نوع بازگشتی بر اساس عبارت فراخوانی تعیین شود.

نکته مهم این است که پیاده‌سازی بالا فقط فراخوانی مستقیم یک callable را پوشش می‌دهد. برای نمونه، اگر هدف پشتیبانی عمومی از pointer-to-memberها یا انواع خاص دیگر فراخوانی باشد، باید راهکار متفاوتی در نظر گرفت.

در ++C17، `std::invoke` این مدل از فراخوانی را به‌صورت عمومی‌تر پشتیبانی می‌کند. در ++C11 نیز می‌توان برای چنین نیازهایی از abstractionهای اختصاصی یا کتابخانه‌های سازگار استفاده کرد.

### کاربرد در ساخت Wrapperها

در طراحی کتابخانه‌ها، wrapperها برای افزودن رفتارهای جانبی به یک فراخوانی به کار می‌روند؛ برای مثال، اندازه‌گیری زمان اجرا، ثبت log یا مدیریت خطا.

```
#include <iostream>
#include <utility>

template <typename Callable, typename... Args>
auto logAndCall(Callable&& callable, Args&&... args)
    -> decltype(
        std::forward<Callable>(callable)(
            std::forward<Args>(args)...
    )
) {
    std::cout << "Calling function\n";

    return std::forward<Callable>(callable)(
        std::forward<Args>(args)...
    );
}
```

این wrapper آرگومان‌ها را بدون نیاز به تعریف overloadهای متعدد منتقل می‌کند. با این حال، برای پوشش کامل callableهایی که خروجی `void` دارند یا فراخوانی‌هایی که نیازمند `std::invoke` هستند، باید طراحی دقیق‌تری انجام شود.

## مدیریت نوع و مقدار آرگومان‌ها

یکی از مهم‌ترین مسائل در طراحی تابع‌های variadic، نحوه استنتاج نوع آرگومان‌ها و نحوه انتقال آن‌هاست. انتخاب نادرست نوع پارامتر می‌تواند موجب کپی غیرضروری، از دست رفتن قابلیت move یا محدود شدن نوع‌های قابل استفاده شود.

### مقایسه پارامترهای مقداری و ارجاعی

در مثال زیر، پارامترها با مقدار دریافت می‌شوند:

```
template <typename... Args>
void processByValue(Args... args) {
}
```

این روش می‌تواند باعث کپی یا move شدن آرگومان‌ها شود و برای اشیای بزرگ هزینه داشته باشد.

در مقابل، نسخه زیر از ارجاع به `const` استفاده می‌کند:

```
template <typename... Args>
void processByReference(const Args&... args) {
}
```

این روش از کپی غیرضروری در ورودی جلوگیری می‌کند، اما اجازه تغییر اشیا را نمی‌دهد و برای همه انواع، خصوصاً مواردی که انتقال مالکیت مدنظر است، بهترین گزینه نیست.

در نهایت، نسخه زیر برای انتقال عمومی آرگومان‌ها مناسب‌تر است:

```
#include <utility>

template <typename... Args>
void forwardArguments(Args&&... args) {
    anotherFunction(std::forward<Args>(args)...);
}
```

در این مثال، فرض شده است که تابع `anotherFunction` در محدوده مناسب تعریف شده است.

### مفهوم Perfect Forwarding

در Perfect Forwarding، هدف آن است که تابع واسط ویژگی‌های اصلی آرگومان را تا حد امکان حفظ کند. اگر آرگومان یک lvalue باشد، انتقال باید به شکل مناسب lvalue باقی بماند؛ اگر آرگومان یک rvalue باشد، امکان انتقال آن به مقصد فراهم می‌شود.

نقش `std::forward` در این فرایند اساسی است. استفاده از `std::move` به‌جای آن در یک forwarding function عمومی، معمولاً اشتباه است؛ زیرا `std::move` همه آرگومان‌ها را به‌صورت rvalue cast می‌کند و ممکن است رفتار مورد انتظار برای lvalueها را تغییر دهد.

نکته دیگر آن است که `std::forward` خودبه‌خود یک شیء را منتقل نمی‌کند. این تابع یک cast انجام می‌دهد؛ عملیات واقعی move یا copy به overload انتخاب‌شده در مقصد وابسته است.

### ملاحظات مربوط به Lifetime

اگر تابعی از forwarding reference استفاده کند، نباید بدون طراحی دقیق، ارجاع به آرگومان‌های دریافتی را برای استفاده پس از پایان عمر آن‌ها ذخیره کند.

برای مثال، بازگرداندن یک reference به یک آرگومان موقتی می‌تواند به dangling reference منجر شود. Variadic Templates هیچ محافظت خودکاری در برابر چنین خطاهایی ایجاد نمی‌کند.

در APIهای عمومی، باید قرارداد مالکیت و طول عمر داده‌ها به‌روشنی مشخص شود.

## کاربرد عملگر sizeof... برای شمارش اعضای Pack

در ++C11، عملگر `sizeof...` برای به‌دست‌آوردن تعداد اعضای یک parameter pack معرفی شده است. این عملگر در زمان کامپایل ارزیابی می‌شود و نتیجه آن یک مقدار صحیح از نوع `std::size_t` است.

```
#include <iostream>

template <typename... Args>
void printCount(Args... args) {
    std::cout << sizeof...(Args) << '\n';
    std::cout << sizeof...(args) << '\n';
}

int main() {
    printCount(10, 3.14, 'A');
    printCount();
}
```

خروجی:

```
3
3
0
0
```

در این مثال، هر دو عبارت `sizeof...(Args)` و `sizeof...(args)` تعداد اعضای pack مربوط را محاسبه می‌کنند؛ یکی برای pack نوع و دیگری برای pack پارامتر تابع.

### کاربردهای عملی شمارش Pack

شمارش اعضای pack در پیاده‌سازی ساختارهایی مانند tuple، اعتبارسنجی تعداد آرگومان‌ها و ایجاد شرط‌های زمان کامپایل کاربرد دارد.

```
#include <type_traits>

template <typename... Args>
struct ArgumentInfo {
    static constexpr std::size_t count = sizeof...(Args);
};

static_assert(ArgumentInfo<int, double, char>::count == 3, "");
static_assert(ArgumentInfo<>::count == 0, "");
```

در این مثال، تعداد آرگومان‌ها به‌عنوان یک مقدار ثابت زمان کامپایل در دسترس است.

## کاربرد الگوی Variadic Templates در کلاس‌ها

قابلیت Variadic Templates محدود به توابع نیست و در تعریف کلاس‌های قالبی نیز کاربرد گسترده‌ای دارد.

### ساخت کلاس برای نگهداری مجموعه‌ای از انواع

نمونه ساده زیر، فهرستی از انواع را تعریف می‌کند:

```
template <typename... Types>
struct TypeList {
    static constexpr std::size_t size = sizeof...(Types);
};
```

این ساختار می‌تواند برای متاپروگرام‌نویسی، ثبت انواع و طراحی abstractionهای عمومی مورد استفاده قرار گیرد.

```
#include <type_traits>

using MyTypes = TypeList<int, double, char>;

static_assert(MyTypes::size == 3, "");
```

البته این کلاس فقط انواع را به‌صورت پارامتر قالبی نگه می‌دارد و به‌تنهایی هیچ شیء یا مقدار زمان اجرایی ذخیره نمی‌کند.

### معرفی ساختار std::tuple

کلاس استاندارد `std::tuple` یکی از مهم‌ترین نمونه‌های استفاده از Variadic Templates است. این ساختار می‌تواند مقادیر ناهمگون با انواع متفاوت را در یک شیء واحد نگهداری کند.

```
#include <iostream>
#include <string>
#include <tuple>

int main() {
    std::tuple<int, double, std::string> data{
        42, 3.14, "hello"
    };

    std::cout << std::get<0>(data) << '\n';
    std::cout << std::get<1>(data) << '\n';
    std::cout << std::get<2>(data) << '\n';
}
```

در این مثال، هر عضو tuple نوع مشخصی دارد و با استفاده از `std::get` و اندیس زمان کامپایل به آن دسترسی پیدا می‌کنیم.

در طراحی ساختارهایی مشابه tuple، Variadic Templates امکان می‌دهد تعداد اعضا و نوع هر عضو در زمان کامپایل مشخص شود، بدون آنکه لازم باشد برای هر تعداد عضو، کلاس جداگانه‌ای تعریف کنیم.

### ساخت کلاس با تعداد متغیر پارامترهای قالبی

در ++C11، امکان استفاده از packها در الگوهای ارث‌بری نیز وجود دارد. برای مثال، می‌توان یک کلاس را از چندین کلاس پایه مشتق کرد:

```
template <typename... Bases>
struct Combined : Bases... {
};
```

در این طراحی، هر نوع موجود در `Bases` به یک کلاس پایه تبدیل می‌شود.

برای استفاده از این الگو، تمام انواع ارائه‌شده باید از نظر قواعد ارث‌بری معتبر باشند. همچنین در صورت وجود نام‌های مشترک، ابهام در دسترسی به اعضای پایه‌ها ممکن است ایجاد شود.

این الگو در طراحی mixinها و ترکیب قابلیت‌های مستقل کاربرد دارد.

## مفهوم Fold Expression و تفاوت آن با ++C11

یکی از محدودیت‌های مهم Variadic Templates در ++C11 این است که برای اجرای یک عملیات روی تمام اعضای pack، اغلب به بازگشت یا تکنیک‌های پیچیده‌تر نیاز داریم.

استاندارد ++C17 با معرفی `fold expression` این مسئله را ساده‌تر کرد. بنابراین Fold Expression جزئی از ++C11 نیست، بلکه قابلیتی است که در نسخه بعدی استاندارد معرفی شده است.

### روش قدیمی در ++C11

برای محاسبه مجموع آرگومان‌ها، می‌توان از بازگشت استفاده کرد:

```
int sum() {
    return 0;
}

template <typename T, typename... Rest>
auto sum(T first, Rest... rest)
    -> decltype(first + sum(rest...)) {
    return first + sum(rest...);
}
```

در این پیاده‌سازی، تابع پایه مقدار صفر را برای مجموعه خالی بازمی‌گرداند. تابع قالبی نیز مقدار اول را با نتیجه پردازش آرگومان‌های باقی‌مانده جمع می‌کند.

این روش برای انواعی که عملگر جمع آن‌ها معتبر است، قابل استفاده است؛ البته نوع بازگشتی و رفتار آن به قواعد overload resolution و نوع آرگومان‌ها وابسته است.

### روش ساده‌تر در ++C17

با استفاده از Fold Expression، همین الگوریتم را می‌توان به شکل زیر نوشت:

```
template <typename... Args>
auto sum(Args... args) {
    return (args + ... + 0);
}
```

این نمونه از یک fold راست‌گرا استفاده می‌کند. با این حال، افزودن مقدار `0` به‌عنوان مقدار اولیه ممکن است برای انواع خاصی که با عدد صحیح سازگاری ندارند، مناسب نباشد.

برای نمونه، نسخه زیر در ++C17 برای مجموعه‌های غیرخالی از انواع سازگار با عملگر جمع مناسب است:

```
template <typename First, typename... Rest>
auto sum(First first, Rest... rest) {
    return (first + ... + rest);
}
```

در این نسخه، وجود حداقل یک آرگومان الزامی است و نوع نهایی به نتیجه عملگرهای جمع وابسته خواهد بود.

نکته مهم این است که Fold Expression جایگزین تمام کاربردهای بازگشت نیست. هرگاه پردازش هر عضو به نوع عملیات مرحله قبل وابسته باشد یا به منطق شرطی پیچیده نیاز داشته باشد، ممکن است بازگشت همچنان انتخاب مناسب‌تری باشد.

## تفاوت Variadic Templates با C-Style Variadic Functions

در زبان ++C، علاوه بر Variadic Templates، سازوکار قدیمی‌تر توابع متغیرآرگومان نیز وجود دارد که از سرآیند `<cstdarg>` و امکاناتی مانند `va_list` استفاده می‌کند.

این دو روش هدف‌های مشابهی دارند، اما از نظر ایمنی نوع، استنتاج نوع و نحوه دسترسی به آرگومان‌ها تفاوت اساسی دارند.

### بررسی تابع متغیرآرگومان قدیمی

نمونه زیر یک تابع با تعداد متغیر آرگومان تعریف می‌کند:

```
#include <cstdarg>
#include <iostream>

double sumValues(int count, ...) {
    va_list args;
    va_start(args, count);

    double total = 0.0;

    for (int i = 0; i < count; ++i) {
        total += va_arg(args, double);
    }

    va_end(args);
    return total;
}

int main() {
    std::cout << sumValues(3, 1.0, 2.0, 3.0) << '\n';
}
```

در این مثال، تابع با دریافت تعداد آرگومان‌ها، آن‌ها را به شکل `double` از فهرست آرگومان‌ها استخراج می‌کند.

در این روش، کامپایلر تضمین نمی‌کند که نوع واقعی هر آرگومان با نوع مورد انتظار `va_arg` مطابقت داشته باشد. استفاده نادرست از این سازوکار می‌تواند به رفتار تعریف‌نشده منجر شود.

### مقایسه دو روش

| ویژگی                         | Variadic Templates                 | C-Style Variadic                     |
| ----------------------------- | ---------------------------------- | ------------------------------------ |
| بررسی نوع در زمان کامپایل     | پشتیبانی می‌شود                    | محدود است                            |
| پشتیبانی از انواع مختلف       | با template deduction              | با محدودیت‌ها و قواعد promotion      |
| دسترسی به نوع هر آرگومان      | از طریق template parameters        | معمولاً نیازمند قرارداد جداگانه      |
| امکان Perfect Forwarding      | بله                                | خیر                                  |
| نیاز به شمارش دستی آرگومان‌ها | معمولاً خیر                        | اغلب بله                             |
| کاربرد متداول                 | APIهای عمومی و Generic Programming | سازگاری با APIهای قدیمی و رابط‌های C |

برای طراحی APIهای جدید در ++C، معمولاً Variadic Templates انتخاب مناسب‌تری هستند. با این حال، در رابط‌های سازگار با C یا APIهایی که قرارداد قدیمی متغیرآرگومان دارند، ممکن است همچنان به روش قدیمی نیاز باشد.

## قواعد استنتاج نوع در Variadic Templates

یکی از بخش‌های مهم درک Variadic Templates، آشنایی با قواعد `template argument deduction` است. این قواعد تعیین می‌کنند که کامپایلر چگونه نوع آرگومان‌ها را با پارامترهای قالب تطبیق می‌دهد.

### استنتاج نوع در پارامترهای تابع

در مثال زیر، کامپایلر نوع آرگومان‌ها را استنتاج می‌کند:

```
template <typename... Args>
void process(Args... args) {
}

int main() {
    process(10, 3.14, 'A');
}
```

در این فراخوانی، pack نوع شامل `int`، `double` و `char` خواهد بود.

اما اگر پارامترها از نوع `const Args&...` باشند، قواعد deduction برای ارجاع‌ها اعمال می‌شود و آرگومان‌ها بدون نیاز به کپی شدن دریافت خواهند شد.

### محدودیت استنتاج در Packهای انتهایی

در تابع زیر، pack در انتهای فهرست پارامترها قرار دارد:

```
template <typename T, typename... Args>
void process(T first, Args... rest) {
}
```

این ساختار برای بسیاری از APIهای variadic مناسب است؛ زیرا اولین آرگومان به `T` اختصاص پیدا می‌کند و آرگومان‌های باقی‌مانده در `Args` قرار می‌گیرند.

در مقابل، قرار دادن یک پارامتر مستقل پس از pack می‌تواند استنتاج نوع را دشوار یا ناممکن کند، به‌ویژه هنگامی که کامپایلر نتواند مرز اعضای pack را از آرگومان‌ها تشخیص دهد.

بنابراین در طراحی توابع عمومی، الگوی «یک پارامتر مشخص به‌علاوه یک pack انتهایی» معمولاً ساده‌تر و قابل پیش‌بینی‌تر است.

## Packهای خالی و حالت‌های مرزی

Variadic Templates می‌توانند مجموعه‌ای خالی از پارامترها داشته باشند. این ویژگی هم انعطاف‌پذیری ایجاد می‌کند و هم نیازمند توجه به حالت‌های مرزی است.

### پذیرش صفر آرگومان

تابع زیر می‌تواند بدون آرگومان فراخوانی شود:

```
template <typename... Args>
void process(Args... args) {
}

int main() {
    process();
}
```

در این حالت، `Args` و `args` هر دو خالی هستند.

با این حال، خالی بودن pack به این معنا نیست که هر عملیاتی روی آن معتبر است. برای مثال، اگر الگوریتم به دسترسی به اولین عضو pack نیاز داشته باشد، باید حالت خالی به‌صورت جداگانه مدیریت شود.

### تفاوت بین مجموعه خالی و مقدار اولیه

در طراحی الگوریتم‌هایی مانند محاسبه مجموع، باید مشخص شود رفتار تابع برای مجموعه خالی چیست.

برای مثال، تعریف یک مقدار اولیه مانند صفر می‌تواند برای جمع اعداد منطقی باشد، اما برای عملیات‌هایی مانند پیدا کردن بیشینه، انتخاب یک مقدار اولیه مناسب به نوع داده وابسته است.

بنابراین بهتر است قرارداد تابع برای pack خالی صریح باشد، نه اینکه یک مقدار اولیه دلخواه صرفاً برای رفع خطای کامپایل انتخاب شود.

## محدودیت‌ها و خطاهای رایج

با وجود قدرت Variadic Templates، استفاده نادرست از این قابلیت می‌تواند موجب خطاهای کامپایل دشوار یا طراحی نامناسب API شود.

### استفاده نادرست از علامت سه‌نقطه

علامت `...` در چند موقعیت مختلف به کار می‌رود؛ از جمله تعریف pack و گسترش آن. این کاربردها از نظر نحوی و معنایی یکسان نیستند.

برای مثال، عبارت `typename... Args` یک pack از پارامترهای نوع تعریف می‌کند، در حالی که عبارت `std::forward<Args>(args)...` یک pack expansion انجام می‌دهد.

درک تفاوت این دو حالت برای خواندن کدهای template ضروری است.

### نادیده گرفتن تفاوت lvalue و rvalue

اگر تابعی برای انتقال عمومی آرگومان‌ها طراحی شده باشد، استفاده از پارامترهای مقداری یا ارجاع‌های ثابت ممکن است رفتار مورد انتظار را تغییر دهد.

در چنین مواردی، استفاده صحیح از forwarding reference و `std::forward` به حفظ ویژگی‌های آرگومان کمک می‌کند.

### ایجاد ابهام در Overload Resolution

توابع variadic می‌توانند با overloadهای دیگر تداخل داشته باشند. برای نمونه، یک overload عمومی که هر نوع و هر تعداد آرگومان را می‌پذیرد، ممکن است در برخی فراخوانی‌ها با overload اختصاصی رقابت کند.

در چنین شرایطی، باید قواعد overload resolution و template partial ordering را بررسی کرد. گاهی محدود کردن دامنه نوع‌های قابل پذیرش یا ارائه overloadهای مشخص‌تر، طراحی قابل پیش‌بینی‌تری ایجاد می‌کند.

### افزایش پیچیدگی کامپایل

استفاده گسترده از templateها می‌تواند باعث افزایش زمان کامپایل، تولید پیام‌های خطای طولانی و افزایش تعداد specializationها شود.

این مسئله به‌ویژه زمانی اهمیت دارد که چندین لایه از templateهای بازگشتی یا abstractionهای عمومی روی یکدیگر قرار بگیرند.

به همین دلیل، بهتر است Variadic Templates فقط در جایی استفاده شوند که انعطاف‌پذیری آن‌ها ارزش پیچیدگی اضافی را داشته باشد.

## راهنمای طراحی API با Variadic Templates

در طراحی APIهای عمومی، انتخاب ساختار مناسب به هدف تابع، نوع داده‌ها و قرارداد استفاده بستگی دارد.

### انتخاب بین بازگشت و Pack Expansion

اگر هدف اجرای یک عملیات یکسان روی اعضای pack باشد، pack expansion معمولاً راهکاری مستقیم است. در مقابل، اگر هر مرحله به نتیجه مرحله قبل وابسته باشد، بازگشت می‌تواند خواناتر باشد.

در ++C17، Fold Expression نیز برای عملیات‌های تکراری روی اعضای pack گزینه مناسبی است.

### استفاده از Perfect Forwarding در صورت نیاز

برای wrapperهایی که باید آرگومان‌ها را به یک تابع دیگر منتقل کنند، forwarding reference و `std::forward` اغلب انتخاب مناسبی است.

اما برای تابعی که فقط مقادیر را می‌خواند و به آن‌ها دست نمی‌زند، استفاده از `const T&` یا حتی دریافت با مقدار، بسته به نوع داده و هدف طراحی، ممکن است ساده‌تر باشد.

### مستندسازی محدودیت نوع‌ها

Variadic Templates به‌خودی‌خود تضمین نمی‌کنند که هر ترکیبی از انواع قابل قبول باشد. اگر الگوریتم نیازمند وجود یک عملگر، سازنده یا تابع خاص است، این پیش‌شرط باید روشن باشد.

در ++C11 می‌توان برای برخی بررسی‌های زمان کامپایل از `static_assert`، `std::enable_if` و type traits استفاده کرد. در استانداردهای بعدی، ابزارهایی مانند Concepts در ++C20 امکان بیان محدودیت‌های نوعی را به شکل مستقیم‌تر فراهم می‌کنند.

## جمع‌بندی

قابلیت Variadic Templates که در ++C11 معرفی شد، یکی از ابزارهای بنیادین برای ساخت APIهای عمومی و پیاده‌سازی Generic Programming است. این قابلیت اجازه می‌دهد تعداد متغیری از پارامترهای نوع و آرگومان‌ها را بدون تعریف overloadهای متعدد مدیریت کنیم.

مهم‌ترین مفاهیم مرتبط با این قابلیت عبارت‌اند از:

- مفهوم `template parameter pack` و `function parameter pack` برای نگهداری تعداد متغیر پارامترها.
- سازوکار `pack expansion` برای گسترش الگو روی اعضای pack.
- روش‌های بازگشتی برای پردازش آرگومان‌ها در ++C11.
- عملگر `sizeof...` برای شمارش اعضای pack در زمان کامپایل.
- کاربرد Variadic Templates در ساختارهایی مانند `std::tuple` و wrapperهای عمومی.
- ترکیب Variadic Templates با `std::forward` برای پیاده‌سازی Perfect Forwarding.
- تفاوت این قابلیت با توابع متغیرآرگومان قدیمی مبتنی بر `<cstdarg>`.
- ارتباط این قابلیت با امکانات جدیدتر مانند Fold Expression در ++C17 و Concepts در ++C20.

در نهایت، Variadic Templates زمانی بیشترین ارزش را دارند که API واقعاً به تعداد متغیر آرگومان‌ها یا انواع نیاز داشته باشد. انتخاب درست میان pack expansion، بازگشت، Perfect Forwarding و abstractionهای استاندارد، کدی ایمن‌تر، خواناتر و قابل نگهداری‌تر ایجاد می‌کند.
