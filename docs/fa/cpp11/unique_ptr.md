## مقدمه

اشاره گر `std::unique_ptr` یکی از مهم‌ترین ابزارهای مدیریت حافظه در ++C مدرن است که از استاندارد C++11 وارد زبان شد.

عبارت `unique_ptr` برای زمانی طراحی شده است که یک شیء در حافظهٔ پویا فقط **یک مالک مشخص** داشته باشد.

کارکرد اصلی این نوع اشاره‌گر بسیار ساده است: تا زمانی که `unique_ptr` زنده است، مالک شیء مورد نظر محسوب می‌شود و زمانی که از بین می‌رود، شیء تحت مالکیت خود را نیز به‌صورت خودکار آزاد می‌کند و از بین می برد.

---

## مشکل قبل از C++11 چه بود؟

مدیریت حافظه در ++C قدیمی معمولاً با `new` و `delete` انجام می‌شد.

عبارت زیر نمونهٔ ساده‌ای از این روش است:

```cpp
MyClass* ptr = new MyClass();

//  ptr استفاده از

delete ptr;
```

مشکل اصلی این روش آن است که برنامه‌نویس مسئولیت کامل آزاد کردن حافظه را بر عهده دارد.

عبارت زیر اگر فراموش شود، باعث نشت حافظه می‌شود:

```cpp
MyClass* ptr = new MyClass();

//  ptr استفاده از

// delete ptr; فراموش شده است
```

مورد دیگری که مشکل‌ساز می‌شود، وجود چند مسیر خروج از تابع است.

عبارت زیر را در نظر بگیرید:

```cpp
void process()
{
    MyClass* ptr = new MyClass();

    if (someCondition())
        return;

    doSomething();

    delete ptr;
}
```

مشکل در این مثال آن است که اگر `someCondition()` مقدار `true` داشته باشد، تابع قبل از رسیدن به `delete` خارج می‌شود.

نتیجه این است که حافظه‌ای که با `new` گرفته شده، آزاد نمی‌شود و موجب نشت حافظه (Memory Leak) می شود.

---

## استثناها مشکل را جدی‌تر می‌کردند

مشکل مهم دیگر، وجود exception است.

عبارت زیر را ببینید:

```cpp
void process()
{
    MyClass* ptr = new MyClass();

    doSomething(); // ایجاد کند Exception ممکن است

    delete ptr;
}
```

مشکل این است که اگر `doSomething()` یک exception ایجاد کند، اجرای معمول تابع متوقف می‌شود و ممکن است `delete ptr` هیچ‌وقت اجرا نشود.

نتیجه می‌تواند نشت حافظه باشد.

---

# راه‌حل چیست؟

مفهوم RAII یکی از اصول بسیار مهم ++C است.

عبارت RAII مخفف `Resource Acquisition Is Initialization` است.

مفهوم RAII این است که مالکیت یک منبع را به طول عمر یک شیء گره بزنیم.

عبارت ساده‌تر این است که بگوییم:

> وقتی شیء مالک منبع ایجاد می‌شود، منبع را در اختیار می‌گیرد و وقتی شیء از بین می‌رود، منبع را آزاد می‌کند.

اشاره گر `std::unique_ptr` دقیقاً بر همین اساس کار می‌کند.

---

# اشاره گر unique_ptr چیست؟

اشاره گر `std::unique_ptr<T>` یک smart pointer است که مالکیت یک شیء از نوع `T` را در اختیار دارد.

عبارت زیر یک `unique_ptr` ایجاد می‌کند:

```cpp
#include <memory>

std::unique_ptr<MyClass> ptr(new MyClass());
```

اما روش پیشنهادی در C++14 و نسخه‌های بعدی استفاده از `std::make_unique` است:

```cpp
auto ptr = std::make_unique<MyClass>();
```

نکته مهم این است که `unique_ptr` خودش مسئول `delete` کردن شیء است.

عبارت زیر باعث می‌شود زمانی که `ptr` از scope خارج شود، شیء نیز آزاد شود:

```cpp
void process()
{
    auto ptr = std::make_unique<MyClass>();

    // استفاده از ptr
}
```

مفهوم این کد این است که دیگر نیازی به نوشتن `delete` نداریم.

---

# چرا نام آن unique است؟

عبارت `unique` به مالکیت یکتا اشاره دارد. عبارت زیر مجاز نیست:

```cpp
auto ptr1 = std::make_unique<MyClass>();

auto ptr2 = ptr1; // خطا
```

دلیل این خطا این است که اگر دو `unique_ptr` یک شیء را مالک باشند، مشخص نیست کدام‌یک باید آن را آزاد کند.

---

# انتقال مالکیت با move

اشاره گر `unique_ptr` قابل کپی نیست، اما قابل انتقال است.

عبارت زیر مالکیت را از `ptr1` به `ptr2` منتقل می‌کند:

```cpp
auto ptr1 = std::make_unique<MyClass>();

auto ptr2 = std::move(ptr1);
```

نکته مهم این است که بعد از این عملیات، `ptr2` مالک شیء است.

وضعیت `ptr1` نیز اینگونه است که دیگر مالک شیء نیست و معمولاً مقدار آن `nullptr` خواهد بود.

عبارت زیر برای بررسی آن مناسب است:

```cpp
if (ptr1 == nullptr)
{
    // ptr1 دیگر مالک شیء نیست
}
```

---

# چرا copy نداریم ولی move داریم؟

مفهوم copy این است که بعد از کپی، هر دو شیء مستقل و معتبر باشند.

عبارت زیر برای `unique_ptr` معنی درستی ندارد و باعث خطای کامپایلر می شود:

```cpp
auto ptr2 = ptr1;
```

متد move متفاوت است؛ در move مالکیت از یک شیء به شیء دیگر منتقل می‌شود.

عبارت استاندارد آن چنین است:

```cpp
auto ptr2 = std::move(ptr1);
```

---

# متد reset چیست؟

متد `reset()` برای تغییر مالکیت یا آزاد کردن شیء فعلی استفاده می‌شود.

عبارت زیر شیء فعلی را آزاد می‌کند:

```cpp
ptr.reset();
```

معنی این عملیات این است که اگر `ptr` مالک یک شیء باشد، آن شیء حذف می‌شود و `ptr` به حالت خالی می‌رود.

عبارت بررسی وضعیت آن چنین است:

```cpp
if (!ptr)
{
    // خالی است ptr 
}
```

---

# عملیات reset با یک شیء جدید

متد `reset` می‌تواند مالکیت یک شیء جدید را نیز به `unique_ptr` بدهد.

عبارت نمونه چنین است:

```cpp
ptr.reset(new MyClass());
```

معنی این کد این است که اگر `ptr` قبلاً مالک شیء دیگری باشد، ابتدا شیء قبلی آزاد می‌شود و سپس مالکیت شیء جدید به `ptr` داده می‌شود.

روش بهتر در C++ مدرن این است که تا حد امکان از `make_unique` استفاده کنیم.

عبارت مناسب‌تر برای ایجاد اولیه چنین است:

```cpp
auto ptr = std::make_unique<MyClass>();
```

---

# آیا می‌توانیم unique_ptr را خالی کنیم؟

اشاره گر `unique_ptr` می‌تواند در هر لحظه مالک هیچ شیئی نباشد.

عبارت زیر یک `unique_ptr` خالی ایجاد می‌کند:

```cpp
std::unique_ptr<MyClass> ptr;
```

بررسی خالی بودن آن نیز ساده است:

```cpp
if (!ptr)
{
    // ptr خالی است
}
```

---

# استفاده از unique_ptr در setter

متد setter برای دریافت یک `unique_ptr` باید با توجه به مالکیت طراحی شود.

عبارت رایج و واضح برای انتقال مالکیت، دریافت `unique_ptr` با `std::unique_ptr&&` است ولی روش صحیح تعریف Setter به صورت ورودی By Value است! به صورت زیر:

```cpp
class Owner
{
private:
    std::unique_ptr<MyClass> value;

public:
    void setValue(std::unique_ptr<MyClass> ptr)
    {
        value = std::move(ptr);
    }
};
```

معنی این طراحی این است که caller باید به‌صورت صریح مالکیت را منتقل کند:

```cpp
auto obj = std::make_unique<MyClass>();

owner.setValue(std::move(obj));
```

نکته مهم این است که بعد از این انتقال، `owner` مالک شیء خواهد بود و `obj` دیگر مالک آن نیست.

---

# چرا گرفتن unique_ptr با مقدار می‌تواند طراحی خوبی باشد؟

دریافت `unique_ptr` به‌صورت value در setter این مزیت را دارد که تابع به‌وضوح می‌گوید:

> این تابع مالکیت یک شیء را دریافت می‌کند.

پس یک Setter درست به این شکل است:

```cpp
void setValue(std::unique_ptr<MyClass> ptr)
{
    value = std::move(ptr);
}
```

نکته دیگر این است که اگر caller بخواهد مالکیت را منتقل کند، مجبور است `std::move` بنویسد.

بنابراین عبارت زیر کاملاً گویاست:

```cpp
owner.setValue(std::move(obj));
```

---

# عملیات getter برای unique_ptr چگونه باید باشد؟

متد getter یکی از قسمت‌های مهم طراحی کلاس است.

نکته مهم این است که نباید صرفاً به این دلیل که عضو کلاس `unique_ptr` است، خود `unique_ptr` را مستقیماً در اختیار caller قرار دهیم.

عبارت زیر معمولاً انتخاب مناسبی نیست:

```cpp
std::unique_ptr<MyClass>& getValue()
{
    return value;
}
```

مشکل این طراحی آن است که caller می‌تواند مالکیت داخلی کلاس را تغییر دهد.

مثلاً عبارت زیر ممکن است اتفاق بیفتد:

```cpp
owner.getValue().reset();
```

معنی این عملیات آن است که caller توانسته شیء تحت مالکیت کلاس را از بین ببرد.

---

# اگر فقط می‌خواهیم به شیء دسترسی بدهیم چه کنیم؟

کار مناسب‌تر آن است که **مالکیت را در کلاس نگه داریم و فقط دسترسی به شیء را ارائه کنیم.**

عبارت زیر برای یک عضو nullable انتخاب مناسبی است:

```cpp
MyClass* getValue()
{
    return value.get();
}
```

تابع `get()` می تواند raw pointer مربوط به شیء را برگرداند، اما مالکیت را منتقل نمی‌کند.

عملکرد caller می‌تواند چنین باشد:

```cpp
MyClass* ptr = owner.getValue();

if (ptr)
{
    ptr->doSomething();
}
```

مهم این است که caller مالک `ptr` نیست و نباید آن را با `delete` آزاد کند.

---

# متد getter بهتر برای شیئی که همیشه وجود دارد

اگر کلاس تضمین می‌کند که شیء همیشه وجود دارد، استفاده از reference می‌تواند طراحی بهتری باشد. عبارت نمونه چنین است:

```cpp
MyClass& getValue()
{
    return *value;
}
```

مفهوم استفاده از آن نیز ساده است:

```cpp
owner.getValue().doSomething();
```

مزیت این روش این است که caller با `nullptr` سروکار ندارد.

شرط مهم آن است که `value` باید واقعاً همیشه معتبر باشد.

---

# متد getter برای دسترسی فقط خواندنی

اگر نمی‌خواهیم caller بتواند شیء داخلی را تغییر دهد، `const` گزینه مناسبی است.

عبارت نمونه چنین است:

```cpp
const MyClass& getValue() const
{
    return *value;
}
```

مفهوم این طراحی آن است که caller می‌تواند شیء را بخواند، اما نمی‌تواند آن را تغییر دهد.

---

# آیا برگرداندن raw pointer از getter خطرناک است؟

اشاره گر raw pointer به‌خودی‌خود مشکل نیست.

مشکل زمانی ایجاد می‌شود که caller تصور کند raw pointer مالک شیء است. عبارت خطرناک زیر نباید انجام شود:

```cpp
MyClass* ptr = owner.getValue();

delete ptr;
```

در اینجا مشکل آن است که `ptr` مالک شیء نیست و `unique_ptr` همچنان تصور می‌کند مالک آن شیء است.

نتیجه می‌تواند `double delete` یعنی 2 بار delete شدن شی Heap و رفتار تعریف‌نشده یا `undefined behavior` باشد.

---

# خطر مهم‌تر raw pointer؛ dangling pointer

خطر دیگر زمانی ایجاد می‌شود که raw pointer را نگه داریم و مالک اصلی شیء از بین برود. عبارت نمونه:

```cpp
MyClass* ptr = owner.getValue();

owner.reset();

ptr->doSomething(); // خطرناک
```

در اینجا بعد از `reset`، به احتمال بالا شیء حذف شده است و `ptr` اکنون به حافظه‌ای اشاره کند که دیگر متعلق به آن شیء نیست. به چنین اشاره‌گری `dangling pointer` گفته می‌شود.

---

# آیا get باعث memory leak می‌شود؟

مهم آن است که خود `get()` باعث memory leak نمی‌شود. عبارت زیر فقط یک raw pointer غیرمالک را در اختیار caller قرار می‌دهد:

```cpp
MyClass* ptr = value.get();
```

نشت حافظه معمولاً زمانی اتفاق می‌افتد که مالکیت را به شکل نامناسب از `unique_ptr` جدا کنیم.

```cpp
MyClass* ptr = value.release();
```

توابع `release()` با `get()` کاملاً متفاوت است. عبارت `get()` می‌گوید:

> فقط آدرس را بده، مالکیت را نگه دار.

عبارت `release()` می‌گوید:

> مالکیت را رها کن و raw pointer را به من بده.

---

# متد release چگونه می‌تواند باعث memory leak شود؟

بعد از `release()` دیگر `unique_ptr` مالک شیء نیست. بنابراین عبارت زیر خطرناک است:

```cpp
auto ptr = std::make_unique<MyClass>();

MyClass* raw = ptr.release();

// استفاده می شود Raw اکنون

// فراموش شده است delete raw
```

در این مثال چون `unique_ptr` دیگر مالک شیء نیست و `delete raw` نیز انجام نشده است، حافظه نشت می‌کند.

در صورت استفادهٔ اجباری از `release()` باید مسئولیت مالکیت جدید را مشخص کنید:

```cpp
MyClass* raw = ptr.release();

delete raw;
```

توصیه مهم آن است که `release()` را فقط زمانی استفاده کنیم که واقعاً می‌خواهیم مالکیت را به یک API قدیمی یا یک سیستم دیگر منتقل کنیم.

---

# متدهای get و release را با هم اشتباه نگیریم

تفاوت این دو تابع بسیار مهم است.

| تابع        |           مالکیت منتقل می‌شود؟ | raw pointer برمی‌گرداند؟ |
| ----------- | -----------------------------: | -----------------------: |
| `get()`     |                            خیر |                      بله |
| `release()` | بله، از unique_ptr خارج می‌شود |                      بله |
| `reset()`   |        مالکیت قبلی آزاد می‌شود |                      خیر |

خلاصه شرح این موارد:

```cpp
ptr.get();      // فقط مشاهده
ptr.release();  // رها کردن مالکیت
ptr.reset();    // حذف شیء فعلی
```

---

# انتقال unique_ptr به یک تابع

اگر یک تابع باید مالکیت شیء را دریافت کند، `unique_ptr` را به آن منتقل می‌کنیم.

عبارت نمونه:

```cpp
void process(std::unique_ptr<MyClass> obj)
{
    obj->doSomething();
}
```

فراخوانی آن چنین است:

```cpp
auto obj = std::make_unique<MyClass>();

process(std::move(obj));
```

در این عملیات، بعد از این فراخوانی، تابع مالک شیء شده است.

---

# اگر تابع فقط می‌خواهد از شیء استفاده کند چه کنیم؟

اگر تابع قرار نیست مالکیت را بگیرد، بهتر است اصلاً `unique_ptr` را دریافت نکند.

عبارت مناسب برای شیئی که باید وجود داشته باشد:

```cpp
void process(const MyClass& obj)
{
    obj.doSomething();
}
```

فراخوانی آن با `unique_ptr` نیز ساده است:

```cpp
process(*obj);
```

اگر وجود شیء اختیاری است، می‌توان raw pointer غیرمالک دریافت کرد:

```cpp
void process(const MyClass* obj)
{
    if (obj)
    {
        obj->doSomething();
    }
}
```

این طراحی باعث می‌شود API تابع دقیقاً بیان کند که آیا مالکیت دریافت می‌کند یا فقط از شیء استفاده می‌کند.

---

# استفاده از unique_ptr در یک کلاس

یکی از رایج‌ترین کاربردهای `unique_ptr` نگهداری یک عضو private در کلاس است.

عبارت نمونه:

```cpp
class Car
{
private:
    std::unique_ptr<Engine> engine;

public:
    Car()
        : engine(std::make_unique<Engine>())
    {
    }
};
```

در این نمونه، `Car` مالک `Engine` است.

همچنین وقتی یک `Car` از بین برود، `Engine` نیز به‌صورت خودکار آزاد می‌شود.

---

# ارتباط unique_ptr و destructor

یکی از مزیت‌های مهم این طراحی این است که معمولاً نیازی به destructor دستی نداریم.

عبارت زیر کافی است:

```cpp
class Car
{
private:
    std::unique_ptr<Engine> engine;
};
```

زمانی که `Car` از بین می‌رود، destructor مربوط به `unique_ptr` اجرا می‌شود و `Engine` را آزاد می‌کند.

عبارت این اصل را نشان می‌دهد:

```text
Car
 └── unique_ptr
      └── Engine
```

مالکیت در این ساختار کاملاً مشخص است.

---

# انتقال مالکیت بین کلاس‌ها

یکی از مزیت‌های `unique_ptr` این است که مالکیت را می‌توان بین اشیاء منتقل کرد.

عبارت نمونه:

```cpp
class A
{
public:
    std::unique_ptr<MyClass> create()
    {
        return std::make_unique<MyClass>();
    }
};
```

شی caller می‌تواند مالکیت نتیجه را دریافت کند:

```cpp
std::unique_ptr<MyClass> obj = a.create();
```

اینجا انتقال مالکیت کاملاً مشخص است و نیازی به `delete` دستی وجود ندارد.

---

# آیا می‌توان unique_ptr را از getter برگرداند؟

بله، اما باید توجه کنیم که این کار معمولاً به معنی **انتقال مالکیت** است.

عبارت نمونه:

```cpp
std::unique_ptr<MyClass> takeValue()
{
    return std::move(value);
}
```

نام `takeValue` عمداً انتخاب شده تا نشان دهد caller مالکیت را دریافت می‌کند.

عبارت استفاده چنین است:

```cpp
auto obj = owner.takeValue();
```

بعد از این عملیات، کلاس دیگر مالک شیء نیست.

---

# متد getter مناسب بر اساس نیاز

می‌توانیم یک قانون ساده برای طراحی getter داشته باشیم:

```text
فقط خواندن:
const T&

خواندن و تغییر بدون انتقال مالکیت:
T&

دسترسی اختیاری:
T*

دسترسی اختیاری و فقط خواندنی:
const T*

انتقال مالکیت:
std::unique_ptr<T>

unique_ptr دسترسی مستقیم به خود:
std::unique_ptr<T>&
```

انتخاب نهایی باید بر اساس قرارداد API باشد، نه صرفاً بر اساس نوع عضو داخلی.

---

# چرا بهتر است unique_ptr را از کلاس بیرون ندهیم؟

اگر کلاس مالک یک منبع است، بهتر است مالکیت را تا حد امکان در همان کلاس نگه داریم.

عبارت نامناسب چنین چیزی است:

```cpp
std::unique_ptr<MyClass>& getValue();
```

این API جزئیات مدیریت حافظهٔ داخلی کلاس را در معرض استفاده‌کننده قرار می‌دهد.

عبارت طراحی بهتر این است:

```cpp
MyClass* getValue();
```

یا اگر nullable نیست:

```cpp
MyClass& getValue();
```

در این حالت کلاس می‌گوید:

> من مالک شیء هستم، اما اجازه می‌دهم از آن استفاده کنی.

---

# همراهی unique_ptr و const

کلمه کلیدی `const` را می‌توان در چند سطح مختلف استفاده کرد.

عبارت زیر یعنی خود شیء قابل تغییر نیست:

```cpp
std::unique_ptr<const MyClass> ptr;
```

عبارت زیر با مورد بالا متفاوت است:

```cpp
const std::unique_ptr<MyClass> ptr;
```

در حالت دوم خود `unique_ptr` قابل تغییر یا انتقال نیست، اما شیء `MyClass` می‌تواند قابل تغییر باشد.

این تفاوت یکی از نکات مهم ++C است و نباید این دو را با هم اشتباه گرفت.

---

# همراهی unique_ptr و polymorphism

اشاره گر `unique_ptr` برای نگهداری اشیای polymorphic نیز بسیار مناسب است.

عبارت نمونه:

```cpp
class Base
{
public:
    virtual ~Base() = default;
};

class Derived : public Base
{
};
```

حالا می‌توانیم بنویسیم:

```cpp
std::unique_ptr<Base> obj =
    std::make_unique<Derived>();
```

نکته بسیار مهم این است که اگر قرار است شیء مشتق‌شده از طریق `Base` حذف شود، destructor کلاس پایه باید حتما `virtual` باشد.

عبارت مناسب چنین است:

```cpp
virtual ~Base() = default;
```

---

# اشاره گر unique_ptr برای آرایه

اشاره گر `unique_ptr` برای آرایه نیز specialization دارد.

عبارت نمونه:

```cpp
std::unique_ptr<int[]> values =
    std::make_unique<int[]>(10);
```

اشاره گر `unique_ptr` هنگام نابودی، آرایه را به شکل مناسب آزاد می‌کند.

عبارت دسترسی به عنصر نیز مانند آرایه معمولی است:

```cpp
values[0] = 10;
values[1] = 20;
```

در کد مدرن معمولاً بهتر است برای آرایه‌های با اندازه مشخص از `std::array` و برای اندازه متغیر از `std::vector` استفاده کنیم، مگر اینکه واقعاً به مالکیت پویا با این شکل نیاز داشته باشیم.

---

# آیا unique_ptr خودش حافظه زیادی مصرف می‌کند؟

در حالت معمول، `unique_ptr<T>` از نظر مفهومی تقریباً به اندازه یک raw pointer است.

نکته مهم این است که `unique_ptr` یک آبجکت کوچک است که مالکیت و مسئولیت آزادسازی را مدیریت می‌کند.

اگر از custom deleter استفاده شود، اندازه `unique_ptr` ممکن است متفاوت باشد.

---

# custom deleter چیست؟

اشاره گر `unique_ptr` فقط برای `delete` کردن اشیای ساخته‌شده با `new` نیست.

می‌توانیم مشخص کنیم منبع چگونه آزاد شود:

```cpp
struct FileDeleter
{
    void operator()(FILE* file) const
    {
        if (file)
            fclose(file);
    }
};

using FilePtr = std::unique_ptr<FILE, FileDeleter>;
```

این قابلیت باعث می‌شود `unique_ptr` برای منابعی غیر از حافظه نیز مفید باشد؛ مانند file handle یا منابعی که باید با تابع خاصی آزاد شوند. در این روش ما با استفاده از تعریف عملگر Functor توانستیم طریقه آزادسازی File را مشخص کنیم!

---

# یک نکته بسیار مهم؛ make_unique

در C++14 تابع `std::make_unique` اضافه شد.

عبارت پیشنهادی چنین است:

```cpp
auto ptr = std::make_unique<MyClass>();
```

مزیت این روش این است که هم ساده‌تر است و هم در کد مدرن ++C انتخاب ترجیحی برای ساخت `unique_ptr` محسوب می‌شود.

اگر پروژه واقعاً C++11 باشد، `make_unique` در کتابخانه استاندارد وجود ندارد و می‌توان از `std::unique_ptr<T>(new T(...))` استفاده کرد یا یک helper مناسب برای C++11 تعریف کرد.

---

# یک اشتباه رایج؛ ساختن چند unique_ptr از یک raw pointer

نباید یک raw pointer را به چند `unique_ptr` بدهیم.

عبارت بسیار خطرناک:

```cpp
MyClass* raw = new MyClass();

std::unique_ptr<MyClass> p1(raw);
std::unique_ptr<MyClass> p2(raw);
```

اکنون دو مالک مستقل وجود دارند که هر دو فکر می‌کنند در انتها باید همان شیء را حذف کنند.

نتیجه می‌تواند `double delete` و رفتار تعریف‌نشده باشد.

---

# اشتباه رایج؛ delete کردن نتیجه get

نتیجه `get()` متعلق به caller نیست.

عبارت زیر غلط است:

```cpp
auto ptr = std::make_unique<MyClass>();

MyClass* raw = ptr.get();

delete raw;
```

اشاره گر `ptr` هنوز مالک همان شیء است و بعداً دوباره تلاش می‌کند آن را حذف کند.

---

# اشتباه رایج؛ نگه داشتن raw pointer برای مدت طولانی

شی raw pointer حاصل از `get()` فقط تا زمانی معتبر است که شیء تحت مالکیت `unique_ptr` وجود داشته باشد.

عبارت خطرناک:

```cpp
MyClass* raw = ptr.get();

ptr.reset();

// raw دیگر معتبر نیست
```

بنابراین اگر طول عمر raw pointer از مالک اصلی بیشتر شود، احتمال `dangling pointer` وجود دارد.

---

# چه زمانی از unique_ptr استفاده کنیم؟

زمانی که یک شیء دقیقاً یک مالک دارد، `unique_ptr` معمولاً انتخاب بسیار خوبی است.

عبارت‌های رایج استفاده عبارت‌اند از:

```text
مالکیت یک عضو داخل کلاس
factory ایجاد شیء در 
انتقال مالکیت بین توابع
مدیریت منابع پویا
custom deleter مدیریت منابع با 
polymorphism پیاده‌سازی 
```

اگر چند مالک مستقل نیاز داریم، باید به سراغ `std::shared_ptr` برویم.

اگر مالکیت مشترک واقعاً نیاز نیست، استفاده از `shared_ptr` صرفاً برای راحتی معمولاً انتخاب مناسبی نیست.

---

# تفاوت unique_ptr و shared_ptr

تفاوت اصلی این دو در مدل مالکیت است.

| ویژگی         | `unique_ptr` | `shared_ptr` |
| ------------- | ------------ | ------------ |
| مالکیت        | یکتا         | مشترک        |
| Copy          | خیر          | بله          |
| Move          | بله          | بله          |
| هزینه مدیریتی | کم           | بیشتر        |
| کنترل مالکیت  | ساده و واضح  | پیچیده‌تر    |
| کاربرد اصلی   | یک مالک      | چند مالک     |

یک قاعده ساده این است:

> اگر نمی‌دانید از کدام استفاده کنید، ابتدا بررسی کنید آیا واقعاً به مالکیت مشترک نیاز دارید یا خیر.

---

# قانون مهم در طراحی مدرن ++C

یکی از قواعد بسیار خوب این است:

> مالکیت را با smart pointer بده و دسترسی غیرمالکانه را با reference یا raw pointer نشان بده.

عبارت نمونه:

```cpp
std::unique_ptr<Engine> engine;
```

مفهوم این عضو یعنی `Car` مالک `Engine` است.

عبارت زیر:

```cpp
Engine* getEngine();
```

مفهوم این getter یعنی caller فقط به `Engine` دسترسی دارد و مالک آن نیست.

عبارت زیر:

```cpp
std::unique_ptr<Engine> takeEngine();
```

مفهوم این API یعنی caller مالکیت را تحویل می‌گیرد.

---

# یک نمونه کامل

یک کلاس واقعی می‌تواند به شکل زیر طراحی شود:

```cpp
class Car
{
private:
    std::unique_ptr<Engine> engine;

public:
    Car()
        : engine(std::make_unique<Engine>())
    {
    }

    Engine* getEngine()
    {
        return engine.get();
    }

    const Engine* getEngine() const
    {
        return engine.get();
    }

    void setEngine(std::unique_ptr<Engine> newEngine)
    {
        engine = std::move(newEngine);
    }

    std::unique_ptr<Engine> takeEngine()
    {
        return std::move(engine);
    }

    void resetEngine()
    {
        engine.reset();
    }
};
```

این طراحی چند نوع رفتار را به‌صورت کاملاً مشخص ارائه می‌کند.

عبارت `getEngine()` فقط دسترسی می‌دهد.

عبارت `setEngine()` مالکیت جدید دریافت می‌کند.

عبارت `takeEngine()` مالکیت را منتقل می‌کند.

عبارت `resetEngine()` منبع را آزاد می‌کند.

در نتیجه API کلاس از نظر مالکیت بسیار شفاف است.

---

# جمع‌بندی نهایی

اشاره گر `std::unique_ptr` راهکاری برای بیان **مالکیت یکتای یک منبع** است.

نکته مهم این است که `unique_ptr` صرفاً یک raw pointer با اسم متفاوت نیست.

مفهوم اصلی آن، **مدیریت مالکیت و طول عمر منبع** است.

عبارت‌های کلیدی که باید به خاطر بسپاریم این‌ها هستند:

```cpp
auto ptr = std::make_unique<T>();
```

در عبارت فوق یک شیء ساخته و مالکیت آن به `ptr` داده می‌شود.

```cpp
ptr.get();
```

در عبارت فوق فقط raw pointer غیرمالک را دریافت کردیم.

```cpp
ptr.reset();
```

در عبارت فوق شیء فعلی را آزاد کردیم و `unique_ptr` را خالی کردیم.

```cpp
ptr.reset(new T());
```

در عبارت فوق شیء فعلی را آزاد کردیم و مالک شیء جدید شدیم؛ هرچند برای ساخت اولیه، `make_unique` ترجیح دارد.

```cpp
ptr.release();
```

در عبارت فوق مالکیت را از `unique_ptr` خارج کردیم و raw pointer را تحویل دادیم.

```cpp
auto other = std::move(ptr);
```
در عبارت فوق مالکیت را از `ptr` به `other` منتقل کردیم.

```cpp
delete ptr.get();
```

در عبارت فوق مالکیت `unique_ptr` را نقض کرده‌ایم و ممکن است به رفتار تعریف‌نشده منجر شود.

نکته نهایی این است که هنگام استفاده از `unique_ptr` همیشه باید یک سؤال را از خودمان بپرسیم:

> **چه کسی مالک این شیء است؟**

اگر پاسخ این سؤال «فقط همین کلاس یا همین متغیر» باشد، `unique_ptr` معمولاً انتخاب مناسبی است.

اگر پاسخ «چند موجودیت به‌صورت مشترک مالک هستند» باشد، باید مدل مالکیت دیگری مانند `shared_ptr` را بررسی کنیم.

اگر هیچ‌کس مالک نیست و فقط می‌خواهیم موقتاً به یک شیء موجود دسترسی داشته باشیم، معمولاً reference یا raw pointer غیرمالک انتخاب مناسب‌تری است.

در نهایت مهم‌ترین مزیت `unique_ptr` این نیست که مجبور نیستیم `delete` بنویسیم؛ مزیت اصلی این است که **مالکیت منبع را به‌صورت صریح، قابل فهم و خودکار در ساختار برنامه بیان می‌کنیم.**
