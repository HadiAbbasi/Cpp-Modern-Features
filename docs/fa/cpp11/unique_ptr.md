## مقدمه

مفهوم `std::unique_ptr` یکی از مهم‌ترین ابزارهای مدیریت حافظه در ++C مدرن است که از استاندارد C++11 وارد زبان شد.

عبارت `unique_ptr` برای زمانی طراحی شده است که یک شیء در حافظهٔ پویا فقط **یک مالک مشخص** داشته باشد.

مفهوم اصلی این نوع اشاره‌گر بسیار ساده است: تا زمانی که `unique_ptr` زنده است، مالک شیء مورد نظر محسوب می‌شود و زمانی که از بین می‌رود، شیء تحت مالکیت خود را نیز به‌صورت خودکار آزاد می‌کند.

---

## مشکل قبل از C++11 چه بود؟

مفهوم مدیریت حافظه در ++C قدیمی معمولاً با `new` و `delete` انجام می‌شد.

عبارت زیر نمونهٔ ساده‌ای از این روش است:

```cpp
MyClass* ptr = new MyClass();

// استفاده از ptr

delete ptr;
```

مشکل اصلی این روش آن است که برنامه‌نویس مسئولیت کامل آزاد کردن حافظه را بر عهده دارد.

عبارت زیر اگر فراموش شود، باعث نشت حافظه می‌شود:

```cpp
MyClass* ptr = new MyClass();

// استفاده از ptr

// delete ptr; فراموش شده است
```

مفهوم دیگری که مشکل‌ساز می‌شود، وجود چند مسیر خروج از تابع است.

عبارت زیر را در نظر بگیرید:

```cpp
void process()
{
    MyClass* ptr = new MyClass();

    if (someCondition())
        return;

    doSomething();

    delete ptr;
}
```

مفهوم مشکل در این مثال آن است که اگر `someCondition()` مقدار `true` داشته باشد، تابع قبل از رسیدن به `delete` خارج می‌شود.

نتیجه این است که حافظه‌ای که با `new` گرفته شده، آزاد نمی‌شود.

---

## استثناها مشکل را جدی‌تر می‌کردند

مفهوم مهم دیگر، وجود exception است.

عبارت زیر را ببینید:

```cpp
void process()
{
    MyClass* ptr = new MyClass();

    doSomething(); // ممکن است exception ایجاد کند

    delete ptr;
}
```

مفهوم مشکل این است که اگر `doSomething()` یک exception ایجاد کند، اجرای معمول تابع متوقف می‌شود و ممکن است `delete ptr` هیچ‌وقت اجرا نشود.

نتیجه می‌تواند نشت حافظه باشد.

---

# راه‌حل چیست؟

مفهوم RAII یکی از اصول بسیار مهم ++C است.

عبارت RAII مخفف `Resource Acquisition Is Initialization` است.

مفهوم RAII این است که مالکیت یک منبع را به طول عمر یک شیء گره بزنیم.

عبارت ساده‌تر این است که بگوییم:

> وقتی شیء مالک منبع ایجاد می‌شود، منبع را در اختیار می‌گیرد و وقتی شیء از بین می‌رود، منبع را آزاد می‌کند.

مفهوم `std::unique_ptr` دقیقاً بر همین اساس کار می‌کند.

---

# unique_ptr چیست؟

مفهوم `std::unique_ptr<T>` یک smart pointer است که مالکیت یک شیء از نوع `T` را در اختیار دارد.

عبارت زیر یک `unique_ptr` ایجاد می‌کند:

```cpp
#include <memory>

std::unique_ptr<MyClass> ptr(new MyClass());
```

اما روش پیشنهادی در C++14 و نسخه‌های بعدی استفاده از `std::make_unique` است:

```cpp
auto ptr = std::make_unique<MyClass>();
```

مفهوم مهم این است که `unique_ptr` خودش مسئول `delete` کردن شیء است.

عبارت زیر باعث می‌شود زمانی که `ptr` از scope خارج شود، شیء نیز آزاد شود:

```cpp
void process()
{
    auto ptr = std::make_unique<MyClass>();

    // استفاده از ptr
}
```

مفهوم این کد این است که دیگر نیازی به نوشتن `delete` نداریم.

---

# چرا نام آن unique است؟

مفهوم `unique` به مالکیت یکتا اشاره دارد.

عبارت زیر مجاز نیست:

```cpp
auto ptr1 = std::make_unique<MyClass>();

auto ptr2 = ptr1; // خطا
```

مفهوم دلیل این خطا این است که اگر دو `unique_ptr` یک شیء را مالک باشند، مشخص نیست کدام‌یک باید آن را آزاد کند.

---

# انتقال مالکیت با move

مفهوم `unique_ptr` قابل کپی نیست، اما قابل انتقال است.

عبارت زیر مالکیت را از `ptr1` به `ptr2` منتقل می‌کند:

```cpp
auto ptr1 = std::make_unique<MyClass>();

auto ptr2 = std::move(ptr1);
```

مفهوم مهم این است که بعد از این عملیات، `ptr2` مالک شیء است.

مفهوم وضعیت `ptr1` نیز این است که دیگر مالک شیء نیست و معمولاً مقدار آن `nullptr` خواهد بود.

عبارت زیر برای بررسی آن مناسب است:

```cpp
if (ptr1 == nullptr)
{
    // ptr1 دیگر مالک شیء نیست
}
```

---

# چرا copy نداریم ولی move داریم؟

مفهوم copy این است که بعد از کپی، هر دو شیء مستقل و معتبر باشند.

عبارت زیر برای `unique_ptr` معنی درستی ندارد:

```cpp
auto ptr2 = ptr1;
```

مفهوم move متفاوت است؛ در move مالکیت از یک شیء به شیء دیگر منتقل می‌شود.

عبارت استاندارد آن چنین است:

```cpp
auto ptr2 = std::move(ptr1);
```

---

# reset چیست؟

مفهوم `reset()` برای تغییر مالکیت یا آزاد کردن شیء فعلی استفاده می‌شود.

عبارت زیر شیء فعلی را آزاد می‌کند:

```cpp
ptr.reset();
```

مفهوم این عملیات این است که اگر `ptr` مالک یک شیء باشد، آن شیء حذف می‌شود و `ptr` به حالت خالی می‌رود.

عبارت بررسی وضعیت آن چنین است:

```cpp
if (!ptr)
{
    // ptr خالی است
}
```

---

# reset با یک شیء جدید

مفهوم `reset` می‌تواند مالکیت یک شیء جدید را نیز به `unique_ptr` بدهد.

عبارت نمونه چنین است:

```cpp
ptr.reset(new MyClass());
```

مفهوم این کد این است که اگر `ptr` قبلاً مالک شیء دیگری باشد، ابتدا شیء قبلی آزاد می‌شود و سپس مالکیت شیء جدید به `ptr` داده می‌شود.

مفهوم روش بهتر در C++ مدرن این است که تا حد امکان از `make_unique` استفاده کنیم.

عبارت مناسب‌تر برای ایجاد اولیه چنین است:

```cpp
auto ptr = std::make_unique<MyClass>();
```

---

# آیا می‌توانیم unique_ptr را خالی کنیم؟

مفهوم `unique_ptr` می‌تواند در هر لحظه مالک هیچ شیئی نباشد.

عبارت زیر یک `unique_ptr` خالی ایجاد می‌کند:

```cpp
std::unique_ptr<MyClass> ptr;
```

مفهوم بررسی خالی بودن آن نیز ساده است:

```cpp
if (!ptr)
{
    // ptr خالی است
}
```

---

# استفاده از unique_ptr در setter

مفهوم setter برای دریافت یک `unique_ptr` باید با توجه به مالکیت طراحی شود.

عبارت رایج و واضح برای انتقال مالکیت، دریافت `unique_ptr` با `std::unique_ptr&&` است:

```cpp
class Owner
{
private:
    std::unique_ptr<MyClass> value;

public:
    void setValue(std::unique_ptr<MyClass> ptr)
    {
        value = std::move(ptr);
    }
};
```

مفهوم این طراحی این است که caller باید به‌صورت صریح مالکیت را منتقل کند:

```cpp
auto obj = std::make_unique<MyClass>();

owner.setValue(std::move(obj));
```

مفهوم مهم این است که بعد از این انتقال، `owner` مالک شیء خواهد بود و `obj` دیگر مالک آن نیست.

---

# چرا گرفتن unique_ptr با مقدار می‌تواند طراحی خوبی باشد؟

مفهوم دریافت `unique_ptr` به‌صورت value در setter این مزیت را دارد که تابع به‌وضوح می‌گوید:

> این تابع مالکیت یک شیء را دریافت می‌کند.

عبارت نمونه چنین است:

```cpp
void setValue(std::unique_ptr<MyClass> ptr)
{
    value = std::move(ptr);
}
```

مفهوم دیگر این است که اگر caller بخواهد مالکیت را منتقل کند، مجبور است `std::move` بنویسد.

عبارت زیر بنابراین کاملاً گویاست:

```cpp
owner.setValue(std::move(obj));
```

---

# getter برای unique_ptr چگونه باید باشد؟

مفهوم getter یکی از قسمت‌های مهم طراحی کلاس است.

عبارت مهم این است که نباید صرفاً به این دلیل که عضو کلاس `unique_ptr` است، خود `unique_ptr` را مستقیماً در اختیار caller قرار دهیم.

عبارت زیر معمولاً انتخاب مناسبی نیست:

```cpp
std::unique_ptr<MyClass>& getValue()
{
    return value;
}
```

مفهوم مشکل این طراحی این است که caller می‌تواند مالکیت داخلی کلاس را تغییر دهد.

عبارت زیر مثلاً ممکن است اتفاق بیفتد:

```cpp
owner.getValue().reset();
```

مفهوم این عملیات این است که caller توانسته شیء تحت مالکیت کلاس را از بین ببرد.

---

# اگر فقط می‌خواهیم به شیء دسترسی بدهیم چه کنیم؟

مفهوم مناسب‌تر این است که **مالکیت را در کلاس نگه داریم و فقط دسترسی به شیء را ارائه کنیم.**

عبارت زیر برای یک عضو nullable انتخاب مناسبی است:

```cpp
MyClass* getValue()
{
    return value.get();
}
```

مفهوم `get()` این است که raw pointer مربوط به شیء را برمی‌گرداند، اما مالکیت را منتقل نمی‌کند.

عبارت caller می‌تواند چنین باشد:

```cpp
MyClass* ptr = owner.getValue();

if (ptr)
{
    ptr->doSomething();
}
```

مفهوم مهم این است که caller مالک `ptr` نیست و نباید آن را با `delete` آزاد کند.

---

# getter بهتر برای شیئی که همیشه وجود دارد

مفهوم اگر کلاس تضمین می‌کند که شیء همیشه وجود دارد، استفاده از reference می‌تواند طراحی بهتری باشد.

عبارت نمونه چنین است:

```cpp
MyClass& getValue()
{
    return *value;
}
```

مفهوم استفاده از آن نیز ساده است:

```cpp
owner.getValue().doSomething();
```

مفهوم مزیت این روش این است که caller با `nullptr` سروکار ندارد.

مفهوم شرط مهم این است که `value` باید واقعاً همیشه معتبر باشد.

---

# getter برای دسترسی فقط خواندنی

مفهوم اگر نمی‌خواهیم caller بتواند شیء داخلی را تغییر دهد، `const` گزینه مناسبی است.

عبارت نمونه چنین است:

```cpp
const MyClass& getValue() const
{
    return *value;
}
```

مفهوم این طراحی این است که caller می‌تواند شیء را بخواند، اما نمی‌تواند آن را تغییر دهد.

---

# آیا برگرداندن raw pointer از getter خطرناک است؟

مفهوم raw pointer به‌خودی‌خود مشکل نیست.

عبارت مشکل زمانی ایجاد می‌شود که caller تصور کند raw pointer مالک شیء است.

عبارت خطرناک زیر نباید انجام شود:

```cpp
MyClass* ptr = owner.getValue();

delete ptr;
```

مفهوم مشکل این است که `ptr` مالک شیء نیست و `unique_ptr` همچنان تصور می‌کند مالک آن شیء است.

نتیجه می‌تواند `double delete` و رفتار تعریف‌نشده یا `undefined behavior` باشد.

---

# خطر مهم‌تر raw pointer؛ dangling pointer

مفهوم خطر دیگر زمانی ایجاد می‌شود که raw pointer را نگه داریم و مالک اصلی شیء از بین برود.

عبارت نمونه:

```cpp
MyClass* ptr = owner.getValue();

owner.reset();

ptr->doSomething(); // خطرناک
```

مفهوم این است که بعد از `reset`، شیء ممکن است حذف شده باشد و `ptr` اکنون به حافظه‌ای اشاره کند که دیگر متعلق به آن شیء نیست.

به چنین اشاره‌گری `dangling pointer` گفته می‌شود.

---

# آیا get باعث memory leak می‌شود؟

مفهوم مهم این است که خود `get()` باعث memory leak نمی‌شود.

عبارت زیر فقط یک raw pointer غیرمالک را در اختیار caller قرار می‌دهد:

```cpp
MyClass* ptr = value.get();
```

مفهوم نشت حافظه معمولاً زمانی اتفاق می‌افتد که مالکیت را به شکل نامناسب از `unique_ptr` جدا کنیم.

عبارت بسیار مهم زیر `release()` است:

```cpp
MyClass* ptr = value.release();
```

مفهوم `release()` با `get()` کاملاً متفاوت است.

عبارت `get()` می‌گوید:

> فقط آدرس را بده، مالکیت را نگه دار.

عبارت `release()` می‌گوید:

> مالکیت را رها کن و raw pointer را به من بده.

---

# release چگونه می‌تواند باعث memory leak شود؟

مفهوم بعد از `release()` دیگر `unique_ptr` مالک شیء نیست.

عبارت زیر بنابراین خطرناک است:

```cpp
auto ptr = std::make_unique<MyClass>();

MyClass* raw = ptr.release();

// raw استفاده می‌شود

// delete raw فراموش شده است
```

مفهوم این مثال این است که چون `unique_ptr` دیگر مالک شیء نیست و `delete raw` نیز انجام نشده است، حافظه نشت می‌کند.

عبارت صحیح در صورت استفادهٔ اجباری از `release()` باید مسئولیت مالکیت جدید را مشخص کند:

```cpp
MyClass* raw = ptr.release();

delete raw;
```

مفهوم توصیه مهم این است که `release()` را فقط زمانی استفاده کنیم که واقعاً می‌خواهیم مالکیت را به یک API قدیمی یا یک سیستم دیگر منتقل کنیم.

---

# get و release را با هم اشتباه نگیریم

مفهوم تفاوت این دو تابع بسیار مهم است.

| تابع        |           مالکیت منتقل می‌شود؟ | raw pointer برمی‌گرداند؟ |
| ----------- | -----------------------------: | -----------------------: |
| `get()`     |                            خیر |                      بله |
| `release()` | بله، از unique_ptr خارج می‌شود |                      بله |
| `reset()`   |        مالکیت قبلی آزاد می‌شود |                      خیر |

مفهوم خلاصه این است:

```cpp
ptr.get();      // فقط مشاهده
ptr.release();  // رها کردن مالکیت
ptr.reset();    // حذف شیء فعلی
```

---

# انتقال unique_ptr به یک تابع

مفهوم اگر یک تابع باید مالکیت شیء را دریافت کند، `unique_ptr` را به آن منتقل می‌کنیم.

عبارت نمونه:

```cpp
void process(std::unique_ptr<MyClass> obj)
{
    obj->doSomething();
}
```

مفهوم فراخوانی آن چنین است:

```cpp
auto obj = std::make_unique<MyClass>();

process(std::move(obj));
```

مفهوم این عملیات این است که بعد از فراخوانی، تابع مالک شیء شده است.

---

# اگر تابع فقط می‌خواهد از شیء استفاده کند چه کنیم؟

مفهوم اگر تابع قرار نیست مالکیت را بگیرد، بهتر است اصلاً `unique_ptr` را دریافت نکند.

عبارت مناسب برای شیئی که باید وجود داشته باشد:

```cpp
void process(const MyClass& obj)
{
    obj.doSomething();
}
```

مفهوم فراخوانی آن با `unique_ptr` نیز ساده است:

```cpp
process(*obj);
```

مفهوم اگر وجود شیء اختیاری است، می‌توان raw pointer غیرمالک دریافت کرد:

```cpp
void process(const MyClass* obj)
{
    if (obj)
    {
        obj->doSomething();
    }
}
```

مفهوم این طراحی باعث می‌شود API تابع دقیقاً بیان کند که آیا مالکیت دریافت می‌کند یا فقط از شیء استفاده می‌کند.

---

# استفاده از unique_ptr در یک کلاس

مفهوم یکی از رایج‌ترین کاربردهای `unique_ptr` نگهداری یک عضو private در کلاس است.

عبارت نمونه:

```cpp
class Car
{
private:
    std::unique_ptr<Engine> engine;

public:
    Car()
        : engine(std::make_unique<Engine>())
    {
    }
};
```

مفهوم این کلاس این است که `Car` مالک `Engine` است.

عبارت دیگر این است که وقتی یک `Car` از بین برود، `Engine` نیز به‌صورت خودکار آزاد می‌شود.

---

# unique_ptr و destructor

مفهوم یکی از مزیت‌های مهم این طراحی این است که معمولاً نیازی به destructor دستی نداریم.

عبارت زیر کافی است:

```cpp
class Car
{
private:
    std::unique_ptr<Engine> engine;
};
```

مفهوم زمانی که `Car` از بین می‌رود، destructor مربوط به `unique_ptr` اجرا می‌شود و `Engine` را آزاد می‌کند.

عبارت این اصل را نشان می‌دهد:

```text
Car
 └── unique_ptr
      └── Engine
```

مفهوم مالکیت در این ساختار کاملاً مشخص است.

---

# انتقال مالکیت بین کلاس‌ها

مفهوم یکی از مزیت‌های `unique_ptr` این است که مالکیت را می‌توان بین اشیاء منتقل کرد.

عبارت نمونه:

```cpp
class A
{
public:
    std::unique_ptr<MyClass> create()
    {
        return std::make_unique<MyClass>();
    }
};
```

مفهوم caller می‌تواند مالکیت نتیجه را دریافت کند:

```cpp
std::unique_ptr<MyClass> obj = a.create();
```

مفهوم اینجا انتقال مالکیت کاملاً مشخص است و نیازی به `delete` دستی وجود ندارد.

---

# آیا می‌توان unique_ptr را از getter برگرداند؟

مفهوم بله، اما باید توجه کنیم که این کار معمولاً به معنی **انتقال مالکیت** است.

عبارت نمونه:

```cpp
std::unique_ptr<MyClass> takeValue()
{
    return std::move(value);
}
```

مفهوم نام `takeValue` عمداً انتخاب شده تا نشان دهد caller مالکیت را دریافت می‌کند.

عبارت استفاده چنین است:

```cpp
auto obj = owner.takeValue();
```

مفهوم بعد از این عملیات، کلاس دیگر مالک شیء نیست.

---

# getter مناسب بر اساس نیاز

مفهوم می‌توانیم یک قانون ساده برای طراحی getter داشته باشیم:

```text
فقط خواندن:
const T&

خواندن و تغییر بدون انتقال مالکیت:
T&

دسترسی اختیاری:
T*

دسترسی اختیاری و فقط خواندنی:
const T*

انتقال مالکیت:
std::unique_ptr<T>

دسترسی مستقیم به خود unique_ptr:
std::unique_ptr<T>&
```

مفهوم انتخاب نهایی باید بر اساس قرارداد API باشد، نه صرفاً بر اساس نوع عضو داخلی.

---

# چرا بهتر است unique_ptr را از کلاس بیرون ندهیم؟

مفهوم اگر کلاس مالک یک منبع است، بهتر است مالکیت را تا حد امکان در همان کلاس نگه داریم.

عبارت نامناسب چنین چیزی است:

```cpp
std::unique_ptr<MyClass>& getValue();
```

مفهوم این API جزئیات مدیریت حافظهٔ داخلی کلاس را در معرض استفاده‌کننده قرار می‌دهد.

عبارت طراحی بهتر این است:

```cpp
MyClass* getValue();
```

یا اگر nullable نیست:

```cpp
MyClass& getValue();
```

مفهوم در این حالت کلاس می‌گوید:

> من مالک شیء هستم، اما اجازه می‌دهم از آن استفاده کنی.

---

# unique_ptr و const

مفهوم `const` را می‌توان در چند سطح مختلف استفاده کرد.

عبارت زیر یعنی خود شیء قابل تغییر نیست:

```cpp
std::unique_ptr<const MyClass> ptr;
```

مفهوم عبارت زیر با مورد بالا متفاوت است:

```cpp
const std::unique_ptr<MyClass> ptr;
```

مفهوم در حالت دوم خود `unique_ptr` قابل تغییر یا انتقال نیست، اما شیء `MyClass` می‌تواند قابل تغییر باشد.

عبارت این تفاوت یکی از نکات مهم ++C است و نباید این دو را با هم اشتباه گرفت.

---

# unique_ptr و polymorphism

مفهوم `unique_ptr` برای نگهداری اشیای polymorphic نیز بسیار مناسب است.

عبارت نمونه:

```cpp
class Base
{
public:
    virtual ~Base() = default;
};

class Derived : public Base
{
};
```

مفهوم حالا می‌توانیم بنویسیم:

```cpp
std::unique_ptr<Base> obj =
    std::make_unique<Derived>();
```

مفهوم بسیار مهم این است که اگر قرار است شیء مشتق‌شده از طریق `Base` حذف شود، destructor کلاس پایه باید معمولاً `virtual` باشد.

عبارت مناسب چنین است:

```cpp
virtual ~Base() = default;
```

---

# unique_ptr برای آرایه

مفهوم `unique_ptr` برای آرایه نیز specialization دارد.

عبارت نمونه:

```cpp
std::unique_ptr<int[]> values =
    std::make_unique<int[]>(10);
```

مفهوم `unique_ptr` هنگام نابودی، آرایه را به شکل مناسب آزاد می‌کند.

عبارت دسترسی به عنصر نیز مانند آرایه معمولی است:

```cpp
values[0] = 10;
values[1] = 20;
```

مفهوم در کد مدرن معمولاً بهتر است برای آرایه‌های با اندازه مشخص از `std::array` و برای اندازه متغیر از `std::vector` استفاده کنیم، مگر اینکه واقعاً به مالکیت پویا با این شکل نیاز داشته باشیم.

---

# آیا unique_ptr خودش حافظه زیادی مصرف می‌کند؟

مفهوم در حالت معمول، `unique_ptr<T>` از نظر مفهومی تقریباً به اندازه یک raw pointer است.

عبارت مهم این است که `unique_ptr` یک آبجکت کوچک است که مالکیت و مسئولیت آزادسازی را مدیریت می‌کند.

مفهوم اگر از custom deleter استفاده شود، اندازه `unique_ptr` ممکن است متفاوت باشد.

---

# custom deleter چیست؟

مفهوم `unique_ptr` فقط برای `delete` کردن اشیای ساخته‌شده با `new` نیست.

عبارت می‌توانیم مشخص کنیم منبع چگونه آزاد شود:

```cpp
struct FileDeleter
{
    void operator()(FILE* file) const
    {
        if (file)
            fclose(file);
    }
};

using FilePtr = std::unique_ptr<FILE, FileDeleter>;
```

مفهوم این قابلیت باعث می‌شود `unique_ptr` برای منابعی غیر از حافظه نیز مفید باشد؛ مانند file handle یا منابعی که باید با تابع خاصی آزاد شوند.

---

# یک نکته بسیار مهم؛ make_unique

مفهوم در C++14 تابع `std::make_unique` اضافه شد.

عبارت پیشنهادی چنین است:

```cpp
auto ptr = std::make_unique<MyClass>();
```

مفهوم مزیت این روش این است که هم ساده‌تر است و هم در کد مدرن ++C انتخاب ترجیحی برای ساخت `unique_ptr` محسوب می‌شود.

مفهوم اگر پروژه واقعاً C++11 باشد، `make_unique` در کتابخانه استاندارد وجود ندارد و می‌توان از `std::unique_ptr<T>(new T(...))` استفاده کرد یا یک helper مناسب برای C++11 تعریف کرد.

---

# یک اشتباه رایج؛ ساختن چند unique_ptr از یک raw pointer

مفهوم نباید یک raw pointer را به چند `unique_ptr` بدهیم.

عبارت بسیار خطرناک:

```cpp
MyClass* raw = new MyClass();

std::unique_ptr<MyClass> p1(raw);
std::unique_ptr<MyClass> p2(raw);
```

مفهوم این است که اکنون دو مالک مستقل وجود دارند که هر دو فکر می‌کنند باید همان شیء را حذف کنند.

نتیجه می‌تواند `double delete` و رفتار تعریف‌نشده باشد.

---

# اشتباه رایج؛ delete کردن نتیجه get

مفهوم نتیجه `get()` متعلق به caller نیست.

عبارت زیر غلط است:

```cpp
auto ptr = std::make_unique<MyClass>();

MyClass* raw = ptr.get();

delete raw;
```

مفهوم `ptr` هنوز مالک همان شیء است و بعداً دوباره تلاش می‌کند آن را حذف کند.

---

# اشتباه رایج؛ نگه داشتن raw pointer برای مدت طولانی

مفهوم raw pointer حاصل از `get()` فقط تا زمانی معتبر است که شیء تحت مالکیت `unique_ptr` وجود داشته باشد.

عبارت خطرناک:

```cpp
MyClass* raw = ptr.get();

ptr.reset();

// raw دیگر معتبر نیست
```

مفهوم بنابراین اگر طول عمر raw pointer از مالک اصلی بیشتر شود، احتمال `dangling pointer` وجود دارد.

---

# چه زمانی از unique_ptr استفاده کنیم؟

مفهوم زمانی که یک شیء دقیقاً یک مالک دارد، `unique_ptr` معمولاً انتخاب بسیار خوبی است.

عبارت‌های رایج استفاده عبارت‌اند از:

```text
مالکیت یک عضو داخل کلاس
ایجاد شیء در factory
انتقال مالکیت بین توابع
مدیریت منابع پویا
مدیریت منابع با custom deleter
پیاده‌سازی polymorphism
```

مفهوم اگر چند مالک مستقل نیاز داریم، باید به سراغ `std::shared_ptr` برویم.

مفهوم اگر مالکیت مشترک واقعاً نیاز نیست، استفاده از `shared_ptr` صرفاً برای راحتی معمولاً انتخاب مناسبی نیست.

---

# تفاوت unique_ptr و shared_ptr

مفهوم تفاوت اصلی این دو در مدل مالکیت است.

| ویژگی         | `unique_ptr` | `shared_ptr` |
| ------------- | ------------ | ------------ |
| مالکیت        | یکتا         | مشترک        |
| Copy          | خیر          | بله          |
| Move          | بله          | بله          |
| هزینه مدیریتی | کم           | بیشتر        |
| کنترل مالکیت  | ساده و واضح  | پیچیده‌تر    |
| کاربرد اصلی   | یک مالک      | چند مالک     |

مفهوم یک قاعده ساده این است:

> اگر نمی‌دانید از کدام استفاده کنید، ابتدا بررسی کنید آیا واقعاً به مالکیت مشترک نیاز دارید یا خیر.

---

# قانون مهم در طراحی مدرن ++C

مفهوم یکی از قواعد بسیار خوب این است:

> مالکیت را با smart pointer نشان بده و دسترسی غیرمالکانه را با reference یا raw pointer نشان بده.

عبارت نمونه:

```cpp
std::unique_ptr<Engine> engine;
```

مفهوم این عضو یعنی `Car` مالک `Engine` است.

عبارت زیر:

```cpp
Engine* getEngine();
```

مفهوم این getter یعنی caller فقط به `Engine` دسترسی دارد و مالک آن نیست.

عبارت زیر:

```cpp
std::unique_ptr<Engine> takeEngine();
```

مفهوم این API یعنی caller مالکیت را تحویل می‌گیرد.

---

# یک نمونه کامل

مفهوم یک کلاس واقعی می‌تواند به شکل زیر طراحی شود:

```cpp
class Car
{
private:
    std::unique_ptr<Engine> engine;

public:
    Car()
        : engine(std::make_unique<Engine>())
    {
    }

    Engine* getEngine()
    {
        return engine.get();
    }

    const Engine* getEngine() const
    {
        return engine.get();
    }

    void setEngine(std::unique_ptr<Engine> newEngine)
    {
        engine = std::move(newEngine);
    }

    std::unique_ptr<Engine> takeEngine()
    {
        return std::move(engine);
    }

    void resetEngine()
    {
        engine.reset();
    }
};
```

مفهوم این طراحی چند نوع رفتار را به‌صورت کاملاً مشخص ارائه می‌کند.

عبارت `getEngine()` فقط دسترسی می‌دهد.

عبارت `setEngine()` مالکیت جدید دریافت می‌کند.

عبارت `takeEngine()` مالکیت را منتقل می‌کند.

عبارت `resetEngine()` منبع را آزاد می‌کند.

مفهوم در نتیجه API کلاس از نظر مالکیت بسیار شفاف است.

---

# جمع‌بندی نهایی

مفهوم `std::unique_ptr` راهکاری برای بیان **مالکیت یکتای یک منبع** است.

عبارت مهم این است که `unique_ptr` صرفاً یک raw pointer با اسم متفاوت نیست.

مفهوم اصلی آن، **مدیریت مالکیت و طول عمر منبع** است.

عبارت‌های کلیدی که باید به خاطر بسپاریم این‌ها هستند:

```cpp
auto ptr = std::make_unique<T>();
```

مفهوم این عبارت یعنی یک شیء ساخته و مالکیت آن به `ptr` داده می‌شود.

```cpp
ptr.get();
```

مفهوم این عبارت یعنی فقط raw pointer غیرمالک را دریافت کن.

```cpp
ptr.reset();
```

مفهوم این عبارت یعنی شیء فعلی را آزاد کن و `unique_ptr` را خالی کن.

```cpp
ptr.reset(new T());
```

مفهوم این عبارت یعنی شیء فعلی را آزاد کن و مالک شیء جدید شو؛ هرچند برای ساخت اولیه، `make_unique` ترجیح دارد.

```cpp
ptr.release();
```

مفهوم این عبارت یعنی مالکیت را از `unique_ptr` خارج کن و raw pointer را تحویل بده.

```cpp
auto other = std::move(ptr);
```

مفهوم این عبارت یعنی مالکیت را از `ptr` به `other` منتقل کن.

```cpp
delete ptr.get();
```

مفهوم این عبارت یعنی مالکیت `unique_ptr` را نقض کرده‌ای و ممکن است به رفتار تعریف‌نشده منجر شود.

مفهوم نهایی این است که هنگام استفاده از `unique_ptr` همیشه باید یک سؤال را از خودمان بپرسیم:

> **چه کسی مالک این شیء است؟**

عبارت اگر پاسخ این سؤال «فقط همین کلاس یا همین متغیر» باشد، `unique_ptr` معمولاً انتخاب مناسبی است.

مفهوم اگر پاسخ «چند موجودیت به‌صورت مشترک مالک هستند» باشد، باید مدل مالکیت دیگری مانند `shared_ptr` را بررسی کنیم.

مفهوم اگر هیچ‌کس مالک نیست و فقط می‌خواهیم موقتاً به یک شیء موجود دسترسی داشته باشیم، معمولاً reference یا raw pointer غیرمالک انتخاب مناسب‌تری است.

عبارت در نهایت مهم‌ترین مزیت `unique_ptr` این نیست که مجبور نیستیم `delete` بنویسیم؛ مزیت اصلی این است که **مالکیت منبع را به‌صورت صریح، قابل فهم و خودکار در ساختار برنامه بیان می‌کنیم.**
