# `constexpr` Lambda Expressions in C++17: Compile-Time Closures and Meta-Programming

`constexpr` lambdas are a core C++17 language feature that makes lambda expressions callable and evaluatable in constant expressions. Prior to C++17, lambda expressions were strictly prohibited in `constexpr` contexts. Starting in C++17, lambdas are **implicitly `constexpr`** if their bodies satisfy constant expression requirements, or they can be **explicitly declared `constexpr`** to guarantee compile-time verification by the compiler.

```cpp
#include <array>
#include <iostream>

int main() {
    // Explicit constexpr lambda
    constexpr auto square = [](int n) constexpr {
        return n * n;
    };

    // Evaluated at compile time to define array capacity
    constexpr int size = square(5);
    std::array<int, size> buffer{};

    std::cout << "Buffer size: " << buffer.size() << '\n'; // 25
}
```

This guide explains the motivation behind `constexpr` lambdas, the mechanics of implicit vs. explicit qualification, capture rules, compile-time algorithms, common pitfalls, performance advantages, and changes introduced in C++20 and beyond.

## 1. Why `constexpr` Lambdas Exist

Modern C++ puts a heavy emphasis on zero-cost abstractions and doing as much computation as possible at compile time (meta-programming, lookup-table generation, protocol validation, static configuration).

Before C++17, if you wanted local, modular computation at compile time, you were forced to:
- Declare separate `constexpr` helper functions outside your local function scope.
- Write verbose template metaprogramming structs or custom functor types with `constexpr operator()`.

Structured bindings and lambdas make local logic clear and expressive. Allowing lambdas inside constant expressions bridges the gap between functional programming style and compile-time evaluation.

---

## 2. What Was the Problem Before C++17?

In C++11 and C++14, the C++ standard explicitly stated that closure types generated by lambdas could **not** have a `constexpr` call operator (`operator()`).

### Before C++17: Verbose External Functions

```cpp
// In C++14: had to be defined at namespace scope
constexpr int factorial_impl(int n) {
    return (n <= 1) ? 1 : n * factorial_impl(n - 1);
}

int main() {
    constexpr int val = factorial_impl(5); // OK
    
    // In C++14, the following was an error:
    // auto fact = [](int n) { return (n <= 1) ? 1 : n * fact(n - 1); };
    // constexpr int x = fact(5); // ERROR: call operator is not constexpr
}
```

### Before C++17: Manual Functors

To get a local-like compile-time functor, you had to define a full struct:

```cpp
struct MultiplyByTwo {
    constexpr int operator()(int x) const {
        return x * 2;
    }
};

constexpr MultiplyByTwo mult;
constexpr int res = mult(10); // OK, but very verbose
```

This boilerplate cluttered codebases with ad-hoc struct definitions and namespace-level helpers that polluted namespaces and reduced locality of reference.

## 3. Syntax Overview

The syntax for an explicit `constexpr` lambda puts the `constexpr` specifier after the parameter list (and after `mutable` if present):

```text
[ captures ] ( params ) specifiers constexpr exception-spec -> return-type { body }
```

### Common Variations

```cpp
// 1. Explicit constexpr lambda
auto add = [](int a, int b) constexpr { return a + b; };

// 2. Mutable constexpr lambda
auto counter = [count = 0]() mutable constexpr { return ++count; };

// 3. Generic constexpr lambda
auto identity = [](auto x) constexpr { return x; };

// 4. Storing the closure itself in a constexpr variable
constexpr auto multiply = [](int a, int b) { return a * b; };
```

> **Note on declaration syntax:**
> The `constexpr` keyword can appear in two places:
> 1. In the lambda declaration itself: `[](int x) constexpr { ... }` — this ensures the generated `operator()` is marked `constexpr`.
> 2. In the variable holding the closure: `constexpr auto f = ...;` — this requires the closure object itself to be a literal type and initialized at compile time.

---

## 4. Implicit vs. Explicit `constexpr`

One of the best design choices in C++17 is **implicit constexpr enablement**.

### 4.1 Implicit `constexpr`

If you omit the `constexpr` keyword in the lambda declaration, the compiler automatically treats the lambda's `operator()` as `constexpr` **if and only if** its body and captured variables satisfy the requirements of a `constexpr` function:

```cpp
// Implicitly constexpr (no 'constexpr' keyword in lambda signature)
auto add = [](int a, int b) {
    return a + b;
};

// Valid! Evaluated at compile time:
constexpr int sum = add(10, 20); 
static_assert(sum == 30);
```

### 4.2 Explicit `constexpr`

If you add `constexpr` explicitly to the lambda signature, you force the compiler to verify that the lambda satisfies constant expression rules. If it violates any rule (such as calling a non-`constexpr` function or throwing uncaught exceptions), the compiler produces a diagnostic error immediately:

```cpp
int runtime_val = 42;

// Compile error: runtime_val cannot be read in a constant expression
auto bad = [runtime_val]() constexpr {
    return runtime_val * 2;
};
```

**Recommendation:** Use explicit `constexpr` when the lambda is fundamentally intended for compile-time logic, so you get actionable compiler errors right at the lambda definition if an accidental runtime dependency is introduced.

## 5. What Really Happens Under the Hood

When you write a lambda in C++, the compiler synthesizes an anonymous class (a **closure type**) with an overloaded `operator()`.

Consider:

```cpp
auto sq = [](int x) constexpr { return x * x; };
```

The compiler expands this conceptually to:

```cpp
class __Lambda_Unique_Name {
public:
    constexpr __Lambda_Unique_Name() = default;

    constexpr auto operator()(int x) const {
        return x * x;
    }

    // Function pointer conversion operator (when captureless)
    constexpr using FPtr = int(*)(int);
    constexpr operator FPtr() const noexcept {
        return &__invoke;
    }

private:
    static constexpr int __invoke(int x) {
        return x * x;
    }
};

__Lambda_Unique_Name sq{};
```

### Key Under-the-Hood Guarantees in C++17

1. **`operator()` is `constexpr`:** It can be invoked during constant expression evaluation.
2. **The closure type is a Literal Type:** As long as all captured variables are literal types, the closure type itself is a literal type. This means the closure object can be marked `constexpr auto f = ...;`.
3. **Captureless Conversion to Function Pointer is `constexpr`:** In C++17, conversion of a captureless lambda to a function pointer is also a `constexpr` operation.

```cpp
constexpr auto f = [](int x) { return x + 1; };
constexpr int (*fn_ptr)(int) = f; // Valid constexpr function pointer!
static_assert(fn_ptr(4) == 5);
```

## 6. Capture Rules at Compile Time

Capturing state inside a `constexpr` lambda follows strict compile-time rules.

### 6.1 Capturing by Value

A lambda can capture variables by value and still be used in constant expressions, provided that the captured variable is evaluated at compile time and is of a literal type:

```cpp
constexpr int factor = 3;

constexpr auto scale = [factor](int x) constexpr {
    return x * factor;
};

static_assert(scale(4) == 12);
```

### 6.2 Capturing by Reference

Capturing by reference in a `constexpr` context is allowed, but the referenced object must have static storage duration or be part of the active constant evaluation frame:

```cpp
static constexpr int offset = 100;

constexpr auto addOffset = [&offset](int x) constexpr {
    return x + offset;
};

static_assert(addOffset(5) == 105);
```

If you capture a local variable by reference and try to invoke the lambda outside the lifetime of that variable during compile time, evaluation fails.

### 6.3 Mutable Captures in `constexpr` Lambdas

In C++14, `constexpr` member functions were no longer implicitly `const`. In C++17, a `constexpr` lambda can be marked `mutable`:

```cpp
constexpr auto runCounter = []() constexpr {
    int total = 0;
    auto step = [&total]() mutable constexpr {
        return ++total;
    };
    step();
    step();
    return total;
};

static_assert(runCounter() == 2);
```

## 7. Calling `constexpr` Lambdas at Runtime vs. Compile Time

Declaring a lambda as `constexpr` does **not** restrict it to compile-time-only execution.

Like any `constexpr` function in C++, a `constexpr` lambda is dual-use:
- If called with compile-time constants in a constant expression context, it executes at **compile time**.
- If called with runtime variables, it executes at **runtime** without any compilation error.

```cpp
auto compute = [](int x) constexpr {
    return x * 10;
};

int main() {
    // 1. Compile-time execution
    constexpr int compile_time_res = compute(5); // Evaluated at compile time
    static_assert(compile_time_res == 50);

    // 2. Runtime execution
    int runtime_input;
    std::cin >> runtime_input;
    int runtime_res = compute(runtime_input); // Evaluated at runtime
    std::cout << runtime_res << '\n';
}
```

## 8. Using `constexpr` Lambdas with `<algorithm>`

In C++17, standard library algorithms such as `std::sort`, `std::accumulate`, or `std::find` are not yet marked `constexpr` (most `<algorithm>` functions became `constexpr` in C++20). However, custom compile-time algorithms can directly accept `constexpr` lambdas.

### Custom Compile-Time Filter / Count

```cpp
#include <array>
#include <cstddef>

template <typename T, std::size_t N, typename Predicate>
constexpr std::size_t count_if_constexpr(const std::array<T, N>& arr, Predicate pred) {
    std::size_t count = 0;
    for (const auto& item : arr) {
        if (pred(item)) {
            ++count;
        }
    }
    return count;
}

int main() {
    constexpr std::array<int, 6> values{1, 2, 3, 4, 5, 6};

    constexpr auto is_even = [](int x) constexpr { return x % 2 == 0; };

    constexpr auto evens = count_if_constexpr(values, is_even);
    static_assert(evens == 3);
}
```

## 9. Immediately Invoked Function Expressions (IIFE) at Compile Time

One of the most powerful patterns unlocked by `constexpr` lambdas is the **Compile-Time IIFE**.

An IIFE allows complex, multi-step initialization of `constexpr` variables or static lookup tables without needing to define external helper functions.

### Creating a Static Lookup Table with IIFE

```cpp
#include <array>

// Compile-time generation of prime or square lookup tables
static constexpr auto lookup_table = []() constexpr {
    std::array<int, 10> table{};
    for (std::size_t i = 0; i < table.size(); ++i) {
        table[i] = static_cast<int>(i * i * i); // cubic values
    }
    return table;
}(); // Immediately invoked!

int main() {
    static_assert(lookup_table[0] == 0);
    static_assert(lookup_table[2] == 8);
    static_assert(lookup_table[3] == 27);
    static_assert(lookup_table[9] == 729);
}
```

This pattern ensures that `lookup_table` is deeply immutable (`constexpr`), has local initialization logic right next to its declaration, and executes zero runtime overhead.

## 10. Higher-Order Functions and Currying at Compile Time

Because closures are literal types in C++17, `constexpr` lambdas can return other `constexpr` lambdas. This enables compile-time currying and functional composition.

```cpp
#include <iostream>

int main() {
    // A lambda returning another lambda
    constexpr auto make_adder = [](int x) constexpr {
        return [x](int y) constexpr {
            return x + y;
        };
    };

    constexpr auto add5 = make_adder(5);
    constexpr int val = add5(10);
    static_assert(val == 15);

    // Function composition at compile time
    constexpr auto compose = [](auto f, auto g) constexpr {
        return [f, g](auto x) constexpr {
            return f(g(x));
        };
    };

    constexpr auto double_it = [](int x) constexpr { return x * 2; };
    constexpr auto inc = [](int x) constexpr { return x + 1; };

    constexpr auto double_then_inc = compose(inc, double_it);
    static_assert(double_then_inc(4) == 9); // (4 * 2) + 1 = 9
}
```

## 11. Generic `constexpr` Lambdas (`auto` parameters)

Generic lambdas (introduced in C++14) integrate seamlessly with C++17 `constexpr`:

```cpp
auto generic_max = [](auto a, auto b) constexpr {
    return (a > b) ? a : b;
};

int main() {
    constexpr int max_int = generic_max(10, 20);
    constexpr double max_double = generic_max(3.14, 2.71);

    static_assert(max_int == 20);
    static_assert(max_double > 3.0);
}
```

When compiled, the generated `operator()` is a template member function:

```cpp
template <typename T, typename U>
constexpr auto operator()(T a, U b) const {
    return (a > b) ? a : b;
}
```

## 12. Interaction with Other C++17 Features

### 12.1 `if constexpr` Inside Lambdas

You can combine `constexpr` lambdas with `if constexpr` to execute compile-time branching:

```cpp
#include <type_traits>

auto stringify_or_double = [](auto x) constexpr {
    if constexpr (std::is_integral_v<decltype(x)>) {
        return x * 2;
    } else {
        return x;
    }
};

static_assert(stringify_or_double(5) == 10);
```

### 12.2 Structured Bindings Inside `constexpr` Lambdas

You can unpack tuples, pairs, or arrays inside `constexpr` lambdas:

```cpp
#include <utility>

constexpr auto unpack_and_sum = [](std::pair<int, int> p) constexpr {
    auto [x, y] = p; // Structured binding in constexpr context
    return x + y;
};

static_assert(unpack_and_sum({3, 7}) == 10);
```

## 13. Common Pitfalls and Gotchas

### 13.1 Calling Non-`constexpr` Functions Inside the Body

If a lambda calls any function not declared `constexpr`, the lambda cannot be evaluated at compile time:

```cpp
#include <cmath>

auto calc = [](double x) constexpr {
    // In C++17, std::sqrt is NOT constexpr!
    return std::sqrt(x); // ERROR when evaluated in constexpr context
};

// constexpr auto val = calc(4.0); // Compiler error!
```

### 13.2 Memory Allocation (`new` / `delete`) in C++17

Dynamic memory allocation inside constant evaluation is not supported in C++17 (it was introduced later in C++20 for transient allocations).

```cpp
auto bad_alloc = []() constexpr {
    int* p = new int(5); // ERROR in C++17 constexpr
    int v = *p;
    delete p;
    return v;
};
```

### 13.3 `constexpr auto f = ...` vs. `auto f = ... constexpr`

Be careful with where `constexpr` is placed:

```cpp
// Case 1: Lambda is constexpr, variable is runtime
auto f1 = [](int x) constexpr { return x + 1; };

// Case 2: Both the closure object and the lambda operator() are constexpr
constexpr auto f2 = [](int x) { return x + 1; };

// Case 3: Capturing a non-constexpr variable in a constexpr variable
int runtime_val = 10;
// constexpr auto f3 = [runtime_val]() { return runtime_val; }; 
// ERROR: f3 cannot be initialized at compile time because runtime_val is not a constant.
```

### 13.4 Recursive Lambdas Without Helpers

A lambda cannot easily deduce its own type for direct recursion:

```cpp
// ERROR: cannot call 'fact' before its deduction is finished
// constexpr auto fact = [](int n) { return n <= 1 ? 1 : n * fact(n - 1); };
```

**Solution:** Pass the lambda to itself (the Y-combinator pattern) or use a normal `constexpr` function:

```cpp
constexpr auto fact = [](auto self, int n) -> int {
    return (n <= 1) ? 1 : n * self(self, n - 1);
};

static_assert(fact(fact, 5) == 120);
```

## 14. Performance Considerations

1. **Zero Runtime Overhead:** Code evaluated at compile time generates no instructions and incurs zero execution time; results are embedded directly as immediate values in the binary.
2. **Binary Bloat Prevention:** Generating static tables using an IIFE at compile time avoids static runtime constructors and guarantees that tables are stored in read-only memory (`.rodata`).
3. **Inlining and Optimization:** Even when invoked at runtime, lambdas marked `constexpr` are typically trivial and completely inlined by the compiler optimization passes.

---

## 15. Best Practices

1. **Use IIFEs for complex `const` / `constexpr` data generation** instead of dirtying your class or namespace scope with single-use functions.
2. **Mark lambdas explicitly `constexpr`** when they are strictly intended for meta-programming or static assertions.
3. **Keep compile-time closures small and pure** (no side-effects, no global dependencies).
4. **Use `std::array` instead of raw arrays** inside `constexpr` lambdas for cleaner element access and size queries.
5. **Combine generic lambdas (`auto`) with `if constexpr`** for expressive type-based compile-time choices.

---

## 16. Evolution: C++20 and Beyond (`consteval` lambdas)

- **C++20: `consteval` Lambdas:** C++20 introduced the `consteval` keyword (immediate functions). While `constexpr` lambdas *can* be executed at runtime, `consteval` lambdas *must* be executed at compile time:
  ```cpp
  // C++20
  auto strict_compile_time = [](int x) consteval {
      return x * 2;
  };
  ```
- **C++20: `<algorithm>` is constexpr:** Algorithms like `std::sort`, `std::copy`, and `std::find` became `constexpr`, allowing standard algorithms inside `constexpr` lambdas.
- **C++20: Dynamic Allocation:** Transient allocation (`std::vector`, `std::string`) is supported within compile-time evaluations.

| Usage | Syntax | Notes |
|---|---|---|
| Explicit constexpr | `[](int x) constexpr { return x; }` | Compiler enforces compile-time compatibility |
| Implicit constexpr | `[](int x) { return x; }` | Automatically constexpr if rules are satisfied |
| Constexpr closure instance | `constexpr auto f = [](...) {};` | Entire closure object is stored as a constant |

## 19. Complete Example

```cpp
#include <array>
#include <iostream>
#include <type_traits>

// Compile-time matrix determinant for a 2x2 matrix
struct Matrix2x2 {
    int a, b;
    int c, d;
};

int main() {
    // 1. Explicit constexpr lambda
    constexpr auto determinant = [](Matrix2x2 m) constexpr {
        return (m.a * m.d) - (m.b * m.c);
    };

    constexpr Matrix2x2 mat{4, 2, 1, 3};
    constexpr int det = determinant(mat); // 12 - 2 = 10
    static_assert(det == 10, "Determinant calculation failed!");

    // 2. IIFE for compile-time lookup table initialization
    constexpr auto squares_table = []() constexpr {
        std::array<int, 5> result{};
        for (std::size_t i = 0; i < result.size(); ++i) {
            result[i] = static_cast<int>(i * i);
        }
        return result;
    }();

    static_assert(squares_table[4] == 16);

    // 3. Generic higher-order constexpr lambda
    constexpr auto multiply_by = [](auto factor) constexpr {
        return [factor](auto val) constexpr {
            return factor * val;
        };
    };

    constexpr auto triple = multiply_by(3);
    static_assert(triple(7) == 21);

    // 4. Runtime reuse of the same constexpr lambda
    int runtime_input = 9;
    std::cout << "Runtime tripled: " << triple(runtime_input) << '\n';

    return 0;
}
```

## 21. Conclusion

`constexpr` lambdas in C++17 remove the friction between modern, local functional idioms and compile-time evaluation.

Key takeaways:
- Lambdas are **implicitly `constexpr`** if their requirements permit it.
- Mark them **explicitly `constexpr`** to catch invalid runtime assumptions early.
- Closure objects of captureless or literal-capture lambdas are themselves **literal types**.
- Compile-time IIFEs are the cleanest modern idiom for initializing complex static read-only tables and constant values.
