# Generic Lambdas in C++14

## Introduction to Generic Lambdas

The Generic Lambda feature was introduced in C++14 and is one of the most important improvements to Lambda Expressions over C++11. It allows Lambda parameters to be declared with `auto` instead of a specific type, enabling a single Lambda to work with different data types.

The core idea can be viewed as a **generic callable** whose `operator()` has template parameters generated by the compiler. As a result, Generic Lambdas are useful when the same logic needs to be applied to multiple types.

A simple C++14 example is:

```cpp
#include <iostream>

int main() {
    auto print = [](auto value) {
        std::cout << value << '\n';
    };

    print(42);
    print(3.14);
    print("hello");
}
```

In this example, the type of `value` is determined for each call. Therefore, a single Lambda can work with `int`, `double`, and a string.

## Understanding `auto` Parameters

The key feature of a Generic Lambda is the use of `auto` in its parameter list.

With a regular Lambda, the parameter type must be specified in advance:

```cpp
auto square = [](int value) {
    return value * value;
};
```

A Generic Lambda, by contrast, leaves the parameter type to the compiler:

```cpp
auto square = [](auto value) {
    return value * value;
};
```

Conceptually, the `auto` in this context behaves similarly to a Template Parameter.

For example, the following calls can result in different `operator()` specializations:

```cpp
auto square = [](auto value) {
    return value * value;
};

auto a = square(10);
auto b = square(2.5);
```

Here, one specialization is needed for `int` and another for `double`.

## Understanding the Conceptual Implementation

To understand Generic Lambdas, it is useful to compare them with a Function Object.

The following is a Generic Lambda:

```cpp
auto add = [](auto lhs, auto rhs) {
    return lhs + rhs;
};
```

Conceptually, it can be viewed as something similar to a closure type with a templated `operator()`:

```cpp
struct Closure {
    template <typename T, typename U>
    auto operator()(T lhs, U rhs) const {
        return lhs + rhs;
    }
};
```

The code above is a **conceptual model** for understanding Lambda behavior and should not be considered an exact language-level representation of the closure type specification. The actual closure type is generated by the compiler and has no directly accessible name.

The important point is that `auto` parameters in a Generic Lambda effectively cause `operator()` to behave as a Template, making the Lambda a compile-time polymorphic callable.

## Differences Between Regular and Generic Lambdas

The main difference between these two Lambda types is how their parameter types are determined.

```cpp
auto normal = [](int value) {
    return value * 2;
};

auto generic = [](auto value) {
    return value * 2;
};
```

The first Lambda can only be used with arguments compatible with `int`.

The second Lambda can accept different argument types, provided that the expression `value * 2` is valid for those types.

Therefore, being generic does not mean that a Lambda is «valid for every type». It means that its validity depends on Template Instantiation.

## Using Multiple `auto` Parameters

A Generic Lambda can have multiple `auto` parameters:

```cpp
auto add = [](auto lhs, auto rhs) {
    return lhs + rhs;
};
```

This Lambda can even accept two different types:

```cpp
auto a = add(10, 20);
auto b = add(1.5, 2.5);
auto c = add(10, 2.5);
```

In the third call, the first parameter can be `int` while the second parameter is `double`.

As a result, Generic Lambdas can support many different combinations of types through compile-time polymorphism.

## Generic Lambdas and Function Templates

Conceptually, a Generic Lambda is very similar to a Function Template:

```cpp
template <typename T>
auto square(T value) {
    return value * value;
}
```

The same idea can be expressed with a Lambda:

```cpp
auto square = [](auto value) {
    return value * value;
};
```

An important difference is that a Lambda creates an **object with a closure type**, whereas a Function Template defines an independent function Template.

A Generic Lambda is particularly useful when a callable is only needed within a specific scope and there is no need to define a named Function Template at namespace scope or a broader scope.

## Using Generic Lambdas with the Standard Library Algorithms

One of the most important applications of Generic Lambdas is using them as callbacks for Standard Library algorithms.

For example:

```cpp
#include <algorithm>
#include <iostream>
#include <vector>

int main() {
    std::vector<int> values{1, 2, 3, 4, 5};

    std::for_each(values.begin(), values.end(), [](auto value) {
        std::cout << value << '\n';
    });
}
```

In this example, the Lambda has no direct dependency on `int` and can also be used when the element type is different.

A similar Lambda can be used with `std::vector<double>` without modification:

```cpp
std::vector<double> values{1.1, 2.2, 3.3};

std::for_each(values.begin(), values.end(), [](auto value) {
    std::cout << value << '\n';
});
```

This pattern is common in Generic Programming.

## Using Generic Lambdas for Comparisons and Sorting

A Generic Lambda can also be used to write reusable comparators:

```cpp
#include <algorithm>
#include <vector>

int main() {
    std::vector<int> values{4, 1, 3, 2};

    std::sort(values.begin(), values.end(), [](auto lhs, auto rhs) {
        return lhs < rhs;
    });
}
```

However, using a Generic Lambda is only appropriate when generic behavior is actually useful. If the type is completely known and there is no benefit to making the comparator generic, a regular Lambda may be clearer.

## Handling the Return Type

Generic Lambdas in C++14 support return type deduction.

```cpp
auto multiply = [](auto lhs, auto rhs) {
    return lhs * rhs;
};
```

The return type is deduced from the expression in the `return` statement.

For example:

```cpp
auto a = multiply(2, 3);
auto b = multiply(2.5, 4.0);
```

In the first case, the result will normally be `int`, while in the second case it will be `double`, because the normal C++ type and operator rules apply.

If the return type needs to be specified explicitly, a trailing return type can be used:

```cpp
auto multiply = [](auto lhs, auto rhs) -> double {
    return lhs * rhs;
};
```

In this case, the result is `double` even if the internal expression would otherwise produce another type.

## Using `decltype(auto)`

C++14 also allows `decltype(auto)` to be used as a Lambda return type:

```cpp
auto get_value = [](auto& value) -> decltype(auto) {
    return value;
};
```

This is important when the exact type and category of the returned expression, including whether it is a reference, need to be preserved.

For example, the difference between `auto` and `decltype(auto)` can matter in cases such as:

```cpp
auto get_copy = [](auto& value) {
    return value;
};

auto get_reference = [](auto& value) -> decltype(auto) {
    return value;
};
```

In the first function, `auto` can cause the result to be returned by value. In the second function, `decltype(auto)` preserves the exact type of the expression according to the rules of `decltype`.

## Using `auto&&`

A Generic Lambda can also use `auto&&`:

```cpp
auto process = [](auto&& value) {
    // Process value
};
```

This creates a **forwarding reference** and allows the Lambda to work with both lvalues and rvalues.

For example:

```cpp
int value = 42;

process(value);
process(42);
```

In this case, deduction for `auto&&` follows the usual Template Argument Deduction rules.

Using `auto&&` is useful when a callable needs to preserve the value category of its input or perform perfect forwarding later.

## Using Perfect Forwarding

A professional application of Generic Lambdas is combining `auto&&` with `std::forward`:

```cpp
#include <utility>

auto forward_value = [](auto&& value) {
    return std::forward<decltype(value)>(value);
};
```

This pattern preserves the type and value category of the input.

It is particularly useful in wrappers, adapters, and generic utilities.

However, perfect forwarding is not necessary simply because a Lambda is generic. It should be used when preserving the lvalue/rvalue nature of an argument is actually part of the callable's contract.

## Captures in Generic Lambdas

Generic parameters are independent of captures. A Lambda can be both Generic and capture variables from its surrounding scope.

```cpp
int factor = 10;

auto multiply = [factor](auto value) {
    return value * factor;
};
```

In this example, `factor` is captured by value while `value` is a generic parameter.

A reference capture can also be used:

```cpp
int factor = 10;

auto multiply = [&factor](auto value) {
    return value * factor;
};
```

In this case, the Lambda depends on the `factor` variable in the surrounding scope.

## Using Init-Capture

C++14 introduced init-capture in addition to Generic Lambdas, and these two features are often used together.

```cpp
auto create_multiplier = [](int factor) {
    return [factor](auto value) {
        return value * factor;
    };
};
```

In this example, the inner Lambda is generic and stores `factor` in its closure.

This pattern is useful for creating specialized callables at runtime.

## Understanding the Closure Type

Every Lambda has a unique closure type that has no directly accessible name.

For example:

```cpp
auto lambda = [](auto value) {
    return value * 2;
};
```

The variable `lambda` is an object of the closure type associated with that Lambda.

Its exact type can be obtained with `decltype`:

```cpp
using LambdaType = decltype(lambda);
```

However, the actual name of the closure type cannot be written directly in C++ code because the language does not expose such a name to the programmer.

## Generic Lambdas and Runtime Polymorphism

A Generic Lambda provides **compile-time polymorphism**, not runtime polymorphism.

In the following example:

```cpp
auto print = [](auto value) {
    std::cout << value << '\n';
};
```

The type of `value` is determined at compile time.

By contrast, polymorphism based on inheritance and `virtual` functions generally performs dispatch at runtime.

Therefore, Generic Lambdas are appropriate when types are known at compile time and compile-time polymorphism can be used without the cost and complexity of runtime polymorphism.

## Using Generic Lambdas with Custom Types

Generic Lambdas are not limited to primitive types.

```cpp
struct User {
    int id;
};

auto get_id = [](auto const& user) {
    return user.id;
};
```

This Lambda can be used with any type that provides the required member.

For example:

```cpp
User user{42};

auto id = get_id(user);
```

If the input type does not have the required member, instantiation fails.

This behavior is both a strength of Generic Programming and one of its limitations.

## Template Error Diagnostics

One limitation of Generic Lambdas in C++14 is that their input requirements cannot be expressed directly in the Lambda syntax.

For example:

```cpp
auto increment = [](auto value) {
    return value + 1;
};
```

This Lambda is not valid for types that do not provide the required addition operation.

In C++14, there is no direct equivalent of C++20 Concepts syntax for constraining such a Lambda.

As a result, the error may only appear when the Lambda is instantiated with an invalid type, and the compiler diagnostic can sometimes be very long.

## Constraints in Newer C++ Versions

An important limitation of C++14 Generic Lambdas is that they do not have a standard mechanism for expressing constraints directly in their Lambda syntax.

C++20 significantly improves this situation through Concepts and constraints.

For example, in C++20 a Lambda can be constrained as follows:

```cpp
#include <concepts>

auto increment = []<std::integral T>(T value) {
    return value + 1;
};
```

This syntax belongs to C++20 and should not be confused with C++14 Generic Lambdas.

In C++14, constraints generally have to be expressed indirectly through interfaces, helper Templates, type traits, or API design.

## C++14 and C++20 Syntax Differences

A C++14 Generic Lambda relies on `auto` in its parameter list:

```cpp
auto lambda = [](auto value) {
    return value;
};
```

C++20 allows an explicit Template Parameter List for a Lambda:

```cpp
auto lambda = []<typename T>(T value) {
    return value;
};
```

These syntaxes are related in purpose but do not provide exactly the same capabilities.

An explicit Template Parameter List cannot be defined in this form in C++14.

Therefore, code that must remain C++14-compatible has to use the `auto`-based syntax.

## Using `std::function`

A Generic Lambda can be stored in `std::function`, but `std::function` itself is not generic and requires a specific signature.

```cpp
#include <functional>

auto square = [](auto value) {
    return value * value;
};

std::function<int(int)> integer_square = square;
std::function<double(double)> double_square = square;
```

Each `std::function` has a specific signature, and the Generic Lambda is used according to that signature.

It is important to note that putting a callable into `std::function` can introduce additional overhead compared with using the Lambda directly, depending on the implementation and usage. Therefore, if type erasure is not required, keeping the callable in its generic form is usually simpler and potentially more efficient.

## Converting a Captureless Lambda to a Function Pointer

A Lambda without captures can, under the appropriate conditions, be converted to a function pointer.

The same capability applies to a Generic Lambda in C++14, but the target type must be specified so that the appropriate specialization can be selected.

```cpp
auto add = [](auto lhs, auto rhs) {
    return lhs + rhs;
};

int (*int_add)(int, int) = add;
```

Here, the target type determines that the required Lambda specialization must work with two `int` arguments.

A different function pointer type can also be selected:

```cpp
double (*double_add)(double, double) = add;
```

This conversion is available only for Lambdas without captures.

## Captures and Function Pointers

A Lambda with a capture cannot be converted to an ordinary function pointer.

```cpp
int factor = 10;

auto multiply = [factor](int value) {
    return value * factor;
};
```

This Lambda depends on state stored in its closure, and an ordinary function pointer cannot represent that captured state.

In such cases, using the Lambda directly or using a type-erased callable such as `std::function` is more appropriate, depending on the design requirements.

## Generic Lambdas as Visitors

One important application of Generic Lambdas is building simple visitors for different types.

C++14 does not yet have `std::variant`; therefore, examples based on `std::variant` belong to C++17 and later.

Nevertheless, Generic Lambdas can be used in many visitor-like or callback-based designs:

```cpp
auto visitor = [](auto const& value) {
    std::cout << value << '\n';
};
```

This pattern is common in generic libraries and algorithms.

## Using Generic Lambdas in Wrappers

Generic Lambdas are well suited to wrappers that add a small amount of logic around another callable.

```cpp
auto log_call = [](auto&& callable) {
    return [callable = std::forward<decltype(callable)>(callable)](auto&& value) {
        std::cout << "Calling callable\n";
        return callable(std::forward<decltype(value)>(value));
    };
};
```

This example combines several C++14 features:

* Generic Lambda
* `auto&&`
* init-capture
* perfect forwarding
* closure objects

Such patterns are powerful in utility and library code, but lifetime and ownership must be considered carefully.

## Lifetime Considerations

When a Lambda captures something by reference, the lifetime of that object must extend until the Lambda is no longer used.

```cpp
auto create_lambda() {
    int value = 42;

    return [&value](auto x) {
        return value + x;
    };
}
```

The code above has a lifetime problem because the Lambda refers to a variable that no longer exists after `create_lambda` returns.

A safer version can capture the value:

```cpp
auto create_lambda() {
    int value = 42;

    return [value](auto x) {
        return value + x;
    };
}
```

Making a Lambda generic does not solve lifetime problems associated with captured objects.

## `const` and `mutable`

By default, a Lambda's `operator()` has specific const behavior, and the `mutable` specifier can be used to modify the Lambda's internal state.

For example:

```cpp
int counter = 0;

auto increment = [counter]() mutable {
    ++counter;
    return counter;
};
```

Here, the Lambda stores its own copy of `counter`, and `mutable` allows that internal state to be modified.

Generic parameters are independent of `mutable`:

```cpp
auto increment = [counter = 0](auto value) mutable {
    ++counter;
    return value + counter;
};
```

This Lambda is both generic and mutable, with mutable internal state.

## Generic Lambdas and Overload Sets

Sometimes a Generic Lambda can replace several simple overloads:

```cpp
auto print = [](auto const& value) {
    std::cout << value << '\n';
};
```

However, if behavior genuinely differs between types, a Generic Lambda may not be the best choice.

In such cases, separate overloads or a more appropriate design can make the intent clearer.

The important principle is that genericity is not a goal in itself. It should make the design simpler and more maintainable.

## Common Mistakes

### Using a Generic Lambda Without a Real Need

If a Lambda only operates on one specific type, using `auto` does not necessarily provide any benefit.

```cpp
auto process = [](int value) {
    return value * 2;
};
```

In such a scenario, making the Lambda generic without a real reason can make its contract less explicit.

### Assuming Every Type Is Accepted

Generic does not mean universally compatible.

```cpp
auto double_value = [](auto value) {
    return value * 2;
};
```

This Lambda only works with types for which the multiplication expression is valid.

### Ignoring Reference Semantics

`auto` and `auto&&` have different behavior:

```cpp
auto by_value = [](auto value) {
    // Process a copy
};

auto by_reference = [](auto&& value) {
    // Preserve reference category
};
```

The choice should be based on the actual requirements.

### Using `std::function` Unnecessarily

If only a local callable is needed, there is usually no reason to immediately place it inside `std::function`.

```cpp
auto operation = [](auto value) {
    return value * 2;
};
```

Keeping the Lambda directly generally preserves its type information and avoids unnecessary type erasure.

### Ignoring Template Diagnostics

When a Generic Lambda is used with an incompatible type, the error may appear at the instantiation site and the compiler diagnostic can be complicated.

For this reason, constraints or a more restricted interface can improve diagnostics in public APIs and library code.

## Limitations of Generic Lambdas in C++14

The most important limitations can be summarized as follows:

* Generic parameters in C++14 are declared with `auto`.
* Explicit Template Parameter Lists for Lambdas are not available in C++14.
* Concepts and requires-expressions are not available.
* The set of permitted types cannot be directly constrained in the Lambda syntax.
* Instantiation errors can be complicated.
* A Lambda with captures cannot be converted to an ordinary function pointer.
* Genericity provides no lifetime guarantees for captured objects.
* Generic use can result in multiple compile-time specializations.
* Unnecessary genericity can make an API's contract less clear.

## Compile-Time and Code-Size Considerations

Generic Lambdas are based on Template Instantiation. Therefore, if a Lambda is used with many different types, the compiler may generate multiple specializations.

For example:

```cpp
auto process = [](auto value) {
    return value * 2;
};

process(1);
process(2L);
process(3.0);
process(4.0f);
```

In this case, depending on the types and compiler optimizations, code associated with multiple specializations may be generated.

This is not inherently a problem and is one of the characteristics of compile-time polymorphism. However, in large libraries, the effect of Template Instantiation on compile time and binary size should be considered.

## Design Considerations for Professional Code

Professional use of Generic Lambdas involves more than simply replacing parameter types with `auto`.

Before making a Lambda generic, it is useful to consider the following questions:

* Is the logic genuinely valid for multiple types?
* Should the interface actually be generic?
* Are there specific constraints?
* Is `auto`, `auto&`, `const auto&`, or `auto&&` the appropriate choice?
* Does the value category of the input need to be preserved?
* Does the Lambda capture anything?
* If it captures by reference, is the lifetime guaranteed?
* Is `std::function` actually necessary?
* Does genericity improve reuse, or does it merely make the contract less explicit?
* Will Template errors be acceptable to users of the API?

Generic Lambdas provide the most value when genericity is a real part of the design rather than simply a technique for removing an explicit type.

## Comparison with Older Approaches

Before Generic Lambdas were introduced in C++14, C++11 Lambdas could not have `auto` parameters.

In C++11, a generic operation often required a Function Template or a Template Function Object:

```cpp
struct Multiplier {
    template <typename T>
    auto operator()(T value) const {
        return value * 2;
    }
};
```

In C++14, the same idea can be expressed much more concisely:

```cpp
auto multiplier = [](auto value) {
    return value * 2;
};
```

Generic Lambdas therefore eliminate much of the more verbose syntax of older Function Objects for local and relatively small generic callables.

## Generic Lambdas and General Generic Programming

A Generic Lambda is only one tool for Generic Programming and is not a replacement for all Template capabilities.

A Function Template or class Template may be more appropriate when the design requires:

* a public and named interface
* multiple related overloads
* Template specializations
* complex constraints in older C++ standards
* complex state and behavior
* extensive reuse across different parts of a program
* an API that should be explicitly invoked by library users

In contrast, Lambdas are often an excellent choice for local callbacks, algorithms, adapters, and small generic operations.

## C++ Standard Versions

Generic Lambdas with `auto` parameters were introduced in **C++14**.

In **C++17**, Lambda capabilities were extended further, including broader support for using Lambdas in compile-time contexts and other related features.

In **C++20**, Lambdas gained important additional capabilities, including explicit Template Parameter Lists and Concepts-based constraints.

Therefore, if code must be strictly compatible with C++14, newer syntax and features should not be mixed with C++14 Generic Lambdas.

## A Complete Practical Example

The following example uses a Generic Lambda to calculate the sum of the elements in a container:

```cpp
#include <iostream>
#include <numeric>
#include <vector>

int main() {
    std::vector<int> values{1, 2, 3, 4, 5};

    auto add = [](auto lhs, auto rhs) {
        return lhs + rhs;
    };

    int result = std::accumulate(
        values.begin(),
        values.end(),
        0,
        add
    );

    std::cout << result << '\n';
}
```

In this example, the Lambda is independent of the exact types of its parameters and can also be used in other contexts where the `+` operation is valid.

## Summary

Generic Lambdas in C++14 provide a concise and powerful way to create generic callables at compile time. Their key feature is the use of `auto` in the parameter list, which makes the Lambda's `operator()` behave as a Template.

The most important point is that a Generic Lambda should not simply be thought of as a «Lambda that accepts any type». In reality, the Lambda is valid for types for which its body can be successfully instantiated.

Combining Generic Lambdas with `auto&&`, perfect forwarding, init-capture, and Standard Library algorithms makes it possible to build powerful and concise utilities.

However, the limitations of C++14—including the absence of Concepts, explicit Template Parameter Lists, and the potentially complex Template diagnostics—should be considered when designing public APIs.

For professional code, the best approach is to use genericity when it is genuinely part of the problem. Otherwise, a Lambda with an explicit type will often provide a clearer and more understandable contract.
