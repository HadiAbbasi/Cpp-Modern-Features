# Introduction to default and delete in C++11

In C++11, two important language features named `default` and `delete` were introduced to provide more precise control over special member functions and class behavior. These features are particularly important for designing safe, predictable classes and for applying the Rule of Zero, Rule of Five, and Rule of Three correctly.

The main idea is that a programmer can explicitly tell the compiler that a special member function should use its default implementation or that the function should not be usable at all.

---

## The General Concept of default and delete

The `default` specifier tells the compiler to use the default implementation for a special member function.

The `delete` specifier tells the compiler that the function exists but must not be used.

For example:

```cpp
class User {
public:
    User() = default;
    User(const User&) = delete;
};
```

In this example, the default constructor is generated normally by the compiler, while the copy constructor is explicitly deleted.

Therefore, the following code is valid:

```cpp
User user;
```

But the following code produces a compile-time error:

```cpp
User first;
User second = first;
```

This approach is clearer than older techniques such as making a function private.

---

## Understanding Special Member Functions

To properly understand `default` and `delete`, you first need to understand special member functions.

In C++, the following six functions are generally considered special member functions:

* default constructor
* destructor
* copy constructor
* copy assignment operator
* move constructor
* move assignment operator

A class can define these functions itself or, when the appropriate conditions are met, allow the compiler to implicitly declare or define them.

For example:

```cpp
class Point {
public:
    int x;
    int y;
};
```

The `Point` class can have appropriate special member functions implicitly available without the programmer explicitly writing them.

---

## Defining a Default Constructor with default

One common use of `default` is to explicitly define a default constructor.

```cpp
class Person {
public:
    Person() = default;

private:
    std::string name;
    int age;
};
```

In this case, `Person()` is a default constructor generated by the compiler.

An important point is that `= default` does not mean that all data members are manually initialized.

For example:

```cpp
class Data {
public:
    Data() = default;

private:
    int value;
    std::string name;
};
```

The `name` member is constructed using its own constructor, but `value` does not automatically receive a specific value such as `0` when the object is default-initialized.

For example:

```cpp
Data data;
```

In this situation, the value of `value` is indeterminate because it is a built-in member without an initializer.

If a specific initial value is required, use a member initializer:

```cpp
class Data {
public:
    Data()
        : value(0),
          name("unknown") {
    }

private:
    int value;
    std::string name;
};
```

In C++11, this can also be written more cleanly using in-class member initializers:

```cpp
class Data {
public:
    Data() = default;

private:
    int value = 0;
    std::string name = "unknown";
};
```

In this case, the member initializers themselves specify the desired default values.

---

## The Difference Between a Default Constructor and Default Member Initialization

The following two concepts should not be confused.

```cpp
class Example {
public:
    Example() = default;

private:
    int value = 42;
};
```

Here, `Example() = default` tells the compiler to generate the default constructor.

On the other hand, `value = 42` specifies the default initializer for the `value` member when that initialization is applicable.

These are two independent features.

In simple terms, `= default` applies to a **function**, while an in-class initializer applies to a **data member**.

---

## Comparing Different Forms of Default Constructors

The following three cases have different characteristics.

### Defining No Constructor

```cpp
class A {
private:
    int value = 10;
};
```

In this case, when the appropriate conditions are met, the compiler provides a default constructor implicitly.

### Explicitly Defaulting the Constructor

```cpp
class B {
public:
    B() = default;

private:
    int value = 10;
};
```

Here, the programmer explicitly requests that the compiler generate the default constructor.

### Providing a Manual Implementation

```cpp
class C {
public:
    C()
        : value(10) {
    }

private:
    int value;
};
```

In this case, the constructor is actually defined by the programmer.

If the desired behavior is exactly the compiler's default behavior, `= default` is generally the simpler and clearer choice.

---

## Understanding delete

C++11 introduced `delete` to allow a function to be explicitly deleted.

For example:

```cpp
class NonCopyable {
public:
    NonCopyable() = default;

    NonCopyable(const NonCopyable&) = delete;
    NonCopyable& operator=(const NonCopyable&) = delete;
};
```

This class cannot be copied.

The following code produces an error:

```cpp
NonCopyable first;
NonCopyable second(first);
```

Likewise:

```cpp
NonCopyable first;
NonCopyable second;

second = first;
```

is also invalid.

---

## Using delete to Prevent Copying

One of the most common uses of `delete` is to prevent copying.

```cpp
class File {
public:
    File() = default;

    File(const File&) = delete;
    File& operator=(const File&) = delete;
};
```

Suppose each `File` object owns an operating-system resource. A simple copy could result in double ownership or a double close.

In such situations, deleting the copy operations can prevent an unsafe class design.

---

## Using delete to Prevent Moving

`delete` is not limited to copy operations.

Move operations can also be deleted:

```cpp
class FixedObject {
public:
    FixedObject() = default;

    FixedObject(FixedObject&&) = delete;
    FixedObject& operator=(FixedObject&&) = delete;
};
```

In this case, the object cannot be moved.

However, move operations should generally be deleted only when there is a clear design reason. For many resource-owning classes, move semantics are a better solution than completely preventing ownership transfer.

---

## Using delete to Prevent Unwanted Conversions

One powerful use of `delete` is to remove overloads that should not be available.

For example:

```cpp
class Number {
public:
    Number(int value) : value_(value) {}

    Number(double) = delete;

private:
    int value_;
};
```

Creating the object from an `int` is allowed:

```cpp
Number a(10);
```

But using a `double` is prohibited:

```cpp
Number b(10.5);
```

This technique is useful for preventing unwanted implicit conversions.

---

## Using delete with Overloads

A specific overload can be deleted while other overloads remain available.

For example:

```cpp
void process(int value) {
}

void process(double) = delete;
```

Now:

```cpp
process(10);
```

is valid, while:

```cpp
process(10.5);
```

produces a compile-time error.

This technique can make an API's interface more precise.

---

## Comparing delete with Making a Function private

Before C++11, a common way to prevent copying was to make the copy constructor and copy assignment operator private.

An older implementation might look like this:

```cpp
class NonCopyable {
private:
    NonCopyable(const NonCopyable&);
    NonCopyable& operator=(const NonCopyable&);

public:
    NonCopyable() {}
};
```

This approach has several drawbacks.

First, the programmer's intent is not expressed as clearly as it is with `delete`.

Second, the resulting diagnostic may be an access-control error rather than an explicit error indicating that the function has been deleted.

In C++11 and later, the standard approach is:

```cpp
class NonCopyable {
public:
    NonCopyable() = default;

    NonCopyable(const NonCopyable&) = delete;
    NonCopyable& operator=(const NonCopyable&) = delete;
};
```

Therefore, in C++11 and later code, `= delete` is the preferred approach for this purpose.

---

## The Difference Between default and a Manual Implementation

The following two declarations may appear similar:

```cpp
class Example {
public:
    Example() = default;
};
```

and:

```cpp
class Example {
public:
    Example() {
    }
};
```

However, they are not completely equivalent from the perspective of the C++ language.

`= default` allows the compiler to manage the special member function as a defaulted function.

By contrast, an empty function body means that the function is user-provided.

This distinction can affect type properties, certain type traits, and the conditions under which implicit special member functions are generated.

Therefore, if you genuinely want the compiler's default behavior, it is better to express that intent with `= default`.

---

## The Difference Between Implicitly Declared and Explicitly Defaulted

These concepts should also be distinguished.

In the implicit case:

```cpp
class User {
private:
    int id = 0;
};
```

The programmer has not written the constructor, so the compiler can implicitly declare it when the language rules allow it.

In the explicitly defaulted case:

```cpp
class User {
public:
    User() = default;

private:
    int id = 0;
};
```

The programmer explicitly asks the compiler to default the constructor.

This explicit declaration can be valuable for expressing the class's design intent.

---

## Important Point About Defaulted Functions That Become Deleted

A function declared with `= default` is not necessarily usable in all circumstances.

If constructing one of the class's members is impossible, the defaulted function may be defined as deleted by the compiler.

For example:

```cpp
class Member {
public:
    Member() = delete;
};

class Container {
public:
    Container() = default;

private:
    Member member;
};
```

Here, `Container()` cannot construct its member, so `Container`'s default constructor is effectively unusable.

Consequently, the following code is invalid:

```cpp
Container object;
```

This demonstrates how the composition of member types affects special member functions.

---

## How Property Types Affect the Default Constructor

The types of a class's members directly affect whether its default constructor can be generated and used.

For example:

```cpp
class A {
private:
    int value;
};
```

There is no problem generating a default constructor.

But consider:

```cpp
class B {
public:
    B() = delete;
};

class A {
public:
    A() = default;

private:
    B value;
};
```

In this case, `A` cannot be default-constructed because `B` cannot be default-constructed.

Therefore, when designing a class with different property types, you must also consider whether all of its members are constructible in the required way.

---

## Designing a Class with Different Property Types

For a simple model such as `User`, the following design is generally clear and predictable:

```cpp
#include <string>
#include <vector>

class User {
public:
    User() = default;

private:
    int id = 0;
    std::string username;
    double balance = 0.0;
    bool active = true;
    std::vector<int> roles;
};
```

In this example:

* `id` has an explicit initial value.
* `username` is constructed using the default constructor of `std::string`.
* `balance` is initialized to `0.0`.
* `active` is initialized to `true`.
* `roles` is constructed as an empty vector.
* The main constructor is delegated to the compiler.

If the class has no complex invariants, this design is generally preferable to writing a long constructor.

---

## When a Default Constructor Is Not Appropriate

You should not add `= default` simply because a class should have a constructor.

If an object has no valid meaning without required data, it may be better to prohibit default construction entirely.

For example:

```cpp
class UserId {
public:
    explicit UserId(int value)
        : value_(value) {
    }

private:
    int value_;
};
```

In this design, constructing a `UserId` without a specific value does not make sense.

It can also be made explicit that default construction is prohibited:

```cpp
class UserId {
public:
    UserId() = delete;

    explicit UserId(int value)
        : value_(value) {
    }

private:
    int value_;
};
```

Now:

```cpp
UserId id(42);
```

is valid, while:

```cpp
UserId id;
```

is invalid.

---

## Using default and delete with the Rule of Zero

One important principle of modern C++ class design is the Rule of Zero.

If a class uses automatic resource-management types such as:

* `std::string`
* `std::vector`
* `std::unique_ptr`
* `std::shared_ptr`
* other RAII types

you generally should not manually manage its special member functions.

For example:

```cpp
#include <memory>
#include <string>

class User {
public:
    User() = default;

private:
    std::string name;
    std::unique_ptr<int> data;
};
```

Here, ownership is managed by `std::unique_ptr`, so there is no need to manually write a destructor or move constructor.

However, the presence of `std::unique_ptr` means that copy operations cannot be generated as usable operations.

If you want to make this intent explicit, you can delete the copy operations:

```cpp
class User {
public:
    User() = default;

    User(const User&) = delete;
    User& operator=(const User&) = delete;

private:
    std::unique_ptr<int> data;
};
```

However, if the member types already enforce the desired behavior, explicitly repeating `= delete` is often unnecessary.

---

## The Relationship Between default and the Rule of Five

For classes that manually manage resources, the Rule of Five becomes important.

The five functions are:

* destructor
* copy constructor
* copy assignment operator
* move constructor
* move assignment operator

For example:

```cpp
class Resource {
public:
    Resource() = default;

    Resource(const Resource&) = delete;
    Resource& operator=(const Resource&) = delete;

    Resource(Resource&&) = default;
    Resource& operator=(Resource&&) = default;

    ~Resource() = default;
};
```

This class can be moved but cannot be copied.

However, this pattern should be used based on the actual semantics of the resource rather than as a fixed template.

---

## The Difference Between Disabling Copying and Supporting Move

These are two separate design decisions.

A class can be:

* copyable and movable;
* movable but not copyable;
* neither copyable nor movable.

For example, `std::unique_ptr` is a well-known example of the second category.

If a class has exclusive ownership of a resource, a typical design is:

```cpp
class ResourceOwner {
public:
    ResourceOwner() = default;

    ResourceOwner(const ResourceOwner&) = delete;
    ResourceOwner& operator=(const ResourceOwner&) = delete;

    ResourceOwner(ResourceOwner&&) = default;
    ResourceOwner& operator=(ResourceOwner&&) = default;
};
```

In this design, ownership can be transferred but cannot be duplicated.

---

## Important Point About Destructors and Move Operations

Defining certain special member functions can affect the implicit generation of other special member functions.

In particular, defining a destructor, copy constructor, copy assignment operator, move constructor, or move assignment operator can affect the conditions under which implicit move operations are generated.

For this reason, when designing a class, you should first determine whether a special member function is actually necessary or whether the compiler-generated behavior is sufficient.

If resources are managed using RAII types from the standard library, the Rule of Zero is generally the better choice.

---

## The Difference Between default and Default Property Initialization

A common mistake is to assume that the following code initializes all properties to zero:

```cpp
class Data {
public:
    Data() = default;

    int count;
    double price;
    bool enabled;
};
```

There is no such guarantee.

If specific initial values are required, provide initializers:

```cpp
class Data {
public:
    Data() = default;

    int count = 0;
    double price = 0.0;
    bool enabled = false;
};
```

This makes the intent explicit.

---

## Comparing Initialization of Different Members

For class-type members, the constructor of the type is generally invoked:

```cpp
class Example {
public:
    Example() = default;

private:
    std::string text;
};
```

By contrast, built-in types such as `int` and `double` do not automatically receive a specific initial value when they are default-initialized without an initializer.

Therefore, these two cases should be considered separately:

```cpp
std::string text;
int number;
```

The first type has a constructor, while the second is a built-in type and does not create a specific initial value by itself.

---

## Using delete to Prevent Unwanted Constructors

Sometimes a constructor can become available through unwanted implicit conversions.

For example:

```cpp
class Identifier {
public:
    Identifier(int value)
        : value_(value) {
    }

    Identifier(double) = delete;

private:
    int value_;
};
```

Now the API is more explicit, and the compiler does not allow a `double` to be used as an identifier.

This technique can be particularly useful for domain types and sensitive APIs.

---

## Limitations of delete

A deleted function remains part of the class's interface, but it cannot be called.

For example:

```cpp
class Example {
public:
    Example() = default;
    Example(const Example&) = delete;
};
```

The presence of the deleted copy constructor does not mean that the copy constructor has completely disappeared from the class's declarations. Instead, using it is ill-formed.

This distinction is also important during overload resolution, because a deleted function can participate in overload selection and then cause a compile-time error.

---

## The Difference Between delete and Not Declaring a Function

These two cases are not equivalent:

```cpp
class A {
public:
    A() = delete;
};
```

and:

```cpp
class B {
};
```

In the first case, the programmer explicitly states that the default constructor must not be used.

In the second case, the behavior of special member functions is determined by the language's implicit-generation rules.

Therefore, `delete` is a tool for explicitly expressing design intent.

---

## Common Mistake with Classes Containing Different Properties

Sometimes a programmer writes a manual constructor simply to avoid indeterminate values:

```cpp
class User {
public:
    User()
        : id(0),
          balance(0.0),
          active(false),
          name("unknown") {
    }

private:
    int id;
    double balance;
    bool active;
    std::string name;
};
```

This code is valid, but in C++11, in-class member initializers can be used instead:

```cpp
class User {
public:
    User() = default;

private:
    int id = 0;
    double balance = 0.0;
    bool active = false;
    std::string name = "unknown";
};
```

This version is generally easier to read, especially when these values are part of the class's default state.

---

## When a Constructor Must Enforce an Invariant

If an object is valid only when a specific set of conditions is satisfied, `= default` may not be appropriate.

For example:

```cpp
class Temperature {
public:
    explicit Temperature(double value)
        : value_(value) {
        if (value < -273.15) {
            throw std::invalid_argument("Invalid temperature");
        }
    }

private:
    double value_;
};
```

In such a design, default construction could create an invalid state.

Therefore, it may be reasonable to prohibit it:

```cpp
class Temperature {
public:
    Temperature() = delete;

    explicit Temperature(double value)
        : value_(value) {
        if (value < -273.15) {
            throw std::invalid_argument("Invalid temperature");
        }
    }

private:
    double value_;
};
```

In this design, the class requires every object to be constructed with a valid value.

---

## Important Design Considerations

In class design, use `= default` when the compiler-generated semantics are exactly what you want.

Use `= delete` as an explicit design tool when you need to prevent unwanted copy or move operations or reject specific overloads and conversions.

For primitive properties that require specific initial values, use in-class member initializers.

For resource management, prefer RAII and standard library types so that manual management of special member functions is minimized.

If a class has no meaningful valid state without required initialization, instead of creating an artificial default state, consider deleting the default constructor.

Also, do not automatically write every special member function with `= default` just to make the class explicit. The code should express the actual design intent and avoid unnecessary repetition.

---

## Summary

In C++11, `= default` and `= delete` are important tools for controlling special member functions and overloads.

The `= default` specifier is useful when you want to explicitly request the compiler's default behavior:

```cpp
class Example {
public:
    Example() = default;
};
```

The `= delete` specifier is used when you want to prohibit the use of a function:

```cpp
class Example {
public:
    Example() = default;
    Example(const Example&) = delete;
};
```

For classes containing different property types, you must understand the difference between initialization of class-type members and built-in types. Using in-class member initializers in C++11 is an effective way to define a predictable default state:

```cpp
class User {
public:
    User() = default;

private:
    int id = 0;
    double balance = 0.0;
    bool active = false;
    std::string name = "unknown";
};
```

Ultimately, the best design is usually to stay as close as practical to the Rule of Zero, manage ownership with standard RAII types, and use `= default` or `= delete` when explicitly expressing the class's semantics provides real value.
